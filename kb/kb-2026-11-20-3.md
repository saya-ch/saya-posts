## 是什么

Vue 的"编译"指把模板（单文件组件里的 `<template>`，或组件选项里的 template 字符串）解析成 AST，再生成一个返回虚拟 DOM 的 render 函数；"运行时"指执行这个函数得到 vnode、挂载成真实 DOM，并在依赖变化时做 patch。一句话直觉：编译器是提前做过功课的出题人，它把"哪些节点会变、变的是 class 还是文本、子节点顺序稳不稳定"写进了 render 函数的参数里，运行时照着这张小抄走，就不必逐层盘问整棵树。

在 SFC 加 Vite 或 webpack 的项目里，这个分工是隐形的：模板在构建期就变成 JS，浏览器只加载运行时，编译器的开销留在开发机上。但在 CDN 直接引脚本、in-DOM 模板、或者需要在浏览器里动态编译模板字符串的场景里，编译器和运行时会一起打进包里，体积、启动耗时与 CSP 约束立刻变得可见。

## 核心原理

官方把这套设计叫 [compiler-informed virtual DOM](https://vuejs.org/guide/extras/rendering-mechanism.html)：框架同时掌握编译器和运行时，才敢让两边串通。编译分三段：parse 把模板字符串切成 AST，transform 处理指令与表达式并打上标记，generate 输出 render 函数源码。生成的不是"等价的 HTML"，而是一段带优化的 JavaScript。拿一个只有静态段落和一处动态绑定的模板去编译，产物大致是这样（`@vue/compiler-dom` 3.5 的实际输出，已省略导入语句）：

```js
return (_openBlock(), _createElementBlock("div", null, [
  // 静态节点：只创建一次，后续复用同一个 vnode 对象
  _cache[0] || (_cache[0] = _createElementVNode("p", { class: "static" }, "hello", -1 /* HOISTED */)),
  // 动态节点：末尾的 3 是位掩码，1=TEXT、2=CLASS
  _createElementVNode("p", {
    class: _normalizeClass(cls)
  }, _toDisplayString(msg), 3 /* TEXT, CLASS */)
]))
```

末尾那个数字叫 patchFlag，是编译期算好的常量，不是一个布尔开关。运行时用按位与判断，只做该做的那几件事：

```js
// runtime-core 的 patchElement：位运算决定进哪个分支
if (patchFlag & 1 /* TEXT */) {
  if (n1.children !== n2.children) hostSetElementText(el, n2.children)
}
if (patchFlag & 2 /* CLASS */) {
  if (oldProps.class !== newProps.class) hostPatchProp(el, "class", null, newProps.class)
}
```

常见取值：1 文本、2 class、4 style、8 props（还要配一份 dynamicProps 键名数组，只比较列出的键）、16 全量 props（模板里写了 `v-bind="obj"` 时退化成这一档）、64/128/256 分别表示稳定、带 key、不带 key 的 fragment。负数也有含义：-1 是被提升的静态节点，-2 表示放弃优化。

第二层优化是 block tree，也就是常说的树扁平化。`openBlock()` 与 `createElementBlock()` 划出一个结构稳定的块，块内所有带 patchFlag 的后代节点——注意是后代，不只是直接子节点——会被收集进这个块的 dynamicChildren 数组。重新渲染时，`patchElement` 发现有 dynamicChildren，就只遍历这个扁平数组，中间那些纯静态的包装层根本不进 diff。模板里出现 v-if 或 v-for 时会新开一个子块，子块作为整体挂在父块的数组里，因此父块的结构和数组长度保持稳定，条件分支可以整体挂载或整体卸载。

第三层是静态提升与字符串化。不含任何动态绑定的节点会被提到模块作用域，或者塞进 render 的 `_cache`，下次渲染返回同一个 vnode 引用；运行时的 patch 一比对发现新旧是同一个对象，直接跳过。当连续静态节点足够多、拼出的 HTML 足够长时，编译器还会把它们合成一个静态 vnode，挂载时用 innerHTML 一次性写入，几十个节点变成一个。服务端渲染的水合阶段同样受益：遇到被提升的子树可以整棵跳过，只激活带标记的节点。

这一切成立的前提，是编译器对模板语法有确定性的了解。手写 render 函数或 JSX 时，运行时拿不到这些标记，`optimized` 为假，只能回到全量遍历。所以 Vue 3 并没有抛弃虚拟 DOM，而是把"哪里需要比较"的判断从运行期前移到了构建期，这也是它和纯运行时虚拟 DOM 实现最本质的分歧。Vue 3.4 重写了模板解析器，把递归下降换成单趟状态机分词，官方给出的解析速度提升是 2 倍（[发布说明](https://blog.vuejs.org/posts/vue-3-4)），属于同一个方向上的持续投入。

## 常见考点与误区

- **"Vue 3 比 Vue 2 快，是因为用了 Proxy"**：这是把响应式和渲染混为一谈。Proxy 只改变依赖收集方式；渲染侧的性能来自 patchFlag、block tree 与静态提升这一整套编译期提示。面试只答 Proxy，通常会被追问到答不上来。
- **"装了 vue 就能在任何地方写 template 字符串"**：打包器走的 `import` 入口是 runtime-only 构建（`dist/vue.runtime.esm-bundler.js`），里面没有模板编译器，传 template 字符串只会得到一条运行时警告，组件渲染为空。要用完整版得显式引 `vue/dist/vue.esm-bundler.js`，代价是包体明显变大。（Node 侧 `require` 的入口 `index.js` 指向的是完整版，所以"能不能编译"还取决于你从哪个入口加载，别拿一边的经验套另一边。）
- **"运行时编译只是慢一点"**：完整版编译模板靠 `new Function` 生成函数，在禁止 unsafe-eval 的 CSP 下会直接失败。很多"本地好好的，上线白屏"的根因就在这里。另外，运行时编译发生在浏览器里，首屏要多付一次解析与生成的成本。
- **"patchFlag 是运行时 diff 出来的"**：它是编译期常量，运行时只做位运算。还有人把 1 记成"动态节点"，其实 1 是 TEXT；写 `v-bind="obj"` 会得到 16，等于放弃细粒度比较，这是模板写法直接影响性能的典型例子。
- **"有了 block tree 就是局部更新"**：它跳过的只是静态节点，组件级更新仍然由响应式 effect 触发整段 render。要缩小更新范围得拆组件、用 `v-memo` 或把昂贵的计算移出渲染，而不是指望 block tree 替你决定哪个组件该刷新。
- **"静态提升缓存了真实 DOM"**：缓存的是 vnode 对象，挂载仍要经过 patch；它的收益是省掉重复创建与比较，不是省掉首次挂载。
- **"v-if 里的节点不会被收集"**：v-if / v-for 会新建子块，子块整体挂在父块的 dynamicChildren 里，所以能整体替换，也能在父块更新时被正确跳过。误以为它们游离在优化之外，就会低估结构指令对 diff 路径的影响。

## 实践建议

- **生产环境一律预编译**：用 SFC 加官方插件，别在运行时传 template 字符串。检查打包结果解析到的是 runtime-only 入口；为了"能动态编译"而全局引完整版，等于让所有用户为少数场景付包体代价。
- **让绑定粒度匹配 patchFlag**：`:class`、`:style`、具体属性各写各的，运行时就能只比较那几项；写成 `v-bind="obj"` 会落到 FULL_PROPS，每次更新全量比 props，还容易把无关字段一起带上。
- **保住块结构的稳定性**：v-for 加稳定 key，别在动态列表外面随意套条件分支；结构越稳定，dynamicChildren 的复用越充分，key 类型选错时 fragment 的 keyed/unkeyed 分支也会走不同的匹配逻辑。
- **严格 CSP 下不要开口子**：不要为了运行时编译去加 unsafe-eval，把 in-DOM 模板搬进 SFC 或预编译步骤即可；第三方组件如果内部传 template 字符串，要在集成前就验证，否则错误只在生产 CSP 生效时才暴露。
- **用编译产物做排查**：怀疑优化没生效时，直接用 `@vue/compiler-dom` 的 `compile()` 看生成的 render 函数，确认 patchFlag 与 dynamicChildren 是否符合预期，比在 DevTools 里猜更新来源快得多。
- **别把手写 render 当性能手段**：除非组件确实需要高度动态的结构，模板能被编译器静态分析，手写 h() 或 JSX 反而丢掉全部提示。真要极致控制，先量出瓶颈再下沉。

*一句话总结：编译器把"哪里会变"提前写进产物，运行时才敢只走那一小撮节点。*
