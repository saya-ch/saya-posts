## 是什么

数据一致性方案，是一组让跨服务、跨数据库的业务动作最终落在同一个确定状态上的协议与模式。单库写入靠本地事务就够了；一旦“扣款在账务库、入账在另一套系统”，本地事务管不到对方，就必须在“锁住等”和“事后补”之间选一条路。

它和 CAP 里的 C 不是一回事：CAP 讲的是分区发生时能在一致性与可用性之间保哪一边，这里讲的是具体用什么协议把一次跨资源写入收尾。一致性也有强弱之分，从线性一致、原子提交到最终一致，方案并不是互斥的四个按钮，而是分别把风险放在了锁、补偿、消息和人工对账上。典型场景是转账、下单扣库存加发券、支付成功后通知履约。

判断标准其实很朴素：如果两个写入必须同时成立，失败后也没有办法用业务动作补回来，才值得把问题升级到分布式协议；否则优先用单库事务或异步事件把耦合拆开，别为了“架构统一”制造一个本来不存在的一致性问题。

## 核心原理

把 A 向 B 转 100 元拆成两个本地事务，四种方案的差别就在于：什么时候让别人看见中间状态，失败之后由谁把已经发生的那一半收回来。

**2PC：先都准备好，再一起提交。** 协调者先向所有参与者发 prepare，参与者执行本地事务、写 undo/redo、把要改的行锁住，但不提交，只回复“可以”或“不行”；全部可以，协调者再发 commit，否则发 abort。XA 就是把这套接口标准化的规范。可以把它想成几个人合改一份合同：先逐个确认自己能改并占住位置，再由主持人统一喊“落笔”；主持人失联，其他人就只能握着笔等。它的原子性很硬，代价是 prepare 之后锁一直不放，协调者在 prepare 之后宕机，参与者会停在 in-doubt 状态，只能等恢复或人工裁决。面试里问“2PC 阻塞在哪”，只答“网络慢”不够，要答出协调者单点与 prepare 阶段资源被长期占用。更麻烦的是，参与者恢复后不能靠超时猜结果，必须找到协调者或查询全局决策；3PC 增加 pre-commit 正是想缓解这段阻塞，但它仍然绕不开网络分区下的不确定性。

**TCC：把锁换成业务层的预留。** Try 先检查并冻结 100 元，Confirm 把冻结的钱真正扣走，Cancel 解冻。它不依赖数据库的长事务，锁的粒度由业务决定，所以高并发下通常比 2PC 灵活；代价是每个参与者都要写三个接口，而且必须处理三类异常：Try 没到、Cancel 先到的空回滚；Cancel 已完成后 Try 才到的悬挂；以及所有 Confirm/Cancel 重试的幂等。Seata 的 TCC 方案用一张 fence 记录表来挡这几类问题，思路值得借鉴（[Seata TCC 的幂等、悬挂与空回滚](https://seata.apache.org/zh-cn/blog/seata-tcc-fence/)）。还要注意，TCC 不是“没有锁”，而是把数据库行锁换成了业务资源锁；如果 Try 只做校验、不真正预留，Confirm 阶段就可能因价格或库存变化而失败，所以 Try 校验的条件必须和 Confirm 时保持一致。

**Saga：一串本地事务，失败就反向补偿。** 把长流程拆成 T1 到 Tn，每步提交本地事务并触发下一步；某步失败，就依次执行 C(n-1) 到 C1。协调方式有两种：编排式由中心状态机下指令，协同式靠各服务发事件自行接力（[Saga 模式](https://microservices.io/patterns/data/saga.html)）。Saga 最大的短板不是补偿难写，而是没有隔离性：T1 已提交、T2 还没跑时，别的请求能看见“转出成功、转入未到”的中间态。常见补法是语义锁——把订单或账户置为 PENDING，配合版本号阻止并发修改。比如两个 Saga 同时给同一件商品锁库存，都读到“还剩一件”，各自提交后才发现超卖；语义锁就是让第二个 Saga 在入口就失败，而不是等补偿时再去抢。

**本地消息表与事务消息：不追求当下一致，追求事件一定发出去。** 先写库再发 MQ 是典型的双写，任何一步失败都会丢事件或发出不存在的事件。本地消息表把业务变更和一条待发消息放进同一个本地事务，再由中继进程或 CDC 读日志投递（[Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)）；RocketMQ 的事务消息则用半消息加回查，把“本地事务结果”与“消息可见性”绑在一起（[事务消息](https://rocketmq.apache.org/zh/docs/4.x/producer/06message5/)）。两者都只能做到至少一次投递，消费端仍要按业务键去重。中继“发送成功”与“标记 SENT”之间仍有窗口，所以至少一次是设计前提：消费端用业务唯一键建唯一索引，让判重记录与业务写入落在同一个本地事务里，才能真正做到重复消息只生效一次。

```sql
BEGIN;
UPDATE account SET balance = balance - 100
 WHERE id = 'A' AND balance >= 100;
INSERT INTO outbox (id, topic, payload, status)
VALUES ('evt-1001', 'transfer',
        '{"from":"A","to":"B","amount":100}', 'NEW');
COMMIT;

-- 中继：用 SKIP LOCKED 让多个实例并发送达，成功后再置为 SENT
SELECT id, payload FROM outbox
 WHERE status = 'NEW' ORDER BY id LIMIT 100
 FOR UPDATE SKIP LOCKED;
```

| 方案 | 一致性 | 隔离性 | 业务侵入 | 适合 |
|---|---|---|---|---|
| 2PC / XA | 原子提交，强 | 靠资源锁，较强 | 低 | 短事务、同构资源 |
| TCC | 业务层原子，较强 | 靠资源预留 | 高，三个接口 | 高并发、可预留资源 |
| Saga | 最终一致 | 基本没有 | 中高，要写补偿 | 长流程、跨团队 |
| 本地消息表 | 最终一致 | 没有 | 中，表加中继 | 事件通知、解耦 |

四种方案可以组合，但要有主次：短事务内部用 2PC 保原子，长流程外层用 Saga 编排，跨服务通知走 outbox。最怕的是每一层都加一套补偿，最后没人说得清一次失败会被补几次。

## 常见考点与误区

- **“2PC 是强一致，所以慢一点也值得”**：2PC 保证的是原子提交，不保证高可用。prepare 后锁不释放，协调者故障会让参与者长期 in-doubt，恢复期间业务可能一直转不动；跨机房、跨长调用的场景尤其明显。
- **“TCC 就是写 Try、Confirm、Cancel 三个接口”**：真正难的是异常路径。Try 未执行而 Cancel 先到，Cancel 不能去释放一笔并不存在的预留，通常要落一条回滚标记再返回成功；Cancel 完成后 Try 才到，必须拒绝，否则资源会永久冻结；Confirm 和 Cancel 还会被重复调用，必须幂等。
- **“Saga 能把数据回滚到原样”**：补偿是业务语义上的反向操作，不是数据库 rollback。退款不是撤销扣款，取消订单也不是删除订单；发出去的短信、打出去的日志通常无法补偿，只能放到流程末尾或做成幂等。
- **“上了 MQ 就自动最终一致”**：数据库与消息之间仍是双写，必须靠本地消息表、事务消息或 CDC 消除缺口；消费端还会收到重复消息，唯一键、去重表或状态机至少要有一样。
- **“最终一致就是先返回、以后总会对”**：没有收敛时限、对账任务和死信兜底的“最终”，只是把问题推迟到用户投诉。至少要能回答：延迟多久算正常，差异由谁发现，补不回来时谁来兜底。

## 实践建议

- 先缩小一致性边界：能放进一个本地事务的，不要拆成分布式事务；必须跨库时，再按“事务长短、并发高低、能否补偿”选型，而不是一上来就套框架。
- 账务、支付这类短而强的写，优先 2PC/XA 或带全局锁的 AT 模式，但把事务压在毫秒级，别在事务里做 RPC、发短信、等人工审核。
- 库存、余额这类高并发热点，用 TCC 的预留而不是直接扣减；预留记录带唯一业务键和状态机，Confirm/Cancel 都按“已处理直接返回成功”设计，并给冻结资源设超时释放。
- 长流程用 Saga 编排，补偿动作要可重试、可观测，且尽量放在流程后段；对不可补偿的副作用，改用本地消息表异步推进，不要指望“失败再撤回来”。
- 最终一致必须配一套可观测指标：outbox 积压、消费延迟、对账差异、死信数量。给每个指标设阈值和责任人，比在代码里多写几个重试更有用。

*一句话总结：一致性方案没有标准答案，只有把锁的时长、错的窗口、补的代价算清楚之后的取舍。*
