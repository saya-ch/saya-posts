## 是什么

HTTP/1.1、HTTP/2、HTTP/3 是同一套语义（方法、状态码、头部字段）落在三代传输方式上的实现。它们真正的差别不在"支持哪些功能"，而在回答同一个问题：一条连接上怎么同时跑多个请求，又不让它们互相堵住。

一句话直觉：HTTP/1.1 是单车道排队，HTTP/2 把货物切成小包、编号后塞进一条隧道，HTTP/3 则直接修了多条互不干扰的隧道。

典型场景就在身边：打开一个页面要拉几十个资源，移动端弱网下丢包频繁，网关后面跑 gRPC，CDN 回源跨地域。这些场景里选 h1、h2 还是 h3，差别往往比换一台服务器更大。

## 核心原理

### HTTP/1.1：串行发送，多开连接换并发

HTTP/1.1 是文本协议，一个请求报文对应一个响应报文。keep-alive 让连接可以复用，但同一条连接上，前一个响应没发完，后一个请求的响应就不能插队。协议里其实有 pipelining（流水线），允许客户端连发多个请求，可服务器必须按请求顺序回响应，第一个慢请求仍然卡住后面所有响应——这就是应用层队头阻塞。浏览器干脆放弃流水线，改成对同一个源开六条左右并发连接，用连接数换并发。

代价显而易见：每条连接都要单独握手、单独慢启动；头部是纯文本，每个请求都重复发送 Cookie、User-Agent，浪费带宽。于是当年的前端优化几乎都在绕开这个限制：域名分片把资源摊到多个子域，从而多开几条连接；精灵图和小图标内联把多个请求压成一个；资源合并把几十个 JS 打成一个包。这些手段不是审美选择，而是协议逼出来的补丁。

### HTTP/2：一条连接上的多条流

HTTP/2 在 TCP 之上加了一层二进制分帧层。连接被切成若干条流（stream），每条流有唯一 ID；流里跑的是帧（frame），HEADERS 帧装头部，DATA 帧装正文。不同流的帧可以交错发送，接收端按流 ID 重新组装，于是多个请求真正并行，不必等前一个响应结束。

```python
import struct

def parse_frame_header(buf: bytes):
    length = int.from_bytes(buf[:3], "big")
    ftype, flags, sid = struct.unpack(">BBI", buf[3:9])
    return length, ftype, flags, sid & 0x7FFFFFFF

# HEADERS 帧：长度 0x20，type=0x1，flags=0x4(END_HEADERS)，流 1
print(parse_frame_header(b"\x00\x00\x20\x01\x04\x00\x00\x00\x01"))
# (32, 1, 4, 1)
```

帧头固定九字节：三字节长度、一字节类型、一字节标志、四字节流 ID（最高位保留）。解析它只需按大端读整数，这就是二进制分帧比解析文本报文省事的地方。

HTTP/2 还做了两件关键的事。一是 HPACK：头部字段用静态表、动态表加霍夫曼编码压缩，同一连接上重复的 Cookie 只传一次索引。二是流优先级与流量控制：接收端通过 WINDOW_UPDATE 按流或按连接发预算，避免一个大文件把整条连接占满。浏览器后来也陆续拿掉了服务端推送（server push），因为它很难猜准客户端到底还需不需要那些资源，推错了反而浪费带宽。

顺带一提，头部压缩是"有状态"的：动态表靠双方按相同顺序更新来保持一致。这个设计在 TCP 上成立，因为字节流本来就有序；到了 QUIC，多条流各自独立到达，同一个表就可能被更新乱序，所以 HTTP/3 改用 QPACK，用额外的控制流同步表的更新，并允许接收端声明最多能容忍多少条流被阻塞。

但 HTTP/2 的多路复用只到应用层为止。底下仍然是一条 TCP 连接，而 TCP 把数据看成一个有序字节流，它不知道哪些字节属于哪条流。任何一个包丢了，内核都要等重传把空洞补上，后面已到达的字节全压在缓冲区里，所有流一起停。这正是"TCP 层队头阻塞"。在丢包率百分之一的链路上，h2 的实际表现可能还不如 h1 的六条连接，因为六条连接各有独立的拥塞窗口和重传队列，丢一个包只影响其中一条。

### HTTP/3：把多路复用下沉到传输层

HTTP/3 换掉了 TCP，跑在 QUIC 上，QUIC 又跑在 UDP 上。QUIC 在用户态实现了可靠传输、拥塞控制、流量控制和加密（TLS 1.3 内嵌），并且从设计之初就把"流"当作传输层的一等公民。每个 QUIC 包带包号，每条流有自己的偏移量；丢包时接收端能判断缺的是哪条流的哪段数据，只阻塞那一条流，其余流照常交付。这是 h3 相对 h2 最实质的改进。

QUIC 还顺手解决了另外几个老问题：握手合并，首次连接一个 RTT、会话恢复可到零 RTT，而 TCP 加 TLS 1.3 至少要先完成 TCP 握手再谈 TLS；连接 ID 让连接不再绑定四元组，手机从 Wi-Fi 切到 5G 时连接可以迁移，不必重握手；传输层元数据被加密，中间设备更难擅自改写。

代价是 UDP 的待遇不如 TCP：部分企业网络和运营商会对 UDP 限速甚至直接封掉 443/UDP，所以 h3 必须保留 h2 回退。另外零 RTT 的数据可以被重放，只能用于幂等请求。

## 常见考点与误区

- **"HTTP/2 已经解决了队头阻塞"**：只解决了应用层。TCP 层的丢包仍会让整条连接停摆，这正是 h3 存在的理由。面试只答"解决了"而不分层，基本会被追问到哑口。
- **"HTTP/1.1 的 keep-alive 就是并发"**：keep-alive 只是复用连接，同一条连接上的请求仍是串行的。想要并发，要么多开连接，要么上 h2。
- **"pipelining 没人用是因为浏览器懒"**：不是。协议要求响应按序返回，前一个慢请求会卡住整条流水线，加上中间设备兼容性差，Chrome 早已移除该选项。
- **"二进制协议所以更快"**：h2 的收益主要来自多路复用、HPACK 和帧解析的确定性，不是"二进制"三个字本身。资源很少、延迟很低的场景下，h2 甚至可能更慢。
- **"HTTP/3 就是在 UDP 上重发 HTTP/2"**：QUIC 重新实现了可靠传输与拥塞控制，流是传输层概念，帧格式也是新的，两者并不兼容。
- **"0-RTT 越快越该开"**：零 RTT 数据可被重放，只应发给幂等接口；支付、下单这类请求不能走零 RTT。

## 实践建议

- 同源资源不要再做域名分片。h2/h3 下多开域名会拆散连接、丢掉 HPACK 动态表的复用收益，反而更慢；把静态资源收敛到一个域名，配 TLS 并用 ALPN 协商出 h2。
- 上 h3 用 Alt-Svc 或 HTTPS DNS 记录宣告，同时保留 h2 回退；监控 443/UDP 的可达率，企业网封 UDP 是常态。
- 调 h2 要关注 SETTINGS 里的 MAX_CONCURRENT_STREAMS 和初始窗口；大文件下载给足连接级窗口，否则多路复用会退化成串行。
- 服务端超时与重试按流语义设计：客户端发 RST_STREAM 取消，不代表服务端没执行，写操作仍需幂等键兜底。
- 压测分开跑 h1/h2/h3，并按网络条件分组（低延迟低丢包对弱网）。数据中心内部 h2 往往不输 h3，h3 的优势在移动网络和跨地域长肥管道上。

*一句话总结：三代 HTTP 争的不是功能，而是把队头阻塞挡在哪一层——连接、TCP 还是流。*
