## 是什么

削峰（peak shaving）指的是：当入口流量在短时间内远高于下游稳定处理能力时，先把请求写进消息队列缓冲，消费者按自己扛得住的速率取出处理，用"多等一会儿"换"不丢、不压垮数据库"。它常出现在秒杀下单、订单创建后的发券加积分、埋点与事件总线、支付回调转异步这些场景。

幂等则是对"同一条业务消息被消费多次"的约束：无论收到几次，最终业务效果与只消费一次相同。

把两者放在一起看，关系不是"削峰之外顺便做个幂等"，而是削峰方案自带的必要组成：队列把"过载时立刻拒绝"换成了"先收下、稍后重投"，而重投正是重复的来源。

## 核心原理

### 削峰改的是曲线，不是工作量

设入口到达速率为 λ(t)，下游稳定处理速率为 μ。峰值期间 λ 远大于 μ，多出来的部分不会消失，只会变成队列里的积压：

Q = ∫(λ(t) − μ) dt

积压的排空时间约等于 Q / μ。举例：峰值 5000 条/秒持续 60 秒，消费者只能处理 500 条/秒，则积压约 27 万条，即使流量立刻回落，也要约 9 分钟才能排完。这三个数字决定削峰是否成立：队列能不能存下、业务能不能等、消费者能不能持续以 μ 工作。

所以"上个消息队列就削峰了"是错觉。队列只是一块缓冲垫，真正决定成败的是 μ 与可接受延迟。若 μ 长期小于平均到达率，积压只会一路涨到保留期上限，然后开始丢消息；若业务要求 3 秒内出结果，把请求塞进要排 9 分钟的队列，只是把超时从入口挪到了出口。

### 重复从哪来：确认之前都是不确定态

消息系统里，"已经处理"和"已经被确认"是两件事。两者之间有一段不确定窗口，重复就从这里长出来。

第一段在生产端。生产者发出消息，broker 写成功，但确认响应在网络上丢了；生产者只能重发。Kafka 的幂等生产者用 broker 分配的 producer ID 加每条消息的序列号做去重，保证重发不会在日志里留下重复条目（[Confluent 投递语义文档](https://docs.confluent.io/kafka/design/delivery-semantics.html)）。但这段去重只覆盖"生产者到 broker"，管不到消费者写数据库。

第二段在消费端。消费者取到消息、处理完、还没提交位点就崩溃，或者分区被重平衡交给别人，新消费者只能从上一次已提交的位点重新开始。Kafka 默认给的是至少一次语义，重复消费是这套语义的正常代价。SQS 的标准队列同样如此：它保证每条消息至少被投递一次，偶尔会投递多份副本，官方文档因此直接建议应用侧按幂等来设计（[SQS 至少一次投递](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)）。

第三段是可见性超时。SQS 的消费者取走消息后，消息会被隐藏一段时间，默认 30 秒；处理完必须显式删除，否则超时后消息重新可见，另一个消费者会再处理一遍（[SQS 可见性超时](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)）。

把三段放在一起，会得到一个反直觉的结论：重复概率与消息的"在途时间"正相关。而削峰做的事，恰恰是把消息在途时间拉长——洪峰时积压多、单条等待久、消费更容易超时、重平衡更频繁。也就是说，系统最忙的时候，正是重复最多的时候。这就是为什么削峰和幂等必须一起设计。

### 去重记录放在哪，决定缝还在不在

最直觉的做法是消费前查一次 Redis：这个 event_id 处理过吗？没处理过就写业务、再写缓存。问题是"写业务"和"写缓存"是两个动作，中间崩溃就会出现两种坏结果：缓存写了、数据库没写，消息重投时被误判为已处理而丢弃；或者数据库写了、缓存没写，重投时再执行一遍。缓存还会过期、会被淘汰、主从切换可能丢最近写入。

正确的做法是把"是否处理过"和"业务效果"放进同一个原子边界。关系型数据库的可行写法是：同一事务里先插入去重记录，靠唯一约束抢占；插入成功才执行业务，最后提交事务，提交成功之后再确认消息。

```go
tx, err := db.Begin(ctx)
if err != nil { return err }
// 唯一键 (event_id, consumer) 抢占，重复消息在这里影响 0 行
res, err := tx.Exec(ctx,
    `INSERT INTO consumed_event(event_id, consumer) VALUES($1,$2)
     ON CONFLICT (event_id, consumer) DO NOTHING`, msg.EventID, "points")
if err != nil { tx.Rollback(); return err }
if res.RowsAffected() == 0 { tx.Rollback(); return msg.Ack() } // 已处理
_, err = tx.Exec(ctx,
    `UPDATE user_points SET points = points + $1 WHERE user_id = $2`, 10, msg.UserID)
if err != nil { tx.Rollback(); return err }
if err := tx.Commit(ctx); err != nil { return err }
return msg.Ack() // 先提交，再确认
```

如果业务本身可以写成条件更新，还有更轻的办法：`UPDATE orders SET status='paid' WHERE id=? AND status='pending'`，第二次执行影响 0 行，效果天然只有一次。它不依赖额外的去重表，但要求状态机设计得足够严谨。

这里要注意幂等键的选法。它应该是生产者在业务意图产生时生成的稳定 ID，比如订单号加事件类型，并在重试、转发、进入死信队列时原样保留。不能用消息体哈希：同一次业务事件重发时，时间戳、追踪 ID 一变，哈希就变了，去重直接失效。

### 顺序与并发：幂等不负责排序

去重只能保证"不会执行两次"，保证不了"按正确顺序执行"。同一个订单的"支付成功"和"取消"如果被拆到两个分区并发消费，即使两条都只执行一次，最终状态仍可能错。需要保序的实体必须用同一个分区键（或同一个消息组），让同一实体的消息串行进入；分区数也不要随意增加，因为取模映射一变，历史消息和新消息的顺序关系就断了。

同时，消费者并发度的上限不是队列的分区数，而是下游真正能承受的并发。把并发从 20 调到 200，队列积压会立刻下降，但压力会原样转移到数据库连接池；数据库一旦排队，消费线程跟着阻塞，积压又会反弹。削峰不是把峰值消灭，只是把它挪到你能看见的地方。

## 常见考点与误区

- **"用了消息队列就是削峰，下游不用扩容"**：削峰只改变到达曲线，不减少总工作量。μ 不够时积压会撞上保留期，SQS 默认只保留 4 天、最长 14 天（[SQS 消息配额](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html)），到期消息直接消失。面试里要能算出积压量和排空时间，而不是只说"缓冲一下"。
- **"开了幂等生产者或 exactly-once 就端到端不重复"**：Kafka 的幂等生产者只去掉 producer 到 broker 的重发重复；事务语义主要覆盖 Kafka 内部的读、处理、写闭环。只要消费者最后写的是 MySQL、Redis 或第三方接口，重复仍会发生，业务侧幂等跑不掉。
- **"先提交位点再处理，吞吐更高"**：那是至多一次语义，进程崩溃就永久丢消息。先处理后提交是至少一次，用重复换不丢。两者只能选一个，选了后者就必须配幂等；没有"既快又不重"的免费选项。
- **"Redis 去重就够了"**：缓存与数据库不在一个事务里，崩溃会留下"标记了没执行"或"执行了没标记"的缝；缓存过期时间还可能短于队列重投窗口。Redis 可以做前置挡板，最终判定要落在带唯一约束的持久存储上。
- **"失败就无限重试，总能成功"**：重试会放大重复、挤占正常消息，还会把下游打得更慢。RocketMQ 的无序消息重试间隔从 10 秒逐级拉长到 2 小时，重试次数有上限，超过后进入死信队列（[RocketMQ 消费重试](https://rocketmq.apache.org/zh/docs/featureBehavior/10consumerretrypolicy)）；没有上限的重试等于把故障摊给整个队列。
- **"FIFO 队列自带去重，业务不用管"**：SQS FIFO 的去重只在 5 分钟的 deduplication interval 内生效（[SQS FIFO 去重](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html)），跨窗口重发照样进队；FIFO 也不覆盖"消费后写库"这一段。

## 实践建议

- **先算三笔账再谈选型**：峰值超出处理能力的面积换算成积压条数；积压除以消费速率得到最长排空时间；队列保留期与最大重试跨度决定消息能活多久。三者对不上，先扩容或入口限流，别指望队列兜底。
- **消费并发按下游容量设，不按积压设**：用信号量或令牌桶把同时写库的请求压在手头连接数以内；积压高时优先看单条处理耗时和下游响应时间，而不是盲目加消费者。
- **幂等键生产端生成、全链路透传**：订单号或事件 ID 在业务意图产生时确定，重试、转发、死信、补偿任务都不重新生成；去重表 TTL 至少覆盖队列保留期加最大重试窗口，清理任务避开仍在途的记录。
- **把重复当指标**：监控去重命中率、可见性超时次数、重平衡次数、死信深度，而不只是积压量。压测时故意重复投递同一批消息，验证副作用只发生一次。
- **需要保序就锁业务键**：同一订单或账户的消息走同一分区或消息组；扩分区前先评估键映射变化，必要时双写过渡，而不是直接翻倍。

*一句话总结：削峰把洪峰摊成等待，也把重复的概率一起拉高；幂等不是附赠项，而是队列消费能成立的前提。*
