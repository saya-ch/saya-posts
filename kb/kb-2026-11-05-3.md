## 是什么

闭包陷阱不是 React 的 bug，而是 JavaScript 闭包与"长生命周期回调"碰在一起的必然结果。函数组件每渲染一次，就是重新调用一次函数；这一次调用里的 props、state、局部变量，构成一个只属于这次渲染的作用域。Effect、事件监听、定时器、Promise 回调如果在某次渲染里创建，就会一直抓着那次渲染的作用域不放。等组件已经渲染了十次，这个旧回调读到的仍是第一次的值。

一句话直觉：每次渲染像拍一张照片，回调保存的是照片，不是实时直播的画面。你以为它在读"当前 count"，其实它读的是"拍下这张照片时的 count"。

典型场景很集中：useEffect 里用 setInterval 做倒计时、注册 window.resize 或 scroll 监听、连上 WebSocket 后处理消息、写 debounce、发请求后在 then 里 setState。它们的共同点是——回调活得比创建它的那次渲染更久。这也是[官方文档](https://react.dev/reference/react/useEffect)反复强调"每个 Effect 都描述了自己的同步过程"的原因。闭包本身没有错，错的是把会过期的值关进一个不会重建的回调里。

## 核心原理

要讲清楚，得先把闭包这一层拆开。JS 的函数在创建时会把当时的词法环境记下来，包括变量绑定，而不是把值复制一份。函数执行时沿着作用域链去找这个绑定，找到什么就是什么。关键在于：每次调用外层函数，都会创建一套新的绑定。所以同一个组件渲染两次，两个 `count` 是两个独立的变量，各自被各自那批回调捕获。Dan Abramov 那篇[《A Complete Guide to useEffect》](https://overreacted.io/a-complete-guide-to-useeffect/)把这件事概括成"每次渲染都有自己的 props 和 state"，说的就是这层机制。

依赖数组回答的则是另一个问题：这次渲染的哪些值变了，需要重新同步。React 用 `Object.is` 逐项比较新旧依赖；只要有一项不等，就先执行上一次 Effect 返回的清理函数，再执行新的 Effect。空数组意味着"没有任何依赖会变"，于是 Effect 只在挂载后跑一次，它创建的回调就被永久留在那里。换句话说，依赖数组不是"何时运行"的开关，而是"何时重新订阅"的声明。

还有一个常被忽略的约束：依赖数组的长度和顺序必须稳定。Hooks 的状态是按调用顺序匹配的，把依赖写成条件分支、或在 if 里调用 Hook，都会让 React 在下一次渲染时对错槽位，轻则状态串味，重则直接报错。依赖可以多写、可以把一个 Effect 拆成两个，但不能时有时无。

那为什么不让 Effect 每次渲染都重跑？因为 Effect 的职责是跟外部系统同步，重建连接、重订阅、重发请求都有真实成本；React 把"哪些值参与同步"的决定权交给依赖数组，是为了让重跑次数可控。代价就是你必须诚实地列出这些值。

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // 永远读到首次渲染的 count = 0
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <h1>{count}</h1>;
}
```

这段代码的表现是：界面永远停在 1。因为每秒执行的都是 `setCount(0 + 1)`，值确实变了，但下一次 tick 还是拿同一个 0 去算。把 `[]` 改成 `[count]` 会正常工作：count 一变，旧 interval 被 clear，新 interval 带着新快照重建。代价是每秒重建一次定时器，多数场景可以接受。

不想重建订阅，还有两条路。第一条是函数式更新：`setCount(c => c + 1)`。回调不再读外部的 count，而是把"怎么算"交给 React 的更新队列，队列里的 c 永远是最新值。这不是绕过闭包，而是把读取最新值的责任转移出去。第二条是 ref：`useRef` 返回的对象在多次渲染间保持不变，`ref.current` 是一个可变的盒子；在 Effect 里把最新值写进去，长生命周期回调读 `ref.current` 就能拿到新值。代价是 ref 变化不会触发渲染，它只适合"给回调看"，不适合驱动 UI。

较新的 React 还提供了 [`useEffectEvent`](https://react.dev/reference/react/useEffectEvent)：它创建的函数总是看到最新的 props 和 state，又不会被算进依赖数组，专门用来把"非响应式的事件逻辑"从 Effect 里分出来。限制是它只能从 Effect 内部调用，不能当普通回调传给子组件。

还有一层容易漏掉：清理函数。React 在重新执行 Effect 前会先跑上一次的 cleanup，所以重建订阅本身不会泄漏；真正会泄漏的是你忘了返回 cleanup，或者 cleanup 只清了定时器、没取消已经发出的请求。

## 常见考点与误区

- **误区一：空依赖数组最安全。** 它只保证 Effect 不重跑，不保证回调读到新值。只要回调里出现 props、state 或其他每次渲染新建的值，空数组就是把整个 Effect 冻结在首帧。它适合的是确实与响应式值无关的一次性初始化，而不是"我想让它只跑一次"的万能写法。
- **误区二：把 count 加进依赖会导致死循环。** 循环的根因是 Effect 里无条件 setState，而不是依赖数组。加依赖再加条件判断，或改用函数式更新，就不会循环；反过来，为了消掉 lint 警告而删依赖，是把真 bug 藏起来。
- **考点三：setTimeout 里为什么读到旧 state？** 因为 setState 不会修改已经创建的闭包，它只是安排下一次渲染。那次渲染会产生新的绑定，但旧回调仍指向旧环境。修复手段就是函数式更新、ref 或 useEffectEvent。
- **考点四：闭包捕获的是变量还是值？** 捕获的是词法环境里的绑定。经典题里 `var` 在循环中只创建一个绑定，`let` 每轮创建一个，所以闭包打印结果不同；Hooks 的旧值问题是同一个机制在组件层面的重演。
- **误区五：ref 改了会触发重渲染。** 不会。ref 是逃生舱，适合存"最新值"和 DOM 引用；把它当 state 用，UI 不会更新。
- **误区六：cleanup 能解决所有异步竞态。** cleanup 只在依赖变化或卸载时执行；同一个 Effect 里并发发出的多个请求仍可能乱序返回，需要 cancelled 标志或 AbortController 显式丢弃过期响应。
- **考点七：依赖里放对象或函数为什么每次都重跑？** 因为对象字面量和内联函数每次渲染都创建新引用，`Object.is` 必然判不等。要么把依赖拆成原始值，要么用 `useMemo`、`useCallback` 稳定引用，而不是直接删依赖。
- **考点八：换成 useLayoutEffect 是不是就没这个问题？** 不是。两者共享同一套闭包捕获与依赖比较机制，区别只在执行时机——一个在绘制前、一个在提交后；旧值问题与用哪个 Effect 无关。

## 实践建议

- 依赖数组如实写，开启 [eslint-plugin-react-hooks 的 exhaustive-deps](https://react.dev/reference/eslint-plugin-react-hooks/lints/exhaustive-deps)。看到警告先问"这个值变了，Effect 要不要重新同步"，而不是先加 disable 注释。
- 需要最新值但不想重建订阅时，优先用 `useEffectEvent`；老版本用 ref 承接，并在 Effect 里同步，不要在渲染期间随手写 `ref.current`。
- 一切"基于旧值计算新值"的更新都写成函数式 setState，它在批量更新和异步回调里都不会失手。
- 订阅、监听、定时器一律返回 cleanup；异步请求用 AbortController，或在 then 里判断本次请求是否已过期。
- 开发环境打开 StrictMode，它会故意 mount、unmount、再 mount，把缺失的 cleanup 和重复注册暴露出来；不要为了"看着不跑两次"把它关掉。
- 怀疑某个回调读到旧值时，先在 Effect 里打日志确认它跑了几次、闭包里是哪一帧，再决定补依赖还是换写法；凭感觉改依赖数组，往往只是把 bug 从 A 场景挪到 B 场景。

*一句话总结：闭包拿的是渲染快照，依赖数组决定何时换新；把两者混为一谈，才会在定时器和监听器里反复读到旧值。*
