## 是什么

Vue 3 的响应式系统里，副作用（effect）是一段会被反复执行的函数，组件渲染、watch 回调、computed 求值最终都挂在各自的 ReactiveEffect 上。它和普通函数的关键差别是：执行期间读到哪些响应式属性，就会被登记进这些属性对应的依赖集合。

直觉上，effect 的依赖不是一份长期合同，而是一张“本次执行实际用到的清单”——下次执行前先销户，执行时再按实际读取重新开户。v-if 切换分支、watch 里按参数读不同字段、组件卸载，都是这张清单会变化的典型场景；静态分析给不出答案，只能靠运行时边读边记。也正因为记的是“谁真正读过”，更新才能做到细粒度：不需要对比整棵组件树，只要沿着依赖集合找到读过该字段的 effect。

## 核心原理

先看存储。最外层 targetMap 是 WeakMap，键为响应式对象；中间一层 Map 的键是属性名；最里面是 Set，装着依赖该属性的 effect。反向索引同样重要：每个 effect 维护一个 deps 数组，记下自己进过哪些 Set。两条索引互为镜像，少了任何一条，清理时就无法快速找到“我该从哪些集合里退出”。

track 发生在 Proxy 的 get 拦截中，把当前 activeEffect 塞进对应 Set；trigger 发生在 set 与 delete 拦截中，取出 Set 逐个执行。这只是教科书版本。真正让依赖“可变化”的，是每次 run 开头的那次 cleanup：遍历 effect.deps，从每个 Set 里删掉自己，再把 deps 清空。它清的是“自己作为成员”的身份，而不是把整个 Set 删除；空 Set 留在原处没有关系，targetMap 是 WeakMap，键对象不可达时整条记录会一起回收。

紧接着，run 把 activeEffect 指向自己并执行 fn，执行过程中每一次 get 又会 track，把本次真正读到的键重新填进 deps。于是旧分支与新分支的依赖不会混在一起：上一次读了 b，这一次条件为假没读 b，后续再改 b 就不会通知这个 effect。这就是“幽灵依赖”不会残留的原因。

这里有个容易忽略的设计取舍：为什么每次是清理关系、而不是直接新建一个 effect？因为 effect 的对象身份必须稳定，调度队列去重、stop 调用、effectScope 回收都依赖同一个引用。清理的是“它和哪些集合相连”，保留的是“它还是它”。从成本看，cleanup 与本次依赖数成正比，track 则是常数级摊还；用这点遍历换取依赖图始终等于最近一次执行的读取集合，是划算的。

嵌套 effect 是第二个坑。外层执行到一半创建了内层，内层 run 会把 activeEffect 改成自己；如果结束后不恢复，外层后半段的读取就会记到内层头上，或者干脆记丢。所以 run 要先把当前 activeEffect 存进 parent（早期实现用一个 effectStack 数组），在 finally 里恢复。只要收集依赖靠的是一个全局单例，这个栈式保存就是必需的。

还有自触发。effect 里既读又写同一个属性时，trigger 遍历依赖集合可能再次执行自己，形成无限递归。Vue 的处理有两层：遍历前先复制一份集合，避免执行过程中增删导致遍历错乱；执行时跳过 effect === activeEffect 的那一个（除非显式允许递归）。复制还顺带解决了“执行中把别的 effect 加进来”的并发修改问题。

```js
let activeEffect = null
function cleanup(effect) {
  for (const dep of effect.deps) dep.delete(effect)
  effect.deps.length = 0
}
class ReactiveEffect {
  deps = []
  active = true
  constructor(fn) { this.fn = fn }
  run() {
    if (!this.active) return
    cleanup(this)                 // 先销户：旧依赖一个不留
    const parent = activeEffect
    activeEffect = this
    try { return this.fn() }      // 执行中按实际读取重新登记
    finally { activeEffect = parent }
  }
}
```

最后是 stop。很多人以为 stop 只是把 active 置为 false，让后续 run 直接返回；真正关键的是先 cleanup，把自己从所有依赖集合里摘干净，再触发 onStop。组件卸载时渲染 effect 会被 stop；effectScope 把一批 effect 收在一起，scope.stop() 逐个停掉。没有 stop 的手动 effect 会一直留在 Set 里、持有闭包，数据一变就跑，这是很典型的泄漏。

## 常见考点与误区

- **考点一：deps 是只增不减的吗？** 面试常问“为什么每次执行前要 cleanup”。答“为了性能”是空话。正确说法是依赖集合必须与本次执行实际读到的属性一致，否则条件分支切换后，旧分支的字段仍会触发更新，出现“改了模板里根本没用的字段，组件却重渲染”。Vue 2 的 watcher 里也有 cleanupDeps，用 newDeps 与 deps 对比后摘除旧订阅，思路一致。
- **考点二：嵌套 effect 为什么需要栈？** 只说“保存外层”不够。activeEffect 是全局单例，内层 run 会覆盖它；恢复必须放在 finally，否则 fn 抛错后全局状态会永久错乱，后续所有依赖都记到错误的 effect 上。
- **误区三：effect 里读写同一个字段一定会死循环。** 不一定。trigger 会跳过当前 activeEffect，而且遍历的是集合副本；但把写操作放进异步回调或 scheduler 后，执行时 activeEffect 已经不是它，跳过判断失效，仍可能循环，需要自己加 guard。
- **误区四：stop 等于不再执行。** 错。stop 的关键动作是 cleanup，把 effect 从所有依赖集合里摘掉；只把 active 置 false 而不断开引用，闭包与依赖仍然挂着，内存和无效回调都还在。
- **误区五：computed 每次访问都会重新求值。** computed 的 effect 是 lazy 的，依赖变化只把标记置脏并通知下游，真正求值推迟到下一次读取 .value。所以“computed 比 method 快”只在依赖没变时成立，依赖一变照样要算。
- **考点六：reactive 是深拷贝还是深代理？** 都不是，它是按需代理：get 到嵌套对象时才递归包一层，所以深层属性也能被 track；这也意味着把整个大对象塞进渲染，依赖面会变得很宽。

## 实践建议

- 手动创建 effect 时成对管理生命周期：组件内用 effectScope 或 onScopeDispose，组件外用 try/finally 调 stop；watch 回调里的定时器、请求放进 onCleanup，不要指望响应式的 cleanup 帮你做业务清理。
- 排查“多余渲染”时，先看 render effect 的 deps 里有没有本次模板根本没用的字段。常见来源是读了整个 store、在模板里调用返回大对象的方法、把 props 整体展开。把读取收窄到具体字段，通常比加 memo 更有效。
- 不要依赖“值没变就不触发”做业务去重。trigger 只认依赖集合，不比较新旧值；需要相等就跳过时，用 computed 或 watch 里显式比较，别把语义押在调度细节上。
- 写 effect 内部的异步逻辑要小心：await 之后 activeEffect 已经恢复，读到的属性不会被收集。需要持续追踪就拆成同步 getter 加 watch，而不是在 async 函数里直接读。
- 调试依赖时，在 getter 里打点或临时打印 effect.deps，确认某个字段是否被登记，再对着组件渲染次数看，能快速区分“依赖过宽”和“调度重复”。

*一句话总结：依赖不是订阅一次就终身有效，每次执行先清空、再按实际读取重记，才是 Vue 3 不留下幽灵依赖的原因。*
