## 是什么

一致性哈希是一种把“键该放在哪台机器上”从取模运算改成环形坐标查找的分区方法。它把节点标识和键都哈希到同一个地址空间（通常画成 0 到 2^32−1 的环），键沿着环顺时针走，遇到的第一个节点就是它的归属。一句话直觉：不是拿键去数机器，而是让机器也站到环上，键找离自己最近的那一站。

它要解决的不是副本之间“强不强一致”，而是**成员变化时映射稳不稳定**：集群加一台、挂一台，尽量只让相邻的一段键换位置。典型场景是分布式缓存、分片存储、RPC 负载均衡和 CDN 节点选路；这个思路最早由 Karger 等人在 1997 年提出（[STOC 论文](https://dl.acm.org/doi/10.1145/258533.258660)），后来因 Amazon Dynamo 的大规模实践而流行（[Dynamo 论文](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)），Cassandra 的 token 也是同一套思路。名字里的“一致性”指哈希映射的一致性，和 CAP 里那个一致性没有关系，这是面试里最常见的望文生义。

## 核心原理

先看取模为什么会出事。集群有 N 台机器时，键落在 `hash(key) % N`。把 8 台扩成 9 台，一个键要留在原位，必须满足 `h % 8 == h % 9`；在 72 个余数里只有 8 个满足，也就是约 1/9 的键不动，其余 8/9 全部改道。缓存的意义是命中，键一改道就等于缓存瞬间清空，请求一起回源，数据库很容易被压垮。一般地，从 N 台加到 N+1 台，只有约 1/(N+1) 的键能留在原地。

哈希环把这件事变了个做法。把每台机器的标识哈希成一个 token，排在环上；键也哈希成环上的一个点，用二分找到顺时针方向第一个 token，那台机器就是归属。新增一台机器，相当于在环上插入一个 token，只有“前一个 token 到新 token”这段弧里的键会改归新机器，其他弧段完全不动。删除节点则相反，它负责的那段弧整体交给顺时针的下一个节点。查找是 O(log M)（M 为 token 总数），迁移量在期望上是 1/(N+1)，这两个数字就是它全部的价值。

但只给每台机器放一个 token，会踩到第二个坑：弧长是随机的。N 个随机点把环切成 N 段，段长近似指数分布，有的机器可能分到平均值的三四倍，有的只有零头。Dynamo 论文里明确写到，只映射一个点会让负载严重不均，所以它让每个节点占多个环上位置，这些位置就叫虚拟节点（virtual node），对应的 token 数可以按机器容量分配。

虚拟节点的作用不是“多哈希几次更随机”，而是**让每台物理机器由多段小弧拼成一份总份额**。假设每台机器挂 k 个虚拟节点，它的总负载是 k 段弧之和，相对标准差大致按 1/√k 下降。Tom White 的模拟显示，1 万个对象分到 10 台缓存时，每个节点 100 到 200 个副本点可以把标准差压到均值的 5% 到 10%（[Tom White 的模拟](https://tom-e-white.com/2007/11/consistent-hashing.html)）；再往上加，收益递减，而环的元数据、重建时间和连接数都在涨。

```python
import bisect, hashlib

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16) & 0xFFFFFFFF

class Ring:
    def __init__(self, nodes, vnodes=150):
        self.tokens, self.owner = [], {}
        for n in nodes:
            for i in range(vnodes):
                t = h(f"{n}#{i}")
                self.tokens.append(t)
                self.owner[t] = n
        self.tokens.sort()

    def get(self, key):
        i = bisect.bisect_right(self.tokens, h(key))
        return self.owner[self.tokens[i % len(self.tokens)]]
```

这段代码把“顺时针找第一个”压缩成一次二分：`bisect_right` 找到插入位置，越界就回到 0 号 token。线上实现通常换用 xxHash 或 MurmurHash 以降低 CPU 开销，并处理 token 冲突；MD5 在这里只是让示例短到可以读完。

副本放置还要再走一步。键归属第一个 token 后，如果要存三副本，不能简单取“后面三个 token”：虚拟节点可能让连续三个 token 都属于同一台物理机，三个副本就落在了一台机器上。正确做法是沿环继续走，跳过同一物理节点的 token，凑齐三个不同节点（最好再跨机架）。Dynamo 的 preference list 就是这么构造的，论文特别提醒虚拟节点会让前 N 个位置属于少于 N 台物理机。

如果连“最坏情况”都不能接受，还有 bounded loads：键先按环找到后继，若该节点负载已超过 `(1+ε)×平均值`，就继续顺时针找下一个还有余量的节点。Google 的论文证明每个节点的负载不超过平均值 1+ε 倍的上取整，而每次增删节点期望只移动 O(1/ε²) 个键，HAProxy 等实现已经采用（[Consistent Hashing with Bounded Loads](https://research.google/blog/consistent-hashing-with-bounded-loads/)、[论文](https://arxiv.org/abs/1608.01350)）。

## 常见考点与误区

- **“一致性哈希保证负载均匀”**：错。它保证的是期望均匀，单 token 的方差很大；虚拟节点把方差压小，但不能消除。均匀的是“键的数量”，不是“请求量”，一个热 key 仍然会把一台机器打满。
- **“扩容只迁移 1/(N+1)”**：这是期望值，不是每次的精确值。实际迁移量取决于新 token 落在哪段弧上；如果副本因子是 3，迁移的数据量大致还要乘 3。更要命的是，新节点分到的是冷缓存，命中率不会立刻回到扩容前。
- **“它和 CAP 的一致性是一回事”**：完全不是。一致性哈希只回答“键放哪”，不负责副本何时收敛、读到的值是否最新；用它的系统可以是最终一致（Dynamo），也可以叠加 quorum 之类的读写约束来提高一致性。面试里把这两个“一致性”混着答，基本会被追问到崩。
- **“环上后一个 token 就是副本”**：错。虚拟节点会让相邻 token 属于同一台物理机，必须跳过重复节点再取副本，否则三副本可能同机，机器一挂数据就没了。
- **“虚拟节点越多越好”**：不对。k 从 1 加到 100 收益明显，从 200 加到 2000 收益很小，但 token 数组、环同步、扩缩容时要搬的小区间和客户端连接都会变多。容量不同的机器可以给不同的 k，但别把 k 当成调优万能键。
- **“取模已经一无是处”**：也不对。节点数长期固定、只按编号取模的场景，取模最简单、分布也最整齐；一致性哈希是用额外的元数据和查找成本换成员变化的稳定性。

## 实践建议

- 虚拟节点数先从 100 到 200 起步，用真实键样本压测每台机器的键数与 QPS 占比，看最大值而不是平均值；大机器按容量加权，小机器别硬撑同样的 k。
- 只有“键数均衡”不够。给每台机器同时监控键数量、请求量、内存和回源流量，四者中任何一个倾斜都说明问题不在哈希环上；热 key 要用拆分键、局部缓存或请求合并单独处理。
- 环的元数据要版本化，推送给客户端时整份原子替换，避免一半旧环一半新环；扩缩容时先迁移再切读，或双读一段时间，观察命中率和回源 QPS 再撤旧节点。
- 副本因子大于 1 时，把“跳过同物理节点、跨机架”写进选点逻辑，并真的做一次单节点故障演练；不要只在代码注释里假设副本是分散的。
- 场景简单时别硬上环：桶编号固定可用 jump consistent hash，查找 O(log N) 且只搬约 1/N；节点少又想避开环维护，可以用 rendezvous（HRW）按 `hash(key, node)` 取最大。选型看的是变更频率和实现成本，不是哪个名字更熟。

*一句话总结：一致性哈希省的是成员变化时的迁移量，虚拟节点补的是随机落点带来的方差，两者都不负责热键和副本一致性。*
