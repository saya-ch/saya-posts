## 是什么

超时是调用方愿意为一次请求等待的上限；重试是在判定失败可恢复之后，再发一次请求的决定。两者必须一起设计：超时决定“什么时候认输”，重试决定“认输之后还起不起来”，而每一次重试都要重新占用时间、连接和下游容量。

一句话直觉：超时像给每次尝试发一个沙漏，重试像沙漏漏完后再掷一次骰子。只盯着单次沙漏、不算总共掷几次，账单最后会在最内层服务那里爆掉。

典型场景遍布日常链路：手机客户端调网关，网关调订单服务，订单服务查库存；任何一跳抖动都会触发上层重试。移动网络切换、云厂商可用区抖动、发布时的连接重置，都是重试最常登场的时刻。真正难的从来不是“加个 try-catch 再调一次”，而是决定这笔重试由谁来做、做几次、花掉谁的预算。

## 核心原理

### 超时是预算，不是每跳的旋钮

端到端 deadline 从入口开始计时，一路传下去，而不是每跳重新给三秒。[gRPC 的 deadline 文档](https://grpc.io/docs/guides/deadlines/)明确把它放在 context 里随请求传播，服务端能算出剩余时间；在 gRPC 的 HTTP/2 传输里，这份剩余时间由 `grpc-timeout` 头承载，网关也可以注入自己的超时头。如果每层都设三秒，三层最坏就是九秒：用户的连接早断了，内层还在认真干活。

剩余预算要在建连、排队、序列化、业务处理之间分配。DNS、TLS、连接池排队最容易被忽略：压测时 p99 是五十毫秒，线上一排队，客户端两百毫秒超时全打在等连接上，看起来像“服务变慢”，实际是客户端自己在门口堵死。

超时值应从 SLO 反推，而不是拍脑袋。取下游 p99 再加余量，并保证总预算小于上游给你的 deadline；平均值没有意义，超时几乎总发生在尾部。超时也不是越短越“灵敏”：过短会把正常长尾判死，制造本不存在的失败，再被重试放大成真实故障。

### 重试会按层数做乘法

这是最容易被低估的部分。若每一层失败后重试两次（一共三次尝试），三层链路最坏是 3×3×3＝27 次对最内层的请求；四层就是 81 次。更糟的是重试通常发生在下游已经过载时：它把“慢”变成“更多慢请求”，把局部超时升级为全局雪崩。

所以工程上要么只在一层重试，通常是离用户最近的边缘或最外层客户端；要么给每层配独立的重试预算，让重试请求数不超过正常请求数的一个固定比例。gRPC 的 [retryThrottling](https://grpc.io/docs/guides/retry/) 用令牌桶实现这件事：maxTokens 是初始令牌，失败扣一，成功按 tokenRatio 加回，低于一半就暂停重试；Envoy 的 [retry budget](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/router_filter) 也限制重试并发占总并发的比例，而不是放任每个请求各试各的。

预算还有一层含义：重试次数、单次超时、退避等待三者相加，必须小于上游给你的 deadline。常见事故是单次超时一秒、重试三次、退避再等一秒，客户端总共耗掉四秒多，而网关只给了三秒，最后两次重试纯属给下游添乱。

### 退避要与抖动一起用

固定间隔重试会把所有失败客户端对齐到同一时刻，形成周期性尖峰。指数退避把间隔拉长（一百、两百、四百毫秒），但如果没有抖动，大家仍在同一批时间点醒来。Full jitter 的做法是在零到当前退避上限之间取随机值，让重试时间散开：

```go
func doWithRetry(ctx context.Context, fn func(context.Context) error) error {
    const maxAttempts = 3
    backoff := 100 * time.Millisecond
    for attempt := 1; ; attempt++ {
        err := fn(ctx)
        if err == nil || attempt == maxAttempts || !retryable(err) {
            return err
        }
        // full jitter：在 [0, backoff] 内随机，打散同时重试的客户端
        wait := time.Duration(rand.Int63n(int64(backoff)))
        select {
        case <-time.After(wait):
        case <-ctx.Done():
            return ctx.Err() // 总预算耗尽，别再试
        }
        if backoff < 2*time.Second {
            backoff *= 2
        }
    }
}
```

这段代码有两个关键点：等待也受 ctx 约束，预算耗尽立即返回；退避有上限，避免第八次重试等到几分钟以后。AWS 的 [Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) 专门比较过 full jitter 与 decorrelated jitter，结论是加抖动比单纯指数退避更能削峰，因为抖动破坏的是“所有客户端同时醒来”这个前提。

### 哪些失败才配重试

重试的前提是“失败是暂时的，而且重放没有副作用”。连接重置、连接池拿不到连接、503、429（按 Retry-After 等）、明确的超时，通常可重试；400、401、403、404、422 这类语义错误重试多少次都一样，业务返回“余额不足”更不该重试。非幂等的 POST 要么不重试，要么带幂等键，这是另一条独立的话题。

还要注意：客户端超时不等于服务端停止。很多框架只在 I/O 边界或显式检查点响应取消，正在跑的 CPU 任务、数据库查询、第三方调用可能继续执行。超时值太短，会让你“以为失败了”，实际下游还在扣库存、写日志，重试再叠一层，等于同一笔业务被做了多次。取消能否真正传递，取决于每一层有没有检查 context 或等价的取消信号。

## 常见考点与误区

- **“只重试三次，量不大”**：错。次数要乘以层数，三层就是二十七倍；重试放大是乘法不是加法，最内层承受的才是真实倍数。
- **“超时越短越安全”**：错。过短会把正常的长尾判死，制造本不存在的失败与重试；超时应从 p99 和 SLO 反推，并留出建连与排队的余量。
- **“指数退避就够了”**：不够。没有抖动，客户端仍会同步醒来；重试风暴要靠 jitter 与重试预算一起压，单靠拉长间隔只是把尖峰推后。
- **“每层都加重试更稳”**：往往相反。嵌套重试让最内层承压最大，且上游超时后下游仍在重试，形成无效流量；重试应尽量收敛到一层。
- **“所有错误都值得再试一次”**：4xx、参数错误、业务拒绝重试无意义；非幂等写还可能重复下单。先分类，再决定是否重试。
- **“设了超时，服务端就停了”**：取消是协作式的，没有检查取消信号的代码会继续跑；要配合取消传递、资源回收和超时后的清理。
- **“重试能救容量不足”**：不能。重试只对瞬时抖动有效，持续过载时它是放大器，该做的是限流、熔断和降级。

## 实践建议

- 先画预算再写代码：入口 deadline 减去序列化与网络余量，得到每次尝试的上限；保证“尝试次数 × 单次超时 + 退避总和”小于上游 deadline，并把这条约束写进配置校验。
- 全链路只留一层重试，或每层使用独立的重试预算（例如重试请求不超过成功请求的一成），再用令牌桶或并发上限兜底；不要把重试次数当成随手可调的旋钮。
- 默认 full jitter，退避基数五十到两百毫秒、上限一到两秒、最多两到三次；429 优先尊重 Retry-After，503 结合熔断器快速失败，别让重试替熔断器挡枪。
- 把超时按阶段拆开观测：DNS、建连、首字节、整体耗时；同时统计重试率、每次逻辑请求的尝试次数直方图、取消后仍运行的时长。只看平均延迟，会漏掉正在形成的重试风暴。
- 对读多写少且幂等的请求可考虑 hedged request：p95 未返回就发第二份，先到先赢并取消另一份；但要设总并发上限，否则等于人为制造重复流量。
- 混沌演练里主动注入“下游变慢十倍”，验证预算耗尽时是否快速失败、重试是否被预算挡住，而不是等故障当天才发现重试链路根本没生效。

*一句话总结：超时管住一次等待，重试预算管住总放大，抖动负责别让大家同时醒来。*
