## 是什么

支付幂等指的是：同一个支付意图，无论请求因为用户双击、客户端超时、网关重试还是渠道回调重发而被送达多少次，资金侧都只发生一次扣款，并且每次调用方拿到的都是同一份结果。一句话直觉：它不是一道"防重复的闸门"，而是给每笔支付意图发一张身份证，再把第一次的答复存档，后来的人凭身份证领同一份答复。

这里要把三层"幂等"拆开看。HTTP 协议层的幂等说的是方法语义：`GET`、`PUT`、`DELETE` 被定义成幂等，`POST` 不是。数据库层的幂等靠唯一约束与状态机。支付真正需要的是"请求级幂等"加"业务状态机"的叠加，只做其中一层，总会在某个窗口漏掉重复。

典型场景包括：用户手抖点了两次"立即支付"；客户端三秒超时，但服务端其实已经成功；反向代理、SDK 或消息队列在失败后自动重试；渠道异步回调因为没有及时收到 ACK 而重发；夜间的补单任务把昨天的失败单又推一遍。这些重复的来源各不相同，但都指向同一个问题——服务端凭什么判断"这两个请求是同一件事"。

## 核心原理

**第一层是身份。** 幂等键必须在"创建支付意图"的那一刻生成，随订单一起持久化，之后所有重试都复用它。最常见的错误是在每次发 HTTP 请求时现生成一个 UUID，那等于宣布每个请求都是新意图，幂等层永远不会命中。键可以由客户端生成——Stripe 建议用 UUID v4 或熵足够的随机串，长度上限 255 字符，并且不要拿邮箱、手机号这类敏感信息当键；也可以由服务端从"订单号 + 操作类型 + 版本"派生。派生键的好处是调用方无法伪造、天然稳定，代价是它的含义被业务字段绑死：一旦金额可改，就必须把影响结果的字段纳入派生，否则两次不同金额的请求会撞成同一个键。

**第二层是记录的状态机。** 一条幂等记录至少要有四个字段：键、请求指纹（把参与计算的参数规范化后取哈希）、状态、首次响应。合法迁移只有几条：不存在 → 处理中 → 成功 / 可重试失败 / 终态失败。重放语义按状态区分：成功就原样返回首次的状态码与响应体；处理中要返回 409 或 202 并告诉调用方稍后查询，而不是再执行一遍；同一个键但请求指纹不同，必须拒绝——[Stripe 的做法](https://docs.stripe.com/api/idempotent_requests)就是比对参数，不一致直接报错，避免"用户改了金额却拿到旧的成功回执"。

有个容易忽略的细节：失败也要存，但存的是"执行过的结论"，不是"收到过请求"。Stripe 文档写得很明确，结果在端点开始执行之后才保存；参数校验失败、或与另一个并发请求冲突这类根本没开始执行的情况，不落结果、允许重试。这两类"失败"在语义上完全不同，混在一起就会把可重试的错误永久钉死。

**第三层是写入顺序。** 正确顺序是先落键、再调用渠道、最后回填结果，而不是"扣款成功后再补一条记录"。后者在"渠道已成功、进程崩了"之间留了一条缝，重试时查不到任何记录，只能再扣一次。抢占键用数据库唯一约束最稳：`INSERT ... ON CONFLICT DO NOTHING`，插入成功的那一个请求获得执行权，其余请求读到已有记录后走重放分支。

这里有个反直觉的点：不要把外部渠道调用包在数据库事务里。渠道可能几百毫秒到几秒才返回，长事务会一直占着行锁和连接；更重要的是，外部系统根本不参与你的本地事务，包进去也买不到原子性。合理的拆法是把"抢占"和"调用渠道"分开，再把"记账 + 回填结果"放进同一个本地事务。

```python
def pay(key, req):
    fp = fingerprint(req)
    got = db.execute("INSERT INTO pay_req(key, fp, status) VALUES (%s,%s,'PROCESSING') "
                     "ON CONFLICT (key) DO NOTHING RETURNING key", (key, fp)).fetchone()
    if not got:                                  # 键已存在：只重放，不再执行
        old = load(key)
        if old.fp != fp:
            raise Conflict("same key, different payload")   # 409
        if old.status == "PROCESSING":
            raise InProgress("query later")                 # 409/202
        return Resp(old.status, old.body)                   # 重放首次结果
    try:
        r = channel.charge(req, request_no=key)             # 渠道侧同号幂等
    except Timeout:
        raise InProgress("stay PROCESSING; query channel")  # 交给查询与对账
    with db.transaction():                       # 记账与回填同一事务
        ledger.write(key, r)
        db.execute("UPDATE pay_req SET status='SUCCEEDED', body=%s WHERE key=%s", (r.body, key))
    return Resp("SUCCEEDED", r.body)
```

**第四层是崩溃窗口。** 键停在"处理中"时，重试请求既不能直接放行（钱可能已经扣了），也不能永久拒绝（用户永远拿不到结果）。这时只能去问渠道：拿同一个商户订单号查询支付状态，查到成功就补记账并回填，查到不存在才允许重新发起。所以键记录里要存渠道请求号，而且这个号本身要能被渠道侧幂等。工程上常给"处理中"加一个租约：超时后允许另一个 worker 接管，但接管动作是"先查后做"，不是删掉记录重来。

**第五层是生命周期。** 幂等窗口必须覆盖整条链路上可能发生重试的时长：客户端重试、网关重试、渠道回调重发、人工补单。Stripe 的键至少保留 24 小时后可被清理，清理之后再用同一个键会被当成全新请求。如果你的对账是 T+1、人工补单可能拖三天，那 24 小时就偏短。窗口长度不该拍脑袋，它等于"最长可能重放的跨度"。

最后是存储选择。Redis 的 `SETNX` 只能当前置快挡：过期、主从切换、内存淘汰任何一个发生，重放就查不到首次结果。权威记录必须和账务待在同一个持久化存储里，才能靠本地事务保证"记账成功"与"幂等记录成功"同生共死。

## 常见考点与误区

- **误区一："加了唯一索引就幂等"**：唯一索引只保证同一个键不会被插两次，它管不了"第二次换了新键"。键的生成位置错了，索引再严也拦不住双扣。
- **误区二："先调渠道，成功后再写幂等记录"**：顺序反了。渠道成功与写记录之间只要崩一次，重试就查不到历史，直接再扣一笔。必须先抢占再执行。
- **误区三："同键不同参数，返回旧结果就行"**：这是最危险的一种"友好"。调用方改了金额或收款人后用旧键重试，拿到的是旧的成功回执，账实当场不一致。必须做指纹校验并返回冲突。
- **误区四："有幂等键就不需要对账"**：幂等只处理"同一意图的重复"，处理不了"两个不同意图指向同一笔钱"，比如用户真的下了两单、渠道侧重复清算、退款与扣款顺序错乱。最终仍要 T+1 对账和状态机兜底。
- **考点五："HTTP 幂等和支付幂等是一回事吗"**：不是。HTTP 幂等是方法语义约定，`POST` 天生不幂等；IETF 的 [Idempotency-Key 草案](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)想给 `POST`、`PATCH` 补上一层可重试语义，但它至今仍是 draft，具体行为要看各家实现。
- **考点六："处理中为什么不直接返回成功"**：因为钱可能还没扣。返回成功会让上层把订单置为已支付，后面真失败就变成"已付款未到账"，比让用户多点一次更麻烦。

## 实践建议

- 在创建支付单时生成键并入库，重试只读不重生成；键用高熵随机串，不要拼接业务字段，更不要把敏感信息写进去。
- 用数据库唯一约束做权威抢占，配请求指纹；同键不同参返回 409，处理中返回 409 或 202 并给出查询入口，成功则重放原响应。
- 处理中加租约加渠道查询，接管前一律"先查后做"；永远不要用"删掉键"来解卡，那等于把重复扣款的风险重新打开。
- 窗口长度取全链路最大重试跨度，清理策略与对账周期对齐；Redis 只做前置快挡，权威记录与账务同库同事务。
- 至少埋四个指标：同键重复率、处理中滞留时长、指纹冲突率、对账差异笔数。任何一个突变，都说明键生成或重试链路出了问题。

*一句话总结：支付幂等不是给请求去重，而是给意图发身份证、给结果留底稿，并用事务与对账守住中间那道缝。*
