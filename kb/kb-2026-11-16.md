## 是什么

用栈实现队列，指的是只允许使用栈的 push、pop、peek、empty 四种基本操作，做出一个满足先进先出语义的队列，对外提供 enqueue、dequeue、peek、empty；用队列实现栈则正好相反，只准用入队、出队、取队首这些操作，做出后进先出的栈。两道题在面试里出现频率极高，往往被当作手写模板题，但它们真正考的是你对「抽象数据类型」和「操作代价」的理解。

一句话直觉：数据结构不是某块内存长什么样，而是一组操作必须遵守的契约。模拟的难点从来不是把元素存进去，而是按另一种顺序把它们取出来。

典型场景包括：底层库只暴露了栈接口，而上层流程需要按到达顺序处理；消息缓冲里用两层结构隔离生产与消费的速度差；以及更常见的——面试官借这道题追问摊还分析、最坏情况与尾延迟。生产代码里很少有人真的手写这两个结构，但「为什么两个栈能占到便宜、两个队列却占不到」这个问题，能直接迁移到缓冲区设计、批量反转和并发队列的取舍上。

## 核心原理

先把两种契约摆在一起：栈只在一端进出，后进先出；队列一端进、另一端出，先进先出。栈的「翻转」是免费的，因为把一摞元素整体倒到另一摞，顺序自然就反了；队列没有这样一个可以整体翻转的动作，元素只能从队首一个个取出、再从队尾一个个放回。

两个栈实现队列的做法是维护 in 和 out 两个栈。入队时把元素压进 in；出队时，如果 out 非空，直接弹出 out 的栈顶；如果 out 为空，就把 in 里的元素逐个弹出并压入 out，此时 out 的栈顶正好是队首，再弹出即可。这里有一条必须守住的不变量：out 的栈顶永远是当前队首，且 out 非空时绝不能从 in 往里倒。

为什么不能倒？假设依次入队 1、2、3，第一次出队把 in 倒进 out，out 从底到顶是 3、2、1，弹出 1，剩下栈顶 2；接着入队 4，in 里只有 4。如果这时又倒一次，4 会被压到 out 顶端，下一次出队就会先拿到 4，而正确顺序应该是 2。原因很直白：4 比 2 更晚到达，却因为后倒而压在更早的元素上面，FIFO 立刻被破坏。

```python
class MyQueue:
    def __init__(self):
        self.inbox, self.outbox = [], []

    def push(self, x: int) -> None:
        self.inbox.append(x)

    def _shift(self) -> None:
        if not self.outbox:                      # 只在 out 空时整体倒一次
            while self.inbox:
                self.outbox.append(self.inbox.pop())
    def pop(self) -> int:
        self._shift()
        return self.outbox.pop()
    def peek(self) -> int:
        self._shift()
        return self.outbox[-1]

    def empty(self) -> bool:
        return not self.inbox and not self.outbox
```

复杂度要分两个口径说。单次出队最坏是 O(n)：out 为空且 in 里攒了 n 个元素时，这一次要把它们全部搬过去。但从一整串操作看，每个元素只会入 in 一次、最多被搬到 out 一次、最后出 out 一次，总搬移量不超过 2n，所以 n 次操作的总代价是 O(n)，均摊到每次就是 O(1)。这就是「均摊 O(1)、最坏 O(n)」的完整含义，两个说法并不矛盾，只是观察的尺度不同。

反过来用队列实现栈，画风就变了。两个队列的版本是：入栈压进 q1；出栈时把 q1 里除最后一个以外的元素全部移到 q2，弹出剩下的那个，再交换两个队列的角色。一个队列的版本更简单：新元素入队后，把前面 n-1 个元素依次出队再入队，让新元素转到队首，出栈时直接出队。前者 push 是 O(1)、pop 是 O(n)，后者 push 是 O(n)、pop 是 O(1)。

问题在于，这两种标准写法都没有均摊红利。被搬走的元素并没有「用掉」，它们原样留在结构里，下一次操作还要再搬几乎全部。n 次操作累计是 1+2+…+n，也就是 Θ(n²)，每次操作的均摊代价仍是 Θ(n)。根因还是那个不对称：栈只有一个口，整体倒一次就把顺序永久翻了过来，这笔搬运费只付一次；队列有两个口，把最新元素转到队首只是一次临时调整，下一次入队又落在队尾，下一轮还得重新转。用类比说，前者像把一摞盘子一次性倒扣到另一摞，后者像回转寿司每来一盘都要把整条传送带转一圈。

## 常见考点与误区

- **误区一：每次出队都无条件倒栈。** 面试官常给「入队 1、2、3，出队，再入队 4，再出队」这串操作，答错的人会在第二次出队前又倒一次，把 4 提前放出来。正确做法是只在 out 为空时倒，out 非空就直接弹。
- **误区二：把均摊 O(1) 说成每次 O(1)。** 这两句话在面试里是两回事。单次 dequeue 确实可能扫过整个 in 栈，均摊说的是任意 n 次操作的总账。更进一步，均摊分析仍是某种意义上的最坏情况分析，它不保证延迟平稳；对延迟敏感的系统，还要单独看那一次 O(n) 的抖动。
- **误区三：以为两个队列比一个队列更优。** 一个队列旋转已经足够，两个队列只是把同样的搬移换了个容器，复杂度和总搬移量都一样，代码反而更长。面试官问「两个队列有什么好处」时，想听的是你看出没有本质收益，而不是硬编一个优点。
- **误区四：以为两种模拟完全对称。** 用栈实现队列有均摊 O(1)，用队列实现栈没有；把前者结论照搬到后者，是这道题最常见的丢分点。判断依据不是「用了几个容器」，而是「一次批量搬移的结果能不能被后续操作继续利用」。
- **误区五：用 list 的 pop(0) 当出队。** 这在 Python 里是 O(n) 的数组整体前移，和「队列应该 O(1) 出队」的契约不是一回事。面试追问「数组怎么实现队列」时，要答环形缓冲或头尾指针，而不是删第一个元素。
- **边界 bug：peek 忘了触发倒栈、empty 只查了一个栈。** peek 和 pop 必须走同一条 _shift 路径；empty 要同时看 in 和 out，只看 in 会在 out 还有元素时误报空。

## 实践建议

- **生产环境优先用现成容器，不要手写。** Python 用 collections.deque，两端插入删除都是 O(1)；Java 用 ArrayDeque 而不是 Stack，后者继承 Vector、方法带同步，语义和性能都不占优；C++ 用 std::deque 或 std::stack 适配器；Go 可以用 slice 模拟栈，用带缓冲 channel 表达队列，但要清楚 channel 的阻塞与关闭语义，别把它当成无界队列。
- **两栈结构适合批处理，不适合硬实时。** 它的优点是把搬移集中到少数几次操作上，适合离线反转、批量消费；在线服务里要警惕那一次 O(n) 带来的尾延迟，可以限制单批规模、提前预热，或者监控 p99 而不是只看平均值。
- **并发场景要重新算账。** 倒栈时若持有一把大锁，所有读操作都会被堵在 O(n) 的搬运上；可以用双缓冲加原子交换缩短临界区，或者直接改用无锁队列。切换容器时别只改数据结构，还要确认内存可见性与 ABA 这类问题由谁负责。
- **用对拍和搬移计数验证，而不是靠肉眼。** 写一个以 deque 为 oracle 的随机测试，覆盖空结构 pop/peek、连续 push 与 pop 交替、倒栈后立刻 push 再 pop；再统计元素在栈间的移动次数，验证 n 次操作不超过 2n，均摊结论就有了实测支撑。

*一句话总结：两栈的均摊 O(1) 来自「每个元素只搬一次」，队列实现栈每次都要重搬，所以只有 Θ(n) 而没有均摊红利。*
