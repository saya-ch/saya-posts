## 是什么

KV Cache（键值缓存）是自回归推理时，把每一层注意力算出的 Key 和 Value 向量按 token 留在显存里，下一步解码直接复用，不必对整段前缀重做投影。一句话直觉：它像把读过的书页复印下来摊在桌上，后面每写一个字都能随手翻，但桌子得先腾出地方，而且摊开的页数只增不减。

它出现的场景很具体：在线对话要估并发容量，长文档与 RAG 要定上下文上限，选卡和切分方案要回答"这张卡能开几条"，推理服务的 SLO 也要靠它反推。这里必须先分清两笔钱。权重是加载一次就固定的房租，不随流量变化；KV 缓存是跟着请求数和生成长度走的水电，请求一多、上下文一长就往外冒。只算房租的人，上线后往往发现水电费才是大头。

还要划清一个边界：KV Cache 并不"减少"显存占用，它只是把重复计算换成了常驻存储。省下的是算力，欠下的是容量，而且这笔容量按 token 计费，不像权重那样一次付清。

## 核心原理

### 一笔可以逐项乘出来的账

每个 token 在每一层要存两份向量，K 一份、V 一份；每份有 H_kv 个 KV 头，每个头 d 维，每个元素占 b 字节。于是单个 token 的缓存大小是：

**2 × 层数 L × KV 头数 H_kv × 头维度 d × 字节数 b**

以 Llama-2-7B 为例，32 层、32 个 KV 头、头维度 128，bf16 每元素 2 字节：2×32×32×128×2 = 524288 字节，正好 512 KiB/token。4K 上下文就是 2 GiB，32K 就是 16 GiB。再看 Llama-2-70B：80 层、64 个查询头但只有 8 个 KV 头，每 token 是 2×80×8×128×2 = 320 KiB。参数大近十倍的模型，每 token 反而更便宜，原因不是层数少，而是 GQA 把 KV 头砍了下来。

这解释了一个常被忽略的事实：KV 成本由"层数 × KV 头数"决定，不由参数量单独决定。拿参数量猜缓存大小，方向就错了。

### GQA 是分母上的杠杆

多头注意力（MHA）里每个查询头都有自己的一份 K/V，KV 头数等于查询头数。[分组查询注意力（GQA）](https://arxiv.org/abs/2305.13245)把若干查询头编成一组，共用一份 K/V，于是 KV 头数可以远小于查询头数；多查询注意力（MQA）更极端，所有查询头共用一份。三者计算量相近，差别主要在缓存体积与表达能力之间取舍，GQA 是常见的中间解，论文里也给了从多头检查点转换的做法。

这里藏着最容易算错的一处：很多资料用 hidden_size 代替 H_kv×d。对 MHA 两者恰好相等，所以 7B 的例子怎么算都对；但对 70B，hidden_size 是 64×128=8192，KV 宽度只有 8×128=1024，直接套 hidden_size 会把缓存高估 8 倍。写出 H_kv 和 d 再相乘，就不会踩这个坑。

### 权重之外，还有三块要预留

一张卡的总显存大致分成四份：权重、KV 池、激活与临时 workspace、框架与通信预留。权重最好算，参数量乘 dtype 字节，量化模型再加上 scale 与 zero-point。激活峰值出现在 prefill：一次要处理整段 prompt，中间张量比逐 token 解码时大得多，长 prompt 会把峰值顶上去。框架自身的 CUDA context、CUDA graph、张量并行的 NCCL 缓冲，也都是固定开销。

主流框架的做法是先加载权重，跑一次 profiling 估出峰值激活，再把剩余额度预分配成 KV 块（vLLM 的[显存优化文档](https://docs.vllm.ai/en/v0.15.0/configuration/optimization/)就是这么描述 `gpu_memory_utilization` 的）。所以"总显存减权重就是 KV 池"是个过于乐观的算法。把这个比例调得太满，等于把安全垫拆了，平时能跑，一遇到长 prompt 就在 prefill 阶段 OOM。

### 并发是一道除法，不是两个独立旋钮

KV 池大小固定为 P 字节后，一条上下文上限为 C 的序列要占 C × 每 token 字节，能同时容纳的条数约为 P ÷ (C × 每 token 字节)。这条除法说明：`max_model_len` 和最大并发不是可以分别调大的两个参数，它们乘在一起才是显存承诺。上下文从 4K 提到 32K，并发不是"稍微降一点"，而是按同样的倍数缩小；如果缩小后连一条都放不下，调度器只能排队、抢占或换出重算。

[PagedAttention](https://arxiv.org/abs/2309.06180) 用分页思路把 KV 切成块，按需分配、允许共享，显著减少了内部碎片和预留浪费，但它是把"已分配但没用满"的浪费压下去，并不改变每个 token 的固有体积。前缀缓存也一样：命中的是共享前缀那一段，省的是 prefill 的重复计算，新生成的 token 仍然要各自占块。

张量并行则是另一把杠杆。KV 头会随张量并行度切到各张卡上：70B 有 8 个 KV 头，8 卡切分后每卡只存 1 个头的 K/V，每 token 降到 40 KiB，32K 一条只要 1.25 GiB，60 GiB 的池子能放四十多条。但如果并行度超过 KV 头数，多出来的卡只能复制同一份 KV，单卡占用不再下降，这也是"加卡不一定加并发"的原因。

```python
def kv_kib_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    # 每层、每 token 存一份 K 和一份 V
    return 2 * layers * kv_heads * head_dim * dtype_bytes / 1024

def max_seqs(gpu_gib, weights_gib, reserve_gib, ctx, **arch):
    pool_kib = (gpu_gib - weights_gib - reserve_gib) * 1024 ** 2
    return int(pool_kib // (kv_kib_per_token(**arch) * ctx))

llama7b = dict(layers=32, kv_heads=32, head_dim=128)   # 512 KiB/token
for ctx in (4096, 8192, 32768):
    print(ctx, max_seqs(24, 14, 2, ctx, **llama7b))    # 4, 2, 0
```

24 GiB 的卡放 7B 权重，再留 2 GiB 给激活与框架，只剩 8 GiB 左右的池子：4K 上下文勉强四条，32K 一条都开不出来。这不是代码的极限，而是乘法的结论。

## 常见考点与误区

- **误区一："参数量乘 2 就是全部显存"**：这只算出权重。面试里追问"7B 模型 24G 卡能开多少并发"，正确答法是先扣权重、再扣激活与预留，最后用剩余池除以每条序列的 KV 占用，而不是回答"能放好几个"。
- **误区二："用 hidden_size 算 KV"**：MHA 下碰巧对，GQA 下会把 KV 宽度按查询头数放大。标准写法是 2×L×H_kv×d×b，H_kv 是 KV 头数，不是查询头数。答错这一条，容量规划会差出四到八倍。
- **误区三："上了 PagedAttention 就能多开并发"**：它解决的是碎片与共享，不是每 token 的固有开销。前缀缓存同理，只对共享前缀有效，不能把新 token 的账抹掉。把工程优化当成免费容量，是面试里很典型的减分点。
- **误区四："max_model_len 设大一点只是慢一点"**：它是对显存的承诺。池子不够时，框架会抢占请求、换出后重算，表现为 TPOT 抖动、吞吐下降，极端情况下直接拒绝。长上下文能力与长上下文并发，是两个必须分开验收的指标。
- **误区五："KV 量化 4bit，容量就乘 4"**：容量近似按位宽缩小，但要额外存 scale/zero-point，反量化有算力与访存开销，内核和模型支持也不一致。它救的是容量与带宽，不是无条件提速。
- **考点六："张量并行度越大，单卡 KV 越少吗"**：只在并行度不超过 KV 头数时成立；超过之后多出的卡复制同一份头，单卡占用触底。KV 头数少的模型，TP 扩到一定程度就只剩算力收益。

## 实践建议

- **先做预算表，再谈参数**：按"权重 + 激活峰值 + 框架/通信预留 + KV 池"四行落表，激活峰值用框架 profiling 或长 prompt 压测实测，不要用短请求的占用代替。预算表里最容易被低估的是 prefill 峰值。
- **用 P95 长度反推，而不是用 max_model_len 反推**：先定并发目标与上下文分位数，算 C×每 token 字节×N，放不下时优先降上下文上限、换 GQA/MQA 模型、上 KV 量化或加卡，最后才考虑把 `gpu_memory_utilization` 往上顶；顶满会把 OOM 风险留给激活峰值。
- **给调度留余量并监控**：盯 KV 使用率、抢占与重算次数、TTFT 和 TPOT 的分位数。抢占开始出现，说明池子已经贴着上限跑，此时加并发只会把延迟打崩。
- **长上下文产品要分开验收"能塞"和"能并发"**：单条百万 token 的稠密 KV 可能上百 GiB，需要稀疏/线性注意力、分层缓存或卸载等手段，不能拿"支持 1M"当容量承诺。对外标注上下文上限时，同时标注对应的并发档位。
- **共享前缀能省则省，但别记错账**：多轮对话、固定系统提示、RAG 公共模板都适合前缀缓存与块共享，收益取决于共享段占比；新生成的 token 仍按原价计费，容量规划里不能按命中率打折。

*一句话总结：KV 显存是"每 token × 层数 × KV 头数 × 并发"乘出来的，先算清这道乘法，再谈长上下文。*
