## 是什么

Go 的变量不是默认住在堆上。标准工具链里，编译器会先判断一个值的生命周期能不能在编译期确定：能，就安排在当前 goroutine 的栈帧里；不能，才让它逃逸到堆，交给垃圾回收器管理。这个判断过程就是逃逸分析。它不改变程序语义，只决定内存放在哪里，以及后续要不要为这块内存做 GC 扫描。

一句话直觉：栈像每个人的工位，函数结束就收走；堆像公共仓库，东西放进去容易，什么时候清走要等 GC 盘点。逃逸分析就是门口的门卫，它不关心这个值“看起来重不重要”，只关心它的地址会不会被带出工位，或者被别的执行流拿走。

典型场景就在日常代码里：HTTP handler 里返回局部结构体的指针、闭包捕获循环变量、把值塞进 `interface{}`、用变量长度 `make` 一个切片、在热循环里反复拼字符串。这些写法有的确实把对象推到堆上，有的只是看起来像，实际会被编译器留在栈上。把“看起来会分配”当成“一定分配”，是性能判断里最常见的起点错误。

这里的栈是 goroutine 栈，不是操作系统线程栈。它初始很小，按需增长，增长时 runtime 会复制整段栈并修正其中的指针；这也是后面两条不变量存在的根本原因。

## 核心原理

Go 编译器的[逃逸分析源码](https://go.dev/src/cmd/compile/internal/escape/escape.go)里把约束写得很直白：指向栈对象的指针不能存进堆；指向栈对象的指针不能比对象活得更久。第一条是因为栈会搬家，堆里如果留着旧地址，复制之后就指向了废弃内存；第二条是因为函数返回后，这块栈空间会被后续调用复用，地址还在，对象却可能已经被覆盖。逃逸分析本质上是在编译期证明这两件事不会发生，证明不了就保守地放到堆上。

具体做法不是“看到 `&` 就标记”，而是建一张有向图。每个变量、`new`、`make`、复合字面量都是一个位置，赋值是边，边权表示取地址和解引用的次数差。编译器从这些位置出发，看地址能不能沿着赋值路径走到堆、全局变量、函数返回值，或者另一个 goroutine 能访问到的地方；只要能走到，相关对象就被标记为需要堆分配。这个过程是静态且保守的，不区分运行时分支，也不精确区分结构体字段和切片元素，所以“可能”比“一定”更容易触发逃逸。

跨函数时，编译器会给每个函数记录参数和返回值的数据流摘要，也就是常说的 parameter tags；调用点再拿这些摘要判断实参要不要逃逸。内联会改变结论：一个小函数被展开到调用者之后，原本隔着函数边界的指针流向变得可见，`return &T{}` 也可能因为调用点没有把指针带出去而留在栈上。反过来，加 `//go:noinline` 阻止内联，诊断结果就可能从“栈”变成“堆”。这不是编译器前后矛盾，而是它能看到的作用域变了。

真正把对象推向堆的常见情况大致有四类。第一类是大小在编译期未知，比如切片底层数组的长度来自变量，栈帧大小必须提前确定，只能去堆上要空间。第二类是地址被写进已经逃逸的对象，比如全局变量、堆上的结构体字段、map 的 value；逃逸具有传递性，容器跑了，装进去的指针也得跑。第三类是被闭包或新 goroutine 捕获，且闭包或 goroutine 活得比当前函数久。第四类是地址经过 `unsafe.Pointer`、`uintptr` 或反射，编译器往往无法再证明它的流向，只能保守地放弃栈分配。`new(T)` 和 `&T{}` 只是“申请一个 T”，本身不构成判决；取地址只是让问题变得可能，最终还要看这个地址去了哪。

```go
package main

import "fmt"

type user struct{ name string }
var sink *user

func local() int {
	u := user{name: "gopher"}
	return len(u.name) // 只读字段，u 可留在栈上
}

func escaped() *user {
	u := user{name: "gopher"}
	sink = &u // 地址进入全局变量，u 必须去堆
	return &u
}

func main() { fmt.Println(local(), escaped().name) }
```

用 `go build -gcflags='-m'` 能看到 `moved to heap: u` 之类的诊断，`-m=2` 还会补充原因。要注意这是编译器调试输出，不是稳定 API，升级 Go 版本后行号和措辞都可能变化，别把某一条输出当成语言规范。

对象确定上堆之后，分配由 runtime 的 size class 体系接手。小对象按 size class 从当前 P 的 `mcache` 取，无指针且不超过 16 字节的对象走 tiny allocator；`mcache` 不够就向 `mcentral` 要，再不够才落到 `mheap`。大对象直接走 `mheap`。所以“堆分配一定慢”并不准确，单次小分配可以很快，真正贵的是后面的账：三色标记要顺着指针扫描存活对象，写屏障要记录并发标记期间的指针变化，分配速度超过回收速度时，业务 goroutine 还会被拉去执行 mutator assist。Go 的 GC 是[非移动的标记清扫](https://go.dev/doc/gc-guide)，不压缩对象，碎片和堆峰值也要纳入考虑。

## 常见考点与误区

- **误区：取了地址就一定逃逸。** 取地址只是让地址可能流出，不是判决本身。`p := &u` 之后只在当前函数里读 `p.name`，编译器完全可能把 `u` 留在栈上。面试时只回答“有 `&` 就逃逸”，说明没有理解流向分析。

- **误区：返回局部变量的指针一定在堆上。** Go 允许安全地返回局部变量地址，但是否堆分配要看调用点。函数被内联、指针没有继续外流时，仍可能栈分配；没有内联或指针被存进全局变量时，才会稳定地看到堆分配。正确说法是“语义上允许返回，分配位置由逃逸分析决定”，而不是背一句口诀。

- **误区：栈分配一定比堆分配快。** 栈分配和释放通常更便宜，但 goroutine 栈扩容要复制、要修正指针，超大栈帧也会带来额外开销。堆分配的单次成本也不高，痛点是 GC 扫描和分配速率。脱离真实负载谈“栈一定快”，很容易优化错地方。

- **误区：`GOGC=off` 或 `GOMEMLIMIT` 能消除 GC 开销。** `GOGC=off` 是关掉按比例触发的回收，不是让回收变免费，堆会一直涨到 OOM；`GOMEMLIMIT` 是软限制，存活对象超过限制时运行时也无法凭空变出内存。它们改变的是回收时机和代价，不是把 GC 删掉。

- **误区：Go 的 GC 会压缩堆。** Go 使用的是非移动的标记清扫，对象在堆上的地址不会因为 GC 而改变，所以不存在“压缩后缓存更友好”这回事，碎片也要靠分配模式和对象大小控制。

- **误区：`sync.Pool` 是稳定缓存。** Pool 里的对象可能在 GC 时被清掉，命中率没有保证。它适合复用临时的大缓冲区，降低短命对象的分配速率，不适合当跨请求的持久缓存；放进去之前要重置状态，拿出来之后也不能假设一定是热的。

- **考点：为什么堆里不能存栈指针？** 因为 goroutine 栈会增长和复制，栈上对象的地址会变化。如果堆里允许保存旧地址，复制后就会产生悬空指针。这个约束不是实现细节，而是 Go 能同时做可增长栈和非移动堆的前提。

## 实践建议

- 先测量再改。基准测试加 `-benchmem` 看每轮分配次数和字节数，pprof 看 `alloc_objects` 与 `alloc_space`，再用 `GODEBUG=gctrace=1` 或 `runtime/metrics` 观察 GC 周期和堆目标。不要在生产热路径频繁调用 `runtime.ReadMemStats`，它会短暂停顿；持续采集更适合走 metrics 接口。

- 只优化热路径上的分配。每请求一次的 JSON 缓冲、日志字符串、临时切片值得处理；初始化阶段和冷分支的几次分配通常不影响尾延迟。把“零分配”当全局目标，往往会换来更差的 API 和更难的维护。

- 减少无谓的逃逸，而不是消灭所有指针。热循环里优先用具体类型，避免不必要的接口装箱；容量已知的切片提前 `make([]T, 0, n)`；闭包只捕获真正需要的值；大对象复用时再考虑 `sync.Pool`。但接口是解耦工具，不该为了逃逸诊断把公共 API 全部改成泛型或具体类型。

- 给 Pool 设边界。池化对象要重置字段、避免把请求相关的大对象长期留在池里；池不是越大越好，保留过多内存会让堆峰值更高。对很小的对象，池化的锁和分支成本可能超过分配本身。

- 调 GC 参数要成对看。`GOGC` 调低通常换来更小的堆、更高的 CPU 占比；调高则相反。容器里设置 `GOMEMLIMIT` 时给运行时和突发流量留余量，不要贴着容器上限；上线前用真实流量压测，别只跑空载 benchmark。

- 把逃逸结论当成版本相关的观测值。不同 Go 版本的内联阈值和分析精度都会变，性能测试要固定工具链版本；如果为了诊断临时加 `//go:noinline`，测完要记得移除，别把实验手段带进生产代码。

*一句话总结：逃逸分析决定变量能不能安全留在栈上，不是让变量变快的魔法；先看流向，再看分配，最后用数据说话。*
