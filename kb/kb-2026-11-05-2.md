## 是什么

Fiber 是 React 从 16 版本起重写的协调（reconciliation）引擎，同时也是树里每个元素对应的内部数据结构：每个组件、每个 DOM 节点在 React 手里都是一个 fiber 节点，靠 child、sibling、return 三类指针连成链表。它要解决的核心矛盾很具体：JavaScript 只有一条主线程，渲染、输入响应、动画全挤在上面，而旧版 React 的递归式渲染一旦开始就不能停，组件树一大，一次 setState 就能把键入卡住上百毫秒。

一句话直觉：把"一锅端的大渲染"拆成一个个可以随时放下的小任务，更急的事来了就先放下，发现手里的活过期了就整批扔掉。

这套机制平时感知不到，但大列表过滤、路由切换、搜索联想这些"输入一响、界面重画一大片"的场景里，是它在决定卡不卡。React 18 的并发渲染、Suspense、流式 SSR，全都架在它之上。

## 核心原理

先把渲染流程摆出来。官方文档把一次展示分成三步：触发、渲染、提交（[Render and Commit](https://react.dev/learn/render-and-commit)）。所谓"渲染"，就是 React 调用你的组件函数，递归算出这棵树该长什么样；所谓"提交"，才是真正改 DOM。旧架构里这两步连在一次不可打断的函数调用栈里，中间没有任何暂停点。

Fiber 的第一刀，是把递归改写成循环。递归的进度藏在调用栈里，栈不弹完就停不下来；而链表把"处理到哪个节点"变成一个可以随手记录、随时恢复的状态——渲染器拿着当前 fiber 节点逐个处理，处理完顺着指针走向下一个节点，每个节点就是一个独立的工作单元。每处理完一小片，都回头问一句：有没有更急的事？要不要把主线程还给浏览器？这句话就是 Fiber 的灵魂：合作式调度。React 把这部分逻辑抽成了独立的 scheduler 包，专门负责"在浏览器环境里合作式地排班"（[scheduler 说明](https://raw.githubusercontent.com/facebook/react/main/packages/scheduler/README.md)）：维护一个按优先级排序的队列，用宏任务把长任务切成小片，片与片之间让浏览器有机会处理输入和绘制。

优先级怎么排？官方对 18 的描述是把更新分成"紧急"与"非紧急"两档：键入、点击这类直接交互必须立刻响应；视图切换、结果列表这类中间状态用户根本不在乎（[React v18.0](https://react.dev/blog/2022/03/29/react-v18)）。内部实现上还有从"立即"到"空闲"的完整优先级分档，React 17 之后又用 lane 位图取代旧的过期时间戳来表达"一批更新里混着哪些优先级"，高优先级更新因此能钻进正在进行的低优先级渲染中间插队。

中断发生在渲染阶段，提交阶段不适用。React 官方的说法是：并发渲染可能开始渲染一个更新、中途暂停、稍后继续，甚至整个放弃进行中的渲染；为了让你永远看不到半成品界面，React 把 DOM 变更一直攒到整棵树算完之后才一次性做完。渲染期间用的是双缓冲：当前上屏的 current 树和正在后台计算的 workInProgress 树各一份，中断、重来都只动后台那份。这也是为什么 React 反复强调组件函数必须纯——渲染可能被打断后重放，StrictMode 甚至在开发期故意把组件函数调用两次来暴露不纯的写法。

插队的完整样子：一个 transition 更新正在慢慢渲染，用户又敲了一个键。键入是紧急更新，React 中断手头工作，扔掉那份没算完的过期渲染，先处理键入，再按最新状态从头渲染。所以 transition 不是"延迟一会儿再执行"，而是"低人一等，随时让路"。

```jsx
import { useState, useTransition } from 'react';

function FilterList({ items }) {
  const [query, setQuery] = useState('');
  const [shown, setShown] = useState(items);
  const [isPending, startTransition] = useTransition();
  const onChange = e => {
    const q = e.target.value;
    setQuery(q);                  // 紧急更新：输入框立刻回显
    startTransition(() =>         // 非紧急更新：可被插队、可整批丢弃
      setShown(items.filter(it => it.text.includes(q))));
  };
  return (
    <div>
      <input value={query} onChange={onChange} />
      {isPending && <p>筛选中…</p>}
      <ul>{shown.map(it => <li key={it.id}>{it.text}</li>)}</ul>
    </div>
  );
}
```

## 常见考点与误区

- **考点一："并发渲染是不是多线程？"** 不是。JS 主线程永远只有一个，并发指的是渲染任务可分片、可中断、可丢弃，是单线程上的协作式调度，和 Web Worker 那种真并行是两回事。追问常到这：那图什么？——图的是主线程不被单段长任务独占。
- **考点二："升级 React 18 后所有更新都可中断了？"** 错。并发是 opt-in 的：只有用到 transition、Suspense、流式 SSR 这类并发特性时才启用，普通 setState 仍然是一次跑完的同步渲染，行为与旧版一致。
- **考点三："commit 阶段也能暂停吗？"** 不能。可中断只属于渲染阶段，DOM 变更集中在最后一次性提交。为什么必须这样？用户不能看到改了一半的界面，这是 React 敢中途整批放弃渲染的前提。
- **误区四："startTransition 就是防抖或节流。"** 它没有固定延时，只是给更新降优先级；输入每敲一下都可能重新开始渲染，过期的那次被整批丢弃。想要固定间隔才轮到防抖出场。
- **误区五："fiber 是线程。"** 名字取的是"可暂停、可恢复的执行单元"这层含义，不是操作系统的 fiber，也不是协程或 Worker。
- **考点六："为什么不能在 render 里写副作用？"** 渲染可能被中断重放，StrictMode 又会双调用，副作用会被执行多次；它们应该放进提交之后才跑的 useEffect。

## 实践建议

- 先分轻重再写代码：输入框回显、按钮按压保持默认的紧急更新；把重的派生渲染（过滤大列表、切换路由、画图表）包进 startTransition 或 useTransition，用返回的 isPending 给用户一个"正在算"的信号（[useTransition](https://react.dev/reference/react/useTransition)）。
- Fiber 切片压缩的是"最长的不可打断块"，不是总耗时，总工作量一点没少。所以先虚拟化长列表、memo 真正昂贵的子树，把 fiber 节点总数压下来，比硬调优先级更见效；改完用 React DevTools 的 Profiler 对比一次提交里每个组件的渲染时长，让数据说话。
- 升级到 React 18 及以上必须改用 createRoot/hydrateRoot 挂载，否则并发特性整体不生效；开发期开着 StrictMode，它会主动暴露依赖"只执行一次"副作用的组件。
- 别在渲染函数里读外部可变量、发请求、改全局状态，并发重放会让这些代码跑多次；外部数据源订阅用 useSyncExternalStore 对齐并发语义。
- 视图切换配上 Suspense：transition 里内容重新挂起时，React 会保留当前界面、在后台准备新内容，避免整页闪一下加载态。

*一句话总结：Fiber 把一次不可打断的大渲染拆成可中断、可丢弃的小任务，用优先级决定谁让路，用一次性提交保证界面永远完整。*
