## 是什么

调度器是内核里决定"下一个谁上 CPU"的那部分代码。时间片（time slice，也叫 quantum）是它发给某个可运行任务的一张限时通行证：任务最多连续运行这么久，额度用完就交还 CPU、回到队列尾部，换下一个任务。按固定次序反复发放通行证，就是时间片轮转（Round Robin，RR）。

一句话直觉：柜台只有一个，每位顾客限时办理，办不完就重新取号排队。

这套机制解决的是"谁先跑、跑多久"。它出现在分时操作系统让多个进程看起来并行的时候，出现在 Linux 的 SCHED_RR 实时策略里，也出现在多级反馈队列给新任务先发一小片时间片的规则中。Web 服务里一个慢查询占满线程池，请求排队时间被放大，本质上也是同一个问题：可运行的工作比 CPU 多，队列长度决定了你等多久。时间片本身不创造算力，它只决定算力被切得多碎、以及谁先拿到。

## 核心原理

**一笔轮转账。** 假设 n 个任务同级、都随时可运行，时间片为 q。一个任务从队首跑完到下一次被选中，最坏要等 (n-1)q；响应时间正比于 q，也正比于队列长度。另一头，每次切换都有成本 c：保存和恢复上下文、调度器记账，更贵的是缓存与 TLB 被搅乱。CPU 真正用于计算的比例大致是 q/(q+c)。q 越小，等待越短，c 的占比越高；q 越大，吞吐越好，交互越迟钝。这就是调度器最核心的一对矛盾，不存在放之四海皆准的最优 q，只有和负载匹配的 q。

```python
def rr(bursts, q):
    left, t, switches = list(bursts), 0, 0
    while any(left):
        for i, b in enumerate(left):
            if b <= 0:
                continue
            run = min(q, b)
            t += run
            left[i] -= run
            switches += 1
            if left[i] == 0:
                print(f"task{i} done at {t}ms")
    return switches

for q in (1, 4, 16):
    print(f"q={q}ms -> {rr([5, 5, 20], q)} 次调度")
```

三段同样的活，总耗时都是 30ms，q=1 却要调度 30 次，q=16 只要 3 次。切换次数是 1/q 量级，这是"时间片不能无限小"的第一层理由。第二层更隐蔽：每次切换都可能把工作集从缓存里挤出去，对内存密集的程序，重新预热缓存的开销远大于保存寄存器的几微秒。所以别只数切换次数，要看切换之后有多少工作被作废。

**抢占从哪里发生。** 时间片到期不等于立刻换人。到期一般由时钟中断或高精度定时器发现，内核置上"需要重新调度"的标志，真正切换要等到调度点：中断返回用户态、系统调用返回，或者可抢占内核里的显式检查。如果此刻没有别的可运行任务，配额耗尽的任务会继续跑。反过来，更高优先级的任务一被唤醒就可能立即抢占，根本不等当前任务用完时间片。把时间片理解成硬性的定时器，是很多错误推论的起点。

**Linux 的普通进程没有固定时间片。** 长期承担这类调度的是 CFS，它用虚拟运行时间 vruntime 记账：谁累计跑得少，谁在红黑树里最靠左，就被优先选中；nice 值改的是权重，不是片长，相邻一级大约相差 1.25 倍权重。调度器还会设一个最小粒度，防止可运行任务一多，切片碎到全是切换开销。也就是说，时间片是"按权重和并发度算出来的"，不是"配置里写死的"。从 6.6 起，主线转向 EEVDF：用 lag 表示"被亏欠了多少 CPU"，用虚拟截止时间挑下一个任务；时间片短的任务截止时间更近，于是延迟敏感的任务更快被选中，但它拿到的总份额并不因此变多。这解释了一个常被忽略的点：低延迟和更高的 CPU 份额并不是一回事。

**多级反馈队列为什么能兼顾两头。** MLFQ 不只用一条队列，而是按优先级分多层：新任务进最高层，拿一小片；用完整片就降一层，片长变长；主动阻塞等 I/O 的任务留在高层，醒来很快能跑。再加一条周期性提升规则，把饿太久的长任务拉回高层，避免 CPU 密集任务被永久压在底层。它用"历史行为"预测"接下来是交互还是批处理"，比单一固定时间片更适应混合负载，代价是规则多、参数敏感、行为不如 RR 好分析。

**多核不是把时间片放大。** 每个 CPU 有自己的运行队列，调度决策在本地做，任务通常不会为了"轮转"跨核迁移；只有负载不均衡时才触发迁移，而迁移本身会让缓存失效。所以讨论时间片时，先确认你在说单核竞争，还是多核上线程数超过核数的排队。

## 常见考点与误区

- **"时间片越短越公平、越流畅"**：更短的片改善的是等待上限，不是总吞吐；把 q 压到 1 毫秒追求响应，在可运行任务上百时只会放大换场比例；当 q 接近切换成本，CPU 大量时间花在换场上，缓存反复冷却，尾延迟反而更差。公平也只对同权重、同优先级的可运行任务成立。
- **"Linux 普通进程的时间片可以调大"**：CFS 没有那个固定片。改 nice 或 cgroup 的 cpu.weight 改的是权重份额；能调的是调度粒度一类的底层参数，而且随内核版本变化，不该当作稳定接口。
- **"时间片用完一定切换"**：没有其他可运行任务时，当前任务继续跑；有更高优先级任务唤醒时，又会提前抢占。到期只是"可以换"，不是"必须换"。
- **"优先级高就等于延迟低"**：普通任务的 nice 只是权重，不保证唤醒即运行；SCHED_FIFO 和 SCHED_RR 才严格压过普通任务，但滥用会饿死别人，还要面对优先级反转。实时任务整体默认最多也只能占每个周期 95% 的 CPU 带宽，并不是无限权力。
- **"RR 的时间片是个固定毫秒数"**：它是 SCHED_RR 的轮转额度，可以用 sched_rr_get_interval(2) 读出来，不同内核与配置并不相同；普通任务的 CFS/EEVDF 没有对应接口，别把实时策略的常量套到所有进程上。
- **"上下文切换只是存寄存器"**：直接成本是微秒量级，间接成本是 TLB、分支预测器和数据缓存失效；线程越多、工作集越大，这部分越贵。
- **"RR 和 FIFO 差不多"**：FIFO 没有时间片，一直跑到阻塞、主动让出或被更高优先级抢占；RR 在同优先级内按 quantum 轮转，被抢占后还会跑完剩余额度。

## 实践建议

- 先量再调。看 `/proc/<pid>/schedstat` 的第二列（等运行队列的时间）、cpu.stat 里的 nr_throttled 与 throttled_usec，配合 runqlat、pidstat -w 区分"CPU 不够"和"排队太久"。很多所谓时间片问题，其实是可运行线程太多或 cgroup 限流。
- 降延迟优先减并发。把线程池压到核数量级、用异步 I/O 或协程，比微调调度参数更有效；可运行队列短了，同样的 q 下等待自然变短。
- 容器限 CPU 别只写一个很小的 quota。cpu.max 默认周期是 100ms，quota 用完后整个组会被节流到下一个周期，表现为规律性的停顿尖刺；要么留足 quota，要么缩短 period，相对分配则用 cpu.weight。
- CPU 密集的批处理可以用 SCHED_BATCH 或较低权重，减少被交互任务频繁打断；但注意 autogroup 会把 nice 的作用范围限制在同一个会话或任务组内，跨组比较时它未必按你预期生效。
- 实时线程要克制：设好 RLIMIT_RTPRIO，保留 RT 带宽余量，用 taskset 绑核并压测最坏路径；一个死循环的 SCHED_FIFO 线程足以让整台机器失去响应。
- 别在生产上调底层调度旋钮。base_slice 这类参数随内核版本变化，收益高度依赖负载形态；没有可复现基准和回滚方案时，优先改并发模型与配额。
- 观测看趋势不看单点：perf sched 与 /proc/sched_debug（若内核开启）能给出迁移与等待的分布，比盯一个平均值有用。

*一句话总结：时间片是响应与吞吐之间的汇率，调它之前先看队列有多长。*
