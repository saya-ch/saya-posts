## 是什么

自动配置（auto-configuration）不是什么代码生成器，而是**随依赖 jar 一起发布的一批普通 @Configuration 类**。这些类不在你的 `@ComponentScan` 路径里，也不会被扫描到；它们由一组固定路径的清单文件点名，Spring Boot 启动时读清单、筛条件、再决定注册哪些 Bean 定义。一句话直觉：它像酒店给每间房准备的“默认布置清单”，只有客人没自带、房间又确实需要的东西才补上，客人自己带了就以客人的为准。

典型场景：引入 `spring-boot-starter-web` 后，不用手写 `DispatcherServlet`、`MappingJackson2HttpMessageConverter` 和内嵌 Tomcat 的装配；类路径里出现 JDBC 驱动、又配了 `spring.datasource.url`，`DataSource`、`JdbcTemplate` 就会被张罗好；测试里只加 `@WebMvcTest`，MVC 相关的一小片上下文也能单独搭起来。理解它的价值不只在“少写配置”，更在于出问题时知道默认值从哪来、为什么你的 Bean 没生效、为什么排除某个类后启动直接失败。

## 核心原理

链路从启动类开始。`@SpringBootApplication` 里组合了 `@EnableAutoConfiguration`，后者通过 `@Import` 引入 `AutoConfigurationImportSelector`。这个选择器有个关键身份：它实现的是 **DeferredImportSelector**，不是普通 ImportSelector。所谓“延迟”，指的是它导入的配置类要等应用自己写的 `@Configuration`、`@ComponentScan` 找到的配置都解析完之后，才轮到它们上场。正是这个先后顺序，让“用户配置优先”有了实现基础。

选择器做的事情可以拆成五步：

1. **读清单**：从每个 jar 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 读取候选类名，一行一个全限定名。Spring Boot 2.7 引入这套格式，3.0 起自动配置不再从 `spring.factories` 读取。
2. **去重与排除**：去掉重复类名，再移除 `@EnableAutoConfiguration(exclude=…)` 或 `spring.autoconfigure.exclude` 指定的类。
3. **早筛**：交给 `AutoConfigurationImportFilter` 做一轮快速过滤，常见实现按类是否存在、是否 Web 应用等粗筛，避免把明显不相关的配置类送进解析器。
4. **排序**：通过 `@AutoConfigureOrder`、`@AutoConfigureBefore`、`@AutoConfigureAfter` 做拓扑排序。排序只决定**Bean 定义的注册顺序**，不决定 Bean 的创建顺序；后者仍由依赖关系决定。
5. **条件装配**：每个候选类被当成普通 `@Configuration` 解析，类上和方法上的 `@Conditional` 在注册 Bean 定义时逐条求值。条件不满足，这个类或这个 `@Bean` 方法就被记为 negative match，不会进入容器。条件在启动解析阶段算一次，之后 Bean 定义就固定下来，不会在你每次 `getBean` 时重新判断。

条件注解里最常考的是 `@ConditionalOnClass` 与 `@ConditionalOnMissingBean`。前者判断类路径上有没有某个类，它通过 ASM 读注解元数据，所以目标类即使不在运行时 classpath 上，也不会先抛 `NoClassDefFoundError`；后者判断容器里是否已经有同类型的 Bean 定义，只有“还没有”时才补默认实现。除此之外还有按属性、按资源、按 Web 类型、按 SpEL 表达式的条件。

一个最小的自定义自动配置大致是这样：

```java
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    AuditClient auditClient(AuditProperties props) {
        return new AuditClient(props.getEndpoint());
    }
}
// META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// com.example.audit.AuditAutoConfiguration
```

`@AutoConfiguration` 本身元注解了 `@Configuration(proxyBeanMethods = false)`，所以它就是一个配置类；真正让它“自动”的，是 imports 文件里的那一行点名，以及类上的条件。清单没写、或者类被业务包扫描到，都会破坏这套约定。

官方文档把清单路径、排序和条件注解写得很完整（[Creating Your Own Auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)），Spring Boot 4 的模块化拆分则见[官方博客](https://spring.io/blog/2025/10/28/modularizing-spring-boot)。

## 常见考点与误区

- **误区一：自动配置靠 classpath 扫描发现。** 面试官常问“Spring Boot 怎么知道 jar 里有配置类”。正确答案是读固定路径的 imports 清单，不是扫所有 jar、也不是扫 `@ComponentScan` 包。自动配置类必须放在业务扫描路径之外，否则会绕过这套加载约定，条件判断和覆盖关系都可能乱。
- **误区二：入口还是 `spring.factories`。** 这是过期答案。2.7 开始用 `AutoConfiguration.imports`，3.0 起自动配置不再支持 `spring.factories`；后者仍用于 `EnvironmentPostProcessor` 等其它 SPI，但不再是自动配置入口。能分清“哪个版本、哪个用途”才是加分项。
- **考点三：`@ConditionalOnMissingBean` 为什么有时不生效。** 它只看得见“此刻已经注册的 Bean 定义”，对注册顺序敏感。放在普通 `@Configuration` 或 `@Component` 上，可能先于用户配置求值，于是错误地补了一个默认 Bean；官方建议只把它用在自动配置类里。
- **考点四：`@ConditionalOnClass` 写在 `@Bean` 方法上为什么会炸。** 方法条件生效前，JVM 往往已经为了解析返回类型加载了目标类；类不存在时，条件还没机会判断就失败了。正确做法是把 `@Bean` 方法放进一个带类级条件的嵌套 `@Configuration`，用类级条件把整个配置隔离开。
- **考点五：排除父配置能不能带走子配置。** 不能。排除项按全限定类名精确匹配，子配置若也在清单里，需要单独排除；较新版本还会校验排除项必须是自动配置类，写错类名可能直接启动失败。
- **考点六：自动配置顺序等于 Bean 创建顺序。** 不是。`@AutoConfigureBefore` 只影响定义注册的先后，Bean 什么时候实例化由依赖图和 `@DependsOn` 决定；把两者混为一谈，排障时就会盯错地方。
- **考点七：Spring Boot 4 把机制推倒重来了。** 机制没变，变的是打包方式：单一 `spring-boot-autoconfigure` 拆成按技术划分的模块，每个模块带自己的 imports 清单。于是“类路径上有 Flyway 就会自动配置”在 4 里不再成立，要加对应 starter 才能把模块带进来。

## 实践建议

- **先看条件报告，再改代码。** 启动加 `--debug`，或测试里挂 `ConditionEvaluationReportLoggingListener`，能看到每个自动配置类是 matched 还是 negative match、被哪条条件挡下。比盲猜“是不是版本不兼容”快得多。
- **自定义 starter 拆成两个模块。** `acme-spring-boot` 放自动配置与属性绑定，`acme-spring-boot-starter` 只负责拉依赖；配置类放在独立包、只通过 imports 清单暴露，不要开组件扫描。默认 Bean 尽量配 `@ConditionalOnMissingBean`，把覆盖权留给使用方。
- **条件写得越窄越稳。** 优先用 `@ConditionalOnClass`、`@ConditionalOnProperty` 这类静态条件；少用会提前初始化 Bean 的 SpEL 条件。`@ConditionalOnMissingBean` 的返回类型尽量写具体类，不要用过于宽泛的接口，否则类型判断容易误判。
- **覆盖默认值用“自己声明 Bean”，不要用排除。** 排除是把整套自动配置拿掉，自己声明一个同类型 Bean 才是只替换一部分；确需排除时按全限定名精确写，并先确认它确实在清单里。
- **升级 Spring Boot 4 先补 starter。** 以前靠“库在 classpath 上”触发的技术，现在要显式加 starter；自定义 starter 要跟着改包名和依赖，短期可用 classic starter 兜底，但别把它当长期方案。
- **给自动配置写测试。** 用 `ApplicationContextRunner` 配 `AutoConfigurations.of(...)`，再加 `FilteredClassLoader` 模拟类缺失，验证“有依赖时装配、没依赖时退让、用户自定义时覆盖”三条路径。

一句话总结：自动配置不是替你写代码，而是把一份带条件的 @Bean 清单，在你自己的配置之后按顺序兑现。
