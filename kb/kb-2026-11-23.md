## 是什么

类型体操（type gymnastics）不是官方术语，而是社区对一类 TypeScript 写法的称呼：把类型系统当成一门小语言，用条件类型做分支、映射类型做遍历、`infer` 做解构、模板字面量类型做字符串匹配、递归类型做循环，最终在编译期算出一个新类型。它描述的往往不是“这个对象长什么样”，而是“给定一个字符串或一个类型，能推出另一个什么类型”。

一句话直觉：类型别名像纯函数，泛型参数是入参，条件类型是 `if`，递归是唯一的循环，整个求值过程在编译器里完成，这些类型本身不会在产物里留下任何代码。

典型场景是“单一事实来源”：路由表里写了 `/users/:id/posts/:postId`，希望 `useParams` 直接给出 `{ id: string; postId: string }`；数据库 schema 或校验器已经定义了字段，希望查询结果的类型自动跟着走；事件总线只登记一次事件名与参数，`emit` 和 `on` 就都有提示。这些地方的共同点是：信息本来就在某个字符串或对象里，手写第二份类型只会漂移。

## 核心原理

先看这套子语言有哪几块积木。

- 条件类型 `T extends U ? X : Y` 是唯一的 `if`。它在编译期做可赋值性判断，不是运行时的 `instanceof`。
- 映射类型 `{ [K in keyof T]: ... }` 是 `for...in`，可以改属性类型、用 `-?`/`-readonly` 去掉修饰符，也可以用 `as` 重映射键名。
- `infer` 是模式匹配里的绑定变量，只能出现在 `extends` 左侧的类型模式中，用来把匹配到的部分取出来。
- 模板字面量类型让字符串进入类型层，`` `${infer A}-${infer B}` `` 这类写法可以按分隔符拆字符串。
- 递归类型别名是循环；TypeScript 没有 `for`，重复只能靠“把剩下的输入再传给自己”。

模板字面量类型与递归条件类型都在 TS 4.1 落地，两者一结合，字符串就成了可以被逐段消费的输入（[TypeScript 4.1 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-1.html)）。把这些积木拼起来，就能在类型层做真正的计算。比如把 `"a/b/c"` 拆成元组再拼回去：

```ts
type Split<S extends string, Sep extends string> =
  S extends `${infer Head}${Sep}${infer Tail}`
    ? [Head, ...Split<Tail, Sep>]
    : [S];
type Join<T extends string[], Sep extends string> =
  T extends [infer Head extends string, ...infer Tail extends string[]]
    ? Tail extends []
      ? Head
      : `${Head}${Sep}${Join<Tail, Sep>}`
    : "";

type A = Split<"a/b/c", "/">;      // ["a", "b", "c"]
type B = Join<A, "-">;             // "a-b-c"
// 裸类型参数会分发，套一层元组就不分发
type Dist<T> = T extends string ? "str" : "other";
type NoDist<T> = [T] extends [string] ? "str" : "other";
type X = Dist<string | number>;    // "str" | "other"
type Y = NoDist<string | number>;  // "other"
```

这段代码里没有一行会进入产物：`Split` 和 `Join` 只在检查器里展开，`Dist`/`NoDist` 的差别也只是类型。`Split` 每次匹配第一个分隔符，把 `Head` 和 `Tail` 绑出来，再对 `Tail` 递归；`Join` 则用元组的首元素和剩余部分递归拼接。最后的 `Dist` 与 `NoDist` 演示了最容易翻车的一点：**裸类型参数**遇到联合类型会分发，`Dist<string | number>` 得到 `"str" | "other"`；把参数包进元组后，`[T] extends [string]` 整体判断，不再分发。

条件类型不是立即求值的：泛型参数还没确定时，检查器先把它保留成一个延迟节点，等实参进来再展开。这解释了一个常见现象——工具类型在自己的文件里看起来人畜无害，错误却总在调用点爆发。映射类型则默认是同态的：`{ [K in keyof T]: T[K] }` 会原样保留 `readonly` 和 `?`，只有显式写 `-?` 或 `-readonly` 才会去掉，`Partial`、`Required` 能在不改其他修饰符的前提下增删 `?`，正是靠这条规则。

这里有两个容易被忽略的求值规则。

第一，分发只发生在“裸”类型参数上。`T extends U ? ...` 里的 `T` 如果直接出现，联合类型的每个成员会各自进一次分支，结果再合并；`[T] extends [U]` 会阻止分发。`never` 是空联合，分发后结果还是 `never`，所以 `T extends never ? true : false` 永远得不到 `true`，判断 `never` 必须写 `[T] extends [never]`。`any` 更特殊：它同时满足两边，条件类型会返回两个分支的联合，`any extends string ? 1 : 2` 是 `1 | 2`。

第二，`infer` 的候选合并方向由位置决定。属性、返回值这些协变位置出现多个同名 `infer`，推断结果是并集；函数参数这种逆变位置，结果是交集（[TypeScript 2.8 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-2-8.html)）。TS 4.7 起还能写 `infer U extends string`，先给推断结果加约束，不满足就走 false 分支。理解这一点，才能看懂官方工具类型里为什么有时要套一层函数签名。

递归也不是免费的。条件类型每展开一层都要实例化一次，非尾递归写法在五十层左右就会撞上 `Type instantiation is excessively deep and possibly infinite`（ts2589）；TS 4.5 对尾递归形式的条件类型做了消除，深度可以到一千层左右，但仍有硬上限（[TypeScript 4.5 发布说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-5.html#tail-recursion-elimination-on-conditional-types)）。优化只对“某条分支直接返回下一次递归”成立；一旦把递归结果拿去拼联合，优化就失效，得像写尾递归函数那样加一个累加器参数。所谓“类型体操图灵完备”，说的是这套子语言能编码自然数、算术甚至 JSON 解析器，不是说编译器会陪你无限跑下去。

## 常见考点与误区

- **误区一：类型体操能在运行时校验数据。** 面试常问“用类型保证接口返回一定合法行不行”。不行：类型在编译后全部擦除，`as` 只是让检查器闭嘴，不会转换值。外部输入必须在运行时校验，类型可以从 schema 反推，但不能替代 schema。
- **误区二：条件类型遇到联合类型一定分发。** 只有裸类型参数才分发；`[T] extends [U]` 会关掉分发。`never` 分发后是 `never`，`any` 则返回两个分支的并集，这两个边界是手写工具类型时最常见的 bug。
- **误区三：`infer` 只能取返回值。** 它能在参数、属性、数组元素、模板字面量里绑定；多个同名 `infer` 在协变位置取并集、逆变位置取交集。TS 4.7 的 `infer U extends X` 是“先约束再匹配”，不是普通的类型断言。
- **误区四：递归可以随便写。** 非尾递归五十层左右就会报 ts2589，尾递归优化也只把上限推到一千层左右；每多一层都增加实例化数量，复杂类型会让 `tsc` 和编辑器一起变慢。
- **误区五：类型越复杂越“高级”。** 类型体操的收益是消除重复、让错误提前暴露；如果一段类型只有作者自己能读懂，报错信息变成一屏乱码，它已经在增加维护成本而不是降低。
- **考点六：复杂类型的报错点在调用方。** 泛型工具类型在定义处只是一个延迟求值的节点，真正展开发生在传入具体类型时；所以库自己的 `tsc` 全绿，不代表使用方不会在调用点看到“实例化过深”。类型测试要在最坏输入上跑，而不是只测一个漂亮例子。

## 实践建议

- **先判断值不值得。** 只有“信息已在字符串/对象里、手写第二份会漂移”时才值得推导；一次性类型直接写清楚，别为了炫技把三行类型写成三十行。
- **运行时边界交给 schema。** 接口响应、表单、环境变量用 Zod 这类校验器，类型用 `z.infer` 反推；类型体操负责“从已有类型推导”，不负责“证明运行时值合法”。
- **给递归设上限。** 能写成尾递归就写尾递归，必要时加深度计数器并在超限时回退到宽类型；超大字符串解析放到构建脚本，不要在每个源文件的类型里跑。
- **量化编译成本。** 用 `tsc --extendedDiagnostics` 看实例化数量、类型数量与检查耗时，用 `--generateTrace` 定位慢的类型；CI 里给类型检查耗时设阈值，别等编辑器卡了才回头删。
- **把体操关进内部工具库。** 复杂类型放在内部类型工具包里，用 `.d.ts` 收口，配 `@ts-expect-error` 的正反用例当测试；业务代码只消费结果，不复制实现。官方文档也提醒，昂贵的递归类型不要随 npm 包发出去，除非你愿意替所有使用者的检查时间买单。跨版本时先确认目标 TS 版本是否支持 `satisfies`（4.9）、`const` 类型参数（5.0）等语法。
- **先写用例再写类型。** 用 `type Expect<T extends true> = T` 或 `@ts-expect-error` 把期望的正反例固定下来；类型体操没有运行时测试，这些编译期断言就是唯一的回归网。

*一句话总结：类型体操是编译期的纯函数编程，能推导形状，不能替代运行时校验。*
