## 是什么

分库分表是把一张表的数据按规则拆到多个数据库实例上的一套做法，包含垂直与水平两个方向：垂直分库按业务边界拆，垂直分表按列拆，而通常说的“分库分表落地”指水平拆分——同一份表结构复制多份，行按分片键分散到不同库表。一句话直觉：总账太厚，按客户号拆成 N 本，各自放在不同柜员手里；查单个客户只需找一本，查“所有客户”就得跑遍全部再汇总。

它解决的不是“SQL 写得慢”，而是单实例的天花板：单表行数让 B+ 树变高、索引与热数据超出 buffer pool、写入 QPS 顶到单主上限、DDL 与备份的窗口越来越不可接受。典型场景是订单、流水、消息、日志这类只增不改、量大且按用户或租户查询的表。

要先分清三个容易混的东西：读写分离只分摊读，写仍在一个主库；分区表（partition）在同一个实例内把表切成多个物理分区，能裁剪扫描、方便按分区归档，但不跨机器；分库分表才把数据放到多个实例，同时换来写吞吐和存储上限，也把跨分片查询、事务和扩容的账一起接了过来。

## 核心原理

**第一件事是分片键与路由。** 分片键是 WHERE 条件里用来算分片的那一列，路由函数通常是 `shard = hash(key) % N`。哈希分片分布均匀，但范围查询要广播到所有分片；范围分片能按区间裁剪，可如果拿自增订单号或时间当键，新数据会全压到最后一个分片，形成写热点。分片键还必须稳定：一旦更新分片键，这一行就要从一张分片表搬到另一张，通常得按跨分片事务处理。

更关键的是，分片键要覆盖大多数高频查询。按 order_id 分片、业务却总按 buyer_id 查，等于每次查询都扇出到全部分片。常见补救是基因法：生成订单号时把 buyer_id 的低位编码进订单号，使订单号与 buyer_id 落到同一分片；或者维护一张 order_id 到 buyer_id 的异构索引表，先查索引再定向路由。前者省一次查询，后者更灵活，但都要求写入时同步维护。

```java
// 4 库扩到 8 库：新库号 = 旧库号，或旧库号 + 4
int hash = Math.floorMod(userId.hashCode(), 8);
int newDb = hash;              // 扩容后按 8 取模
int oldDb = hash % 4;          // 扩容前按 4 取模
boolean needMove = hash >= 4;  // 每个旧库恰好一半数据要搬
```

这段代码说明双倍扩容为什么温和：4 扩到 8 时，只有哈希值落在 4 到 7 的那一半行需要迁移；而 4 直接改成 5，绝大多数键的余数都会变，几乎等于全量重刷。

**第二件事是 SQL 改写与结果归并。** 单分片查询最便宜：解析 SQL、算出目标分片、把逻辑表名换成实际表名、下发、返回。一旦路由到多个分片，中间件就要并行下发再合并：`AVG` 不能把各分片的平均值再平均，必须改写成 `SUM` 与 `COUNT` 两路再相除；`ORDER BY` 要在内存里做多路归并；`COUNT(DISTINCT)` 要去重；`GROUP BY` 要按分组键二次聚合。`LIMIT 100000, 10` 更贵——每个分片都得先取出 100010 行，再合并排序后丢掉前十万行，偏移量越大，内存与网络越先扛不住。

扇出还会放大连接数。一个逻辑查询打到 64 个分片，若单个分片允许 20 个并发，理论上就要 1280 条连接；分片数上去以后，连接池、线程池和超时预算都要按“最坏扇出”重算，而不是按单表时代的 QPS 估算。

**第三件事是跨分片事务与全局唯一 ID。** 只落在一个分片上的写，用本地事务就够了；跨分片的写要么上 XA/2PC，由协调者准备再提交，代价是资源锁持有到第二阶段；要么用 TCC、Saga、本地消息表这类业务补偿，接受中间态与最终一致。落地时优先改设计，让同一笔业务的数据落在一个分片，而不是默认让分布式事务兜底。

全局 ID 也是拆表后才暴露的问题：自增主键只在单表内唯一，多张分片表各自从 1 开始必然冲突；UUID 虽然全局唯一，但随机性会让 InnoDB 的聚簇索引频繁页分裂，16 字节也比 8 字节的 bigint 更占空间。常见方案是 Snowflake 这类 64 位 ID（时间戳、机器号、序列号），或者号段模式——数据库一次发一段，应用在内存里递增，把发号压力从每行一次降到每段一次。Snowflake 要处理时钟回拨，号段要处理服务重启后的浪费与续租，两者都不是“引个库就完了”。

**第四件事是扩容。** 取模的分片数一旦定死，改 N 就要重哈希。工程上要么按 2 的幂扩容（4→8→16，每次只搬一半），要么预分片：先建 1024 个逻辑分片，再映射到少数物理库，扩容时整段逻辑分片搬走，不用逐行重算。迁移过程也不是停机导数据：先双写新旧集群，用 CDC 追平增量，再全量校验，然后灰度切读、切写，保留回滚开关。任何一步少了校验，都可能把“少了一行”带到线上。

## 常见考点与误区

- **误区一：分区表就是分库分表。** MySQL 的[原生分区](https://dev.mysql.com/doc/refman/8.4/en/partitioning.html)仍在同一个实例里，能减少扫描、方便按分区归档，但不跨机器、不提供跨实例事务。而且按[分区限制](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations.html)，InnoDB 分区表不支持外键，有唯一键时唯一索引必须包含分区列——这两条常被用来判断候选人有没有真的用过。
- **误区二：分片键选主键最省事。** 主键唯一不等于查询覆盖。订单按 order_id 分片、页面却按 buyer_id 查，每次都要广播；反过来按 buyer_id 分片，用 order_id 查详情又需要异构索引。分片键选的是“最常用、最均匀、最不变的查询维度”，不是“最像主键的那一列”。
- **误区三：中间件透明，业务不用改。** 中间件能改写 SQL，但改不了语义：跨分片 JOIN 可能退化成内存 JOIN，深分页仍然要每片取偏移量，跨分片事务仍然要选 XA 或补偿，全局唯一仍然要单独发号。把这些当成“配置一下就有”是落地翻车的头号原因。
- **误区四：分片越多，扩展性越好。** 分片数上去，连接数、SQL 解析与结果归并的成本都会跟着上涨，小表还会让优化器更难选索引。分片数通常按未来两到四年的增长预留，而不是一步拆到几百片。
- **误区五：扩容就是改一下取模。** 改 N 会重哈希；4 改 5 时八成以上的键都要搬家。正确做法是双倍扩容、预分片或一致性哈希，并且把迁移做成可校验、可回滚的流程。
- **考点六：绑定表能解决所有 JOIN 吗。** 不能。ShardingSphere 所说的[绑定表](https://shardingsphere.apache.org/document/current/en/user-manual/shardingsphere-jdbc/java-api/rules/sharding/)要求主表和子表的分片键与算法完全一致，例如订单与订单明细都按 buyer_id 分片，JOIN 才能落在同一分片；分片规则不一致，仍然会跨分片。广播表适合字典数据，写入要广播到所有分片，读只需走其中一个分片，但只适合小表、低频写。

## 实践建议

- **先把单库手段用尽。** 加对索引、冷热分离与归档、用分区表做生命周期管理、读写分离接读流量、缓存挡住热点，再评估分库分表。触发条件别只看“表有多少行”，要一起看热数据是否超出内存、写 QPS 是否顶到单主上限、DDL 与备份窗口是否已经不可接受。
- **用四个问题选分片键。** 基数够不够高、分布够不够均匀、能不能覆盖大多数查询、会不会被更新。四个答案有一个是否定，就要准备基因法、异构索引或查询改造，别指望上线后再补。
- **把跨分片成本写进表设计。** 能绑定的表用同一分片键，字典表做广播表，高频关联字段冗余到主表，核心链路避免跨分片事务；需要跨分片时，明确用 XA 还是最终一致，并把幂等与对账一起设计。
- **扩容方案在第一次拆分前定好。** 选 2 的幂、预分片或一致性哈希，确定全局 ID 方案，准备好双写、CDC、校验、灰度与回滚脚本。迁移工具要能回答三个问题：迁了多少、差了多少、怎么退回去。
- **按分片看监控。** 除了整体 QPS 与 p99，还要看每个分片的流量、连接数、慢查询和数据量偏差；单分片倾斜往往比整体水位更早出问题。中间件选型也别只看功能：ShardingSphere-JDBC 少一跳但耦合应用，Proxy 对应用透明但多一层运维，TiDB、Vitess 这类方案则把复杂度换到了别处。

*一句话总结：分库分表真正的成本不在拆表那一刻，而在分片键定下之后，每条查询、事务与扩容都要按它重算。*
