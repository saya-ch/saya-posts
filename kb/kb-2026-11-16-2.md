## 是什么

TLS（Transport Layer Security）是夹在传输层与应用层之间的一层协议，给上层数据提供三件事：机密性、完整性、对端身份认证。HTTPS 只是"HTTP over TLS"的俗称，真正干活的是 TLS 握手，以及握手之后建立的记录层。

一句话直觉：握手不是"把加密打开"，而是两个人在一个人人都听得见的广场上，先互相核对证件，再当场协商出一副只有他俩能用的临时密码本。

典型场景远不止浏览器：App 与网关之间的双向认证、DNS over TLS、服务网格里的 mTLS、QUIC 内嵌的 TLS 1.3 握手，都是同一套流程的变体。凡是"要在不可信网络上开一条可信通道"的地方，都绕不开这两件事——证明对面是谁，以及造出一把别人拿不到的钥匙。

## 核心原理

### 两类密码学各干各的活

非对称密码（RSA/ECDSA 签名、ECDHE 密钥交换）负责"证明身份"和"在不安全的信道上造出一个共享秘密"，它慢、贵、还有长度限制；对称密码（AES-GCM、ChaCha20-Poly1305）负责搬数据，快得多。握手的全部工作，就是把后者安全地引导出来。任何"用非对称加密传网页"的说法，都搞错了这两者的分工。

### 1.2 的两个往返花在哪

TLS 1.2 的完整握手是这样的：客户端发 ClientHello（版本、套件列表、随机数）；服务端回 ServerHello、Certificate、ServerKeyExchange、ServerHelloDone；客户端再发 ClientKeyExchange、ChangeCipherSpec、Finished；服务端最后回自己的 Finished。客户端必须等到服务端的证书和密钥交换参数才能算主密钥，服务端又必须等客户端回话才能确认密钥，于是整整两个 RTT。第一个 RTT 里，双方基本只在"报菜单"和"看证件"。

### 1.3 的 1-RTT：把赌注提前下

TLS 1.3 的完整消息序列与密钥调度写在 [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446) 里，它做的第一件事是给 ClientHello 加一个 `key_share`：客户端直接按自己认为服务端会选的椭圆曲线组（比如 x25519）算好临时公钥，随第一个包发过去。服务端如果接受这个组，就能在收到 ClientHello 的同一回合算出 ECDHE 共享秘密，立刻派生握手密钥，然后把 EncryptedExtensions、Certificate、CertificateVerify、Finished 全部加密，塞进一个 flight 发回。客户端验完证书、回一个 Finished，握手结束——一个往返，而且证书是密文。

代价是"猜错"。服务端若不接受客户端给的组，会回 HelloRetryRequest 让客户端换组重发，这一下就退回两个往返。所以真实部署里 `key_share` 通常只带一到两个最可能的组：带得越多，第一个包越大，越容易在弱网下丢包，也越容易被拿来做放大攻击。

### 密钥不是一把，是一串

TLS 1.3 用 HKDF 做密钥调度：Early Secret（有没有 PSK）→ Handshake Secret（混入 ECDHE 共享秘密）→ Master Secret。每一步都掺入 transcript hash，也就是此前所有握手报文的哈希。这意味着任何一条握手报文被改动——删套件、换曲线、降版本——后面的密钥就对不上，Finished 校验直接失败。这就是降级保护的落点，比在字段里写一句"我不接受低版本"可靠得多。握手结束后，两个方向各有自己的流量密钥与独立的 IV、序列号，AEAD 的 nonce 不会被重用。

```python
import socket, ssl

ctx = ssl.create_default_context()          # 默认校验证书链与域名
with socket.create_connection(("example.com", 443), timeout=5) as raw:
    with ctx.wrap_socket(raw, server_hostname="example.com") as s:
        print(s.version(), s.cipher())      # 协商结果：TLSv1.3 与 AEAD 套件
        cert = s.getpeercert()
        print(cert["subjectAltName"])       # 域名绑定写在 SAN 里，不是 CN
        print(cert["notAfter"])             # 有效期同样要校验
```

### 身份这一半：证书只证明"这把公钥属于这个域名"

服务端在 Certificate 消息里给出证书链，客户端从内置信任锚（根 CA）开始逐级验签，检查有效期、用途（EKU）、域名（SAN，不是优先看 CN），再查吊销状态（CRL、OCSP，或服务端 stapling 带过来的响应）。随后服务端用证书对应的私钥对 transcript 签名，放进 CertificateVerify——这一步才证明"你手里真有私钥"，否则任何人把别人的证书原样转发就能冒充。证书解决的是"公钥与域名的绑定"，它不解决"这个网站是不是骗子"。

### 复用与 0-RTT：省下的信任余量

服务端在握手后发 NewSessionTicket，客户端下次带 PSK 上来，可以跳过证书交换，但仍会派生新密钥。如果客户端在第一个 flight 里就带 `early_data`，用 PSK 派生的 early secret 加密请求，这就是 0-RTT：请求和数据一起到，服务端不用等握手完成。省下的那一个 RTT，是用"这条请求可能被重放"换来的——early data 不依赖服务端的新鲜随机数，攻击者可以把同一段密文重放；它也不具备前向保密。

## 常见考点与误区

- **误区一："HTTPS 是用非对称加密传数据"**：非对称只做签名认证和 ECDHE 参数交换，跑起来后是 AES-GCM/ChaCha20 这类对称 AEAD。追问"为什么不全用非对称"，答案是性能与报文膨胀差几个数量级。
- **误区二："TLS 1.3 快是因为砍了密码套件"**：砍套件只是清理历史包袱，真正省掉一个 RTT 的是 `key_share` 提前发送，让服务端第一个回合就能算出密钥、连证书一起加密返回。只答"套件少了"会被继续追问到卡住。
- **误区三："0-RTT 是纯赚的优化"**：early data 可被重放，且没有前向保密。只应承载幂等请求，服务端要有 anti-replay 窗口，被拒时按 425 Too Early 重试。
- **误区四："证书链能建起来就说明连对了人"**：还要校验 SAN 与访问域名一致、有效期、EKU、吊销状态。客户端里关掉校验、往 trust store 塞自签根、或者习惯性"点继续访问"，都会让这一层形同虚设。
- **误区五："握手加密了，所以看不出用户访问哪个站"**：TLS 1.2/1.3 的 SNI 默认明文（除非部署 ECH），IP、端口、包长与时序同样泄露。握手保护的是内容与完整性，不是元数据。
- **考点六："会话复用是不是降低了安全性"**：复用仍会为每条连接派生新的 traffic secret，风险主要落在 0-RTT 与 ticket 密钥管理——ticket key 要轮转，泄露等于可解历史会话。
- **考点七："QUIC 是不是不用 TLS"**：QUIC 内嵌 TLS 1.3，只是不再跑在 TCP 上，握手消息装进 CRYPTO 帧，所以第一趟就能带数据。

## 实践建议

- **先量再调**：用 `curl -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n'` 把 DNS、TCP、TLS、首字节拆开。TLS 占比高时再谈 1.3、会话复用与边缘终止，不要凭感觉下"上 HTTPS 变慢了"的结论。
- **版本与套件**：开 TLS 1.3 与 1.2，关掉 1.0/1.1 以及 CBC、RC4 一类套件；用 `openssl s_client -tls1_3 -brief` 或外部评分工具验证真实配置，别只看配置文件写了什么。
- **证书运维**：ACME 自动续期，配到期前 30/14/7 天三级告警；下发时给全链（叶子 + 中间证书），不要把根证书塞进链里；开启 OCSP stapling，减少客户端额外查询与超时。
- **0-RTT 白名单**：只对 GET/HEAD 这类幂等请求开 early data，下单、支付、改密一律走完整握手；服务端记录 ticket 的接收时间窗，超出窗口直接拒绝。
- **内部服务用短证书**：mTLS 场景用小时级证书加自动轮转，私钥不进镜像、不进环境变量；做 pinning 时预留备份 pin，否则换证就是一次全量事故。
- **监控握手失败率**：按版本、套件、证书剩余天数、SNI 维度打点。握手失败往往先表现为"某些老客户端连不上"，而不是服务端自己报错。

*一句话总结：握手谈成的不是算法，而是"对面是谁"和"这次连接专用的钥匙"；1-RTT 省的是等待，0-RTT 押上的是可重放性。*
