## 是什么

React Fiber 是 React 16 起替换旧栈协调器（Stack Reconciler）的协调内核。它既是一个数据结构——每个组件或宿主节点对应一个 JS 对象，记着类型、props、父子兄弟指针和优先级；也是一套执行机制——把原来"一次递归跑完整棵树"的渲染，拆成一个个可以单独处理、也可以中途放下的工作单元。这套设计由一份广泛流传的 [React Fiber 架构文档](https://github.com/acdlite/react-fiber-architecture) 系统整理。

一句话直觉：React 把程序自己的调用栈，换成了存在堆上、可以随时合上再翻开的一份任务清单。输入框要保持跟手、筛选大列表时不能白屏、路由切换要能被更急的更新打断，这些需求靠的不是算得更快，而是算到一半能先让浏览器喘口气。

但要先划清"可中断"的边界：能停的地方只在 fiber 与 fiber 之间，不在组件函数体内部；只有 render 阶段能停，commit 阶段不能。Fiber 也不是新的虚拟 DOM，diff 规则（同层比较、类型不同整棵替换、key 决定复用）基本没变；它更不是多线程，所有计算仍在主线程上完成。它改变的是工作怎么被组织、何时让出、以及让出之后还剩多少能接着用。

## 核心原理

### 中断点为什么必须落在 fiber 之间

旧协调器靠函数递归下降，调用栈由 JS 引擎维护：一旦进入 render，栈不空就不会返回，期间浏览器既画不了帧，也处理不了点击。开发者只能把树剪小，没法要求 React"先停一下"。

Fiber 把树改成三根指针：child 指向第一个子节点，sibling 指向下一个兄弟，return 指向父节点。遍历于是变成一个循环加一个显式栈：能往 child 走就往下（beginWork，做 diff、生成子 fiber）；走不下去就 completeWork 收尾，再找 sibling；没有 sibling 就沿 return 一路向上。当前处理到哪个节点，记在 workInProgress 这个指针里——断点于是从引擎的调用栈，变成了一个可以随时读写的内存地址。

调度器给每一轮工作一个帧预算，[源码里的 frameYieldMs](https://github.com/facebook/react/blob/main/packages/scheduler/src/SchedulerFeatureFlags.js) 默认为 5 毫秒。工作循环每处理完一个 fiber 就问一次 shouldYield()：这一轮的时间用完了没有。用完就保存指针、返回主线程，让浏览器绘制和处理输入；下一轮任务再从指针处继续。5 毫秒不是魔法数字，它是按 60 帧下每帧约 16.7 毫秒倒推的：绘制和输入要留时间，渲染一次最多占用其中一小段。

```js
// 简化模型：断点是一个指针，不在 JS 调用栈里
let workInProgress = null;

function workLoop() {
  while (workInProgress && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
  if (workInProgress) scheduleCallback(workLoop); // 超时，下一轮接着来
}

function performUnitOfWork(fiber) {
  const child = beginWork(fiber);        // 向下：diff，返回第一个子节点
  if (child) return child;
  let node = fiber;
  while (node) {
    completeWork(node);                  // 向上：收尾并标记副作用
    if (node.sibling) return node.sibling;
    node = node.return;
  }
  return null;                           // 根节点完成，进入 commit
}
```

这里没有 requestIdleCallback。React 早期试过它，最终换成基于 MessageChannel 的调度：setTimeout 有最小 4 毫秒的钳制，而空闲回调的触发时机又太不可控。还要注意这是协作式中断，不是抢占式：只有跑到 fiber 边界、并且 React 主动查了 shouldYield()，才存在让出的机会。一个组件的函数体是一整段同步 JS，不会因为时间片到期就停在半路。

### 被打断之后，哪些工作真的白干了

假设一个 transition 更新正在搭树，用户突然敲了键盘。离散输入拿到更高的 lane，React 会让当前这棵 workInProgress 作废，从 current 树重新开一轮。已经写进 wip 节点的部分成果确实被丢掉了，但"全部重算"是误读。

重启后的遍历仍然从根开始，可 beginWork 会先做判断：这个 fiber 的 props 没变、它自己身上也没有本次 render 要处理的 update，就可以走 bailout。若它的 childLanes 里也没有需要渲染的 lane，整棵子树直接跳过，连子节点都不用访问；若子树里还有活儿，就复用旧的子 fiber 结构、只往下走需要更新的分支。childLanes 是在 completeWork 阶段一路往上冒泡出来的，相当于每个节点都记着"我的子树里还有没有活"。

所以代价是不均匀的：被新更新直接波及的分支要重跑，旁边无关的兄弟子树基本只花一次判断的钱。这也是为什么把状态放得离使用点越近越好——更新波及的范围，直接决定了打断后要重算多少。

### 一次渲染可能跑很多遍，所以 render 必须是纯的

同一棵组件树，在一次提交前可能被渲染多次：高优先级插队会重启、StrictMode 在开发环境会双调用、Suspense 重试也会重来。这不是实现缺陷，而是可中断调度的必然结果——既然算到一半可以丢，React 就必须假设任何一次 render 都可能不被采用。

于是 render 里发请求、写全局变量、改 ref、读 offsetHeight，都会变成"可能执行零次、一次或多次"的副作用。更隐蔽的是撕裂：两个组件在同一次 render 里读了同一个可变对象，中途被插队改写，最终提交的界面就可能一半新、一半旧。纯函数不是风格建议，而是这套机制能成立的前提。

### 优先级也会饿死人

只有"能停"不够，还得知道"先算谁"。React 17 起逐步用 lane 取代 expirationTime：31 条 lane（[源码里的 TotalLanes](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberLane.js)）排成一个位掩码，SyncLane、InputContinuousLane、DefaultLane、TransitionLanes、RetryLanes、IdleLane 各占若干位。每个 update 带着自己的 lane 挂到 fiber 上，再冒泡到 root 的 pendingLanes；取最高优先级就是 lanes & -lanes，留下最低的那个置位。

位运算的好处是一次能表达"这批更新里混着好几个优先级"，合并、纠缠和批量处理都变成按位操作。代价是低优先级可能长期排不上：用户连续输入时，transition 渲染一次次被推翻，看起来像永远算不完。React 给等待过久的 lane 记过期时间，到期后按同步优先级处理，避免彻底饿死；但这只是兜底，不是完成保证。

### commit 为什么不能切

render 算完后进入 commit，这一段同步执行，不能被打断。它分三个子阶段：before mutation（读 DOM、跑 getSnapshotBeforeUpdate）、mutation（插入、更新、删除 DOM，触发 componentWillUnmount）、layout（DOM 已更新，跑 componentDidMount、useLayoutEffect、挂 ref）。三步做完浏览器才绘制，useEffect 这类 passive effect 一般在绘制之后异步执行。

不让 commit 切片，是因为 DOM 改到一半被暂停，用户会看到残缺界面，布局、焦点、滚动位置都会进入难以恢复的中间态。React 的选择是把长任务尽量挪到可中断的 render 阶段，commit 则保持短而原子。换句话说，可中断渲染的上限，是由 commit 的不可中断换来的。

## 常见考点与误区

- **"可中断就是任意一行都能暂停"**：停的粒度是 fiber。单个组件的函数体是一次同步调用，中间没有检查点；commit 全程不停；同步优先级的更新（例如离散输入触发的）也会一口气跑完。面试里答"用了链表所以随时能停"，漏掉的正是这个边界。
- **"被打断后所有节点都要重新 render"**：不对。作废的是那棵 workInProgress，重启后未受影响的子树会沿 childLanes 走 bailout，childLanes 为 0 时整棵剪掉。真正重跑的是被新 lane 波及的分支。
- **"concurrent 是多线程，所以一定更快"**：仍是单线程协作式调度。它优化的是响应性而不是吞吐，调度、克隆 fiber、丢弃重算都要付钱；慢组件不会因为开了并发就变快，反而可能在反复打断中更慢。
- **"commit 也可以时间切片"**：不行。DOM 变更、布局读取和生命周期钩子必须原子完成，否则界面会撕裂；能切的只有 commit 之前的计算。
- **"startTransition 是防抖或延迟"**：[startTransition](https://react.dev/reference/react/startTransition) 没有定时器，也不承诺延迟多久，只是把更新标到较低的 transition lane。高优先级更新到来时它会被打断并重启；受控输入必须留在紧急更新里，否则打字都会变卡。
- **"render 里发请求没关系，反正会重跑"**：重跑意味着请求可能发多次，且返回顺序不可控；在 render 里读可变的外部状态还会造成撕裂。副作用应放在事件处理、useEffect 或 useLayoutEffect。

## 实践建议

- **先分清卡在 render 还是 commit**：用 Performance 面板看长任务落在哪个阶段。render 长，才轮到 startTransition、useDeferredValue、虚拟列表；commit 长（大量 DOM 变更、强制同步布局），切片帮不上忙，要减少一次提交的节点数和布局读写。
- **主动制造让出点**：Fiber 只能在组件之间停，所以把动辄渲染几千行的巨型组件拆成边界清晰的小组件，或直接上虚拟滚动。一个组件里跑一个 O(n²) 的循环，时间切片救不了它。
- **保持 render 纯，把副作用外置**：不在组件函数里发请求、改 ref、写 localStorage、读 offsetHeight；提交后的逻辑放 useEffect，必须早于绘制的测量放 useLayoutEffect。开启 StrictMode，让双调用尽早暴露问题。
- **按"能否等待"给更新分级**：搜索过滤、图表切换、Tab 内容这类可以稍后到的更新，包进 startTransition，并用 useTransition 的 isPending 给反馈；输入框、拖拽、悬停反馈留在紧急优先级。低优先级任务多时，注意它们互相打断造成的饥饿。
- **别用并发特性替代该做的减法**：昂贵计算先 memo 或移到 Worker，重复渲染先查 context 与状态粒度，长列表先虚拟化。Fiber 只负责把长任务切开，切完的总量一点没少。

一句话总结：Fiber 把递归调用栈换成堆上的工作单元，让 React 能在 fiber 之间让出主线程；它买到的是可打断的响应性，代价是重算与边界，而不是更快的渲染或更多线程。
