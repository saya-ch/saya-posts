## 是什么

热点数据治理，是在访问分布严重偏斜时，围绕“发现热点、削减热点、分散热点、隔离热点”建立的一整套机制。一句话直觉：它不是把整条路修宽，而是先找出所有人都挤的那扇门，再决定是在门口提前发货、多开几扇门，还是干脆限流。典型场景包括秒杀单品详情、热搜话题、明星微博评论区、活动券领取，以及恶意爬虫盯着同一个账号或接口猛刷。

热点 key 和大 key 经常被混为一谈，其实两者不是一回事。大 key 说的是 value 太大，读写一次就占掉大量网络带宽，甚至阻塞其他命令；热点 key 说的是访问密度太高，value 可能只有几百字节，却能在瞬间打出几十万 QPS。一个大 key 可能很冷，一个热 key 也可能很小。治理手段因此不同：大 key 要拆值、压缩、分页，热 key 要削峰、分散、前置缓存。

## 核心原理

**单 key 为什么是天然单点。** Redis Cluster 把键空间切成 16384 个哈希槽，键先做 CRC16，再对 16384 取模，决定它属于哪个槽、哪个主节点（[Redis Cluster 规范](https://redis.io/docs/latest/develop/reference/cluster-spec/)）。这条链路上，一个 key 只能对应一个槽，一个槽在同一时刻只由一个主节点负责。增加节点只会迁移槽，不会把一个 key 的请求拆成两半；增加副本能分担读，但写入仍然落到主节点，而且复制默认是异步的。再加上 Redis 的命令执行仍是单线程，同一个分片上的所有命令只能排队，于是一个热点 key 就能把整条队列堵死。此时会出现很反直觉的容量图：集群平均 CPU 只有 20%，某一个分片却长期 100%，因为所有请求都压在同一个 key 上。按平均值做容量规划，在这里必然失灵。

**先看见，再谈治理。** 热点探测有三类观测面。第一类是客户端采样上报：业务进程把待测 key 批量传给探测集群，集群用滑动窗口累加，超过阈值就推送到各台机器的本地内存。京东开源的 JD-hotkey 走的就是这条路，上报间隔可配到 1–500ms，阈值可以设成“某个 key 两秒二十次”这类规则（[JD-hotkey](https://gitee.com/jd-platform-opensource/hotkey)、[京东云实战文章](https://developer.jdcloud.com/article/2854)）。第二类是代理层统计，在统一入口按 key 计数，业务无侵入，但代理自身要扛住全量请求。第三类是 Redis 自身的 LFU 频次，`OBJECT FREQ` 能读出近似访问频率，`redis-cli --hotkeys` 可以扫描候选键；它依赖 LFU 淘汰策略，结果是采样近似值，全量扫描也有成本，不能当成精确账本（[OBJECT FREQ](https://redis.io/docs/latest/commands/object-freq/)）。

有赞的 TMC 给了一个很具体的窗口设计：SDK 异步上报访问事件，服务端每 3 秒做一次映射，每个 key 维护 10 个时间片，合起来就是最近 30 秒的滑动热度，再把 TopN 通过 etcd 推给应用集群（[有赞 TMC](https://developers.youzanyun.com/article/1557135495456)）。这里的关键不是“窗口越大越好”，而是窗口要覆盖一次突发，又不能让昨天的热度继续占着本地缓存。固定窗口在边界处容易把连续突发切成两段，滑动窗口或时间轮更平滑；代价是要维护更多状态。

**治理动作从近到远分四层。** 第一层是本地缓存：把热点值放进进程内存，TTL 设 1–5 秒，配一个变更广播做失效，读请求根本不打到 Redis。有赞公开的某次活动数据里，本地缓存命中率接近 80%，接口 RT 反而下降。第二层是请求合并：同一个 key 的并发回源只放一个请求过去，其余等待结果，避免缓存击穿时把数据库打穿。第三层是隔离与限流：给热点 key 单独的连接池、独立的缓存集群，按 key 做令牌桶，超过阈值直接返回兜底值或默认页，保护同分片上的长尾请求。第四层才是拆分：把 `hotkey` 变成 `hotkey:0` 到 `hotkey:N-1` 多个副本，读请求随机选一个，写请求双写或异步同步。

拆分听起来最彻底，限制也最多。Redis Cluster 的 hash tag 只对花括号里的内容做哈希，`{hotkey}:0` 和 `{hotkey}:1` 会落进同一个槽，拆了等于没拆；要拆就不能带同样的 tag。副本之间没有事务，`INCR`、`SETNX`、分布式锁这类依赖单 key 原子性的操作会直接失效；写请求还要扇出到 N 份，写热点反而更贵。所以拆分只适合读多写少、可容忍短暂不一致、且业务上能接受“多个副本各自计数”的场景。

```go
func GetProduct(ctx context.Context, id string) (string, error) {
    if v, ok := local.Get(id); ok { // local 为带 1~3s TTL 的进程内缓存
        return v.(string), nil
    }
    v, err, _ := group.Do(id, func() (any, error) {
        if v, ok := local.Get(id); ok { // 双重检查，避免并发重复回源
            return v, nil
        }
        s, err := rdb.Get(ctx, "product:"+id).Result()
        if err == nil {
            local.Add(id, s)
        }
        return s, err
    })
    if err != nil {
        return "", err
    }
    return v.(string), nil
}
```

这段读路径把“本地缓存”和“请求合并”叠在一起：命中就直接返回，未命中时同一个 key 只有一个 goroutine 去查 Redis，其余在 `singleflight` 里等结果。它解决的是读热点和击穿，不解决写热点。

## 常见考点与误区

- **误区一：热点 key 就是大 key。** 面试官常让比较两者。答错在于只背“大 key 要拆”，却说不清热 key 可能很小、瓶颈在 QPS 而不是字节数。正确答法是先问“是值大还是访问集中”，再分别给治理手段。
- **误区二：加机器、加副本就能解决。** 加主节点只能迁移槽，不能拆开同一个 key；加副本能扩展读，前提是客户端或代理把读路由到副本，写仍然单点，而且副本有复制延迟。面试里能补一句“先看是读热点还是写热点”，层次就出来了。
- **误区三：把 key 加后缀就一定打散了。** 如果后缀写在同一个 hash tag 里，所有副本仍然同槽；如果业务还有跨 key 原子操作，拆分会直接破坏语义。这个坑在真实故障里很常见。
- **误区四：本地缓存 TTL 越长越省事。** TTL 越长，脏数据窗口越大，失效广播丢失时越难收敛；本地缓存还要限容量，否则热点一多就把堆撑爆。强一致场景不适合把值放到进程内。
- **误区五：探测越灵敏越好。** 全量上报会放大网络和 CPU 开销，阈值太低会把大量普通 key 误判成热点，本地缓存被垃圾数据占满；阈值太高又会在故障发生后才报警。合理做法是采样上报，同时看绝对 QPS 和占分片流量的比例。
- **误区六：限流等于降级。** 限流只是把入口关小，如果没有兜底值、没有重试退避，被拒绝的请求会立刻重试，反而形成第二波洪峰。限流必须和降级、熔断、幂等一起设计。

## 实践建议

- **先量化偏斜，再选工具。** 至少看四个指标：单 key QPS、单分片 CPU 与网卡、回源 QPS、p99 延迟。阈值用“绝对值 + 占比”双条件，例如单 key 超过 5000 QPS 且占该分片流量 30% 才判定热点，能过滤掉大量噪声。
- **处置顺序从便宜到昂贵。** 先本地缓存和请求合并，再隔离限流，最后才拆 key。拆分引入的一致性成本最高，应该作为读多写少场景的最后手段，而不是第一反应。
- **本地缓存要按“会丢、会脏、会满”来设计。** TTL 加随机抖动避免同时失效，容量设上限并用 LRU 淘汰，变更走广播加版本号，关键交易数据不要放本地。广播只是加速失效，TTL 才是最终兜底。
- **拆分要提前验证原子性。** 列出所有依赖单 key 的命令和业务语义，确认没有 `INCR`、锁、排名、去重；写路径做好幂等和补偿；上线前压测 N 个副本的读扩散和写扇出。
- **写热点换思路。** 本地缓存和读副本都救不了写热点，应该用请求合并、批量落库、内存计数异步刷盘，或者把“扣减”改成按桶分片、读时汇总。库存、配额这类场景尤其要先和业务确认能否接受最终一致。
- **把治理做成闭环。** 探测、决策、执行、观测四步都要有负责人和回滚开关；活动前预热，活动后复盘误判和漏判；定期做单 key 压测，确认限流阈值和兜底页面真的可用。

*一句话总结：热点治理的关键不是加机器，而是承认单 key 不可分，再决定在哪一层把它挡住、拆开或放弃。*
