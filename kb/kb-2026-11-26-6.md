## 是什么

Rust 的错误处理有两条明确的出口：可恢复的失败写成 `Result<T, E>`，当作普通返回值交给调用方；不可恢复的程序缺陷用 `panic!` 终止当前线程。它没有 try/catch，也没有隐式的栈展开去找一个看不见的处理器。一句话直觉：错误像一件必须签收的退货包裹，沿着调用栈一层层交接，每一层要么打开处理，要么在运单上写清楚下一站能收什么货。

这套模型最重要的不是语法，而是**可见性**。一个函数会不会失败，写在签名里；调用方忘了处理，编译器会用 `unused_must_use` 警告提醒；想把失败继续往上送，就必须在返回类型里声明对应的错误类型。典型场景是读配置、解析请求参数、访问数据库、调用下游 HTTP 服务：这些失败都不是"程序写错了"，而是运行时的正常分支，应该由上层决定重试、降级还是返回 4xx。

与之相对，`panic!` 处理的是"本不该发生"的情况：数组越界、断言失败、`unwrap` 碰到 `Err`、调试模式下的整数溢出。它默认展开栈并执行 `Drop`，也可以编译成直接 abort。两者不要混着用：拿 panic 做参数校验，等于把一次可返回的 400 变成整个任务甚至进程的崩溃。

## 核心原理

**Result 只是一个枚举。** 标准库把它定义成 `Ok(T)` 与 `Err(E)` 两个变体，没有任何语言级魔法（[Rust Book 第 9 章](https://doc.rust-lang.org/book/ch09-00-error-handling.html)），所以它能被模式匹配、被 `map`/`and_then`/`or_else` 组合，也能被 `collect` 收成 `Result<Vec<T>, E>`。`Option<T>` 只回答"有没有"，`Result<T, E>` 还要回答"为什么没有"。这也解释了为什么二者不能随手互换：丢失原因容易，编造原因难。

**`?` 的真实身份是提前返回加类型转换。** 对 `Result` 使用时，它大致展开成（[Book 对 `?` 的解释](https://doc.rust-lang.org/book/ch09-02-recoverable-errors-with-result.html)）：

```rust
match expr {
    Ok(v) => v,
    Err(e) => return Err(From::from(e)),
}
```

这里有两个动作，缺一不可。第一是 `return`：从**当前函数**返回，而不是像异常那样一路展开到某个 catch。第二是 `From::from`：把底层错误转换成当前函数返回类型里的错误。由此得到一条关键推论——`?` 的目标类型由函数签名决定。同一个 `File::open(path)?`，放在返回 `io::Error` 的函数里没问题，放进返回自定义 `ConfigError` 的函数里，就必须存在 `From<io::Error> for ConfigError`，否则编译报 E0277。

```rust
use std::{fs, io, num::ParseIntError};

#[derive(Debug)]
enum ConfigError { Io(io::Error), Port(ParseIntError) }

impl From<io::Error> for ConfigError {
    fn from(e: io::Error) -> Self { ConfigError::Io(e) }
}
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self { ConfigError::Port(e) }
}

fn load_port() -> Result<u16, ConfigError> {
    let s = fs::read_to_string("app.conf")?; // io::Error 经 From 变成 ConfigError
    let port = s.trim().parse::<u16>()?;     // ParseIntError 同理
    Ok(port)
}
```

这段代码能编译，靠的不是 `?` 聪明，而是两个 `From` 实现把"下一站能收什么货"补齐了。手写这两个 impl 很啰嗦，`thiserror` 的 `#[from]` 就是替你生成它们，并把该字段登记为 `source`。

**错误类型是 API 的一部分。** 库应该返回具体枚举，让调用方能 `match` 出 `NotFound` 与 `PermissionDenied`，从类型上决定重试还是报错；应用则在顶层用 `anyhow::Error` 或 `Box<dyn Error>` 把各种来源收进一个袋子，换开发效率。[`std::error::Error`](https://doc.rust-lang.org/std/error/trait.Error.html) 只要求 `Debug + Display`，`source()` 默认返回 `None`，实现它时把底层错误挂到 `source` 上，日志才能打印出整条因果链。规范是底层原因要么由 `source` 暴露，要么由 `Display` 渲染，不要两边都做，否则同一句"connection refused"会在日志里出现两遍。

**panic 是另一条通道。** 默认的 unwind 会执行析构，`catch_unwind` 能接住一部分，但它要求 `UnwindSafe`，也不保证所有 panic 都能恢复；编译成 `panic = "abort"` 后连这个机会都没有。panic 穿过 FFI 边界通常直接 abort，所以跨语言接口要在边界内把它吃掉。`main` 可以返回 `Result<(), E>`，此时 `Err` 会以 `Debug` 格式打印并以退出码 1 结束，适合小工具，不适合当作服务端的错误处理策略。

**类比收个尾。** 异常像把包裹扔进一个全楼共用的滑梯，谁在底下接住取决于调用顺序；Rust 的 `Result` 像逐层转寄，`?` 是贴一张转寄单，单子上必须写明收件人类型。转寄不丢件，但也意味着没人能假装自己没收到。

## 常见考点与误区

- **误区一："`?` 就是 Rust 的 catch"**：错。`?` 不处理错误，只做提前返回和 `From` 转换；它不打日志、不重试、不降级。真正的处理要写 `match`、`unwrap_or_else` 或 `or_else`。面试常追问"`?` 展开成什么"，答不出 `From::from` 这一层就会被认为只背了语法。
- **误区二："用了 `?` 就不会崩"**：`?` 只接管 `Err`，管不了 `panic`。索引越界、整数除零、`unwrap` 到 `Err`、调试模式溢出照样崩；`panic = "abort"` 下更是直接终止。把"没有异常"理解成"不会失败"是典型混淆。
- **误区三："`Box<dyn Error>` 到处都能用"**：trait object 默认不携带 `Send`/`Sync`。把它放进 `tokio::spawn` 的 future，编译器会要求 `Send + 'static`，于是报错。跨线程要写 `Box<dyn Error + Send + Sync>`，或者直接用 `anyhow::Error`（它满足 `Send + Sync + 'static`）。
- **误区四："`Option` 和 `Result` 的 `?` 可以混用"**：不行，会得到 E0277。`Option` 的 `?` 在 `None` 时返回 `None`，只能用在返回 `Option` 的函数里；要把"缺失"升级成"错误"，用 `ok_or_else(|| ...)`；反向则用 `.ok()`。`ok_or` 会立刻构造错误值，错误构造有成本时用惰性版本。
- **误区五："库也该返回 `anyhow::Error`"**：`anyhow` 适合二进制和顶层编排，不适合公开 API。它把具体类型擦掉了，调用方只能靠 `downcast` 或解析字符串来分支，既脆弱又丢掉了编译期检查。库返回枚举，应用再在边界处统一收口，是更稳的分层。
- **误区六："`unwrap` 只是少写几行"**：在库或请求路径上，`unwrap` 把一次可恢复的失败升级成 panic，还剥夺了调用方选择处理方式的权利。真正确信"不可能失败"时用 `expect("不变量说明")`，让崩溃信息能自解释；测试里随便 unwrap 没问题。
- **误区七："`#[from]` 可以随便加"**：同一个来源类型在一个枚举里只能有一个 `#[from]`，否则会生成两个冲突的 `From` impl；也不能给 `Box<dyn Error>` 手写 `From<MyError>`，标准库已有覆盖所有 `E: Error` 的 blanket impl，一定冲突。公开错误枚举还应加 `#[non_exhaustive]`，否则以后新增变体就是破坏性变更。
- **误区八："把错误 `to_string()` 存下来最省事"**：字符串一落地，类型、`source` 链和可匹配的变体全丢了，后面既没法按错误码映射 HTTP 状态，也没法判断该不该重试。要存就存错误本身，展示时再格式化。

## 实践建议

- **按边界选型**：库和领域层用 [`thiserror`](https://docs.rs/thiserror/latest/thiserror/) 定义具体枚举，`#[from]` 管转换、`#[source]` 管因果链、`#[error(transparent)]` 透传包装错误；应用层用 [`anyhow::Context`](https://docs.rs/anyhow/latest/anyhow/) 给每一步补"当时在做什么"，在 HTTP/CLI 边界统一映射状态码和用户文案。
- **日志只在边界打一次**：中间层用 `context`/`map_err` 补充语义，不要每层都 `eprintln!` 或 `to_string()`，否则同一故障会刷出一串重复日志。打印时遍历 `source()`，或 anyhow 的 `{:#}`，把整条链一次打全。
- **给 panic 划出白名单**：启动期缺失关键配置、确实不可达的分支、测试断言可以 panic；请求路径、后台任务、库代码禁止 `unwrap`。装一个 panic hook 上报位置与回溯，二进制可以评估 `panic = "abort"` 换取更小的体积和更确定的终止行为，但要接受失去 `catch_unwind`。
- **跨线程先过类型关**：spawn 出去的 future 里，错误类型必须 `Send + Sync + 'static`；不要跨 `await` 持有非 `Send` 的临时值或错误引用。共享错误用 `Arc<dyn Error + Send + Sync>`，需要按类型分支时再 `downcast_ref`。
- **测试断言变体而不是文案**：用 `matches!(err, ConfigError::Port(_))` 锁住类型契约，文案改动不该弄挂测试；为错误到状态码的映射写表驱动用例；升级依赖时重点回归 `source` 链是否还完整。
- **知道成本在哪**：`Result` 成功路径通常没有额外分配，`?` 本身也很轻；真正可能分配的是 `Box<dyn Error>`、`anyhow` 和带 `String` 的上下文。热路径别为了"统一风格"把每个错误都装箱，但也别为了省一次分配把错误类型设计成无法匹配的字符串。

*一句话总结：Rust 把失败变成返回值，`?` 只负责转寄，真正决定程序稳不稳的，是错误类型的设计和边界上的那次处理。*
