## 是什么

Service Worker 是浏览器在页面与网络之间安插的一段可编程代理脚本：它注册在某个源和一段路径范围上，能拦截这个范围内的请求、决定响应来自缓存还是网络，也能在没有页面打开时被推送或后台同步事件唤醒。它跑在独立的 worker 线程里，没有 DOM，只能使用异步 API，并且只在 HTTPS（localhost 例外）下可用。

一句话直觉：它像小区门口的代收点，包裹进出都要经过它，它可以先把货架上的那份递给你；但代收点不是全天值守的保安，没人来就关门，有件到了再把人叫起来。

PWA 就建立在这层代理上：manifest 给应用一个身份、图标和启动方式，Service Worker 提供离线兜底、推送与后台同步的入口，HTTPS 保证这层代理不被中途篡改。三者凑齐，浏览器才愿意把它当作"可安装的应用"对待，而不是一个普通网页。

## 核心原理

先看生命周期与控制权。首次调用 register() 后，浏览器下载脚本、触发 install、成功后 activate；再往后访问，如果脚本字节有变化（importScripts 引入的脚本也参与比较），新版本会在后台装好并停在 waiting，直到所有受旧版本控制的页面都关闭，才轮到它 activate。这个"等待"是刻意设计的：同一个页面里的 HTML、JS、CSS 必须来自同一版本，新旧混用会直接报错。想让它立刻接管，可以在 install 里调用 skipWaiting()；想让已打开的页面也换到新版本，还要 clients.claim()。代价正是拆掉那层版本一致性——旧页面手里的 HTML 配上了新版本的 JS，问题往往比"多等一次刷新"严重。

控制权还有一个起点问题：第一次访问时没有任何 worker 在控制页面，所以首屏那些请求根本不经过 fetch 处理器。注册成功只说明"装上了"，不代表"这次就生效"；页面要等 activate 或 claim 之后的下一次导航、下一次请求才被接管。这也解释了为什么"我本地明明有缓存，第一次打开还是白屏"。

真正决定它脾气的是另一条约束：它不是你能拥有的常驻进程。规范只承诺"事件到来时启动、处理期间尽量存活、处理完可以被终止"。空闲一段时间后浏览器就会回收它，各浏览器阈值不同，Chrome 的空闲回收在几十秒量级；单次事件拖得太久也会被打断。下次事件到来时重新拉起一个全新的执行环境，模块顶层变量、内存里的队列、闭包里的状态全部归零。

这条约束推出一串工程后果。第一，状态必须外置：待发送的请求、上次同步时间、临时草稿，都要落到 IndexedDB 或 Cache Storage，localStorage 在 worker 里根本不存在，DOM 也没有。第二，保活是反模式：用 setInterval 发心跳、拿 setTimeout 当定时任务，只在"这次事件还活着"的期间有效，浏览器一回收就断，而且费电、会被判定为滥用，真正的周期任务要靠后台同步或服务端推送。第三，长任务要显式声明：install/activate 里用 event.waitUntil(promise) 告诉浏览器"这件事没完，别急着收"，fetch 里用 respondWith 同理；没有这层声明，异步工作可能在第一个 await 之后就被掐掉。第四，超时要自己设：请求等太久，等的是用户，在 respondWith 里用 Promise.race 加一个上限，比让导航一直转圈体面得多。

```js
// sw.js：待发送的请求不能放在模块作用域，SW 被回收就没了
const OUTBOX = 'outbox-v1';

async function park(request) {
  const cache = await caches.open(OUTBOX);
  const body = await request.text();
  await cache.put(new Request(`/__outbox/${Date.now()}`), new Response(body));
}

self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'POST') return;
  event.respondWith((async () => {
    try {
      return await fetch(event.request.clone());
    } catch {
      await park(event.request.clone());   // 落盘，下次唤醒还在
      return new Response('{"queued":true}', { status: 202 });
    }
  })());
});
```

上面用 Cache Storage 演示，生产上的待办队列更常放 IndexedDB，但思路是同一个：状态必须离开内存。代码里还有一处容易忽略——`event.request` 被 clone 了两次，因为 fetch 会消费掉请求体，不克隆的话第二次读 body 会直接抛错。

再往上看 PWA 的边界。可安装性通常要求 HTTPS、一份包含名称、图标、start_url 与 display 的 manifest，以及一个带 fetch 处理器的 Service Worker。但"能安装"不等于"离线一定可用"，离线只是缓存命中；"能推送"也不等于"实时送达"，消息要先经过推送服务，Service Worker 只是被唤醒后的处理器，用户关掉通知权限就什么也收不到。iOS 的安装入口与后台策略与 Chromium 不是一套判定，不能照搬。

## 常见考点与误区

- **"Service Worker 就是 Web Worker"**：两者都是 worker 线程、都没有 DOM，但 Web Worker 由页面 new 出来、生命周期跟着页面；Service Worker 由浏览器按注册管理，页面关了它可能还在，也可能已经被回收，而且它能拦截网络。只答"都是后台线程"就丢掉了全部关键差异。
- **"register() 成功就能离线"**：注册只是下载与安装，首屏请求根本不受控，脚本还要过 install 与 activate 两关。决定离线的是 fetch 里有没有兜底分支、缓存里有没有那份资源。
- **"SW 里可以随便用 localStorage、DOM、同步 XHR"**：都不行。worker 全局没有 document，Web Storage 与同步 XHR 被排除在外，动态 import() 也会抛错（静态 import 可以）。要存状态就用 IndexedDB 或 Cache Storage。
- **"加个 skipWaiting 就万事大吉"**：它让新版本立刻激活，却没有让已开页面换掉手里的旧 HTML 与旧 JS，很容易新旧混搭；要配合 clients.claim 和"新版本可用，点击刷新"的提示，并想清楚是否真的需要立刻接管。
- **"缓存命中越多越好，Cache Storage 很可靠"**：Cache 会被存储配额与系统压力驱逐，用户清站点数据也会一起清掉，部分浏览器对可写存储的清理更激进。把它当成"有则更好"的加速层，关键数据要有服务端兜底。
- **"DevTools 里显示 running 就说明它一直活着"**：那只代表此刻。不能靠它维持 WebSocket、定时器或内存任务队列，这些在移动端切后台后尤其不可靠。

## 实践建议

- **缓存名带版本，清理只清自己的前缀**：`shell-v3`、`img-v3` 这类命名让 activate 能精确删旧；不要 `keys()` 之后一把全删，同源下别的应用或库的 cache 也会遭殃。
- **按资源类型定策略**：带内容哈希的静态资源用 cache-first；HTML 与接口用 network-first 并设超时；列表页可以 stale-while-revalidate，但界面上要标出"可能不是最新"。策略跟着资源变，不要一个 respondWith 打天下。
- **更新走"提示 + 用户确认"**：监听 registration.waiting，弹出刷新入口，而不是静默 skipWaiting。表单填到一半、视频播放中被强行换版本，是很典型的线上投诉来源。
- **写操作设计成幂等**：状态外置之后，重复唤醒、重试、用户连点都会让同一个请求被执行多次，给每个待办带上 requestId，服务端按它去重，比在客户端保证"只发一次"现实。
- **把 SW 当增强而不是依赖**：埋点记录注册失败、install 失败、缓存命中率与兜底率；SW 被禁用、被卸载时页面要能正常跑。测试至少覆盖首访、二次访问、更新中、离线四个状态，并清一次 storage 再验。

*一句话总结：Service Worker 给的是可编程的网络拦截点和一个随时会被回收的事件入口，不是常驻后台；PWA 的可靠来自状态外置与降级，而不是保活。*
