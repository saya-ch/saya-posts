## 是什么

JVM 在启动时会把可用内存划成几块职责不同的区域，规范里称为运行时数据区（run-time data areas）。按线程是否共享可以分成两类：堆和方法区归所有线程共享，程序计数器、虚拟机栈、本地方法栈则是每个线程一份，随线程创建而创建、随线程结束而销毁。直觉上它像一家公司的办公区：堆是公共仓库，方法区是存放图纸和档案的资料室，虚拟机栈是每个员工桌上的工作台，程序计数器则是"当前读到哪一页"的书签。

这套划分之所以重要，是因为每一块都有独立的容量、溢出条件和排查工具。线上一句"内存不够了"，可能指堆里对象太多，也可能指元空间被动态生成的类撑爆，还可能是直接内存或线程栈吃掉了容器配额。面试问它，考的是你能否把"存什么、谁共享、怎么溢出"三件事对上号。

## 核心原理

先看线程私有的三块。程序计数器（pc register）是规范里唯一不会抛 OutOfMemoryError 的区域，它保存当前线程正在执行的字节码指令地址；如果当前方法是 native 方法，它的值按规范是未定义的。分支、循环和异常跳转都靠它找回下一条指令。

虚拟机栈描述 Java 方法执行的内存模型：每次调用压入一个栈帧，帧里有局部变量表、操作数栈、动态链接和返回地址。局部变量表的容量在编译期就确定，long 和 double 占两个 slot，对象引用只占一个 slot，真正的对象仍在堆上。栈深度超过 -Xss 限制会抛 StackOverflowError；栈动态扩展却申请不到内存时抛 OutOfMemoryError，这两者常被混为一谈。

堆是最大的一块，存放对象实例和数组，也是 GC 的主战场。HotSpot 在堆里给每个线程划 TLAB，让小对象分配不必抢锁；新生代、老年代只是 GC 的实现划分，不是规范要求。堆耗尽通常抛 java.lang.OutOfMemoryError: Java heap space；如果 GC 花了大量时间却只回收出很少空间，还可能抛 GC overhead limit exceeded。

方法区存放每个类的结构信息：字段与方法描述、方法字节码、运行时常量池、类加载器引用等。它是规范概念，落地方式随版本变化：JDK 7 及以前 HotSpot 用永久代实现，容量受 -XX:MaxPermSize 限制；JDK 8 移除永久代，改用本地内存中的 Metaspace，参数变成 -XX:MaxMetaspaceSize，默认不设上限，只受进程可用内存约束。运行时常量池是每个类一份，存放编译期字面量与符号引用，逻辑上属于方法区；而字符串常量池（StringTable）是全局的，JDK 7 起已经从永久代搬进 Java 堆，所以 JDK 8 之后它既不在方法区，也不在元空间。元空间也不是真的无限：它仍受进程地址空间和容器内存限制，JDK 8 还额外划出压缩类空间（Compressed Class Space）存放启用压缩类指针时的类元数据，类加载器泄漏时同样会抛 Metaspace 溢出。

还有一块规范之外但天天遇到的内存：直接内存。NIO 的 ByteBuffer.allocateDirect、Netty 的池化缓冲区都从这里分配，它不受 -Xmx 管，而受 -XX:MaxDirectMemorySize 约束；未显式设置时，HotSpot 通常按最大堆大小给出上限。DirectByteBuffer 靠 Cleaner 在对象被回收时释放本地内存，所以"堆里对象不多"不代表直接内存没涨；反过来，堆长期没有压力、Full GC 又被禁用时，已经废弃的缓冲区也可能迟迟不归还。

```java
import java.nio.ByteBuffer;
import java.util.ArrayList;
import java.util.List;

public class WhereOOM {
    public static void main(String[] args) {
        List<ByteBuffer> buffers = new ArrayList<>();
        while (true) {
            buffers.add(ByteBuffer.allocateDirect(8 * 1024 * 1024));
        }
    }
}
// java -Xmx64m -XX:MaxDirectMemorySize=64m WhereOOM
// 结果是 java.lang.OutOfMemoryError: Direct buffer memory
```

这段代码把上限压到 64 MB，几轮之后就会抛 Direct buffer memory。它的堆占用几乎为零，用堆 dump 也看不出问题，这正是"堆没满却 OOM"的典型。

最后别忘了线程栈也在堆外：总占用约等于线程数乘以 -Xss。线程开得太多，可能先遇到 unable to create new native thread，而不是堆溢出。把这些区域放在一起看，JVM 进程的常驻内存大致是堆、元空间、直接内存、线程栈、代码缓存和 GC 自身结构的和，-Xmx 只框住了其中一块。

## 常见考点与误区

- **"方法区就是永久代"**：错。方法区是规范定义的概念，永久代只是 JDK 7 及以前 HotSpot 的实现。JDK 8 之后方法区仍在，只是换成了元空间；在 JDK 8 上配 -XX:MaxPermSize 不会生效，启动时只会得到一条忽略警告。
- **"字符串常量池在方法区"**：这是旧教材里最常见的过期结论。字符串常量池在 JDK 7 就移入堆，JDK 8 的元空间只存类元数据；运行时常量池和字符串常量池也不是一回事，前者每个类一份、含符号引用，后者是全局的表。
- **"栈里存对象"**：栈帧的局部变量表存基本类型和引用，对象本体在堆上。逃逸分析后的标量替换、锁消除属于 JIT 优化，不是规范承诺；不能拿它当"对象一定在栈上"的依据。
- **"堆没满就不会 OOM"**：元空间、直接内存、线程栈、代码缓存都能独立耗尽。更隐蔽的是容器场景：进程总内存超过 cgroup 限制时会被内核直接杀掉，退出码 137，日志里没有 Java 异常，只有一条 OOMKilled。
- **"StackOverflowError 和 OutOfMemoryError 是一回事"**：两者都是 Error，但触发条件不同。前者是栈深度超限，后者是申请不到内存；一个要查递归深度与 -Xss，一个要查容量与泄漏，排查方向完全不同。
- **"Xmx 就是进程内存上限"**：错。RSS 还要算上元空间、直接内存、每个线程的栈、JIT 代码缓存和 GC 的辅助结构，容器内存限制只比 -Xmx 大一点，很容易被内核杀掉。
- **"Metaspace 溢出就加堆"**：方向反了。元空间吃的是本地内存，调 -Xmx 帮不上忙，应该查类加载器泄漏、动态代理生成的类是否被缓存，再决定要不要设 -XX:MaxMetaspaceSize 兜底。

## 实践建议

- 容器里别只写 -Xmx。可以给 JVM 设 -XX:MaxRAMPercentage=60～70，把剩余空间留给非堆；也可以显式配 -Xmx、-XX:MaxMetaspaceSize、-XX:MaxDirectMemorySize，三项都有上限，排查时才有边界。
- 堆的 -Xms 与 -Xmx 设成相同值，避免运行期反复扩缩；但不要靠盲目调大堆解决泄漏，堆越大，单次 Full GC 的停顿和 dump 文件也越大。
- 排查先分层：jcmd <pid> VM.native_memory summary 看堆外去向（需加 -XX:NativeMemoryTracking=summary），jcmd GC.heap_info 和 jstat -gc 看堆与 GC，直接内存则看 BufferPool 的 MXBean 指标，最后才用 jmap 做堆 dump。
- 加上 -XX:+HeapDumpOnOutOfMemoryError 与明确的 dump 路径，并确认容器磁盘放得下；堆外内存溢出时，堆 dump 里也照不出那部分占用，别把"堆里很小"误判成"没有溢出"。
- 线程数上千时，把 -Xss 从默认的约 1 MB 适当调小能省下可观的本地内存，但要先压测最深的递归与框架调用链，避免把 StackOverflowError 提前引爆。
- 元空间阶梯式上涨多半是类加载器泄漏：用 jcmd <pid> VM.classloader_stats 或 jmap -clstats 对比加载器数量，重点查热部署、脚本引擎和动态代理的类缓存。

*一句话总结：JVM 内存是堆内堆外的一整套版图，-Xmx 只是其中一块，认清边界才不会误判 OOM。*
