## 是什么

Fiber 是 React 16 起使用的协调数据结构：每个组件实例对应一个 Fiber 节点，节点之间用 `child`、`sibling`、`return` 组成一棵可以显式遍历的树，从而把过去“递归到底、一气呵成”的渲染过程，拆成一个个可以暂停、恢复、重排的工作单元。

在这之上还有一层常被忽略的设计——**双缓存（double buffering）**：React 在任意时刻最多保留两棵 Fiber 树。一棵叫 `current`，它对应屏幕上已经画出来的界面；另一棵叫 `workInProgress`，是内存里正在搭建的下一帧草稿。两个树里的同位置节点通过 `alternate` 指针互相指向，成为彼此的镜像。屏幕上的树是只读的，草稿随便改；等草稿全部建完，一次指针交换让它变成新的 `current`，旧的那棵则退下来，成为下一轮的草稿容器。

## 核心原理

这个设计借自图形学：游戏不会直接往屏幕正在显示的那块帧缓冲里画下一帧，否则玩家会看到画到一半的天空和还没画上去的人物。渲染器准备两块缓冲区，一块给显示器读，一块在后台画，画完交换。React 面对的是同一类问题，只不过“半张脸”变成了”列表已经更新、侧边栏还是旧数据”的界面撕裂。

**第一层：`alternate` 让两棵树可以互相借用。** 每个 Fiber 上都有一个 `alternate` 字段。更新发生时，React 从根开始，为需要变化的路径创建新节点，并让新节点的 `alternate` 指向旧树里的对应节点，同时让旧节点的 `alternate` 指回来。没有变化的子树不重建，新树直接复用旧节点的引用。所以“复制一整棵树”并不成立，真正分配的是变动的那些节点；两棵树始终是一对可以互相翻面的镜像。

```js
class Fiber {
  constructor(tag, text = "") {
    this.tag = tag;
    this.text = text;
    this.child = null;
    this.alternate = null; // 指向另一棵树里的自己
  }
}

const current = new Fiber("ul");
current.child = new Fiber("li", "旧值");

const draft = new Fiber("ul");        // 草稿树，屏幕毫无感知
draft.child = new Fiber("li", "新值");
draft.child.alternate = current.child; // 新旧节点配对
current.child.alternate = draft.child;

// 提交：一次引用替换，草稿成为新的 current
current.child = draft.child;
console.log(current.child.text);       // 新值
```

上面这段刻意把“提交”缩成一行 `current.child = draft.child`，是为了说明交换本身与树的规模无关：三万节点和三个节点，都只是一次指针赋值。真实实现当然还要在这一步之前把 DOM 改完，但那个动作同样集中在提交阶段，而不是散落在渲染过程中。

**第二层：草稿可以丢，因为没人看得见。** 渲染阶段遍历的是 `workInProgress`，只读 `current` 里的 props、state 和 DOM 引用，绝不写回旧树。于是 React 可以在任意两个工作单元之间停下来：检查这一帧还剩多少时间，不够就把主线程还给浏览器去处理输入和绘制，自己等下一个宏任务再续上。更关键的是，如果这期间来了一个更高优先级的更新——比如用户敲了一个键——React 可以直接把整棵草稿扔掉，从 `current` 重新开始，屏幕上不会留下任何半成品。这正是并发渲染里“可中断”三个字的物理基础：不是调度器有多聪明，而是被改的那份数据本来就不影响显示。

**第三层：优先级决定先画哪一版。** React 用 lanes 表示优先级：优先级被压进一个位图整数，每一位（lane）代表一档紧急程度，一次更新被归入某一组 lane，多个更新落在同一组就合并成一次渲染。同步输入、默认更新、transition、空闲任务各占不同的位；一次渲染挑出当前最高优先级的 lane 先做，低优先级的留到后面。位运算的好处是可以把“这批更新里包含哪些优先级”压进一个整数，做包含、相交、合并都很便宜。但要注意它带来的是一个现实约束：低优先级渲染做到一半被高优先级插队，插队完成后低优先级那部分要重做——所以 transition 里的组件如果每次渲染都新建对象，就会被反复重算，这也是”把昂贵计算放进 `useMemo`”在并发模式下更重要的原因。

**第四层：提交阶段不能停。** 草稿建完后进入提交，分成变更前、变更、布局三个阶段：先读一遍需要的信息，再统一改真实 DOM，最后同步执行 `useLayoutEffect` 并交换根指针。这一段是同步的，不允许被打断，因为它操作的是用户已经能看见的那份真实结构；如果改到一半让出去，浏览器就可能把中间状态画出来，前面所有的隔离都白做了。`useEffect` 则被安排到绘制之后异步执行，正是为了不挡住这一帧。

把这四层连起来看，双缓存解决的从来不是“渲染更快”，而是”渲染可以失败”。一次被丢弃的草稿不产生任何用户可见的后果，React 才敢在单线程里做抢占式调度。

## 常见考点与误区

- **“并发渲染就是多线程渲染”**：错得最普遍。JavaScript 主线程仍然只有一条，React 做的只是把工作切碎、在宏任务之间让出控制权，再按优先级重排。它是并发（concurrent）而非并行（parallel），任何时刻真正执行的仍是一段代码。
- **“更新过程中 DOM 是逐节点变化的”**：如果真是这样，就不会有双缓存。渲染阶段完全不碰 DOM，只计算草稿；所有真实变更集中在提交阶段一次做完。面试里被追问”为什么不会看到中间态”，答案要落在两棵树的隔离上，而不是”React 很快”。
- **“两棵树很浪费内存”**：变的是路径上的节点，未变化的子树在新旧树之间共享引用，`alternate` 的存在还让节点对象可以翻面复用，避免每轮都重新分配整棵树。真正需要警惕的不是这层结构，而是自己在渲染函数里创建大对象、在列表里用下标当 key，逼 React 重建本可复用的节点。
- **“提交阶段也能被 transition 打断”**：不能。`startTransition` 降低的是渲染阶段的优先级，一旦进入提交就一路走完。把提交当成“也可中断”会推出错误结论，比如以为 `useLayoutEffect` 会在某一帧中途执行一半。同理，React 在绘制后异步执行 `useEffect`、在绘制前同步执行 `useLayoutEffect`，这条分界也不因优先级改变。
- **“丢弃草稿等于这次更新白算了”**：被丢弃的是渲染结果，不是更新本身。更新还在队列里，等更高优先级的事情做完会重新参与调度。反过来说，如果一个低优先级更新持续被插队，它可能长时间得不到执行——这就是优先级饥饿，也是 transition 不适合承载”必须最终落地”的关键业务的原因。
- **“加了 `memo` 就一定更快”**：`memo` 只是跳过该子树的重新渲染，比较 props 本身也要花时间；在双缓存下，真正昂贵的是被标记为需要更新的路径有多长。优化顺序应该是先缩短这条路径（状态下沉、拆分组件），再考虑记忆化。

## 实践建议

- 把组件写成纯函数，不在渲染期间改外部变量、不写 DOM、不发请求。双缓存能在草稿被丢弃时保证安全，前提是渲染没有副作用；一旦有，重算就会重复执行副作用。
- 列表用稳定且唯一的 key，不要用数组下标。key 决定 React 能否在旧树里找到可复用的节点；key 选错，等于强迫它重建整段子树，双缓存省下的那点收益会被抵消掉。
- 区分“输入反馈”和”结果展示”：输入框的受控更新走同步优先级，由它触发的大列表过滤、图表重算放进 `startTransition`，让用户先看到字符回显，再看到结果。
- 把昂贵计算移出渲染路径：`useMemo` 缓存派生数据，虚拟列表控制节点数量，重组件用 `React.lazy` 拆包。并发渲染改善的是响应性，不会让 O(n) 的渲染变成 O(1)。
- 排查卡顿时先分清是渲染阶段长还是提交阶段长。渲染阶段可用 Profiler 观察重复渲染的组件；如果单次提交就很慢，问题在 DOM 体量与布局抖动，调优先级没有用。

*一句话总结：双缓存让 React 把“算”和”画”分开，草稿可丢、提交必整，界面才不会撕裂。*
