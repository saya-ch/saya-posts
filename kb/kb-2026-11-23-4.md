## 是什么

多智能体（multi-agent）系统，是把一个任务交给多个各自拥有独立上下文窗口、工具集和角色提示的 Agent，让它们通过消息、共享状态或显式交接共同完成。一句话直觉：它不是"多个大脑一起思考"，而是"把一块装不下的上下文切成几块，各自算完再用协议拼回去"。它真正解决的是单窗口的容量与注意力问题，而不是让模型突然变聪明。

常见场景有三类：需要大量检索与交叉验证的深度研究；跨多个文件、多个模块的代码库改造；以及长流程业务（客服、审批、内容生产），其中每一步需要不同的工具与约束。区分它们的关键不是"用几个 Agent"，而是任务能不能拆、拆完要不要相互等待。

## 核心原理

先看收益从哪里来。Anthropic 在[多智能体研究系统的复盘](https://www.anthropic.com/engineering/multi-agent-research-system)里给出两个数字：多智能体系统消耗的 token 约为普通对话的 15 倍，而在他们的 BrowseComp 评测中，token 使用量一项就解释了 80% 的性能方差。换句话说，多智能体的"更强"很大程度是"在彼此独立的上下文里，花了更多 token 并行推理"。这决定了它的经济学：只有任务价值足够高、且确实可并行时才划算。

协作模式其实由两个问题决定：控制流（下一步谁说了算）和数据流（上下文怎么过去）。按这两个维度，工程上常见四类。

**主管-工人（supervisor / orchestrator-worker）**：一个 lead 负责拆解、分派、汇总，worker 只拿到子任务和必要背景，算完回传结果。它适合"可分解、结果可独立验证"的任务，比如并行检索十个子问题。好处是 worker 的上下文干净、可以并发；坏处是 lead 成为瓶颈和单点，而且层层转述会丢细节——Anthropic 把这叫 telephone 问题，他们的做法是让 subagent 把产物写进文件系统，只把轻量引用交回 lead，而不是把所有内容塞进对话历史。

**流水线（pipeline）**：上游的输出就是下游的输入，阶段固定，比如抓取→抽取→校验→渲染。它的优势是每段都能单独评测、单独换模型；代价是错误会逐级放大，所以阶段之间必须有明确的 schema 契约，而不是自然语言"看着办"。

**交接（handoff / swarm）**：没有中心调度，当前 Agent 判断该由谁接手，就把控制权连同对话状态转给另一个 Agent。它适合路径不确定的会话式任务，比如售前咨询转到退款专员，这也正是 [LangGraph 的多智能体文档](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)里 supervisor 与 swarm 两种拓扑的分野。注意 handoff 不是函数调用：转交之后原 Agent 不再持有栈帧，也没有"返回"这一步，所以必须有 hop 上限和兜底路由，否则两个 Agent 会来回踢皮球。

**辩论 / 黑板（debate / blackboard）**：多个角色对同一份产物挑错，或往共享黑板写中间结论。它适合高风险判断与方案筛选，但同一模型、相似上下文产生的错误高度相关，投票很容易"一起错"，需要异构模型或外部工具做裁判。

```python
from concurrent.futures import ThreadPoolExecutor

def run(task, workers, max_steps=8):
    plan = lead(f"拆成不超过 {max_steps} 个互不依赖的子任务：{task}")
    with ThreadPoolExecutor(max_workers=4) as pool:
        futures = [pool.submit(work, w, sub) for w, sub in plan]
        results = [f.result(timeout=120) for f in futures]
    refs = [save_artifact(r) for r in results]  # 只回传引用，不搬全文
    return lead(f"基于这些产物作答：{refs}")
```

这段骨架里，真正决定成败的不是并发，而是三件事：子任务之间没有隐藏依赖、worker 的输出被落成可引用的产物、lead 拿到的是引用而不是几千字转述。

成本也要按这个结构算。总 token 大致等于每个 Agent 的上下文长度乘以它的轮次再求和，协调消息和重试另计。串行依赖越多，并行收益越接近 Amdahl 定律描述的上限：能并行的比例只有三成，加再多 worker 也快不过三倍，还要额外付调度与合并的钱。所以"拆几个 Agent"应该由依赖图决定，而不是由组织架构图决定。

## 常见考点与误区

- **"Agent 越多，效果越好"**：错。多智能体买到的是上下文容量与并行采样，账单是十几倍 token 和更高方差；依赖紧密、需要共享同一份细节的任务（多数编码任务就是）拆分后协调开销常常大于收益。
- **"多智能体就是并行"**：错。大量框架只是同一模型被调用多次，受 rate limit 约束；handoff 和 pipeline 本质是串行，延迟反而叠加。
- **"子 Agent 能看到主 Agent 的记忆"**：默认看不到。每个 Agent 有独立上下文，共享必须显式通过外部存储、共享 state 或产物引用实现。面试里常拿"主 Agent 为什么不记得子 Agent 的推理过程"来考这一点。
- **"handoff 等于函数调用，会原路返回"**：错。控制权转移后原 Agent 退出，没有调用栈，任务容易在转交中丢失；需要显式记录当前负责人和未完成事项。
- **"多轮辩论或投票能消除幻觉"**：不一定。同源模型加相似上下文会让错误相关，投票只是把同一个偏见放大；有效的做法是异构模型、工具验证或确定性校验器。
- **"让模型自己判断任务完成"**：不可靠。终止条件应该是预算、轮次上限加一个独立的验收器，而不是参与者的一句"我完成了"。

## 实践建议

- 先做单 Agent 基线，再决定拆不拆。用同一套评测对比"单 Agent + 更多轮工具调用"和"多 Agent"，如果前者只差几个点，就不值得付十几倍的 token。
- 按上下文边界拆，不按人类岗位拆。一个 worker 的判据是"它需要的那部分信息是否自洽、能否独立验收"，而不是"现实里有没有这个职位"。
- 给每个 worker 定契约：输入 schema、输出 schema、超时、token 预算、可用的工具白名单。lead 只接受通过 schema 与校验器的结果，失败就重派而不是把错误往下传。
- 中间产物落外部存储，对话里只传引用。这样既避免转述失真，也让长任务可以断点续跑、人工抽查。
- 上可观测性：按 span 记录每个 Agent 的 token、延迟、工具调用与重试次数，设总预算熔断；handoff 系统额外记录跳转图，用来发现乒乓循环。
- 评测要做消融：去掉一个 Agent、换掉一个模型、把并行改成串行，各跑一遍。多智能体系统的回归往往不是"答错"，而是"某条路径上多绕了两圈"。

*一句话总结：多智能体买的不是更多智能，而是更多互不干扰的上下文；协作模式选错，这笔钱就白花。*
