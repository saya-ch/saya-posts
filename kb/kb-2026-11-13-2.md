## 是什么

TCP 的“连接”不是一条被占住的物理线路，而是两端内核里的一对状态、一个四元组（源 IP、源端口、目的 IP、目的端口）和一套共同约定的序号空间。所谓三次握手，就是双方在正式传数据之前交换三件事：我的初始序号是多少、我收到了你的初始序号、你收到了我的初始序号。四次挥手则是两个方向各自宣布“我没有数据要发了”，再各自确认对方的关闭请求。

典型场景从浏览器打开一个 HTTPS 页面，到数据库连接池取一条连接，再到网关与微服务之间的长连接，背后都是这套状态机。它值得讲透的原因很实际：线上大部分“连不上”“请求超时”“端口耗尽”，都能在握手与挥手的状态里找到归因，而不是靠重启碰运气。

## 核心原理

### 三次握手在确认什么

把握手想成对讲机测试。A 说“你能听到我吗”（SYN），B 回“能，你能听到我吗”（SYN+ACK），A 再回“能”（ACK）。两句话不够：B 说完“能”之后，并不知道 A 有没有收到，只有第三句才让 B 确认。三次刚好让双方都完成“我说的话你收到了”和“你说的话我收到了”这两件事。

技术上还多一层：SYN 和 FIN 都各占一个序号。A 发 SYN 时带初始序号 ISN_A，B 的 SYN+ACK 里 ack=ISN_A+1，既确认了 SYN，也告诉 A“下一个字节从 ISN_A+1 开始”；同时 B 带上自己的 ISN_B，A 的第三个 ACK 再回 ack=ISN_B+1。这样双方的发送与接收才有了共同的序号基准。

```python
import struct

def header(src, dst, seq, ack, flags):
    # 数据偏移 5（无选项），窗口 65535；校验和与紧急指针置 0 仅供演示
    return struct.pack("!HHIIBBHHH", src, dst, seq, ack, 5 << 4, flags, 65535, 0, 0)

def parse(raw):
    src, dst, seq, ack, _, flags, *_ = struct.unpack("!HHIIBBHHH", raw)
    names = [n for bit, n in ((0x02, "SYN"), (0x10, "ACK"), (0x01, "FIN")) if flags & bit]
    return f"{src}->{dst} seq={seq} ack={ack} {'|'.join(names)}"

syn = header(50000, 80, 1000, 0, 0x02)
syn_ack = header(80, 50000, 9000, 1001, 0x12)
print(parse(syn))      # 50000->80 seq=1000 ack=0 SYN
print(parse(syn_ack))  # 80->50000 seq=9000 ack=1001 SYN|ACK
```

ISN 不能是固定值。若每次从 0 开始，上一个连接迟到的报文就可能被新连接当成合法数据。[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) 明确写了三次握手的首要目的是防止旧的重复连接初始化造成混乱；现代实现还会用带密钥的哈希把四元组和时间混进 ISN，让外部难以猜测。

第三个包还有一层作用：它是客户端对“我是否真的要建这条连接”的最终裁决。网络里如果漂着一个很早以前发出的重复 SYN，两次握手会让服务端单方面建好连接、分配资源，而客户端早已不认这条连接，资源只能等超时释放。三次握手把这个决定权交回发起方。

### 握手发生在内核，应用看到的是队列

服务端收到 SYN 后，连接先进入 SYN_RCVD，挂在半连接队列（SYN queue）；收到第三个 ACK 后才算 ESTABLISHED，转入全连接队列（accept queue），等应用调用 accept 取走。SYN flood 打的就是第一层：攻击者只发 SYN 不回 ACK，把半连接队列占满，正常握手进不来。Linux 的 syncookies 是兜底，队列满时不再保存半连接状态，而是把必要信息编码进 SYN+ACK 的序号里，等 ACK 回来再还原。

第二层也会满。全连接队列满了以后，Linux 默认丢掉第三个 ACK 并重传 SYN+ACK，客户端以为自己连上了，应用层却一直等不到响应；只有打开 `tcp_abort_on_overflow` 才会回 RST。所以“服务端 backlog 调大了还是超时”，问题常常在 accept 循环被阻塞，而不是队列长度。

### 挥手为什么多一个包

TCP 是全双工的，两个方向独立关闭。FIN 的含义只是“我这个方向没有数据要发了”，不代表“我也不能再收”。所以主动关闭方发 FIN 后进入 FIN_WAIT_1，收到对方的 ACK 进入 FIN_WAIT_2，此时它还能继续接收；被动方进入 CLOSE_WAIT，等应用把剩下的数据发完、调用 close，才发自己的 FIN，然后进 LAST_ACK，收到最后的 ACK 才关闭。

多出来的那一步就多在这里：被动方收到 FIN 时，ACK 必须马上回，否则对方会重传；但应用可能还有数据没发完，FIN 不能跟着 ACK 一起走。ACK 与 FIN 是两个方向、不同触发条件的动作，逻辑上必须分开。只有被动方也没有数据、应用立刻 close 时，这两个包才可能被合并成一个，抓包看起来像三次——所以“四次”说的是四次交互，不是必须抓到四个包。

### TIME_WAIT 在等两件事

主动关闭方发出最后一个 ACK 后不是直接消失，而是进入 TIME_WAIT。它等两件事：一是这个 ACK 可能丢，被动方会重传 FIN，主动方还在，才能再补一个 ACK；二是让这条四元组的旧报文在网络里自然过期，避免它们窜进随后用同一四元组建立的新连接。

RFC 用 2MSL 描述这段等待，MSL 是报文在网络里的最大生存时间。Linux 没有按理论值算，而是用一个 60 秒的固定常量（TCP_TIMEWAIT_LEN），所以看到 TIME_WAIT 持续一分钟是正常的，不是“连接泄漏”，用 `ss` 观察或对照内核常量都能验证（[参考](https://developer.aliyun.com/article/1474881)）。真正要盯的是被动方的 CLOSE_WAIT：那是应用收到 FIN 却没调 close，堆多久都不会自己消失。

## 常见考点与误区

- **“三次握手是为了保证可靠传输”**：握手本身也会丢包重传，它保证的是双方收发能力与初始序号对齐；可靠传输靠的是序号、确认、重传和校验和，不是握手这个仪式。
- **“两次握手也能确认双方能力”**：不能。服务端发完 SYN+ACK 就不知道客户端收没收到，也无法拒绝一个过期的重复 SYN，会凭空建立一条没人使用的连接。
- **“SYN 和 FIN 不占序号”**：都占一个，所以确认号是 ISN+1，重传时序号不变；这也是 SYN 超时要按指数退避重试、而不是无间隔猛发的原因。
- **“挥手一定是四个包”**：ACK 与 FIN 可以合在一个包里，抓包可能是三个。四次描述的是两个方向各自关闭这一逻辑过程。
- **“TIME_WAIT 太多要调小或复用”**：它是主动关闭方的正常终态，缩短会削弱最后 ACK 的重发能力。`tcp_tw_reuse` 只对出向连接生效，曾经的 `tcp_tw_recycle` 已从内核移除，不要再照旧文档打开它。
- **“CLOSE_WAIT 堆积是内核参数问题”**：CLOSE_WAIT 在被动关闭方，含义是内核已回 ACK、应用还没 close，改参数没用，要查代码里漏掉的关闭路径。
- **“握手成功说明对端还活着”**：中间设备掉电、NAT 表项过期都会留下半开连接，两端都以为自己 ESTABLISHED，直到一方发数据收到 RST 或超时。

## 实践建议

- 排障先看状态分布：`ss -tan` 按 state 统计，SYN-SENT 多说明 SYN 或 SYN+ACK 被丢在路上，SYN-RECV 多说明半连接在堆积（队列吃紧或第三个 ACK 被丢），CLOSE-WAIT 多去查应用，TIME-WAIT 多则看谁在主动关连接。
- backlog 要和 accept 速度一起调。只把 `somaxconn` 和 listen 参数调大，而事件循环里做了阻塞操作，全连接队列照样溢出；压测时同时观察队列溢出计数。
- 连接由谁先关要统一约定。服务端主动关会让自己背上 TIME_WAIT，高并发短连接下容易撞端口上限；能用连接池复用就别每次重握。
- 长连接不要依赖 TCP keepalive 的默认值，它的空闲探测周期以小时计，通常比 NAT 映射的存活时间长；在应用层加心跳，才能及时发现半开连接。
- 抓包验证比看文档可靠：用 tcpdump 看 SYN、ACK、FIN 的标志与相对序号，确认中间设备没有改写或丢弃握手包，再决定是改应用还是改内核参数。

*一句话总结：三次握手对齐序号并挡掉过期连接，四次挥手让两个方向各自收尾；TIME_WAIT 是正常终态，不是故障。*
