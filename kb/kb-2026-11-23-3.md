## 是什么

Spring AOP 常被说成“面向切面编程”，但它在 Spring 里的落地方式并不神秘：不改你的源代码，也不在编译期织入，而是在 Bean 初始化完成后，由一个 BeanPostProcessor（`AbstractAutoProxyCreator`）判断这个 Bean 是否命中切点；命中就生成一个代理对象，替换掉容器原本要返回的实例。调用方拿到的是代理，方法调用先进入拦截器链，链走完了才落到真正的目标对象。

一句话直觉：切面不是长在你的类里，而是长在代理这层“壳”上。

典型场景随处可见：`@Transactional` 的事务开启与提交、`@Cacheable` 的缓存命中、`@Async` 的线程池切换、自定义 `@Around` 的日志、权限和限流。业务代码里只写了一个注解，真正干活的是代理。也正因为如此，“注解为什么不生效”十有八九不是注解写错了，而是调用没有经过这层壳。

## 核心原理

Spring 只负责“什么时候代理”，“怎么代理”交给两条技术路线。

**第一条：JDK 动态代理。** 它要求目标类至少实现一个接口。`Proxy.newProxyInstance` 在运行时生成一个类，这个类实现目标类所实现的全部接口，每个方法体只做一件事：把调用转给 `InvocationHandler.invoke(proxy, method, args)`。代理类和目标类都实现同一个接口，是“兄弟”关系，谁也不继承谁。所以 JDK 代理只能暴露接口里声明的方法，目标类自己的 public 方法如果不在接口上，代理对象上根本没有。

**第二条：CGLIB。** 它用 ASM 在运行时生成目标类的子类，重写可重写的方法，在方法里插入回调。代理是目标类的“儿子”，因此不需要接口，也能代理目标类额外的方法；代价是它必须能继承——final 类不能继承，final 方法不能重写，private 和 static 方法也不在重写范围内。

选哪条路由 `DefaultAopProxyFactory` 决定：`proxyTargetClass=true`，或者目标没有任何用户接口，就走 CGLIB；否则走 JDK 动态代理。原生 Spring 默认偏向 JDK 代理；Spring Boot 2.x 起，自动配置把 `spring.aop.proxy-target-class` 的默认值改成了 `true`，所以大多数 Boot 项目实际拿到的是 CGLIB 代理。手写 `@EnableAspectJAutoProxy` 时仍要看它自己的 `proxyTargetClass` 属性，不能想当然。

调用链可以简化成：代理方法 → `JdkDynamicAopProxy.invoke` 或 CGLIB 的 `DynamicAdvisedInterceptor.intercept` → `ReflectiveMethodInvocation.proceed()` → 依次执行 `MethodInterceptor` → 反射调用目标方法。`@Around` 之所以能包住目标方法，是因为它拿到的 `ProceedingJoinPoint` 就是这条链上的一个节点；不调用 `proceed()`，目标方法就不会执行。

两条路线的回调形态也不一样。JDK 的 `InvocationHandler` 只有一个 `invoke` 入口，所有方法都挤在这里，只能靠 `method` 参数自己分派；CGLIB 可以用 `CallbackFilter` 按方法选择回调，`MethodProxy` 还能直接调用父类方法。手写 JDK 代理时那串 `if (method.getName().equals(...))`，就是这种“单入口”设计的直接后果。

代理类本身也不是每次调用都现生成。JDK 的 `Proxy` 按“类加载器 + 接口数组”缓存代理类，CGLIB 的 `Enhancer` 也缓存已生成的子类；重复创建的是代理实例，不是 Class。真正决定一次调用能不能被增强的，对 JDK 路线是方法在不在接口上，对 CGLIB 路线是能不能被重写、是不是 private 或 final，这些判断在方法进入拦截器链之前就已经做完了。

关键的一点：代理对象和目标对象通常是两个实例。目标被 `AdvisedSupport` 或 CGLIB 的回调持有，代理自己并没有把业务字段复制过来。所以目标方法里的 `this` 是目标对象，不是代理；`this.bar()` 这种自调用直接落在目标上，拦截器链被绕过。这不是 Spring 的 bug，而是“代理”这种方案的必然结果。还有一层容易忽略：CGLIB 代理是子类，`bean instanceof 你的实现类` 为 true；JDK 代理不是，它只是同接口的另一个实现。很多“按类型注入突然失败”的现场，根因就在这里。

```java
import java.lang.reflect.Proxy;
interface Greeter { String greet(String name); }
class GreeterImpl implements Greeter {
    public String greet(String name) { return "hi, " + name; }
}
class Demo {
    public static void main(String[] args) {
        Greeter target = new GreeterImpl();
        Greeter proxy = (Greeter) Proxy.newProxyInstance(
            Greeter.class.getClassLoader(), new Class<?>[]{Greeter.class},
            (p, m, a) -> {
                System.out.println("before " + m.getName());
                Object r = m.invoke(target, a);
                System.out.println("after");
                return r;
            });
        System.out.println(proxy.greet("saya"));
        System.out.println(proxy.getClass().getName());
    }
}
```

这段代码跑出来，`proxy.greet("saya")` 会先打印 before、再打印 after；而 `proxy.getClass().getName()` 不是 `GreeterImpl`，而是带 `$Proxy` 的运行时生成类。JDK 代理连 `equals`、`hashCode`、`toString` 也会转进 `InvocationHandler`，所以处理器里如果又去打印 `proxy`，很容易递归。

## 常见考点与误区

- **误区一：“JDK 代理一定比 CGLIB 慢”**：这是早年 benchmark 留下的口诀。现代 JDK 会缓存生成的代理类，稳定态下两者的调用开销在同一量级；CGLIB 首次生成子类要跑 ASM，启动阶段反而更贵。选型首先看类型约束，性能要用自己的调用模式压测，别背结论。
- **误区二：“CGLIB 什么类都能代理”**：final 类不能继承，直接失败；final 方法能留在代理类里，但不会被增强；private、static 方法同样不进回调。反过来，JDK 代理可以代理 final 类——只要它实现接口，因为代理根本不继承目标类。这是最容易被忽略的非对称。
- **误区三：“注入进来的就是我写的那个类”**：JDK 代理下，`bean instanceof GreeterImpl` 是 false，按实现类注入可能抛 `BeanNotOfRequiredTypeException`，按接口注入才稳。反射看到的是代理类的字段布局：JDK 代理多出 handler，CGLIB 代理多出 callback，属性拷贝很容易拷出意外。
- **误区四：“Spring AOP 能拦自调用、构造器和字段”**：Spring AOP 只支持方法执行这一种连接点，而且必须经过代理。`this.bar()`、构造器内部调用、字段读写、static 方法都拦不到；需要这些能力要用 AspectJ 的编译期或加载期织入，它把通知写进字节码，不依赖代理。
- **误区五：“`proxyTargetClass=true` 是万能开关”**：它只是强制走 CGLIB。目标如果是 final 类，CGLIB 无法生成子类，启动就会报错，并不会自动退回 JDK 代理；这时要么把 `proxyTargetClass` 关掉、让它走接口代理，要么改用 AspectJ 织入，别指望换个注解就自动兼容。
- **考点六：“`@Transactional` 为什么没生效”**：先看方法是不是 public（默认只对 public 方法生效），再看调用有没有经过代理，最后看异常类型是否触发回滚。把注解写在实现类的方法上，比写在接口上更不容易踩坑。

## 实践建议

- **先确认代理类型，再谈失效原因。** 用 `AopUtils.isAopProxy(bean)`、`AopUtils.isJdkDynamicProxy(bean)`、`AopUtils.isCglibProxy(bean)` 判断；看类名里是 `$Proxy` 还是 `$$EnhancerBySpringCGLIB$$`；需要目标类信息时用 `AopProxyUtils.ultimateTargetClass(bean)`，不要直接 `bean.getClass()`。
- **注入优先面向接口，但别为了 AOP 硬造接口。** 团队大量按实现类注入时，保持 Boot 默认的 CGLIB 更省事；如果类本身是 final（包括 record），代理模式下的出路是让它实现接口并关掉 `proxyTargetClass`，或者改用 AspectJ 织入。给 final 类加切面之前先想清楚，别等上线才发现切面根本没织进去。
- **切点要收窄。** 不要用 `execution(* com.example..*.*(..))` 一把梭，切面越多、代理链越长，越容易把框架内部方法也包进来。优先用注解切点，把切面限定在明确的业务层包名和方法签名上。
- **自调用优先拆类。** 把需要增强的方法搬到另一个 Bean，是最干净的做法；其次注入自身代理（配合 `@Lazy` 打破循环依赖）；`AopContext.currentProxy()` 需要 `exposeProxy=true`，还会把业务代码绑死在 Spring AOP 上，只适合兜底。
- **多个切面要定顺序。** 用 `@Order` 或 `Ordered` 明确先后；事务、重试、缓存这类切面嵌套时，谁包谁直接决定回滚和缓存写入的结果，别依赖默认顺序，写完用一个失败用例验证。
- **排错按顺序走。** 注解是否在实现方法上 → 方法是否 public → 调用是否经过代理 → 代理类型是否匹配 → 切点表达式是否命中。这个顺序能排掉绝大多数“切面不生效”，比盲目加 `@EnableAspectJAutoProxy` 有效。

*一句话总结：Spring AOP 的差异不在切面怎么写，而在代理是接口的兄弟，还是目标类的子类。*
