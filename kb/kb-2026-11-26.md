## 是什么

限流器是在一段时间内给请求发通行证的组件：通过的放行，超出的被拒绝、排队或降级。它保护的从来不是"请求数量"本身，而是请求背后的稀缺资源——数据库连接、线程池、下游接口的配额、模型推理的 GPU 时间。流量超过资源上限时，如果没有一层东西替你做决定，决定就会由超时和雪崩来做。

令牌桶的形状是：系统以速率 r 往桶里放令牌，桶最多装 b 个；每个请求取走一个，取不到就被拒或等待。一句话直觉：桶里攒的是"可以提前花掉的额度"，b 决定能一次性花多少，r 决定花完多久能攒回来。漏桶的形状是：请求是往桶里倒的水，桶底有一个固定口径的孔，水以恒定速率漏出；桶满了，新来的水只能溢出。一句话直觉：漏桶关心的不是"你攒了多少额度"，而是"流出去的水必须多匀"。

典型场景包括开放 API 的套餐配额（按秒、分钟或月）、网关按 IP 防刷、保护慢查询多的数据库、给不同租户做公平隔离，以及给重试和爬虫设上限。它们常和并发限制、熔断、排队一起出现，但解决的并不是同一个问题。

## 核心原理

### 令牌桶：把速率和突发拆成两个参数

令牌桶的状态只有两个数：当前令牌数 `tokens` 和上次结算时间 `last`。不必真的起一个定时器每秒加令牌，来一个请求时按经过的时间惰性结算即可：`tokens = min(b, tokens + (now - last) * r)`。取到令牌就放行，取不到就拒绝，或者算出还需要等多久。

这个设计把两个原本纠缠的指标拆开了：r 决定长期平均速率，b 决定瞬时能放出多少。r=100/s、b=1 时，输出几乎是一条均匀的线；r=100/s、b=300 时，空闲三秒后可以一口气放 300 个，然后回落到 100/s 的补充节奏。b 越大，系统对突发的容忍越强，但下游必须接得住这 300 个，否则桶只是把排队从入口挪到了更里面。

```python
import time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity
        self.tokens, self.last = capacity, time.monotonic()

    def allow(self, cost=1):
        now = time.monotonic()
        self.tokens = min(self.capacity,
                          self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True, 0.0
        return False, (cost - self.tokens) / self.rate
tb = TokenBucket(rate=100, capacity=300)
print(tb.allow())          # (True, 0.0)
print(tb.allow(cost=500))  # (False, 2.0)：两秒后才够
```

注意初始值是 `capacity`，也就是桶一开始是满的。这会让进程刚启动时立刻放出一个完整突发；有些系统故意从空桶开始，宁可让第一批用户多等一会儿，也不让冷启动叠加流量高峰。

### 漏桶：输出形状由"漏"决定

漏桶也有两个数：当前水位和漏出速率，但语义与令牌桶相反——令牌桶的桶满意味着"额度充足"，漏桶的桶满意味着"没地方排了"。只看计量器版本，水位 = 容量 − 令牌数，进水对应消耗，漏水对应补充，两者可以互相换算，数学上属于同一族。

真正拉开差距的是溢出之后怎么办。nginx 的 [`limit_req`](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html) 明确说明自己用的是漏桶：`rate=1r/s` 表示平均每秒一个，`burst=5` 表示最多允许 5 个请求排队；超出 rate 的请求会被延迟到按设定速率处理，排队数超过 burst 才报错，默认返回 503。加上 `nodelay` 则不再延迟，突发直接放行；1.15.7 之后还能用 `delay=n` 指定从第几个请求开始延迟。这段行为说明漏桶并非"不允许突发"，而是把突发从"立刻放行"改成了"排队、再按恒定速率放行"——代价是延迟，收益是下游看到的流量曲线被抹平。

### 同一个桶的两种写法：GCRA

GCRA（Generic Cell Rate Algorithm）是漏桶的变体，也可以看作令牌桶的等价实现：它不存令牌数，只存一个"理论到达时间" TAT。每来一个请求，就比较 `now` 与 `TAT − (τ + T)`，其中 T 是发射间隔（即 1/r），τ 是突发容差；通过之后把 TAT 往后推一个 T。一个 key 只占一个时间戳，没有后台滴漏进程，天然适合放进 Redis 用 Lua 原子执行——这正是 redis-cell 与不少 Go 限流库的做法。Brandur 在[讲 GCRA 的这篇长文](https://brandur.org/rate-limiting)里特别提醒：多机部署必须用存储端的时间（例如 Redis 的 `TIME`），否则各机器时钟漂移会把正常用户误判成超限。

### 和其他计数方式的关系

固定窗口只维护一个计数器，实现最省事，但窗口边界会翻倍：0:59 打满 100 个，1:01 又打满 100 个，两秒内实际通过了 200 个。滑动窗口日志精确，代价是内存与请求数成正比；滑动窗口计数用前一个窗口的加权值近似，便宜且基本消除边界翻倍。令牌桶与漏桶是"速率 + 容量"模型，状态是 O(1)，更擅长表达"平均速率是多少、允许多大的突发"这两件事。

## 常见考点与误区

- **误区一："令牌桶和漏桶是两种毫不相干的算法"**：从计数器视角看，水位 = 容量 − 令牌，两者可以互相换算，GCRA 更是直接被称为漏桶变体。真正的区别在溢出语义：令牌桶没令牌就拒绝或等待，漏桶满了就溢出，队列版则先排队。面试只答"一个允许突发、一个不允许"会被追问到底。
- **误区二："漏桶绝不允许突发"**：nginx 的 `burst` 就是漏桶的排队容量，配 `nodelay` 时突发会被立刻放行。漏桶限制的是长期输出速率，短窗口内仍可吸收最多 burst 个请求，只是它们要么排队、要么被拒。
- **误区三："桶容量越大越安全"**：容量换的是突发容忍度，不是吞吐。b 一旦超过下游连接池、线程池队列或数据库能吸收的量，限流器就从保护装置变成延迟放大器——请求全被放进来，然后在更深处排队超时。
- **误区四："每台机器限 100 QPS，全局就是 100 QPS"**：N 台实例就是 N×100，负载不均时还会有个别实例先超限。要全局准确就得集中式扣减（Redis + Lua，一次网络往返），或者按实例分摊配额并定期归还，接受一定误差。用本地时钟做分布式判定，同样会被漂移坑。
- **误区五："限流等于并发控制"**：QPS 限制的是到达速率，慢请求会让在途数暴涨。Stripe 同时运行请求速率、并发请求、机队配额与 worker 利用率[四类限制器](https://stripe.com/blog/rate-limiters)，恰恰说明"每秒多少个"和"同时多少个"是两件事。
- **误区六："返回 429 就完事了"**：没有 `Retry-After`、没有剩余额度与重置时间，客户端只能立刻重试，限流反而制造重试风暴。还要区分 429（你超额了）与 503（我过载了）：前者让客户端退避，后者该由服务端主动削减负载。

## 实践建议

- 先定保护目标再选算法：要保护脆弱下游、希望输出平滑，选漏桶队列（如 `limit_req` 的 burst + delay）；要给开放 API 配额、允许短时突发，选令牌桶，b 取"允许的瞬时突发"，常见是 1–10 秒的量；要在 Redis 里用单键判限，选 GCRA。
- 分层设限并逐层递减：入口按 IP 或租户粗粒度挡刷，业务层按用户与接口细粒度保公平，内部按依赖设并发上限；最外层再用并发数或 goodput 兜底，别只盯一个 QPS 数字。
- 参数用实测反推：burst 约等于"下游可接受排队时长 × 下游处理速率"；上线前用 dry-run（nginx 的 `limit_req_dry_run`）观察会拦掉哪些流量，再决定阈值；监控 rejected 与 delayed 的比例，而不只是峰值 QPS。
- 失败要开放：限流依赖的 Redis 挂掉时，降级为本地令牌桶并记日志，而不是把全部请求拒掉；同时准备 kill switch，误伤时能一键关掉限流。
- 错误要可执行：429 响应带上 `Retry-After` 与限额、剩余、重置字段；客户端指数退避加抖动，并对重试流量单独计数，避免重试又被算进正常配额、触发新一轮限流。

*一句话总结：令牌桶与漏桶算的是同一个桶，区别在于溢出时是拒绝还是排队，以及你允许多大的突发。*
