## 是什么

volatile 是 Java 的字段修饰符，只能修饰实例字段和静态字段，不能修饰局部变量，也不能和 final 同时用。它在 Java 内存模型（JMM）里承担的角色很窄：把一个普通字段升级为同步动作，让对这个字段的写与后续读之间建立 happens-before 关系。

一句话直觉：它像公告板上的「最新通知」，保证你看到的是最新一版，但不保证两个人同时改公告板上的数字不会互相覆盖。

典型场景有线程停止标志、初始化完成标志、配置或状态的一次性发布、双重检查锁定（DCL）单例里的引用，以及生产者把数据写好后再置 ready 的握手。它们的共同点是「一个人写、其他人读」，而且读的人只关心「新值有没有到」，不要求多个线程互斥地修改。

需要先划清一条边界：volatile 不是「更轻的 synchronized」。synchronized 同时提供互斥和可见性；volatile 只提供可见性与一部分有序性，不提供互斥，也不会把复合操作变成原子操作。

## 核心原理

JMM 把线程间的交互抽象成一组动作：普通读、普通写、volatile 读、volatile 写、加锁、解锁、线程 start 与 join。两个访问同一变量、至少有一个是写的动作，如果没有被 happens-before 排好序，就叫数据竞争。volatile 的作用，就是在写和读之间补一条边。

规则本身很短：对同一个 volatile 变量 v，写 v 与后续读 v 之间是 synchronizes-with 关系；再叠加程序顺序和传递性，写线程在写 v 之前完成的所有普通写，都会对读到 v 新值的读线程可见。[JLS §17.4](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html) 把这条写成：对 volatile 字段的写 happens-before 后续对同一字段的每一次读。

这里有两个容易被忽略的词：**同一个**和**读到新值**。写 volatile f、读 volatile g 不会建立这条边；如果读线程读到的还是旧值，它就没有和这次新写配对，后面的普通读自然不能指望看到新数据。所以正确的握手必须写成：写线程先写数据，再写 `ready = true`；读线程先读 ready，确认是 true 之后再去读数据。顺序反过来，先读数据再读 ready，等于没有握手。

可以用装车来类比：volatile 写像货物装好后升起「已发货」的旗子，volatile 读像看到旗子之后才去卸货。旗子保证「看到旗子时货物已经装好」，但不保证只有一个人能装货。这也正好解释了 `i++` 为什么不行：它是「读 i、加一、写回」三步，volatile 只让每一步的读和写各自可见，三步之间仍然可能被别的线程插进来。

```java
public class Publish {
    static int data;
    static volatile boolean ready;

    public static void main(String[] args) throws Exception {
        Thread reader = new Thread(() -> {
            while (!ready) { }        // 没有 volatile，JIT 可能把读提到循环外
            System.out.println(data); // 有 volatile，保证看到 42
        });
        reader.start();
        data = 42;                    // 普通写
        ready = true;                 // volatile 写：发布
        reader.join();
    }
}
```

没有 volatile 时，这个循环可能被优化成只读一次 ready，于是永远不退出；也可能退出，却打印出 0。加上 volatile 后，`data = 42` 与 `ready = true` 之间的顺序被固定，读到 true 的线程一定能看到 42。这类 bug 的麻烦之处在于它不总复现，换台机器、换个 JIT 编译阈值，结果就可能变。

有序性方面，JMM 不允许把 volatile 写之前的普通写下沉到它之后，也不允许把 volatile 读之后的普通读上浮到它之前。注意这是「相关访问」的约束，不是「一加 volatile，整段代码就顺序执行」。两个与 volatile 无关的操作仍可被重排，面试里把 volatile 说成「禁止一切指令重排」是不准确的。

硬件层面则没有统一答案。JMM 只规定允许出现的行为，不规定必须发哪条指令。HotSpot 在 x86 上通常把 volatile 读编译成普通 load，在 volatile 写后加一条 StoreLoad 性质的屏障（常见是带 lock 前缀的空操作或 mfence）；ARM 上则常见 `dmb`、`ldar`、`stlr` 一类指令。早期 [JSR-133 Cookbook](https://gee.cs.oswego.edu/dl/jmm/cookbook.html) 给过一张屏障对照表，但作者已注明它只具历史参考价值，别把「volatile 等于四条内存屏障」当成标准答案。

原子性边界也要说清。volatile 的单个读、单个写是原子的，volatile 的 long 和 double 读写也是原子的；但 `count++`、`check-then-act`、以及「两个字段必须一起变」都不在保证范围内。另外，`volatile int[] a` 只让 a 这个引用具有 volatile 语义，`a[0]` 的读写仍然普通；`volatile` 修饰对象引用时，也只保护引用本身，不保护对象内部字段。

DCL 单例是这条规则最经典的应用。`instance = new Singleton()` 在字节码层面可以拆成分配内存、执行构造、把引用赋给字段三步，没有 volatile 时，引用赋值可能先于构造完成而可见，另一个线程看到非 null 就返回，拿到的却可能是构造尚未完成、普通字段还是默认值的半成品。给 instance 加 volatile，等于把「构造完成前的所有写」与「引用发布」绑成一条 happens-before 边。更简单的写法是静态 holder，让类初始化机制替你完成安全发布。

## 常见考点与误区

- **误区一：volatile 保证原子性。** 面试常拿 `volatile int count` 让两个线程各加一万次，问结果是不是两万。答是就错了：两个线程可能读到同一个旧值，各自加一后先后写回，更新就丢了一次。计数器应该用 `AtomicInteger` 或 `LongAdder`；涉及多个字段的不变量，用锁或不可变快照。
- **误区二：volatile 就是「每次读写主内存」，所以是轻量锁。** JMM 的正式表述是 happens-before，不是字面上的主存与缓存刷新，实现可以自由优化。volatile 不阻塞、不互斥，两个线程仍可能同时进入同一段临界区，也保护不了「先检查后执行」。
- **考点三：happens-before 只对同一个 volatile 变量配对。** 写 f、读 g 不会建立边；读到旧值时也没有和这次新写配上。很多人背得出「volatile 保证可见性」，却答不出「可见的到底是哪些写、在什么条件下可见」。
- **误区四：volatile 能保证多个变量的一致快照。** 两个 volatile 字段分别更新，读线程完全可能看到一个新、一个旧。要么把状态封装进不可变对象，用 volatile 引用整体替换；要么用锁把「一起读、一起写」保护起来。
- **考点五：volatile 数组和对象引用保护到哪一层。** `volatile int[] a` 只保护引用，元素读写不是 volatile；`volatile` 的对象引用也只保护引用本身。需要元素级原子性时用 `AtomicIntegerArray`，或用 `VarHandle` 的 acquire/release 模式。
- **考点六：DCL 为什么非要加 volatile。** 因为 `new` 的分配、初始化、引用赋值可能重排，引用先可见会让别的线程拿到半成品；volatile 写把构造完成前的写发布出去。能不用 DCL 就不用，静态 holder 更短也更稳。

## 实践建议

- 只把 volatile 用在「状态旗标、一次性发布、单写多读」这类没有复合不变量的地方。变量名要写出语义，例如 `running`、`initialized`，并在注释里注明它保护哪些数据、配对的写在哪里。
- 计数器用 `AtomicInteger` 或 `LongAdder`；需要「检查再更新」、多个字段联动、读写混合的不变量，用 `synchronized`、`ReentrantLock`，或者把状态做成不可变对象整体替换。不要用 volatile 硬凑一个无锁协议。
- 发布对象优先用 final 字段加安全发布：volatile 引用、静态初始化、并发容器都行；避免在构造器里把 `this` 注册出去。DCL 能不用就不用，holder idiom 更不容易写错。
- 不要用 volatile 数组元素。需要元素级可见性与原子性时，用 `AtomicIntegerArray`，或用 Java 9 引入的 [VarHandle](https://openjdk.org/jeps/193) 的 `getAcquire`/`setRelease`；高频写的 volatile 字段还要注意伪共享，必要时做缓存行隔离。
- 并发假设要用 jcstress 或压力测试验证，别用 `Thread.sleep` 碰运气。代码评审时对每个 volatile 追问三件事：配对的写在哪、读到旧值时走哪条路、这个字段和它保护的数据是不是一起变的。
- 性能上先测量再下结论。x86 的 volatile 读接近普通读，写侧要付屏障成本；高争用下同一缓存行来回失效，可能比想象中贵。若只需要 acquire/release 语义，VarHandle 比完整 volatile 更精细，但别为了这点收益把代码变得难懂。

*一句话总结：volatile 卖的是可见性与有序性，不是互斥；它让写出去的旗子看得见，却管不住读-改-写之间的空隙。*
