## 是什么

TopK 问题是在 n 个元素里选出按某个关键字最大（或最小）的 k 个，通常 k 远小于 n。它要的往往不是一份完整榜单，而是「第 k 名」这条分数线：分数线以上的人可以进决赛，但没必要把所有人按顺序排好。反过来说，如果业务本来就要完整名次，那它就不是 TopK，而是一次排序。

典型场景很多：热搜榜取前 50、从访问日志里找耗时最长的 100 个请求、推荐系统在百万候选里截断召回、监控里找流量最大的几个 IP，以及面试里那句「一亿个数找最大的十个」。这些场景看着相同，约束却不一样：日志是一次性文件还是持续到达的流、原始数组能不能被改动、结果要不要按顺序展示、元素是整数还是带权对象，都会改变答案。

所以动手前先问三件事：结果要不要有序；输入是一次性还是不断到来；能不能修改原数组。这三个答案组合起来，基本就决定了该用哪条路。

## 核心原理

三种解法对应三种「省掉不必要工作」的方式：排序省不掉比较，只能靠库的常数；堆省掉了「除前 k 名之外的所有顺序」；快速选择更进一步，连候选区都不维护，只反复缩小第 k 名所在的区间。

**全排序：把全序都算出来。** 时间 O(n log n)，结果天然有序，实现最简单。它最容易被低估：当 k 接近 n，或者本来就要完整榜单时，排序反而最省事，标准库的实现经过多年优化，常数很小。但当 k=10、n 是一亿时，为了十个数把一亿个数排好，多出来的比较几乎全是浪费。排序是「用全序换通用性」，适合 k 大、需要稳定顺序、或数据量本来就不大的场合。

**大小为 k 的堆：只维护候选区。** 求前 k 大时建小顶堆，堆顶是这 k 个候选里最差的那个，也就是进入榜单的门槛。扫描时先装满 k 个；之后每个元素只和堆顶比一次，不大于门槛就直接丢弃，大于才替换堆顶并向下调整。这里有个常见错法：把所有元素都塞进堆再弹出 k 次，那是 O(n log n)，等于用堆做了一次排序，并没有省。正确做法是堆的容量始终为 k，时间 O(n log k)，空间 O(k)，天然支持流式输入，也不修改原数组。若数据顺序随机，一个元素越往后越难进榜，期望替换次数约为 k·ln(n/k)，实际比较开销常明显低于最坏估计；但 k 与 n 同阶时它会退化成全排序，对象大、比较器贵时每次调整也不便宜。

**快速选择：只进入包含第 k 名的那一侧。** 它借用了快排的 partition：选一个 pivot，把数组分成小于它和大于它的两段，pivot 落在下标 i。若 i 正好是目标位置，答案就定了；若 i 偏小，第 k 名只可能在右段，左段整个丢掉；反之亦然。每轮期望把问题规模减半，总代价是 n + n/2 + n/4 + … = O(n)（平均）。它返回的是「前 k 个的集合」，内部无序；要按顺序展示，再对这 k 个排一次，代价 O(k log k)。最坏情况是 O(n²)：在已排序数组上固定取首尾作 pivot，每轮只削掉一个元素。随机 pivot 只是把最坏情况变成小概率，并没有消除；三数取中可以缓解；确定性的线性保证要靠 median-of-medians，但常数很大；工程里的 introselect（如 C++ 的 `nth_element`）会在深度超限时切换到堆选择兜底。它还会原地打乱输入，并且依赖随机访问，不适合流式数据。

```python
import random

def topk(a, k):
    k = len(a) - k            # 第 k 大 = 升序下标 n-k
    lo, hi = 0, len(a) - 1
    while lo < hi:
        p = random.randint(lo, hi)
        a[p], a[hi] = a[hi], a[p]
        i = lo
        for j in range(lo, hi):
            if a[j] < a[hi]:
                a[i], a[j] = a[j], a[i]
                i += 1
        a[i], a[hi] = a[hi], a[i]
        if i == k:
            break
        lo, hi = (i + 1, hi) if i < k else (lo, i - 1)
    return a[k:]              # 无序的前 k 大
```

这段代码只做选择，不保证 `a[k:]` 内部有序，而且会改动传入的列表；生产代码应当把这两点写进注释或接口约定。

**计数与分桶：换一种坐标。** 如果元素是范围不大的整数，比如考试分数、年龄段、耗时档位，可以开一个长度为 V 的计数数组扫一遍，再从高到低取满 k 个，时间 O(n+V)、空间 O(V)。V 远大于 n 时反而浪费内存；元素是浮点数、字符串或复合对象时也不适用。分布式场景则是另一条线：每个分片先算本地 TopK，再对这批小结果归并。全局前 k 一定落在各分片的本地前 k 里，否则该分片已有 k 个元素比它大，与「它是全局前 k」矛盾；网络传输量是 O(mk)，m 为分片数。

## 常见考点与误区

- **求前 k 大却建了大顶堆。** 这是最典型的翻车点。堆顶必须是当前候选里最差的那个，新元素才有机会把它替换掉；大顶堆的堆顶是候选里最好的，拿它当门槛会把真正的强者误删。记住方向：前 k 大用小顶堆，前 k 小用大顶堆。
- **把堆解法背成 O(n log n)。** 准确说是 O(n log k)：k 是常数时是 O(n)，k 接近 n 时才是 O(n log n)。反过来也不能说「O(n) 的快速选择一定更快」，常数、缓存局部性、是否流式都会让结论翻盘。
- **以为快速选择最坏也是 O(n)。** 它平均 O(n)，最坏 O(n²)；随机化只降低概率，不提供保证。面试追问「如何保证线性」时，要能说出 median-of-medians 是确定性最坏 O(n)，而 introselect 是工程折中：平时用快选，深度超限再兜底。
- **以为选完就有序。** partition 只保证第 k 名就位、两侧大小关系正确，前 k 个内部是乱的；`nth_element` 同理，只保证第 n 个位置及左侧不大于它。要榜单顺序，就再排一次。
- **忽略输入副作用与内存。** 快速选择原地改数组；不能改就复制一份，额外 O(n) 空间，这时堆的 O(k) 反而更稳。流式场景更是如此：数据只来一次，没有「回头再 partition」的机会。
- **把「前 k 个元素」和「前 k 个不同值/高频元素」混为一谈。** 后者要先哈希计数，再对（值，频次）做选择；并列名次怎么算、重复元素算一个还是多个，都要先定义清楚。
- **分布式各片取完 k 个后随手平均或只取最大。** 正确做法是归并各片本地 TopK；每片取 k 个是安全上界，不是随便采样，更不能把各片最大值直接当全局前 k。

## 实践建议

- 先定语义再选型。k 很小且数据流式到来，用大小为 k 的堆；数据一次性、内存放得下、只要集合，用快速选择或 `nth_element`；k 接近 n 或结果必须有序，直接全排序；整数且值域小，考虑计数或分桶；数据分布在多个分片，先本地 TopK 再归并。
- 优先用标准库而不是手写。C++ 用 `nth_element`（只要集合）或 `partial_sort`（要前 k 个有序）；Python 用 `heapq.nlargest` / `nsmallest`，k 不小于 n 时它会直接退化为排序；Java 用 `PriorityQueue` 维护 k 个；Go 用 `container/heap`。库的边界处理和常数通常比现场手写更可靠。
- 堆实现抓三个细节：容量始终为 k、先比较堆顶再决定是否入堆、需要顺序时最后一次性排序而不是反复弹出。高频调用的路径上复用容器，减少分配和扩容。
- 快速选择抓三个细节：用高质量随机源选 pivot；对已排序、逆序和大量重复元素做专项测试，重复多时用三路 partition；设置迭代深度上限并在超限时兜底，别让最坏情况悄悄变成线上超时。
- 用基准测试代替只看 Big-O。同样复杂度下，partition 的顺序扫描和堆的下标跳跃在缓存上的表现差别很大；把 n、k、数据分布、对象大小都纳入压测，才能知道哪条路真的快。
- 别把 TopK 和分位数混了。P99 要的是分位点，不是「最大的 1%」，流式上通常用 t-digest 或 sketch 做近似；精确 TopK 的堆并不能直接回答分位数问题。

*一句话总结：TopK 的关键不是把 n 个排好，而是用最小代价找到第 k 名那道门槛。*
