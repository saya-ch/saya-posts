## 是什么

RAII（Resource Acquisition Is Initialization）是 C++ 里把资源和对象生命周期绑定的做法：构造函数拿资源，析构函数还资源，对象的存储期一结束，清理就必然发生。这里的资源不只是堆内存，还包括文件描述符、互斥锁、socket、数据库连接、临时目录。直觉上，它把"记得收尾"从人的纪律变成了语言规则：只要对象在栈上，栈帧退出就会替你把析构函数跑一遍。

智能指针是 RAII 在堆内存上的标准答案。`unique_ptr` 表示独占所有权，`shared_ptr` 表示共享所有权，`weak_ptr` 不拥有对象、只观察 `shared_ptr` 管理的对象。它们把 `new` 和 `delete` 从业务代码里挪进析构函数，于是提前 return、抛异常、循环 break 这些多条出口都不再需要各写一遍清理。

典型场景很具体：函数打开文件或加锁后可能中途抛异常；工厂返回多态对象；缓存里想持有对象却不想延长它的寿命；回调注册之后要能安全注销。这些场景的共同点是"资源的寿命"和"某段代码是否执行到"并不一致，而 RAII 把两者重新对齐到同一个对象上。

## 核心原理

先看 RAII 为什么在异常下也成立。C++ 的栈展开（stack unwinding）会在异常离开作用域时，按构造的逆序调用所有**已完整构造**的局部对象的析构函数；成员按声明逆序销毁，基类在成员之后销毁。若构造函数本身抛出，这个对象自己的析构不会执行，但已经构造完的成员和基类会正常销毁。这条规则解释了两件事：为什么 RAII 不需要 `finally`，以及为什么"构造函数里先拿 A 再拿 B，B 抛了"通常不会漏掉 A——前提是 A 已经交给一个完整构造的 RAII 成员，栈展开会调用它的析构。反过来说，如果 A 只是裸指针、资源又在构造函数体里手工申请，构造中途抛出就会漏，因为对象尚未完整构造。

析构的可靠性也有边界：`std::exit` 不会展开栈，`longjmp` 会跳过析构，`std::terminate` 直接结束进程；信号处理函数里也不该指望析构。这些是 RAII 的例外，不是日常路径，但面试里常被用来检验你是背了结论还是理解机制。

`unique_ptr` 是最轻的所有权表达。它禁止拷贝、允许移动，默认删除器无状态时通常只占一个指针大小，解引用与裸指针同价。移动只是一次指针交接，源指针随即变为空；被移动过的 `unique_ptr` 不要再解引用。删除器是类型的一部分：函数指针删除器会让对象变大，捕获了状态的 lambda 也会；但换来的是能给 C 接口套上 `fclose`、`close` 这类清理函数。`unique_ptr<T[]>` 会对数组调用 `delete[]`，别把 `new T[n]` 塞进 `unique_ptr<T>`。

常见实现里，`shared_ptr` 是"对象指针加控制块指针"两套东西。控制块里放着强引用计数、弱引用计数、删除器、分配器；拷贝一个 `shared_ptr` 是对强计数的一次原子加，析构是一次原子减；移动则只交接指针，不碰计数。强计数归零时销毁被指对象，但控制块要等弱计数也归零才释放。所以 `weak_ptr` 能安全判断对象是否还活着：`lock()` 会原子地尝试把弱引用提升为强引用，成功就延长生命周期，失败返回空。

```cpp
#include <cstdio>
#include <memory>

struct Node {
    std::shared_ptr<Node> next;
    ~Node() { std::puts("node freed"); }
};

int main() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;   // b 的强计数 = 2
    b->next = a;   // a 的强计数 = 2
    std::printf("a=%ld b=%ld\n", a.use_count(), b.use_count());
}   // 栈退出各减一，两个对象仍互相持有，析构不会打印
```

这段代码不会打印 `node freed`：`a`、`b` 这两个栈上的 `shared_ptr` 销毁后，堆上的两个 `Node` 仍各被对方强引用着，计数停在 1。把其中一条边改成 `std::weak_ptr<Node>`，环就断了——弱引用不增加强计数，对象该销毁时照样销毁。控制块本身会留到弱计数归零，所以 `weak_ptr` 仍然可以安全地问"它还在吗"。

`make_shared` 把对象和控制块放进一次分配，少一次 `new`，缓存局部性也更好；代价是只要还有 `weak_ptr` 活着，整块内存都退不回去，而且它不支持自定义删除器。`shared_ptr` 的删除器存放在控制块里、被类型擦除，所以不同删除器的 `shared_ptr<T>` 仍是同一类型；`unique_ptr` 的删除器则在类型里，这一点常被拿来考"为什么不能把带不同删除器的 `unique_ptr` 塞进同一个 vector"。

还有一个容易忽略的点：`shared_ptr` 的计数操作是原子的，但被指对象不是。两个线程各自拷贝自己的 `shared_ptr` 副本没问题；同一个 `shared_ptr` 实例被一个线程读、另一个线程写（赋值、reset）就是数据竞争。要共享可变对象，锁还是得自己加。

标准措辞与边界可以对照 cppreference 的 [RAII](https://en.cppreference.com/w/cpp/language/raii) 与 [std::shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)。

## 常见考点与误区

- **误区一："RAII 就是智能指针"**：RAII 是一种绑定生命周期的惯例，`std::lock_guard`、`std::fstream`、`std::vector` 都在用；智能指针只是它管堆内存的一个特化。面试若只答"用 shared_ptr 管内存"，会把 RAII 说窄了。
- **误区二："shared_ptr 线程安全，所以对象也线程安全"**：控制块的计数是原子的，被指对象没有任何同步；同一实例的并发读写仍是数据竞争。正确说法是"不同 shared_ptr 实例可以并发操作同一个控制块"。
- **误区三："两个 shared_ptr 指向同一块内存没问题"**：用同一个裸指针分别构造两个 `shared_ptr`，会生成两个独立控制块，各自计数到零、各自 delete，最终二次释放。要共享就从已有的 `shared_ptr` 拷贝，或直接 `make_shared`。
- **考点四："循环引用怎么破"**：把环中一条边改为 `weak_ptr`，通常是"子指父"或"观察者指被观察者"那一侧；`weak_ptr::lock()` 提升后再用，不要长期持有裸指针。
- **考点五："make_shared 有什么代价"**：一次分配、异常安全是优点；弱引用延长整块内存寿命、不能传自定义删除器是代价。对象很大且弱引用长期存在时，先构造对象再交给 `shared_ptr` 反而可能更合适。
- **考点六："enable_shared_from_this 为什么在构造函数里抛 bad_weak_ptr"**：C++17 起，`shared_from_this` 依赖已经关联好的控制块，而构造函数执行时外层 `shared_ptr` 还没接管对象；正确做法是构造完成后由工厂返回 `shared_ptr`，再调用。
- **考点七："基类指针 delete 派生对象"**：多态基类的析构函数必须是 virtual，否则通过基类指针或 `shared_ptr<Base>` 销毁派生对象是未定义行为；`unique_ptr<Base>` 同样受影响。
- **考点八："析构函数能不能抛异常"**：析构函数默认是 `noexcept`，异常逃出析构会直接 `std::terminate`；如果此时正在栈展开，等于二次终止。清理失败只能记录或吞掉，不能把异常抛给调用者。

## 实践建议

- **默认 unique_ptr，确实共享才上 shared_ptr**：所有权唯一时 `unique_ptr` 零开销、语义清楚；函数参数用 `T*` 或 `T&` 表示"不拥有"，用 `unique_ptr<T>` 按值表示"接管"，只有生命周期真需要共同延长时才传 `shared_ptr`。
- **优先 make_unique 与 make_shared**：少写 `new`，异常安全；但给 C 接口（`FILE*`、fd、`SSL*`）配自定义删除器时，用 `unique_ptr<T, Deleter>` 把清理函数写进类型，别手写 try/catch。
- **按声明顺序检查析构依赖**：成员逆序销毁，若 A 的析构会读 B，就让 B 在 A 之后声明，即先构造、后销毁；跨对象的析构依赖则说明所有权没理清。
- **共享所有权要画图**：出现 `shared_ptr` 成环、回调长期持有 `this`、缓存里放 `shared_ptr` 时，逐个问"谁负责断环、谁负责注销"；缓存和观察者用 `weak_ptr`，并在使用时 `lock()`。
- **别为省拷贝传 shared_ptr 值**：传 `const shared_ptr<T>&` 不改变生命周期；只有确实要"多一个所有者"时才按值传。频繁拷贝的计数原子操作在热路径上会被放大。
- **用工具兜底**：ASan 抓 use-after-free 与 double free，Valgrind 的 leak check 抓泄漏，`-fsanitize=address` 下跑异常路径的测试，比代码评审更能发现"某条 return 漏了清理"。

*一句话总结：RAII 把清理押在栈展开上，智能指针把所有权写进类型；计数能替你释放，但替不了你想清楚谁拥有谁。*
