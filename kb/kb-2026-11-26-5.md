## 是什么

缓存分层，是在一次请求的路径上按"离数据源的距离"摆放多级缓存：浏览器与 CDN 在最外层，往内是应用进程内的本地缓存（常称 L1），再是 Redis 这类共享的分布式缓存（L2），最后才是数据库。每层只回答两件事：有没有这份数据，以及这份数据有多旧。一句话直觉：**分层不是在多个地方存同一份数据，而是用副本数量换访问距离**。

典型场景是读多写少、访问高度集中的数据：商品详情、类目与字典表、权限元数据、配置开关。它们单个 key 被反复读，改一次却要很久才改第二次。反过来，余额、库存余量这类每次都要准的数据，放进任何一层缓存都只是在给自己制造对账工作。

分层之后，同一份数据同时存在多个"版本"，而它们的**一致性半径**完全不同：数据库只有一份，Redis 是全局共享的一份（分片与主从另说），本地缓存却是每个进程一份。半径越大，失效要通知的人越多，这正是后面所有麻烦的来源。

## 核心原理

### 命中的叠加，收益却是递减的

一次读请求从 L1 开始，未命中才问 L2，再未命中才回源。设两层命中率为 h1、h2，回源比例约为 (1-h1)(1-h2)，平均延迟约为 h1·t1 + (1-h1)h2·t2 + (1-h1)(1-h2)·t3。这组式子说明两件事：L1 把大部分请求挡在进程内，省掉的是网络往返；而**当 h1 已到 80%，再提到 90%，回源量只是从 20% 降到 10%**，收益减半，却要多维护一条失效通道。分层是否值得，要看这条曲线，而不是看层数。

这里有个容易算错的点：L1 命中之后，L2 根本看不到这次访问，所以不能拿 L2 的历史命中率去推算加入 L1 后的整体命中率。正确做法是看回源 QPS 和每层独立打点，而不是把几个命中率相乘。

### 一致性半径：总部改价，门店招牌要一家家换

把数据库想成总部价目表，Redis 是仓库里的一块共享白板，本地缓存则是每家门店门口的招牌。总部改价只改一次；白板擦一次，所有门店下次来仓库都能看到；但招牌挂在几十家门店门口，你得挨家挨户去换。换的过程中有人没收到通知、有人收到的是上一条通知，门口就会挂着旧价。

这就是本地缓存的核心成本：**失效不再是"删一个 key"，而是"向 N 个实例广播一次删除"**。广播通道通常用 Redis Pub/Sub 或消息队列，而 Pub/Sub 发完即忘、不持久化，消费端断线重连的窗口里消息就丢了；网络分区时，某个实例会带着旧副本继续服务。Redis 自带的客户端缓存（[client-side caching](https://redis.io/docs/latest/develop/clients/client-side-caching/)）用服务端 tracking 记录每个连接读过哪些 key，key 被写时回发失效消息，并且**连接一断就清空该客户端的全部本地缓存**——这个"断开即全清"正是给分区兜底的。自建广播若只抄了"发消息"，没抄"断线全清"，就会留下长期脏副本。

### 写路径：为什么是"先更库，再删缓存"

Cache-aside 的标准写法是读时回填、写时删除，顺序必须先更新数据库、再删缓存（[Azure 的 Cache-Aside 文档](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)专门强调了这一点）。若先删缓存再更新库，删完到提交之间来了一个读请求，它会 miss、读到旧值、再回填，旧值就留在缓存里；先更库后删，这个窗口被压到极小。

那为什么不"更新缓存"而是"删除缓存"？因为两个并发写会乱序：A 写 1、B 写 2，若各自把值写进缓存，到达顺序反了就会留下 1。删除是幂等的，最坏结果只是多一次未命中，而乱序的"写新值"会制造真正的脏数据。这个取舍在分层里同样成立：**失效消息发"删除"比发"新值"安全**。

但"先更库后删"不是零窗口。考虑这个交错：读线程 miss，从库里读到旧值；写线程更新库、删缓存；读线程这时才把旧值回填。缓存从此是旧的，直到 TTL 到期。补丁有几类：延迟双删（再删一次，靠猜时间，不可靠）、订阅 binlog 在提交后异步删（更稳，但仍有延迟）、给缓存值带版本并在回填时做 CAS，以及把 TTL 设短，让窗口有上界。没有哪一种给出强一致，只能把窗口和影响面压到业务可接受。

### 版本号与 TTL 梯度

版本号解决"谁有资格写"：库里的每行带一个单调递增的 version，回填时只在 incoming 不低于 current 时写入。这样两个并发读一快一慢，慢的拿着旧版本回来，不会把新值盖掉。注意它挡不住"删除后无版本可比"的场景——删掉 key 的同时也删掉了比较基准，所以要么保留一个短 TTL 的版本墓碑，要么接受这段窗口。TTL 在这里不是一致性机制，而是**所有失效通道都失败时的最后兜底**。

TTL 也不该每层一样。越靠近请求的层，副本越多、失效越难，TTL 就该越短：本地缓存常见几秒到几十秒，Redis 几分钟，CDN 可以更长。反过来，如果 L1 的 TTL 比 L2 还长，L1 就成了"最难失效且活得最久"的一层，等于把最脏的副本放在离用户最近的地方。

### 每一层都要防击穿

分层会放大未命中：L1 过期的一瞬间，同一个热点 key 的并发请求会一起打到 L2；L2 再过期，就一起打到数据库。所以 singleflight（同 key 只放一个请求回源，其余等待结果）要放在**每一层的回源口**，而不是只包在最外层。空值缓存防穿透、逻辑过期防热点失效、TTL 加随机抖动防雪崩，这些手段在分层下不是选一个，而是每层各自要有。

```python
def read(key):
    ent = l1.get(key)
    if ent and ent.expires_at > time.time():
        return ent.value
    packed = redis.get(key)                 # 值里带版本号
    if packed is None:
        ver, val = db.load(key)             # 回源，读到的可能已是旧版本
        packed = pack(ver, val)
        redis.set(key, packed, ex=300)      # 与写方的删除竞争，靠短 TTL 兜底
    ver, val = unpack(packed)
    l1.put_if_newer(key, ver, val, ttl=3)   # 旧版本不覆盖新版本
    return val
```

这段只展示读路径；写路径是"更库 → 删 Redis → 广播删本地"，删除消息幂等，广播里带版本只是为了少做无谓的失效。

## 常见考点与误区

- **误区一：多一层缓存，命中率一定更高。** 增量取决于访问分布有多集中。若 key 很分散，L1 命中率上不去，却要多维护一条广播通道和一份堆内内存，净收益可能为负。
- **误区二：本地缓存和 Redis 用同一个过期时间。** 越近的层副本越多，TTL 必须更短；同 TTL 会让 L1 在 Redis 已经换新之后还长期保留旧值。
- **考点三：先删缓存再更新数据库行不行？** 不行，删后到提交之间的读会把旧值回填；标准顺序是先更新库、再删缓存。面试官往往接着问"先更库后删就绝对安全吗"，正确答案是仍有回填窗口，要靠版本、binlog 或短 TTL 收敛。
- **误区四：用 Pub/Sub 广播失效就强一致了。** Pub/Sub 不持久化，断线、分区、消费失败都会漏；它只能做到最终一致，且必须配断线全清和 TTL 兜底。
- **考点五：穿透、击穿、雪崩的区别。** 穿透是查不存在的数据，击穿是单个热点 key 失效，雪崩是大量 key 同时失效；分层之后三者会在每一级回源口重复出现，防护要逐层布置。
- **误区六：Redis 挂了，L1 还能顶住。** 能顶一阵，但 L1 容量小、数据旧，且此时所有未命中会直接砸向数据库；这是有损降级，不是无损高可用，必须限流和熔断。
- **考点七：什么数据不该进本地缓存。** 强一致数据（余额、库存可用量、要求立即生效的权限变更）不适合放进每个进程各一份的副本里；这类数据要么只走数据库，要么用带版本校验的共享缓存。

## 实践建议

- **按一致性等级分层，而不是"能缓存就缓存"。** 先给数据分三档：必须强一致、秒级可见、分钟级容忍。只有第三档适合 L1；第二档放 Redis 并配失效；第一档别进缓存。
- **每层独立监控，别只看整体命中率。** 打点记录命中发生在哪一层、回源 QPS、失效消息的延迟与丢失、L1 的堆占用。整体命中率 95% 可能掩盖 L2 已经被打穿。
- **失效通道按"会丢"来设计。** 消费端重连后全量清空本地缓存；消息带版本；删除失败要重试或落 binlog 补偿；再叠一个短 TTL 作为最后兜底。
- **L1 必须有界，且避开大对象。** 用 Caffeine 这类带容量上限和淘汰策略的库（[Caffeine wiki](https://github.com/ben-manes/caffeine/wiki)），按堆内存比例设上限；缓存大 value 会带来复制与 GC 成本，省下的网络时间可能还不够付停顿。
- **把 L2 故障当成必答题。** 演练 Redis 整体不可用时回源会放大多少倍，提前给数据库加连接池上限、熔断和排队上限；否则分层只是把故障推迟到更脆弱的一层爆发。

*一句话总结：分层用副本换距离，收益看回源曲线，代价看一致性半径；越近的层越要短 TTL 和可靠的失效。*
