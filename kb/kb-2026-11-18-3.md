## 是什么

React 里的“闭包陷阱”，指的是某次渲染中创建的回调——定时器、事件监听、Effect 内的异步回调——在此后一直读取**那次渲染**的 props 和 state，而不是最新值。一句话直觉：每次渲染都给组件拍了一张快照，回调是贴在照片背面的便签；屏幕早已换了新照片，便签还粘在旧照片上。

典型场景包括倒计时与轮询、搜索框防抖、WebSocket 订阅、第三方图表的事件绑定。组件明明已经更新了好几轮，回调里打印出来的却还是第一次的值。这类 bug 往往不报错、不崩溃，只是“数据不动”或“条件永远不成立”，因此比抛异常更难排查。

## 核心原理

先回到 JavaScript：闭包捕获的是**变量绑定**，不是变量在某一刻的值。一个函数只要还活着，它引用的外层作用域就不会被回收，里面每个标识符指向哪个变量、那个变量当前是什么，都是确定的。

函数组件不过是一个被反复调用的普通函数。React 每次渲染都会重新执行它，函数体里的 `const count`、参数 `props`、甚至 `setCount` 都是这一次调用新建的绑定。上一轮的作用域不会被“更新”，它只是被新一轮的作用域遮住了。state 确实存在 Fiber 节点上，但你在本次函数体里读到的 `count`，只是 React 在这一次调用时递给你的一份拷贝。所谓“组件更新了”，更新的是下一份拷贝，不是旧闭包里的那个变量。

可以把它想成打印工单：每次渲染打印一张新工单，回调拿着工单上的数字去柜台办事；柜台系统里的余额早就变了，工单不会自动改写。

```jsx
import { useEffect, useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // 这个 count 来自首次渲染，永远是 0
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // 空依赖：Effect 不重建，闭包也不更新

  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

这段代码里，Effect 在首次渲染后启动。回调闭包里的 `count` 绑定值为 0，于是每秒执行的都是 `setCount(1)`。第一次从 0 变 1 会触发重渲染；第二次 `Object.is(1, 1)` 为真，React 通常会跳过这次更新。于是定时器一直在跑，界面却停在 1，而且每次 tick 都在做无用功。

那“把 `count` 补进依赖数组”对不对？它能让回调拿到新值，但代价是每秒销毁并重建一次定时器。重建发生在渲染之后，计时起点被不断推迟，倒计时会漂移，密集更新时甚至等不到下一次触发。这就是闭包陷阱最难受的地方：**补依赖解决了新鲜度，却改变了副作用的生命周期**。

真正要分清的是两类逻辑。第一类，下一次 state 只由上一次 state 推出，比如自增、累加、切换布尔值，用函数式更新 `setCount(c => c + 1)` 即可，回调根本不需要读 `count`。第二类，副作用需要读取最新值、但不想因此重新订阅，可以用 `useRef` 保存一个跨渲染稳定的盒子，在事件或 Effect 边界写入 `ref.current`，回调再读盒子；代价是手动同步，而且在渲染期间读写 ref 会破坏纯函数假设。React 19.2 起还提供了 `useEffectEvent`：它创建的函数始终看到最新的 props 与 state，不参与依赖比较，也不会让 Effect 因此重新订阅，专门用来把“非响应式逻辑”从 Effect 里拆出去。但它只能从 Effect（或另一个 Effect Event）中调用，不能当普通事件处理器传给子组件，也不能在渲染期间调用，这些限制由 lint 规则把关。

还有一处容易漏掉：**清理函数同样属于那次渲染的闭包**。它在卸载或重新同步时读到的，仍是创建它的那一轮的 props 与 state，而不是“卸载那一刻”的最新值。例如只在挂载时启动的轮询，其 cleanup 里拿到的 id 或 token 就是首轮的值；如果你希望按最新参数退订，参数本身就必须进入依赖，让 setup 与 cleanup 成对更新，而不是指望闭包自己刷新。

## 常见考点与误区

- **“依赖数组是控制 Effect 何时执行的开关”**：这是最根深蒂固的误解。依赖数组声明的是 Effect 用到了哪些响应式值，React 用 `Object.is` 逐项比较，决定是否需要重新同步。空数组的准确含义是“没有响应式输入”，不是“保证只执行一次”；开发模式下 StrictMode 还会刻意多跑一轮 setup 与 cleanup 来暴露清理缺陷。
- **“连续调用三次 `setCount(count + 1)` 会加 3”**：不会。三次调用读的是同一个快照，算出来都是 `count + 1`，最终只加 1。函数式更新才会把 updater 排队，依次拿到最新的待处理 state。事件处理里的批处理也不改变这个结论。
- **“函数放进依赖会死循环，所以用 `useCallback` 包一层就行”**：`useCallback` 只稳定函数身份，不改变它内部读到的值。若回调依赖了每次变化的值，`useCallback` 的依赖照样变，Effect 照样重跑；若强行写空依赖，只是把闭包陷阱从 Effect 挪到了回调里。正确顺序是先判断这段逻辑该不该响应式，能移进 Effect 就移进去，不能再用 Effect Event。
- **“清理函数能读到卸载时的最新值”**：不能。cleanup 与 setup 来自同一次渲染，捕获的是同一份快照。典型表现是异步回调在组件卸载后仍去 setState，或 cleanup 里读到的参数与你以为的“当前参数”对不上。
- **“`useRef` 是闭包陷阱的标准答案”**：ref 是逃生舱，不是默认解法。它擅长“我要最新值但不想重订阅”，不擅长“这段派生逻辑本来就不该用 Effect 写”。在渲染阶段写 `ref.current` 还会让组件不再纯粹，并发渲染下可能读到半成品。

## 实践建议

- 打开 `eslint-plugin-react-hooks` 的 `exhaustive-deps`，把依赖数组当成契约而不是噪音。确实要抑制时写清理由，并补一条回归测试；React Compiler 只会做记忆化，不会替你修正错误的依赖语义。
- 能派生就不要同步。由 props 算得出的值直接算，别先塞进 state 再用 Effect 追平；计数、累加、toggle 一律用函数式更新，减少对旧快照的依赖。
- 订阅外部系统时，setup 与 cleanup 必须成对且对称。回调若需要最新值，优先用 `useEffectEvent`（React 19.2+，见[官方文档](https://react.dev/reference/react/useEffectEvent)）；低版本用 ref 包装，不要在渲染中写 ref。
- 异步请求要带 `AbortController`，并在 cleanup 中中止；仅靠一个 `ignore` 布尔量只能挡住 setState，挡不住已经发出去的请求和竞态。
- 复现闭包问题别只靠手点。用假定时器推进到第 N 秒，断言界面值与回调参数；再把组件包进 StrictMode 跑一遍，清理不干净的问题会立刻现形。依赖语义可对照[useEffect 文档](https://react.dev/reference/react/useEffect)，版本变化可查 [React 19.2 发布说明](https://react.dev/blog/2025/10/01/react-19-2)。

一句话总结：闭包捕获的是那一轮渲染的绑定，想让回调看到新值，得换一种读取方式，而不是假装旧快照会自己更新。
