## 是什么

用户态和内核态不是两个进程，而是 CPU 的两种运行特权级。x86 提供 ring 0 到 ring 3，Linux 只用其中两级：应用代码跑在 ring 3，能访问的地址受页表限制，也不能执行改页表、关中断、直接碰设备寄存器这类特权指令；内核代码跑在 ring 0，拥有完整的指令与地址空间权限。

一句话直觉：用户态像写字楼里的租户，只能用自己的房间和水电接口；内核态像物业与配电房，能改总闸、能进任何机房。租户想改线路，不能自己动手，只能填一张报修单——这张单子就是系统调用。

典型场景随处可见：`read`/`write` 读写文件、`socket`/`sendto` 收发网络包、`mmap` 映射内存、`clone` 创建线程、`futex` 等待锁、`ioctl` 操作设备。它们的共同点是：请求的资源或权限不在用户态手里，必须交给内核代做。

关键结论先说：这是一次**同一执行流内的权限切换**，不是换了一个进程，也不是换了一个线程。

## 核心原理

先看硬件做了什么。x86-64 用 [syscall 指令](https://man7.org/linux/man-pages/man2/syscall.2.html)进入内核：系统调用号放在 `rax`，前六个参数依次放在 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`（注意第四个是 `r10` 而不是 `rcx`）。CPU 收到指令后，从 MSR 里取出内核代码段和入口地址，把返回地址存进 `rcx`、把标志寄存器存进 `r11`，再按配置屏蔽部分标志位，跳到内核入口。整个过程由硬件完成，用户代码无法指定跳到哪里，这正是安全边界所在。

但 `syscall` 只改了特权级和指令指针，**并没有换栈**。真正换栈的是内核入口汇编。以 Linux 的 `entry_SYSCALL_64` 为例，它紧接着做四件事：`swapgs` 切到内核的 per-CPU 数据；把用户栈指针暂存到 TSS；在[开启页表隔离（PTI）](https://www.kernel.org/doc/html/latest/arch/x86/pti.html)时切换到内核页表；最后把 `rsp` 指向当前线程的内核栈顶。之后才在栈上构造 `pt_regs`，保存通用寄存器，调用 C 语言的 `do_syscall_64`。这段顺序在[内核入口文档](https://www.kernel.org/doc/html/latest/arch/x86/entry_64.html)和 `entry_64.S` 里都能对上。

为什么非换栈不可？因为用户栈不可信：它可能已被换出、可能越界、可能被恶意构造，内核不能把返回地址和局部变量放在一个用户能改的地方。x86-64 上[每个线程有一份固定大小的内核栈](https://www.kernel.org/doc/html/latest/arch/x86/kernel-stacks.html)，通常是 4 个页共 16KB；外部中断还会切到独立的 per-CPU 中断栈，NMI、双重故障这类事件则走 IST 专用栈，原因同样是"不能假设出事时的栈还可信"。

进入内核后，第一件事不是直接干活，而是校验参数。用户传进来的指针只是个数，内核不能直接解引用：要先 `access_ok` 检查范围，再用 `copy_from_user`/`copy_to_user` 搬运，这期间还要处理缺页、被换出、甚至地址在系统调用中途失效的情况。现代 CPU 的 SMAP 特性会让内核直接访问用户页时触发异常，就是为了逼着代码走这套受控路径。

返回路径分快慢两条：状态干净时用 `sysretq` 快速回到用户态，需要恢复更多状态时退回 `iretq`。两条路都要再做一次 `swapgs` 和（PTI 下的）CR3 切换。

开销就藏在这些步骤里。普通函数调用只压一个返回地址、跳转、再返回；系统调用则要动特权级、换栈、保存和恢复一整组寄存器、切换页表。内核文档明确写到，PTI 下每次进入和退出都要写 CR3，一次写 CR3 是"百周期量级"的成本，还要算上 TLB 与分支预测器被扰动的影响。单次通常在几十到数百纳秒，高频路径上就会变成可观的占比。

这里必须区分两个概念：**模式切换**只改 CPU 特权级，`current` 仍指向同一个任务，地址空间还是自己的，调度器没有参与；**上下文切换**才会换任务、换栈、换地址空间并让出 CPU。一次 `read` 如果数据已在页缓存里，往往只发生模式切换；只有真正阻塞等待磁盘或锁时，才会调用 `schedule()` 发生上下文切换。把两者混在一起，后面的优化判断就全错了。

最后是 [vDSO](https://man7.org/linux/man-pages/man7/vdso.7.html)。内核把一小段代码和一页数据映射进每个进程，`clock_gettime`、`gettimeofday`、`getcpu` 这类调用可以直接在用户态读共享数据完成，根本不执行 `syscall`。所以 `strace` 里看不到它们，seccomp 也过滤不到它们——这不是内核"作弊"，而是把只读的、无副作用的信息下放，省掉整条陷入链路。

下面这段代码直接验证寄存器约定：`rax` 放调用号，返回值也在 `rax`，而 `syscall` 会破坏 `rcx` 和 `r11`，所以内联汇编必须把它们列进 clobber。

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

static long raw_getpid(void)
{
    long ret;
    __asm__ volatile("syscall"
                     : "=a"(ret)
                     : "a"((long)SYS_getpid)
                     : "rcx", "r11", "memory");
    return ret;
}

int main(void)
{
    printf("libc=%ld raw=%ld\n", (long)getpid(), raw_getpid());
    return 0;
}
```

## 常见考点与误区

- **考点：进入内核态有哪几条路？** 标准答案是系统调用、异常、中断三类。系统调用是主动的、同步的；缺页、除零、断点属于异常，被动但同步；时钟中断、网卡中断是异步的。面试常追问"中断算不算系统调用"，正确答案是不算：它没有系统调用号，也不走系统调用表，但同样要经过入口汇编、保存现场，同样在内核态执行。

- **误区：系统调用等于上下文切换。** 这是最高频的错答。系统调用只提权，任务没变；除非内核里睡眠、阻塞或被抢占，否则不会切换任务。把 `read` 一概说成"切进程"，会得出"系统调用一定很贵"的错误结论。

- **误区：系统调用就是一次函数调用，只是多了一层封装。** 错在"只是"二字。函数调用信任调用者，系统调用不信任：入口地址由硬件决定，参数要校验，用户指针要搬运，返回时要恢复完整现场。glibc 的 `syscall()` 包装函数本身确实很薄，但跨过特权边界的那一下才是成本主体。

- **误区：系统调用越少越好，最好做到零系统调用。** 方向对一半。能走 vDSO 的时钟读取、能合并的 `writev`/`sendmmsg`、能批处理的 io_uring，确实省掉了大量陷入；但为了"零 syscall"去忙轮询，会把 CPU 烧在空转上。优化目标是降低单位工作的陷入次数，不是把数字压到零。

- **考点：为什么不能直接读用户指针？** 因为指针值由用户提供，可能指向内核地址、未映射页或正在被换出的页。`copy_from_user` 会做范围检查、处理缺页，并在失败时返回未拷贝字节数；SMAP 则从硬件层面阻止内核误用用户页。答"加个 `if` 判空就行"是典型的安全意识缺失。

- **误区：`int 0x80` 和 `syscall` 差不多。** 在 x86-64 上 `int 0x80` 走的是 32 位兼容入口，寄存器约定不同（参数用 `ebx`、`ecx` 等），还要经过中断门，明显更慢。64 位程序应让编译器或 libc 使用 `syscall`。

- **考点：系统调用能不能被信号打断？** 能。阻塞中的系统调用收到信号会返回 `EINTR`，所以健壮的代码要在循环里重试；这也是"系统调用返回 -1 不一定代表真失败"的经典坑。

## 实践建议

- 先测量再优化。用 `perf` 看内核态占比、用 `strace -c` 看调用次数与耗时分布；但注意 `strace` 本身会放大每次陷入的成本，生产环境更适合 `perf trace` 或 eBPF，别拿调试数据直接当容量结论。

- 高频时间戳优先用 vDSO 路径。`clock_gettime(CLOCK_MONOTONIC, ...)` 在 x86-64 上通常由 vDSO 提供，确认方法是看 `strace` 里有没有对应记录；如果没有，说明没陷入内核，这正是你要的效果。

- 小 IO 要合并。逐条 `write` 改成 `writev`，逐包 `sendto` 改成 `sendmmsg`，高并发磁盘/网络场景评估 io_uring 的批量提交；但批量会增加单次延迟和内存占用，吞吐与尾延迟要一起看。

- 减少无谓的唤醒与锁竞争。线程池、连接池、`eventfd` 通知都可能在高 QPS 下变成 futex 风暴；先看 `/proc/<pid>/status` 的上下文切换计数，再决定是调池大小还是改架构。

- 安全边界别抄近路。驱动或内核模块里任何来自用户态的指针都必须走 `copy_from_user`；应用侧可以用 seccomp 收窄可用的系统调用集合，但要知道过滤本身也有每次调用的检查成本，别在极热路径上叠加过多规则。

*一句话总结：系统调用贵在特权切换与现场重建，不在"进了一次内核"；把它和上下文切换分开，优化才有靶子。*
