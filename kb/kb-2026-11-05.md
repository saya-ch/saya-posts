## 是什么

channel 是 Go 语言内置的、带类型的通信管道，用 `make(chan T)` 或 `make(chan T, n)` 创建。它同时承担两件事：传数据，以及让两个 goroutine 在某个点上会合。无缓冲 channel 的容量是 0，发送方必须等到有人接收才能继续；有缓冲 channel 有一段固定长度的环形槽位，槽位满时发送阻塞、空时接收阻塞。

一句话直觉：它不像邮局门口的信箱，更像便利店柜台上一排固定格数的取餐口——窗口只有一个店员（一把锁），格子满了就挡住后厨，空了就挡住取餐的人。

典型场景包括：用流水线把多个处理阶段串起来，用 fan-out/fan-in 分发任务，用 `close(done)` 广播取消，用容量为 N 的 channel 当信号量限制并发，以及用 worker pool 分发 job。这些场景的共同点是“交接”与“同步”，而不是“堆积”。

## 核心原理

运行时里一个 channel 变量就是一个指针，指向 `hchan` 结构：`buf` 指向环形缓冲区，`dataqsiz` 是容量，`qcount` 是当前元素数，`sendx` 与 `recvx` 是读写下标，`recvq` 和 `sendq` 挂着等待中的 goroutine（用 `sudog` 表示），外加一把互斥锁 `lock` 和一个 `closed` 标志。

一次发送可以拆成三步。先加锁，看 `recvq` 里有没有正在等收的 goroutine：有就直接把值拷到对方栈上、唤醒它、解锁返回，无缓冲 channel 的“直接交接”走的就是这条快路径。没人等但缓冲区没满，就把值拷进 `buf[sendx]`，下标前移后解锁返回。缓冲区也满了，就给自己造一个 `sudog` 挂到 `sendq` 尾部，调用 `gopark` 让出 P，等被唤醒后再重新竞争。接收是对称的：先看 `sendq` 有没有等待的发送者，有就从对方那里取；否则看缓冲区；再否则把自己挂到 `recvq` 上睡眠。

关闭时把 `closed` 置位，唤醒 `recvq` 里的接收者，它们统一读到零值和 `ok=false`；`sendq` 里的发送者被唤醒后则触发 panic。这也解释了为什么“关闭”只能由发送方做：关闭意味着“不会再有新值”，而不是“我不要了”。反过来，close 是一种很便宜的广播：一次关闭能同时唤醒所有阻塞在接收上的 goroutine，不必给每个人各发一条消息，所以取消信号几乎总是用关闭 `done` 来表达。

这里有两项容易被忽略的成本。第一是**拷贝**：只要值经过缓冲区，就是进 `buf` 一次、出 `buf` 再一次；即使无缓冲直接交接，整块值的复制也省不掉。传大结构体，走缓冲就是两次整块搬运，直接交接也要复制一次；传指针才只搬一个机器字。第二是**串行化**：同一个 channel 上的所有收发都要抢同一把 `lock`，goroutine 再多也无法并行通过同一个 channel，这是它和“高性能消息队列”最本质的区别。

`select` 的语义就建立在这套结构上。编译器把每个 case 的 channel 与操作打包，运行时 `selectgo` 先做两件事：生成一个随机的轮询顺序 `pollorder`，再按 channel 地址排序得到 `lockorder`，统一加锁顺序，避免两个 select 互相锁死。然后按 `pollorder` 扫一遍，看有没有就绪的 case。若一个都没就绪且写了 `default`，就走 default；否则给每个 case 挂一个 `sudog` 并睡眠，直到某个 channel 把它唤醒，醒来后再把自己从其余 channel 的等待队列里摘掉。

```go
package main

import "fmt"
func main() {
	a, b := make(chan int, 1), make(chan int, 1)
	a <- 1
	b <- 2
	counts := map[string]int{}
	for i := 0; i < 1000; i++ {
		select {
		case <-a:
			counts["a"]++
			a <- 1
		case <-b:
			counts["b"]++
			b <- 2
		}
	}
	fmt.Println(counts["a"], counts["b"]) // 约 500 500
}
```

这段代码跑一千轮，两个 case 的计数大致各占一半。随机化是为了避免固定顺序把某条分支饿死，但它**不提供优先级**：两个 case 同时就绪时，谁先谁后没有保证。

select 也不是零成本的：每次进入 `selectgo` 都要按 case 数量准备轮询数组、对所有涉及的 channel 加锁，case 越多越贵。把几十条 channel 塞进同一个 select 里做轮询，等于每轮都做一次全量加锁，通常不如按 key 分片、各管各的。

还有一个常被考到的细节：nil channel 上的收发会永久阻塞，但在 `select` 里，nil 分支会被直接跳过。于是可以把某个 case 的 channel 置为 nil，动态“关掉”这条分支，而不必写两套 select。

同步语义也来自这里。Go 内存模型规定：无缓冲 channel 的接收发生在对应发送完成之前；容量为 C 的 channel，第 k 次接收发生在第 k+C 次发送完成之前；close 发生在因关闭而返回零值的接收之前。换句话说，channel 不只是传值，它还是一条 happens-before 边。

## 常见考点与误区

- **误区一：“channel 就是队列，cap 开大点吞吐就上去了”**。缓冲只改变阻塞时机，不改变“一把锁加两次拷贝”的事实；缓冲区越大，积压越隐蔽，背压越晚暴露。被问到“`make(chan int, 100000)` 能不能提速”时，正确答法是先问生产与消费速率、延迟目标，再谈批量与分片。
- **误区二：“close 之后就不能再读了”**。关闭后缓冲区里的元素仍能被读完，之后才返回零值与 `ok=false`；`for range ch` 也是先排空再退出。真正的规则是不能再发送，发送会 panic；重复 close 和 close(nil) 同样 panic。
- **误区三：“谁都能 close”**。从接收端关闭，或多个发送者各自关闭，都是常见 panic 来源。约定是由发送方关闭；多发送者场景用 `WaitGroup` 加一个专门的关闭 goroutine，或者用独立的 `done` channel 广播取消。
- **误区四：“nil channel 会 panic”**。不会，它只是永远阻塞；在 select 里则永远不就绪。这是动态禁用分支的正规写法。
- **考点五：“select 有优先级吗”**。没有。多个 case 同时就绪时伪随机选一个；`default` 表示“都不就绪时走这里”，是非阻塞轮询，不是高优先级。要严格优先，只能嵌套 select：先非阻塞试高优先级，再阻塞等待。
- **考点六：“用 len(ch) 判断有没有数据”**。`len` 只是一个瞬间快照，判断完到真正接收之间，别的 goroutine 可能已经取走或塞满，拿它做正确性判断必然有竞态，只适合监控和日志。
- **考点七：“channel 传的是引用”**。传的是值的副本；map、slice、指针本身是引用语义的句柄，所以看起来像共享，但 channel 并没有做额外的浅拷贝。

## 实践建议

- 共享状态优先用 `sync.Mutex` 或 `atomic`，channel 留给所有权转移、事件通知和流水线。临界区很短时，锁通常比一次 channel 往返更快，也更不容易泄漏 goroutine。
- 缓冲区大小按“可接受的突发量”设，不要凭感觉。握手与取消信号用无缓冲或容量 1；削峰用有界小缓冲，并配合超时或 `ctx.Done()`，避免生产者在满缓冲上永久挂起。
- 每个可能阻塞的发送都要有退出路径：`select { case ch <- v: case <-ctx.Done(): }`。只要有一端可能提前退出，就要保证另一端不会永远卡在 `sendq` 或 `recvq` 里。
- 高吞吐场景先批量再谈 channel：把 N 条消息合成一个 slice 发，或按 key 哈希到多条 channel 分片，减少同一把锁的争用；实在不够，再考虑无锁队列或共享内存加锁。
- 函数签名用方向类型（`<-chan T` 与 `chan<- T`），让“谁负责关闭”在类型层面就写清楚；配合 `go vet` 和竞态检测跑测试。
- 大结构体传指针或下标，不要整块拷贝；同时注意指针会把对象的生命周期交给接收方，别在发送后继续改。

*一句话总结：channel 是同步原语而不是消息队列，理解锁、拷贝与随机选择，才能用对它。*
