## 是什么

WebAssembly（简称 Wasm）是一份可校验的二进制指令格式，也是编译器的一个目标平台：C/C++、Rust、Go、Kotlin 等语言先编译成 `.wasm`，再由浏览器或独立运行时编译成本地指令执行。它可以被想成"一种没有操作系统、没有全局命名空间、默认什么权限都拿不到的 Java class 文件"——能带类型、能带函数表，却不能自己打开文件、拉网络、读环境变量。

工程上还要区分两个层次：单个 `.wasm` 模块是执行单元；组件（component）则在模块之上加了类型化接口，是能跨语言拼装、分发的单元。它最常见的四类场景：浏览器里跑重计算（图像处理、编解码、CAD、游戏引擎）；宿主程序加载第三方插件（代理网关的自定义过滤器、电商的结算函数）；边缘与 Serverless 的轻量函数；以及把已有的 C/C++ 推理或音视频库搬进 Web 与移动端。

## 核心原理

**第一层：为什么能接近原生。** Wasm 不是解释执行的脚本，而是一套类型明确的栈式字节码。模块加载时先做一次线性扫描的验证：栈高度、局部变量类型、分支目标、函数签名全部可静态确定，验证通过才允许编译。这带来两个好处：JIT/AOT 可以省掉大量运行时类型检查与去优化分支；控制流是结构化的（block/loop/if），没有任意 goto，编译器能安全地做寄存器分配。代价也在同一处：数组越界、间接调用签名、整数除零仍要插检查，所以它是"接近原生"，不是"等于原生"。

**第二层：沙箱靠的是地址空间。** 每个模块实例拥有一段连续的线性内存，本质是一块可以增长的字节数组。所有 load/store 都被限制在这段内存里：要么编译器插边界检查，要么用保护页让越界访问直接触发 trap；函数只能跳到模块内已验证的入口，拿不到宿主栈上的指针。模块获取宿主能力的唯一通道是导入表——它想读文件，就得宿主显式传入一个"读文件"的函数；宿主不传，它在语言层面就没有这个能力。WASI 把这套能力做成了标准接口：预打开目录、socket、时钟、随机数，全是显式授予，而不是"整个文件系统默认可见"。

```wat
(module
  (import "host" "now_ms" (func $now_ms (result i64)))
  (memory (export "memory") 1)

  (func (export "checksum") (param $n i32) (result i64)
    (local $i i32)
    (local $acc i64)
    (block $done
      (loop $next
        (br_if $done (i32.ge_u (local.get $i) (local.get $n)))
        (local.set $acc
          (i64.add (local.get $acc) (i64.extend_i32_u (local.get $i))))
        (local.set $i (i32.add (local.get $i) (i32.const 1)))
        (br $next)))
    (local.get $acc))

  (func (export "stamp") (result i64) (call $now_ms)))
```

这个模块只声明了一个宿主导入 `now_ms`，外加一页自己可导出的内存；它能执行计算、能导出内存，却没有文件、网络和系统调用的入口。所谓"默认安全"，指的是模块默认拿不到任何能力，安不安全取决于导入表里究竟放了什么。

**第三层：现状已经不只是"浏览器里的 C++"。** 2025 年宣布的 WebAssembly 3.0 版本线，把垃圾回收、64 位内存、异常处理、尾调用、多内存、宽松 SIMD 收进同一套基线，Kotlin/Wasm、Dart 这类 GC 语言终于可以把对象分配交给 Wasm 自己的堆类型，而不是拖着一整套自制运行时。浏览器之外也不再是实验：Figma 把渲染器、Envoy 把自定义过滤器、Shopify 把商家结算逻辑放进 Wasm，Fastly 与 Fermyon 则拿它当边缘函数的最小执行单元。服务端由 WASI 接管：WASI 0.2 建立在组件模型与 WIT 接口之上，让 Rust 写的组件和 Go 写的组件按接口组合；2026 年 6 月定稿的 WASI 0.3 把 async、stream、future 做进规范 ABI，事件循环由宿主统一驱动，组件之间可以在同一进程内直接调用，不必绕一次网络。但要看清版本现实：0.3 目前只有 Wasmtime 46 等少数运行时默认支持，多数工具链仍在 0.2，而生产里大量模块还停在 0.1 的 `wasi_snapshot_preview1`。

**第四层：启动快不等于免费。** Wasm 的实例化确实轻，但把几 MB 的模块编译成机器码并不便宜。浏览器会先用基线编译器快速起跑、后台再优化；服务端通常预编译成 AOT 产物并缓存，配合池化分配器复用内存，才能把冷启动压到毫秒级。把"Wasm 启动快"当成无条件结论，是压测里最常见的翻车点。

## 常见考点与误区

- **"Wasm 一定比 JavaScript 快"**：面试常让你解释"既然快，为什么不全用 Wasm"。正确答案是分场景：数值密集、分支可预测的热点循环，Wasm 通常能赢；但一旦频繁跨边界调用、每次都要把字符串和对象在两边搬运，胶水成本会吃掉收益，DOM 操作更是只能回到 JS。合理说法是"计算在内、编排在外"。
- **"Wasm 是容器的替代品"**：两者不在同一层。容器打包的是整个用户态文件系统与进程模型，Wasm 只是一个需要宿主提供能力的执行格式；它没有 fork、没有通用系统调用，也管不了网络命名空间。边缘函数和插件适合 Wasm，需要内核特性、GPU 驱动、后台常驻服务的场景仍应留在容器或虚机里。
- **"跑在沙箱里就等于安全"**：沙箱保证的是内存隔离与控制流完整性，不是业务正确性。真正的攻击面是宿主导入的那些函数：一个"读任意路径"的导入等于把沙箱门打开；此外还有内存耗尽、无限循环、侧信道，以及 JIT 自身的漏洞。生产上必须配 fuel/epoch 抢占、内存上限、导入白名单和模块签名，缺一不可。
- **"WASI 就是 POSIX"**：WASI 是能力制接口，默认看不到根文件系统，只有被预打开的目录；0.1、0.2、0.3 三代接口差异很大，`preview1` 只是历史兼容层，不是长期目标。面试里把 WASI 说成"Wasm 版 Linux 系统调用"会被追问细节。
- **"组件模型就是动态链接"**：组件在部署期按 WIT 接口组合，跨语言调用要经过 canonical ABI 的 lifting/lowering，值会被复制、句柄会被转换，并不共享同一地址空间。它解决的是接口与组合，不是符号解析。
- **"GC 提案一来，Java 就能直接跑"**：Wasm GC 提供的是结构化的堆类型和由 Wasm 自己管理的引用，不等于 JVM 的对象头、类加载和反射；语言运行时仍要移植。同理，Python 进 Wasm 往往是把整个 CPython 编译过去，体积与启动成本都要单独评估。

## 实践建议

- 先判场景再选型：单个热点函数耗时超过几十毫秒、已有成熟的 C/C++/Rust 库、或需要让不可信第三方代码跑在宿主里，才值得引入 Wasm；纯表单、纯 IO、强依赖 DOM 的前端没有必要多一层。
- 插件系统按"最小能力"设计：用 WIT 定义版本化接口，导入表只开放确实需要的函数，路径用预打开目录而不是字符串拼接；给每次调用设 fuel 或 epoch 截止时间与内存上限，模块加载前验签、加载后缓存编译产物。
- 性能上先消灭边界往返：把一批小调用合并成一次批量调用，传 TypedArray 而不是逐元素 set；复用实例与内存，避免反复 instantiate；服务端预编译 AOT 并做持久化缓存，浏览器用 streaming compile 与 Brotli 压缩。
- 版本要锁死并做能力探测：服务端明确目标是 `wasm32-wasip1` 还是 `wasm32-wasip2`，别让 0.2 与 0.3 的接口混用；浏览器侧用 `wasm-feature-detect` 判断 GC、Memory64、JSPI 是否可用，准备纯 JS 回退路径，尤其是 Safari。
- 把 wasm 当普通制品管：进 OCI 仓库、带 SBOM 与可复现构建，对宿主导入函数做 fuzz，对模块做超时与内存压测；观测上至少记录实例启动耗时、导入调用次数和 trap 类型。

*一句话总结：Wasm 的护城河不是性能，而是把不可信代码关进一条可移植、可组合、能力受限的边界。*
