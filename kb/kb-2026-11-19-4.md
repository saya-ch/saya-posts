## 是什么

库存扣减是在交易链路中把一定数量的商品从“可售”变成“已承诺”的动作。它的结果不是一个更小的数字，而是一份承诺：这件货已经有人要了，不能再卖给第二个人。把库存当成计数器，是绝大多数设计事故的起点；把它当成一本有状态的账，很多取舍就自然清楚了。

一句话直觉：酒店前台把房间从“可预订”改成“已锁定”，客人入住才转“已住”，到店不来再放回可预订——库存扣减就是这套房态管理，只是并发量高得多。

典型场景包括电商下单、票务锁座、优惠券名额、云资源配额、课程报名。它们共同面对一个约束：判断“还有没有”和“把它占住”必须是一次不可分割的操作，否则并发请求会同时看到“还有”，然后一起把它占掉。库存扣减的设计难点，从来不是那条减法语句，而是围绕它的一整套状态与补偿。

## 核心原理

先看账本。一个 SKU 的库存至少有三个数：available（可售）、locked（已锁定）、sold（已售出），满足 available + locked + sold = total。扣减发生的时点不同，本质是把数量在这些状态之间迁移：下单是 available → locked，支付成功是 locked → sold，超时关闭是 locked → available。只存一个 stock 字段也能跑，但一旦要回答“有多少被未付款订单占着”“为什么可售是 0 却还有货”，就查不出来了。

迁移必须原子。数据库里正确的写法是把判断写进 WHERE，让“读—判—改”发生在同一条语句里：

```sql
-- 1) 同一事务内先落占用记录：唯一索引 (biz_id, sku_id) 让重复请求在这里失败
INSERT INTO stock_hold (biz_id, sku_id, qty, status, expire_at)
VALUES ('O20261119001', 1001, 1, 'locked', NOW() + INTERVAL 15 MINUTE);

-- 2) 再扣库存：判断和修改在同一条语句里，影响行数 0 表示不足，回滚
UPDATE stock
   SET available = available - 1,
       locked    = locked + 1
 WHERE sku_id = 1001 AND available >= 1;

-- 3) 释放：只有 locked -> released 成功的那一次才回补
UPDATE stock_hold
   SET status = 'released'
 WHERE biz_id = 'O20261119001' AND status = 'locked';
-- affected_rows = 1 时，才执行：
UPDATE stock SET available = available + 1, locked = locked - 1 WHERE sku_id = 1001;
```

`UPDATE` 在 InnoDB 里是当前读：它读最新已提交的版本并加行锁，所以两个并发事务会排队，第二个重新判断 `available >= 1` 后失败，返回影响行数 0。很多人的写法是先 `SELECT available` 再在应用里判断，最后执行 `UPDATE stock = stock - 1`。即便包在事务里也不安全：REPEATABLE READ 下普通 SELECT 是快照读，两个事务都读到 1，都认为够，最后都扣成功。事务保证的是原子提交，不是“判断与修改不被别人插队”。要救这种写法，得用 `SELECT ... FOR UPDATE` 把读也变成当前读，或者干脆改成条件更新。

第二个问题是扣减放在哪一步。三种常见选择，风险完全不同：

- **下单就扣**：体验最好，下单即锁定，但未支付订单会占住库存。窗口越长，可售越少，必须配套超时释放。
- **支付才扣**：下单时不占库存，支付回调里再抢。好处是不会被恶意占单，坏处是用户付完钱才发现没货，超卖变成了退款与客诉，而且支付回调会重试，扣减必须幂等。
- **发货才扣**：账面最准，但承诺最弱，超卖要到拣货时才暴露。

多数交易系统选的是“下单锁定、支付确认、超时释放”：把窗口压到十几分钟，用可接受的少卖换取不超卖。这个选择不是技术偏好，而是业务承诺——你更怕卖了发不出货，还是更怕货压在锁定态里卖不掉。

第三个问题是释放。超时未支付要把 locked 退回 available，支付成功要把 locked 转 sold。这两步都必须是“有且仅有一次”的状态迁移，不能是简单的 `available = available + 1`。支付回调可能重复、消息可能重投、定时任务可能重跑，每多执行一次回补，库存就凭空多一件，最终变成超卖。正确做法是给每次占用建一条 hold 记录，用状态字段和条件更新控制迁移：只有 `affected_rows = 1` 的那次才允许动库存，重复请求拿到 0，直接按成功返回即可。hold 表上的唯一索引是最后一道防线，它把“同一订单重复占用”挡在插入阶段。

第四个问题是跨系统。秒杀类场景常在 Redis 做预扣，把绝大多数无效请求挡在数据库之前；Redis 的单线程执行模型让一段 Lua 脚本天然原子。但 Redis 是闸门，不是账本：主从复制默认异步，故障切换可能丢掉最后一段写入；内存压力下键也可能被淘汰。预扣成功的正确含义是“你有资格去创建订单”，而不是“订单已经成立”。真正的账在数据库，Redis 与数据库之间的差异要靠对账收敛，不能假设它们一致。

第五个问题是热点。同一个 SKU 的所有扣减都落在同一行上，行锁把并发排成串行，单行更新能力就是天花板。常见做法是把总量拆成 N 个桶（例如 1000 件拆成 10 个 100），请求按哈希落到桶上，桶空了再换下一个；代价是售罄判断、回补和总量校验都要按桶记账，不能只维护一个总池。

## 常见考点与误区

- **“加了事务就不会超卖”**：错。事务只保证要么全成功要么全失败，不阻止两个事务读到同一个旧值。RR 下普通 SELECT 是快照读，必须用条件更新、`FOR UPDATE` 或唯一约束把判断和修改合成一步。
- **“支付成功再扣库存最安全”**：错。支付时库存可能已经被别人买走，钱收了发不出货，超卖只是推迟暴露；而且回调重试要求扣减幂等。下单锁定、支付确认才是常见解。
- **“回补就是加一”**：错。重复回调、消息重投、补偿脚本重跑都会多加。必须用 hold 状态做条件迁移，只有迁移成功的那一次才回补，并留下流水。
- **“分布式锁能解决超卖”**：能，但不划算。锁把并发串行化，租约过期、续期失败、主从切换丢锁都会引入新问题；单行条件更新本身就是原子的，锁更适合保护跨行、跨资源的复合操作。
- **“Redis 扣成功就等于下单成功”**：错。Redis 可能丢数据，预扣只是挡流量、占名额，最终以数据库为准；没有对账的预扣系统，故障后一定对不上账。
- **“少卖不是问题”**：少卖往往比超卖更隐蔽。释放消息丢失、hold 记录卡在 locked、对账缺失，都会让库存被永久占住；要监控 locked 的账龄，而不是只看可用数。

## 实践建议

- 先写清楚业务承诺：能不能接受超卖、未支付订单最多占多久、释放失败由谁兜底。这三个答案决定扣减时点和窗口长度，比选型更重要。
- 表结构上把“库存”和“占用”分开：stock 表存 available/locked/sold，hold 表存 biz_id、sku_id、qty、status、expire_at，并在 `(biz_id, sku_id)` 上建唯一索引；所有变更写流水，方便对账与追责。
- 释放用“延迟消息 + 定时扫表”双保险：消息负责实时性，扫表按 expire_at 索引兜底消息丢失；扫表要分批、限速，避免大促时和正常交易抢行锁。
- 热点 SKU 再做分桶，不要一上来就分。分桶会让回补、总量校验、售罄标记都变复杂，先确认单行更新真的到了瓶颈。
- 对账要常态化：分钟级比对 Redis 预扣量、DB 的 locked/sold、有效订单量与支付流水，差异写异常表并告警；对账不是故障后的补救，而是最终一致性的组成部分。
- 压测别只看 QPS，盯四个数：超卖件数、少卖率、locked 账龄 P99、回补延迟。前两个是正确性，后两个是资金与体验。

*一句话总结：库存扣减的难点不在减法，而在把“预留—确认—释放”做成一次可幂等、可对账的状态迁移。*
