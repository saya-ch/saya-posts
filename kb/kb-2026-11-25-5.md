## 是什么

批处理与调度是推理服务里绑在一起的两个决定：每个模型步（step）把哪些请求的 token 拼成一批送进 GPU，以及这一步结束后谁离开、谁补进来、谁被临时换出。用一句直觉概括：后厨不是等一桌客人到齐才开火，而是炒好一道立刻补下一道，锅始终不空。

它出现的场景很具体。在线对话要求首字快、出字稳；离线打分只在乎总吞吐，延迟可以放宽；Agent 与 RAG 又会把 prompt 拉到几千甚至几万 token。这三类负载对 TTFT（首 token 时间）与 TPOT（每个输出 token 的平均间隔）的要求完全不同，一套参数不可能都照顾到。

先分清两组词。TTFT 由排队时间加 prefill 时间决定；TPOT 由单步 decode 时间决定，有的系统还用 TBT（相邻两个 token 的间隔）来度量流式输出的平滑度，TPOT 是它的平均值。峰值吞吐（tokens/s）与满足 SLO 的吞吐（goodput）也是两个数，后者才是真正的容量，因为超时返回的 token 并不产生价值。

## 核心原理

### 两段负载：一个吃算力，一个吃带宽

prefill 一次并行处理整段 prompt，矩阵乘足够大，能把 GPU 算力吃满；decode 每步每个请求只算一个 token，算术强度极低。粗算一下：解码一步要读完全部权重和整份 KV 缓存，却只做与批大小成正比的乘加，算术强度大致就是"批大小"这个量级；而 A100 的 FP16 算力除以显存带宽，拐点在一百多 FLOP/字节。于是在常见的几十路并发下，decode 是彻底的显存带宽瓶颈——批越大，权重读取被摊得越薄，单个 token 摊到的成本越低。

这也解释了一个反直觉现象：把批从 1 加到 8，吞吐几乎线性上涨而延迟涨幅很小；从 64 加到 128，吞吐涨得慢，TPOT 却明显变差。前者是在摊薄固定开销，后者已经撞上算力与显存的天花板。

### 静态批的等齐代价

最早的做法是静态批：攒够 B 条请求一起送进去，直到批里最长的那个生成完，才收下一批。长短不一时，先结束的槽位只能空着等。下面这段模拟把 40 条长度 20 到 200 的请求放进 8 个槽位，对比两种策略的完成步数与槽位占用率。

```python
import random

def simulate(lengths, cap=8, continuous=True):
    waiting, running, steps, busy = list(lengths), [], 0, 0
    while waiting or running:
        if continuous:                    # 每步结束都能补位
            while waiting and len(running) < cap:
                running.append(waiting.pop(0))
        elif not running:                 # 静态批：整批清空才收下一批
            running, waiting = waiting[:cap], waiting[cap:]
        busy += len(running)
        running = [n - 1 for n in running]
        running = [n for n in running if n > 0]
        steps += 1
    return steps, round(busy / (steps * cap), 2)

random.seed(7)
lens = [random.randint(20, 200) for _ in range(40)]
print(simulate(lens, 8, False), simulate(lens, 8, True))   # (862, 0.58) (572, 0.87)
```

静态批跑了 862 步、槽位利用率 58%；按步调度 572 步、87%。差距不在算力，而在"等"。

### 连续批处理：把调度粒度从请求改成步

Orca 在 OSDI'22 把这件事讲清楚了：调度器每一步都重新组批，请求完成立刻退出，新到的请求下一步就能进；配套的 selective batching 只对能拼的算子做批处理，避免变长序列互相 padding 浪费。论文在 GPT-3 175B 上报告，同等延迟下吞吐是 FasterTransformer 的 36.9 倍（[Orca, OSDI'22](https://www.usenix.org/conference/osdi22/presentation/yu)）。

但"能中途进出"要有显存支撑。KV 缓存随生成长度动态增长，按连续大块分配会产生严重碎片，一条请求多占几个字节，几十路并发下来就少开好几批。vLLM 把操作系统的分页搬到注意力上：KV 切成固定大小的 block，按需映射，逻辑连续、物理可以不连续，新请求随时能拿到零散的空闲块，还能让同前缀的请求共享块。论文报告同延迟下吞吐提升 2 到 4 倍，KV 浪费接近零（[PagedAttention, SOSP'23](https://arxiv.org/abs/2309.06180)）。

### 混批的副作用与分块 prefill

连续批处理带来一个新问题：prefill 和 decode 挤进同一步。一条 4000 token 的 prompt 做一次 prefill，计算量相当于几千个 decode token；它插进来的那一步，所有正在出字的请求都要多等，TBT 出现尖刺，用户看到的就是"字突然卡一下"。

Sarathi-Serve 的办法是 chunked prefill：把一个 prefill 切成接近等大的小块，每步只放一块，保证每步的 token 预算恒定，新请求可以在不暂停已有 decode 的前提下加入，论文称之为 stall-free。代价是这条请求自己的 TTFT 变长，换来的是整批出字平稳。论文报告在尾延迟约束下，Mistral-7B 单卡容量提升 2.6 倍，Yi-34B 双卡 3.7 倍，Falcon-180B 配流水并行 5.6 倍（[Sarathi-Serve, OSDI'24](https://arxiv.org/abs/2403.02310)）。

### 显存才是批的上限

KV 每 token 的字节数是 2 × 层数 × KV 头数 × head_dim × 元素字节。以 32 层、8 个 KV 头、head_dim 128、FP16 为例，每 token 约 128KB；一条 8K 上下文的请求就是 1GB 左右。所以批大小不是想设多大就多大，而是"剩余显存 ÷ 每条请求的 KV 峰值"，这也是 GQA 能把并发拉上去的原因——它砍的是 KV 头数，不是模型宽度。

KV 不够时调度器只能抢占：swap 把 block 换到 CPU 内存，轮到时再按 PCIe 带宽搬回来；recompute 直接丢掉，等轮到时重跑 prefill。前者慢在搬运，后者慢在重复计算，两者都伤吞吐。成熟的调度器会尽量靠准入控制避免走到这一步，因为一旦频繁抢占，延迟分布就不可控了。

### 排队规则也有讲究

FCFS 实现简单，但一条超长请求会堵住后面所有短请求，这就是 head-of-line blocking。按输出长度最短优先能压低平均完成时间，可生成长度事先不知道，只能拿输入长度和已生成比例去猜。FastServe 用 skip-join MLFQ，以输出 token 为粒度做抢占，并按输入长度决定新任务从哪一级队列进入，减少无谓的降级；论文报告在同平均与同尾延迟要求下，吞吐最高为 vLLM 的 31.4 倍与 17.9 倍（[FastServe](https://arxiv.org/abs/2305.05920)）。这类数字要在同样 SLO 下读，不能直接当产品指标。

### 还有一条路：把两段拆开

prefill 吃算力、decode 吃带宽，放在同一张卡上，资源配比必然有一边浪费。DistServe 把两段分到不同 GPU，各自选并行策略，再按集群带宽安排放置，论文报告在 TTFT 与 TPOT 双约束下能多服务 7.4 倍请求，或把 SLO 收紧 12.6 倍（[DistServe, OSDI'24](https://arxiv.org/abs/2401.09670)）。

## 常见考点与误区

- **误区一：批越大吞吐越高。** 超过拐点后每步耗时随批近似线性上涨，TPOT 逼近 SLO 上限，超时请求变多，goodput 反而下降。批的上限由 KV 显存和尾延迟共同决定，不是单一旋钮。
- **误区二：连续批处理就是动态 batch size。** 不是。它是把调度粒度从"一次请求"降到"一步迭代"，真正的难点在变长序列的 selective batching 与 KV 的动态分配；只改批大小而不改调度点，仍然是静态批。
- **误区三：prefill 和 decode 混在一起无所谓。** 混批会让 decode 的 TBT 出现尖刺，长 prompt 越多越明显。要么用 chunked prefill 把 prefill 摊平，要么把两段物理分离。
- **考点：TTFT 与 TPOT 分别由什么决定。** 该答"排队时间加 prefill"与"单步 decode 时间，含批大小、显存带宽、是否混入 prefill"，而不是笼统说"模型慢"或"GPU 不行"。
- **考点：为什么 decode 是 memory-bound。** 每步读的字节数远大于算的 FLOPs，算术强度约等于批大小，离算力拐点差一个数量级。只答"GPU 利用率低"却说不清瓶颈在带宽，等于没答。
- **误区四：抢占只是把请求挪走。** swap 有 PCIe 搬运成本，recompute 会重复 prefill，两者都会让被抢占请求的端到端延迟变差；频繁抢占说明准入或批参数设错了，不是调度器在正常工作。
- **误区五：只看平均延迟。** 排队系统里 p99 往往比 p50 高一个数量级，而 SLO 通常卡在尾部。平均值达标、尾部超时，用户照样投诉。

## 实践建议

- **先定 SLO 再定 batch。** 固定 TPOT 目标，扫并发上限与 chunk 大小，画 goodput 曲线找拐点；不要直接把并发拉到显存上限，那是吞吐最好看、体验最差的点。
- **把 KV 预算算成一张表。** 每 token 字节 × 峰值上下文 × 目标并发，再留 15% 到 20% 给碎片和突增；同时限制单请求最大长度，避免一条超长请求吃掉整批容量。
- **长短请求分池。** 对话类短请求与文档、RAG 类长 prefill 分到不同实例或不同优先级，别让一条 32K 的 prompt 决定所有人的 TBT。
- **优先级要配老化。** 交互流量给高优先级，离线任务用可抢占的低优先级；抢占时选 recompute 还是 swap，取决于 prefill 贵还是 PCIe 搬运贵，要做一次实测而不是拍脑袋。
- **监控五个数。** TTFT 与 TPOT 的 p50/p99、waiting 与 running 队列长度、KV block 使用率、每秒抢占次数、prefill token 占比。队列持续增长说明准入没做，抢占变多说明批开太大。
- **分离式部署看规模。** 它适合 TTFT 与 TPOT 都要保、且机器足够多的场景；跨机传 KV 有带宽成本，小集群先别拆，先把 chunked prefill 调好更划算。

*一句话总结：批处理省的是重复读权重的带宽，调度保的是每个请求的等待上限，两者只能一起调。*
