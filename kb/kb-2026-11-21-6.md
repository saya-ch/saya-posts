## 是什么

JVM 的垃圾回收算法，要解决的是两个问题：哪些对象已经死了，以及它们留下的空间怎么还回去。HotSpot 判断死亡不靠引用计数，而是从 GC Roots 出发做可达性分析；回收阶段则只有三种基本动作——标记-清除、复制、标记-整理。所谓分代收集，并不是第四种算法，而是把这三者按对象的存活年龄组合起来用。

一句话直觉：标记-清除是「把垃圾原地擦掉」，复制是「把活人整体搬到新楼」，标记-整理是「让活人往前挤、把空位并到队尾」。三者争的是同一笔账：空间利用率、碎片程度，以及搬动对象要付多少成本。

典型场景就在堆里：新创建的对象大多朝生夕死，熬过几轮回收的则长期驻留。算法选错，表现往往不是「回收不掉」，而是停顿变长、分配变慢，甚至明明还有内存却分配失败。回收期间暂停应用线程，就是常说的 Stop-The-World（STW）。还要把算法和收集器分开看：算法是策略，Serial、Parallel、G1、ZGC 是把这个策略工程化的实现。

## 核心原理

### 先判活，再谈回收

可达性分析从一组根出发：虚拟机栈里的局部变量、静态字段、常量池引用、JNI 引用、活着的线程与同步锁对象，都算根。根够不着的对象，才是可回收的。这个过程在并发标记时最麻烦：应用线程还在改引用，标记线程同时在遍历对象图。

HotSpot 用三色抽象描述进度：白色是还没访问，灰色是自己访问过、但字段没扫完，黑色是字段也扫完了。并发时若出现「黑色对象新增一条指向白色对象的引用」，同时「灰色对象到该白色对象的引用又被删掉」，这个白色对象就会被漏标——它明明活着，却没人再能到达它。两个条件必须同时成立，所以只要破坏其中一个即可。

- 增量更新（CMS）：记录「新增」的引用，在重新标记阶段把被插入的白色对象重新扫描。破坏的是第一个条件。
- 原始快照 SATB（G1）：记录「被删除」的旧引用，按标记开始那一刻的对象图来算，新插入的引用不影响旧快照的活性。破坏的是第二个条件。

这些记录靠写屏障完成：JVM 在引用赋值前后插入一小段代码，把「哪张卡脏了」「哪个旧值被覆盖了」记下来。写屏障不是业务代码，却直接决定并发标记的正确性与开销。

### 三种基本算法

**标记-清除**最简单：先标记存活对象，再把未标记的格子收回空闲列表。它不移动对象，代价是碎片——大对象可能找不到连续空间，分配器也得在空闲链表里找洞，分配速度随碎片增加而下降。

**复制**把堆分成两块，回收时把存活对象按顺序搬到另一块，然后整块清空。因为目标区一直用指针碰撞分配，天然没有碎片，分配也最快。代价是算法本身要留出一块等大的备用空间；更关键的是，搬运量正比于存活对象数，存活率一高，复制要搬的字节数逼近整个堆，却仍要多付一块等大空间，性价比就被标记-整理反超。

**标记-整理**先标记，再把存活对象向一端滑动，最后直接改分配指针。它不需要第二块空间，也没有碎片，但移动对象意味着所有指向它的引用都要修正，经典实现只能在这段时间暂停应用线程。

```java
public class GcCopyVsCompact {
    static int copy(Object[] from, Object[] to, boolean[] live) {
        int top = 0;
        for (int i = 0; i < from.length; i++)
            if (live[i]) to[top++] = from[i];
        return top;                        // 顺序摆放，天然无碎片
    }
    static int compact(Object[] heap, boolean[] live) {
        int top = 0;
        for (int i = 0; i < heap.length; i++)
            if (live[i]) heap[top++] = heap[i];
        return top;                        // 原地前移，引用要同步修正
    }
    public static void main(String[] args) {
        Object[] h = {"a", null, "b", null, "c"};
        boolean[] live = {true, false, true, false, true};
        Object[] to = new Object[h.length];
        System.out.println(copy(h, to, live) + " " + compact(h, live)); // 3 3
    }
}
```

HotSpot 的分代正是按存活率分工：新生代对象绝大多数活不过一次 Minor GC，存活率低，复制最划算，于是 Eden 与两块 Survivor 按 8:1:1 划分，每次留出一块 Survivor 作复制目标；对象每熬过一次回收年龄加一，超过 `MaxTenuringThreshold`（默认 15），或 Survivor 里累计到某个年龄的对象超过容量一半（此时该年龄及以上的对象提前晋升老年代）。老年代存活率高，复制会搬走大半对象，所以改用标记-整理（Serial Old、Parallel Old）或标记-清除（CMS）。

分代还带来一个必须解决的问题：新生代回收时，老年代可能持有指向新生代的引用。总不能每次都扫整个老年代，于是用记忆集把跨代引用记下来，卡表是它最常见的形式：一段内存对应一个卡页（HotSpot 里通常是 512 字节），写屏障负责把被写的卡标脏，回收时只扫脏卡。

现代收集器只是把这些算法重新编排。G1 把堆切成大小相等的 Region，整体看是标记-整理，局部回收却是把存活对象从一个 Region 复制到另一个，所以它会报 to-space exhausted；它按回收收益给 Region 排序，先收垃圾最多的，这就是 Garbage First 的字面意思。ZGC 用染色指针和读屏障，把标记、转移、重映射的主体工作都做成并发，停顿通常不到 1 毫秒且基本不随堆变大；JDK 21 的[分代 ZGC](https://openjdk.org/jeps/439) 又把新生代拆出来，让「朝生夕死」这件事继续享受复制的便宜。

## 常见考点与误区

- **「JVM 用引用计数判断垃圾」**：错。引用计数无法处理循环引用，每次赋值还要维护计数；HotSpot 用的是从 GC Roots 出发的可达性分析。
- **「新生代用复制，所以没有 STW」**：错。复制同样要暂停应用线程，它优化的是单次停顿的长度，因为要搬的活对象少；真正把转移做成并发的是 ZGC 这类收集器。
- **「CMS 和 G1 都用 SATB」**：错。CMS 用增量更新，G1 用 SATB；两者破坏的是漏标条件的不同一半，写屏障的时机也不同：前者是写后，后者是写前。
- **「G1 是纯标记-整理」**：不准确。G1 整体是标记-整理，Region 之间靠复制疏散；大对象还会占连续的 Humongous Region，这是它特有的失败模式。
- **「`MaxTenuringThreshold=15` 就是 15 岁才晋升」**：不一定。Survivor 空间紧张时会触发动态年龄判定，累计到某个年龄的对象超过一半就提前晋升，日志里常能看到两三岁就进了老年代。
- **「`System.gc()` 会立刻回收」**：它只是向虚拟机提建议，可能被 `-XX:+DisableExplicitGC` 直接关掉，也不保证在你期望的时刻完成；把内存管理寄托在它身上，等于把不确定性写进代码。
- **「堆越大越好，GC 次数少就行」**：堆大能降低频率，却会拉长单次标记与整理的绝对时间，也更容易撞上容器内存上限；只有 ZGC 这类并发收集器才让停顿与堆大小基本脱钩。

## 实践建议

- **先定目标，再选收集器**：吞吐优先看 Parallel，通用平衡用 G1（[JDK 9 起默认](https://openjdk.org/jeps/248)），停顿敏感且堆大用 ZGC（[JDK 15 起转正](https://openjdk.org/jeps/377)，JDK 21 有分代版）。CMS 在 [JDK 14 已被移除](https://openjdk.org/jeps/363)，别再把它写进新项目的启动参数。
- **把 GC 日志当一等公民**：JDK 9 起用统一日志，`-Xlog:gc*,gc+heap=info,gc+age=trace:file=gc.log:time,uptime,level,tags:filecount=5,filesize=50m`，重点看分配速率、晋升速率、Full GC 的触发原因，而不是只盯某一次停顿。
- **堆参数要成对出现**：`-Xms` 与 `-Xmx` 设成同一个值，避免运行期反复扩缩；容器里用 `-XX:MaxRAMPercentage` 跟随 limit，而不是硬编码一个拍脑袋的 `-Xmx`。新生代不是越大越好，Survivor 变大意味着单次复制要搬更多字节。
- **`-XX:MaxGCPauseMillis` 是目标不是承诺**：G1 会据此调整年轻代大小与 Mixed GC 的 Region 数量，负载突变时照样超时；把它当 SLA 写进合同，迟早要赔。
- **Full GC 频繁先分类再调参**：回收后老年代仍居高不下，优先怀疑泄漏与大对象；回收后能降下来，多半是分配速率过高或堆偏小。用 JFR 的 gc 与 allocation 事件定位，别在生产反复跑 `jmap -histo:live`，那一下本身就是 STW。
- **别忽视 Humongous**：达到 Region 一半大小的对象会占连续 Region，G1 下频繁创建大数组会直接触发并发周期甚至 Full GC；能拆批就拆批，能复用缓冲就复用。

*一句话总结：三种 GC 算法没有高下，只有存活率、碎片与停顿之间的一笔账，分代与收集器都是在按场景换算法。*
