## 是什么

Prompt 的上下文管理（context management），是在每次调用模型之前，决定把哪些 token 放进上下文窗口、以什么顺序排列、保留多久、什么时候压缩或淘汰的一整套决策。它管的不是"指令该怎么写"，而是"指令周围堆了什么"。

一句话直觉：模型的工作记忆像一张书桌，桌子再大，能同时摊开并真正读进去的材料也有限；把整柜档案一次倒上来，只会让当前那张纸更难找。

它重要的场景几乎都长得一样：多轮客服对话里历史越滚越长，代码 agent 每轮都要吞下文件内容、终端输出和报错，RAG 问答要决定召回几条片段、怎么排，few-shot 提示要挑哪几个示例。这些问题的共同点是——候选内容永远多于预算，必须做取舍。

## 核心原理

**第一层，预算是一道四则运算，不是感觉。** 一次调用的输入上限等于窗口减去输出预留，输出同样要吃额度，带思维链的模型尤其明显。账本通常分四块：系统指令与工具 schema（稳定、必留）、检索或文件片段（按相关性排）、对话历史（按时间排）、当前问题与输出预留。举个具体的账：128k 窗口、输出预留 8k、工具定义 6k、历史 20k、检索 60k，剩下 34k 是缓冲。缓冲不是浪费，它是留给突发长文件、长报错和重试的余量；预算表里没有缓冲，线上就会在某次异常输入上直接报超长。

**第二层，注意力不均匀，位置有价。** Liu 等人的 [Lost in the Middle](https://arxiv.org/abs/2307.03172) 发现，关键信息放在上下文开头或结尾时准确率最高，沉到中段会明显下降，曲线呈 U 型。一个常见解释是因果注意力与位置编码共同作用：首尾内容与当前问题的"计算路径"更短，而训练语料里答案也常出现在文末。但要补一个容易被忽略的细节：Chroma 2025 年的 [Context Rot](https://research.trychroma.com/context-rot) 报告在他们的检索变体里并没有观察到显著的位置差异。这说明位置效应依赖任务形态与模型，不能当成物理定律照搬；能照搬的是更硬的结论——他们测了 18 个模型，输入变长时性能在每一个长度档上都退化，而且在 LongMemEval 上，约 300 token 的聚焦提示普遍好于约 113k token 的完整历史。换句话说，**相关性密度比位置技巧更根本**。

**第三层，无关内容不是中性填充。** 同一份报告里，主题相关但不回答问题的干扰片段，只加一条就会掉分，加到四条继续掉；问题与证据的语义越接近，长上下文下掉得越快。类比是在嘈杂的餐厅里等人喊你名字：音量没变，信噪比变了。更反直觉的是，他们把段落打乱后模型反而表现更好，说明结构连贯性会改变注意力分配，长上下文并不是"读得越多越明白"。

**第四层，成本与缓存。** 标准全注意力下，预填充的计算量随长度呈平方增长，KV cache 的显存随长度线性增长，所以长上下文首先贵在首 token 延迟（TTFT）。前缀缓存（prompt caching）能把稳定前缀的计算结果复用起来：以 Anthropic 的显式缓存为例，5 分钟档的写入约为普通输入的 1.25 倍价格，命中读取约为 0.1 倍；OpenAI 则对 1024 token 以上的前缀自动缓存，按 128 token 递增。代价是前缀必须逐字节相同——在开头插一个时间戳或打乱检索顺序，后面全部失效。

**第五层，压缩有三条路，各有各的损失。** 截断最便宜，但会丢掉早期定下的约束；滚动摘要省 token，却容易把数字、单位和否定词抹平；检索式记忆把原文放在外部、按需取回，精准但依赖召回质量。工程上通常是三者混用，再加一份结构化状态：把"用户已确认的约束、已做的决定、待办问题"抽成短 JSON，比保留三十轮寒暄有用得多。

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
count = lambda s: len(enc.encode(s))

def build_context(system, tools, history, docs, budget=32_000, reserve=4_000):
    room = budget - reserve - count(system) - count(tools)
    kept, picked = [], []
    for turn in reversed(history):          # 历史从最新往回取，旧的先丢
        if count(turn) > room: break
        kept.append(turn); room -= count(turn)
    for d in sorted(docs, key=lambda x: -x.score):   # 高分优先
        if count(d.text) > room: continue            # 装不下就跳过
        picked.append(d.text); room -= count(d.text)
    # 历史由旧到新，检索由低分到高分：最好的证据贴着问题
    return [system, tools, *reversed(kept), *reversed(picked)]
```

这段代码的重点不在实现，而在两个顺序约定：历史整体放在检索之前，高分证据放在最靠近用户问题的那一端。前者保住缓存前缀的稳定，后者利用近因效应，让最该被读到的内容不落在中段。

## 常见考点与误区

- **考点：窗口大小与有效上下文不是一回事。** 面试常问"1M 窗口是不是就能塞 1M"，正确答法是标称窗口是硬上限、不是质量承诺；有效上下文要靠评测确定，Context Rot 的结论是每个长度档都在退化，而不是只在接近上限时才崩。
- **误区：把 lost in the middle 简化成"关键内容放头尾就行"。** 位置效应依任务和模型而变，Chroma 就没有复现出显著的位置差异；真正稳的做法是提高相关性密度、把证据贴着问题放，而不是迷信某个固定槽位。
- **误区：摘要一定比原文安全。** 摘要有损，最先被抹掉的往往正是数字、单位、否定、日期和 ID，摘要模型自己还会引入幻觉。要保留可回溯的原文锚点（文件、行号、消息 id），摘要只做索引，不做唯一真相。
- **误区：开了前缀缓存就自动省钱。** 前缀里混入时间戳、随机 ID、动态排序，或者缓存 TTL 到期、长度没到最小可缓存门槛，命中率都会归零。另一个高频混淆是把 KV cache 和 prompt cache 当成一回事：前者是单次推理里的注意力状态，后者是服务端跨请求复用前缀计算。
- **误区：RAG 的 top-k 越大越好。** 召回条数增加会同时带入干扰片段，收益很快被抵消；先去重、再重排、最后按预算截断，比单纯调大 k 有效。
- **考点：输入与输出分开计价，长上下文主要贵在预填充。** 被追问"为什么长 prompt 慢"时，答案是最前面的 prefill 要处理全部输入 token，而解码阶段每生成一个 token 都要读一遍 KV cache。

## 实践建议

- **先写预算表，再写 prompt。** 给系统指令、工具、历史、检索各设配额和淘汰顺序；超预算时先删低分检索片段，最后才动最新指令。没有淘汰顺序的预算表等于没有预算。
- **稳定内容在前，易变内容在后。** 系统提示、工具 schema、固定示例放在最前面并保持逐字节稳定；时间戳、请求 ID、动态排序统统挪到后面，否则每次调用都是一次冷启动。
- **关键约束"开头立规矩、结尾再点名"。** 结尾复述一次最容易被遵守，但不要在三处重复同一句话，重复会挤占预算，也会让模型分不清哪条才是重点。
- **历史用"结构化状态 + 按需检索"。** 每轮抽取已确认约束、已做决定、未决问题，原文落到外部存储；需要细节时再取回原始片段，而不是把整段对话反复喂进去。
- **压缩要分级。** 数字、ID、否定、日期、金额不压缩；寒暄、重复确认、已完成的工具输出可以整段丢。压缩后做一次自检：把摘要和原文分别喂给模型，看答案是否一致。
- **评测做二维扫描。** 长度取 4k、16k、64k，位置取头、中、尾，画准确率曲线而不是只测一个点；线上再盯缓存命中率、平均输入 token、首 token 延迟和单任务成本这四个指标。

*一句话总结：上下文管理的目标不是把窗口填满，而是让每一千个 token 都离问题更近一点。*
