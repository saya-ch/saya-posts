## 是什么

Rust 的所有权是一组编译期检查的内存管理规则：每个值都有唯一的负责人，负责人离开作用域时值被释放；赋值、传参、返回默认不是复制，而是把这份责任交出去。把它想成一本书的归属会更直观：你可以把书送给朋友，自己手上就没有了；也可以只借出去几天，书仍然是你的，只是这段时间你不能同时把它转卖或撕掉重写。

这套规则要回答的不是"内存怎么申请"，而是"谁负责释放、并且只释放一次"。它最常出现的场景都在边界上：配置结构体交给构造函数、缓冲区送进线程、集合交给迭代器消费、函数算出一个 String 返回给调用方。只要数据跨越一次函数边界，所有权就要么被移动，要么被借用。

## 核心原理

**三条规则，一次 drop。** 每个值有且只有一个 owner；同一时刻不能有两个 owner；owner 离开作用域时，编译器插入 drop 调用，把值占用的资源释放掉。编译器还会跟踪某个位置上的值是否仍然有效，所以一个已经被移走的值不会被重复 drop，也不会在作用域结束时再释放一次。

**move 搬的是值本身，不是堆。** 以 String 为例，栈上只有三样东西：指向堆的指针、长度、容量；真正的字符数据在堆上。执行 `let s2 = s1;` 时，编译器按位复制这三个字段，然后把 s1 标记为已失效。堆上那串字节一个也没有动，所以这次"移动"的代价接近一次指针拷贝，而不是 O(n) 的深拷贝（[Rust Book 第 4.1 节](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html) 用 String 演示了这个过程）。之后再用 s1 会得到 E0382 编译错误——这正是 Rust 避免 double free 的方式：既然只有 s2 是 owner，就只由 s2 负责释放。需要留意的是，move 的成本与值本身的大小成正比：一个内联在栈上的大数组被移动时，那几十万字节仍然要搬一遍，只是它指向的堆数据不会被递归复制。

**借用是把使用权借出去，不交出所有权。** `&T` 是共享借用，可以有多个，但只能读；`&mut T` 是独占借用，同一时刻只能有一个，而且此时不能有任何共享借用。规则合起来就是"共享不可变，可变不共享"。原因并不抽象：Vec 在 push 时可能重新分配缓冲区，如果此时还留着一个指向旧缓冲区的 `&v[0]`，这个引用就会悬空；编译器干脆禁止"读引用还活着的时候去改容器"（[借用规则](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)）。现代 Rust 用最后一次使用位置来判断借用何时结束，所以借用范围通常比变量作用域短得多，这也是很多"看起来冲突"的代码稍微调整顺序就能通过的原因。

**函数签名就是所有权契约。** 只看参数类型就能知道调用方付出了什么：`&Config` 是只读借用，调用后原值还在；`&mut Config` 是把修改权临时交出去；`Config` 是按值接收，调用方要么把值交出去，要么显式 clone。标准库把这套契约做进了 API：`iter()` 借出元素，`iter_mut()` 借出可写元素，`into_iter()` 则直接消费集合。返回引用时，签名还必须交代这个引用能活多久，这是生命周期标注要解决的问题。

```rust
#[derive(Debug)]
struct Config { addr: String, workers: usize }

fn start(cfg: Config, port: u16) -> Config {   // 按值接收，拿走所有权
    println!("listen on {}:{}", cfg.addr, port);
    cfg                                        // 再把所有权交回调用方
}

fn describe(cfg: &Config) -> usize { cfg.workers }  // 只借不拿

fn main() {
    let cfg = Config { addr: "0.0.0.0".into(), workers: 4 };
    let n = describe(&cfg);        // 共享借用，cfg 仍然可用
    let cfg = start(cfg, 8080);    // 所有权移入，再随返回值移出
    println!("{n} workers on {}", cfg.addr);
}
```

如果调用后不接返回值、直接再用原来的 `cfg`（例如单独写一行 `start(cfg, 8080);`，随后打印 `cfg.addr`），编译器就会报 "borrow of moved value"。修法不是随手 clone，而是先问：这个值到底该由谁持有到最后。

**Copy、Clone 与共享所有权。** 整数、bool、char、由它们组成的元组，以及共享引用 `&T`，都实现了 Copy：赋值时按位复制，源变量继续可用。Copy 是隐式的、不能重载、也不能和 Drop 共存，所以 String、Vec 这类持有堆资源的类型永远不是 Copy（[Copy trait](https://doc.rust-lang.org/std/marker/trait.Copy.html)）。Clone 则是显式调用，可以执行任意代码、可以分配内存。需要多个 owner 时，才轮到 Rc 与 Arc：前者用非原子计数，只适合单线程；后者用原子计数，可以跨线程，但每次 clone 都有原子操作的成本。

## 常见考点与误区

- **误区一："move 就是深拷贝"**：恰恰相反，move 只按位复制值本身，堆上的数据留在原地，然后让源变量失效；clone 才会复制堆数据。面试里常追问"为什么 Rust 赋值后原变量不能用了"，答"防止 double free"只对了一半，另一半是编译器用失效标记把释放责任唯一化。
- **误区二："给类型加上 Clone，赋值就不会失效了"**：Clone 不改变移动语义，只是让你能显式复制；要让赋值后源变量仍可用，类型必须实现 Copy。而 Copy 要求类型没有 Drop，所以带堆分配的类型做不到；`#[derive(Copy, Clone)]` 加在含 String 的结构体上会直接编译失败。
- **误区三："变量被 move 之后，内存马上就释放了"**：move 只是换了个 owner，drop 发生在新 owner 离开作用域时。真正会立刻释放的是"值被新值覆盖"这种场景，旧值在赋值那一刻就 drop 了。这也是为什么把大对象移进一个长生命周期的容器，会让它的内存比预期活得更久。
- **误区四："`&mut T` 和 `&T` 一样，可以随便复制、随便传"**：`&T` 是 Copy，`&mut T` 不是。把 `&mut` 传给一个签名要求 `&mut` 的函数时，发生的是隐式重借用，函数返回后原来的可写借用还能继续用；但同一时刻存在两个活跃的 `&mut` 指向同一个值，编译器一定拒绝。面试常问"为什么可变引用不能别名"，标准答案是避免数据竞争与迭代器失效，而不是"Rust 实现起来方便"。
- **误区五："借用检查有运行时开销，Rust 其实带了个 GC"**：借用、生命周期、drop 插入都在编译期完成，运行时没有追踪式 GC，也没有引用计数，除非你显式用了 Rc/Arc。Rc 的计数是实打实的运行时开销，而且 Rc 不是 Send，不能跨线程共享。
- **误区六："结构体移出一个字段后，整个结构体还能继续用"**：字段被移出后结构体处于部分移动状态，未移动的字段仍可访问，但整体不能再使用；实现了 Drop 的类型则根本不允许把字段移出去。

## 实践建议

- 先定归属，再选签名。只读参数用 `&T`、`&str`、`&[T]`，需要修改用 `&mut T`，需要存起来或消费就用按值；函数返回新值时把所有权交给调用方，不要返回局部变量的引用。
- 把 clone 当成设计信号而不是编译错误的橡皮擦。先试着缩短借用范围、调整语句顺序、用 [`mem::take`](https://doc.rust-lang.org/std/mem/fn.take.html) 或 `mem::replace` 从 `&mut` 里取出值，或者用 `Cow` 延迟复制；热路径上的 clone 要用基准测过再决定。
- 只有真的需要多个 owner 时才上 Rc/Arc。能通过 channel 把数据所有权移进线程，就不要共享；用 `Arc<Mutex<T>>` 时把锁的范围缩到最小，避免一把全局大锁把并发打回串行。
- 跨线程的闭包用 `move` 捕获，传 owned 数据或 Arc；不要把栈上的借用塞进 `thread::spawn`，编译器会用 `'static` 要求拦住你，这个报错是保护而不是障碍。
- 需要"取出再放回"时用 `Option::take` 或 `mem::take`，比 clone 一个默认值再覆盖更清晰，也避免了不必要的分配。

*一句话总结：所有权把"谁负责释放、能借多久"写进了类型，编译期算清账，运行时才敢不要 GC。*
