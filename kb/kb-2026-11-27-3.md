## 是什么

缓存是在数据库前面加的一层吸收层，正常情况下绝大多数读请求在这里就被挡回去了。所谓穿透、击穿、雪崩，说的是这层吸收层在三个不同位置破了洞，结果都是流量绕过缓存砸到数据库，但“为什么没挡住”完全不同。

**缓存穿透**指请求的 key 在缓存和数据库里都不存在。既然数据库也查不到值，就没有东西可以写回缓存，于是这个 key 的每一次请求都会原样落到数据库上。它最常见于伪造 ID、负数参数、爬虫遍历不存在的商品，属于“数据维度”的洞：不是缓存没存，而是根本没有可存的东西。

**缓存击穿**指某个被高频访问的 key 恰好在某一刻过期或被淘汰。在重建完成前的这一小段时间里，所有并发请求同时未命中，一起回源。它的范围只有一个 key，但请求量高度集中，属于“单点时间”的洞。

**缓存雪崩**指大批 key 在同一个时间窗口集中失效，或者缓存实例整体不可用。前者是过期时间被写成了同一个值，后者是整层缓存消失，两者都会让全站或大范围的读流量同时压向数据库，属于“大范围时间”的洞。

## 核心原理

可以用便利店来理解：缓存是货架，数据库是后仓。穿透是顾客要买店里根本不进货的商品，店员每次都白跑一趟后仓；击穿是最畅销的那款刚好卖空，一瞬间所有顾客都催着你去后仓拿；雪崩则是一整排货架同时补货或者干脆停电，所有顾客一起涌向后仓。三种情况后仓都很挤，但该修的是选品、补货时机，还是货架本身的供电，方案并不一样。

先算一笔放大的账。假设一次数据库查询耗时 5 毫秒，某个热点 key 的读流量是每秒 1 万次，它过期后的一秒内如果没有保护，数据库要承接 1 万次查询，等于 50 个核·秒的计算量，需要约 50 个并发连接整整忙一秒。缓存平时把这条曲线压成一条平线，失效瞬间却把它还原成尖峰，这就是三类故障共同的破坏力来源。

**穿透：不存在的 key 没有可缓存的值。** 空值缓存是最直接的办法：查不到也写一个带短 TTL 的空值标记，让后续同样的请求在缓存层就被挡下。但它只对“重复请求同一个不存在的 key”有效，攻击者每次换一个随机 key，缓存里就会塞满永远命中不了第二次的垃圾，反而挤掉真正的热数据。布隆过滤器解决的是另一面：把数据库里存在的 key 先哈希进一个位数组，请求进来先问它。它回答“不存在”时一定正确，回答“可能存在”时则可能是假阳性。因此它能把绝大多数不存在的 key 挡在缓存之前，代价是少量假阳性仍会放行，而且标准布隆过滤器不支持删除——把某一位清零会连带影响其他 key。

**击穿：热点 key 的过期瞬间，重建被并发放大。** 关键在于“重建”这个动作被重复执行了。缓存击穿的本质不是缓存失效，而是失效后没有把并发的回源合并成一次。单飞（singleflight）或互斥锁做的就是这件事：同一个 key 只放一个请求去查数据库，其余请求等待并共享结果。等待期间还要做一次双重检查，因为排在后面的请求拿到锁时，缓存可能已经被前一个人填好了。

```go
var group singleflight.Group

func Get(ctx context.Context, key string) (string, error) {
    if v, ok := local.Get(key); ok {
        return v, nil
    }
    v, err, _ := group.Do(key, func() (any, error) {
        if v, ok := local.Get(key); ok { // 等锁期间可能已被别人回填
            return v, nil
        }
        row, err := db.Query(ctx, key)
        if err != nil {
            return nil, err
        }
        local.Set(key, row, jitter(30*time.Minute))
        return row, nil
    })
    if err != nil {
        return "", err
    }
    return v.(string), nil
}
```

这段代码的合并范围只是单个进程。多实例部署时，每个实例仍会各自放一个请求回源，要跨实例合并就得用分布式锁，或者干脆改成逻辑过期：key 不设物理 TTL，把过期时间写进 value，读到过期数据先返回旧值，再由后台异步刷新。后者用短时间的数据陈旧换取了请求不被阻塞，适合对一致性要求不高的商品详情、排行榜。

**雪崩：失效时间对齐，或者整层缓存消失。** 如果一百万条数据在同一批预热中写入，TTL 都设成 30 分钟，那么 30 分钟后它们会在同一分钟内陆续到期，缓存命中率会像断崖一样掉下去。给 TTL 加随机抖动，就是把这条垂直的断崖摊成一段缓坡：在基础 TTL 上浮动百分之十到二十，同批写入的 key 就会分散到不同时刻失效。但抖动只解决“同时过期”，解决不了“缓存整体挂了”。实例宕机、主从切换、网络分区时，所有 key 一起消失，这时候能救数据库的不是 TTL，而是熔断、限流、多级缓存和降级预案。

**三类工具为什么不能互换。** 布隆过滤器只能判断“这个 key 是否存在”，对存在的热点 key 过期毫无作用；互斥锁只能合并同一个 key 的重建，面对几万个同时失效的不同 key，锁的粒度对不上；TTL 抖动只能打散过期时刻，对根本不存在的 key 无的放矢。判断故障类型，比背方案更重要。

## 常见考点与误区

- **误区一：把三者当成同一件事，按 QPS 大小来分。** 面试里常问“击穿和雪崩有什么区别”，答“一个量小一个大”只对了一半。更准确的区分是：穿透看数据是否存在，击穿看是否单个热点 key 失效，雪崩看是否大范围 key 同时失效或缓存层不可用。分类维度错了，后面选方案必然错。
- **误区二：空值缓存能根治穿透。** 它只能挡住重复的同一个 key。随机 key 攻击会污染缓存、挤占内存，而且数据库后来真的写入了这条数据时，空值标记还会造成一段脏读窗口。正确做法是空值短 TTL、写路径主动删除标记、前置参数校验与限流，再配合布隆过滤器。
- **误区三：布隆过滤器是精确的，而且可以删元素。** 它只有“不存在”是确定的，“存在”可能是假阳性；标准实现不能删除，因为多个 key 共享同一批位，清零会误伤别人。要删除得上计数布隆之类的变体，或者定期重建。重启后位数组为空，如果不预热，等于全部放行。
- **误区四：加了互斥锁就不会击穿。** 锁只让一个请求去重建，其余请求仍在等。如果重建慢，等待会从数据库转移到应用线程池，把接口超时和连接池一起拖垮。锁必须有超时、失败降级和双重检查；跨实例部署时，进程内的锁根本不合并。
- **误区五：TTL 加了随机就防住了雪崩。** 抖动只管“同时过期”，管不了实例宕机、主从切换和网络分区。缓存整体不可用时，唯一能保护数据库的是它前面的限流、熔断和容量隔离，以及本地缓存这类第二层缓冲。
- **误区六：逻辑过期等于数据永远新鲜。** 它明确牺牲了一致性，读到的是旧值。异步刷新失败、刷新任务堆积、写后读旧，都需要额外的重试、告警和业务容忍度评估。

## 实践建议

- **先分类再看板。** 分别统计缓存命中率、空命中率、单 key 回源 QPS 和整体回源 QPS。空命中率异常升高优先查穿透；某个 key 的回源出现尖刺查击穿；回源曲线整体抬升且伴随大量 key 失效查雪崩。没有这几个指标，调参就是盲猜。
- **穿透做三层。** 入口做参数合法性校验和频率限制；中间用布隆过滤器拦不存在的 key，容量按实际 key 量的数倍预估并定期重建；最后用 30 到 60 秒的空值缓存兜住重复请求，写路径记得删标记。
- **击穿按热度分级。** 用采样或本地计数找出热点 key，对它们采用逻辑过期加后台刷新，或者单飞/分布式锁重建。锁的等待时间要短于接口超时，重建失败时返回旧值或走降级，不要让请求无限排队。
- **雪崩要留后手。** TTL 加百分之十到二十的抖动；热点数据预热；部署本地缓存作为第二层；给数据库连接池设硬上限，并在入口配置熔断和限流。定期做“缓存全挂”的演练，确认降级开关真的能打开。
- **把缓存当加速层，不当存储层。** 任何缓存方案都要回答“它失效时系统靠什么活着”。数据库前的最后一道闸——连接数上限、排队超时、只读降级——平时看起来多余，故障时就是唯一的刹车。

*一句话总结：穿透缺的是数据，击穿缺的是合并，雪崩缺的是分散与兜底；先分清病灶，再选工具。*
