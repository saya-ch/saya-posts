## 是什么

虚拟 DOM 是拿 JavaScript 对象描述界面的一棵内存树：每个节点记着类型、属性、子节点和 key，渲染时再由框架翻译成真实 DOM。它像一份可以反复改写的施工图，真正动工前先把新旧两版图纸叠在一起，标出哪些墙要拆、哪些家具只是挪位置。

这里要拆开三个概念：虚拟 DOM 是“用对象描述 UI”的数据结构；diff 是比较新旧两棵树、得出变更的算法；key 则是告诉 diff “这两个节点是不是同一个东西”的身份标记。三者常被混成一句“虚拟 DOM 很快”，但快不快从来不是这个数据结构自带的属性，而是整套更新策略的结果。

典型场景是列表渲染：表格排序、消息流插入、拖拽换位、分页加载。只要界面由数据驱动、又需要频繁局部更新，就绕不开“怎么在一堆相似节点里认出谁是谁”。

## 核心原理

### 同层比较：把三维问题压成一维

最直观的 diff 是求两棵树的编辑距离：删除、插入、替换节点，找总代价最小的操作序列。但有序树的编辑距离要在子树之间做动态规划，量级远高于线性；React 官方文档直接把这类“state-of-the-art”算法概括为 O(n³) 量级（[Reconciliation](https://legacy.reactjs.org/docs/reconciliation.html)）。界面每帧都可能更新，没人愿意在每次 setState 后跑一遍这样的算法。

于是主流框架都退到同一个启发式：**只在一个父节点的子列表内部比较，不跨父节点找“这棵树是不是搬走了”**。更准确地说，“同层”不是绝对深度相同，而是“同一个父节点的 children 数组内”。父节点匹配上了，才递归比较它的孩子；如果某个节点被移到另一个父节点下，旧父节点的列表里少了一个、新父节点的列表里多了一个，diff 只会看到一次卸载加一次挂载，不会追过去复用。

这带来两条硬规则。第一，**类型不同，整棵子树重建**：`<div>` 换成 `<section>`，或 `<ComponentA>` 换成 `<ComponentB>`，框架不会尝试把里面的状态迁过去，而是卸载旧的、挂载新的。第二，**类型相同、身份对得上，才谈复用**：类型相同且身份一致，就保留底层 DOM，只更新变化的属性，再递归 children。

### key：在子列表里认人

只有类型还不够。一个列表里的十个 `<li>` 类型完全相同，框架必须知道“新的第三个节点”对应旧的哪一个。key 就是这份身份契约：key 相同且类型相同，才复用同一个 DOM 节点和组件实例；key 不同，哪怕位置没变，也按新建处理。

React 主要靠一趟扫描：先按位置快速对齐前缀，再给剩余旧子节点建一张 key 到旧 Fiber 的映射，按新顺序逐个查表；查到了且类型一致就复用，查不到就新建，最后把表里剩下的旧节点删掉。它用一个 `lastPlacedIndex` 记录“已经就位的旧下标”，发现当前节点的旧下标更小，就给它打上移动标记。整个过程没有最长递增子序列，因此某些重排会多搬几个节点，但同一次提交里每个节点最多搬一次。

Vue 3 的 keyed diff 分五步：先从两端同步首尾相同的节点，再处理“旧节点用完、新节点还有”和“新节点用完、旧节点还有”两种收尾；剩下中间那段乱序区，先建 key 映射，再遍历旧节点记录“新位置对应哪个旧位置”，最后对这份旧下标序列求最长递增子序列（LIS）。LIS 里的节点相对顺序没变，可以原地不动；不在 LIS 里的才需要移动（新节点则直接挂载）。这样 DOM 移动次数被压到“需要动的节点数”，而不是“整段重排”。这条路径在 Vue 的 [renderer.ts](https://github.com/vuejs/core/blob/main/packages/runtime-core/src/renderer.ts) 里对应 `patchKeyedChildren` 与 `getSequence`。

一段简化代码能看清 key 映射这一层：

```js
// 简化版：key + type 都匹配才复用；index 不参与身份判断
function diffChildren(prev, next) {
  const oldByKey = new Map(prev.map(n => [n.key, n]));
  const ops = [];
  for (const node of next) {
    const old = oldByKey.get(node.key);
    if (old && old.type === node.type) {
      oldByKey.delete(node.key);
      ops.push(`reuse ${node.key}`); // 实际实现还要判断是否需要 insertBefore
    } else {
      ops.push(`mount ${node.key}`);
    }
  }
  for (const key of oldByKey.keys()) ops.push(`unmount ${key}`);
  return ops;
}
console.log(diffChildren(
  [{ key: 'a', type: 'li' }, { key: 'b', type: 'li' }],
  [{ key: 'b', type: 'li' }, { key: 'c', type: 'li' }]
)); // ["reuse b", "mount c", "unmount a"]
```

这段代码只演示“认人”，不演示“搬家”。真实实现还要处理插入锚点、移动标记，以及 React 的 render/commit 两阶段：协调阶段只改 Fiber 树、打 effect 标记，提交阶段才一次性写 DOM；Vue 则是在 patch 里边比较边调用宿主操作，但同样会把同一轮里的多次状态变更合并到微任务，只跑一次更新。

### 启发式不是最优解，但是可预测的解

同层、同类型、key 三条约束，把一次全局树匹配降成了若干次子列表匹配。代价是它明确放弃了一些“更聪明”的复用：跨层级移动会重建，结构包一层会重建，类型换了更会重建。换来的则是近线性（React 是 O(n)，Vue 的 LIS 收尾是 O(n log n)）的比较、稳定的更新边界，以及一套开发者能推理的规则——你知道什么情况下状态会丢，也就知道该把 key 放在哪。

## 常见考点与误区

- **“虚拟 DOM 一定比真实 DOM 快”**：面试常问“为什么用虚拟 DOM，是不是因为快”。答“是”就偏了。虚拟 DOM 多了一层对象分配和比较，手写且高度优化的 DOM 操作完全可能更快；它真正的价值是把“命令式改 DOM”换成“声明式描述结果”，让状态与界面同步、批量更新和跨平台渲染有统一入口。性能是比较出来的，不是定义里带的。
- **“diff 会算最小编辑距离”**：错。主流实现是启发式，不保证全局最优，甚至会多搬节点、把跨层移动拆成重建。React 文档开篇就写明它基于两条假设做 O(n) 的启发式，而不是求最优树编辑。
- **“key 只是性能优化”**：这是最危险的一条。key 首先决定身份，其次才影响复用。列表重排时用数组下标当 key，框架会把“位置 0”的 DOM 和组件实例留给新数据，输入框里没提交的内容、勾选状态、展开状态、动画进度都可能串到另一行。React 文档明确说 key 不是列表专用的，它决定组件状态跟着谁走（[Preserving and Resetting State](https://react.dev/learn/preserving-and-resetting-state)）；Vue 文档也提醒默认的原地 patch 只适合不依赖子组件状态或临时 DOM 状态的列表（[List Rendering](https://vuejs.org/guide/essentials/list.html#maintaining-state-with-key)）。
- **“key 必须全局唯一”**：不必。key 只在同一个父节点的子列表里要求唯一，两个不同列表出现相同 key 没问题。反过来，同一列表里重复 key 才是事故：React 会告警并可能丢节点或错配，Vue 的映射也会被覆盖。
- **“key 相同就一定复用”**：还要类型相同。同一个 key 从 `<div>` 变成 `<span>`，仍然卸载重建；key 本身变了，更是主动要求重置。有人用 `key={Math.random()}` 想“强制刷新”，结果每次渲染都整段重建，表单焦点和动画全丢。
- **“React 和 Vue 的 diff 差不多，反正都是 O(n)”**：骨架像，移动策略不同。React 主要是单趟 key 映射加 `lastPlacedIndex`，Vue 3 在双端同步后对乱序段用 LIS 选“不动的节点”。这也解释了两者在极端重排下的 DOM 操作次数差异，但别把 LIS 当成 React 的实现。

## 实践建议

- **优先用业务稳定 ID 当 key**。数据库主键、后端返回的不可变 id、创建时生成一次的 uuid 都可以；不要用 `Math.random()`、`Date.now()` 或每次渲染新建的对象。对象作 key 在 React 里会被转成字符串，多个对象很容易得到同一个 `[object Object]`。
- **下标 key 只在“静态、只追加、无状态”的列表里可接受**。纯展示的静态清单、不会重排的日志行，用下标问题不大；一旦有排序、筛选、插入头部、拖拽换位，或者行内有输入框、勾选框、展开状态、子组件实例，就必须换稳定 ID。分页“加载更多”也要注意：如果新数据插到前面，下标 key 同样会错位。
- **保持组件类型稳定，别在 render 里定义组件**。每次渲染都创建一个新的函数组件，对 diff 来说就是“类型变了”，整棵子树都会卸载重建，输入框失焦、状态清空。条件渲染时也尽量保持外层结构一致；确实想重置表单，反而应该显式改 key，把“重置”变成有意的设计，而不是结构抖动的副作用。
- **大列表先想窗口化，再想 diff 调优**。虚拟滚动、分页、按需渲染带来的收益，通常远大于抠 key 映射的常数；行组件用 `memo`/`shouldComponentUpdate` 时，确保 props 稳定，别在父组件里传内联对象或新数组，否则浅比较每次都失败。React 可以用 Profiler 看“渲染耗时”和“提交耗时”，Vue 用 devtools 的 Timeline 看组件更新时间线，先分清是 JS 比较贵还是 DOM 操作贵。
- **把 key 当成状态边界来设计**。需要保留状态时，key 要稳定；需要切换身份、清空旧状态时，key 要变化，比如聊天窗口按联系人 id 设 key、表单按记录 id 设 key。不要为了“消除警告”随便补 key，也不要给静态节点层层加 key——key 只在身份真正会变的列表里有意义。

*一句话总结：虚拟 DOM 的 diff 不是求最优，而是用同层、同类型、key 三条约束把树比较压成可承受的启发式；key 是这套启发式的身份契约，选错它，性能问题和状态错乱会一起出现。*
