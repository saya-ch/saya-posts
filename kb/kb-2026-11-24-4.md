## 是什么

CAP 是一条关于共享数据系统的不可能结论：网络发生分区时，一个读/写对象无法同时做到原子一致性（读到的总是最近一次成功写入）和可用性（每个到达非故障节点的请求都能得到响应）。它由 Brewer 在 2000 年 PODC 的主题演讲中提出，2002 年由 Gilbert 和 Lynch 给出形式化证明（[论文](https://users.ece.cmu.edu/~adrian/731-sp04/readings/GL-cap.pdf)）。

一句话直觉：CAP 不是让你从三样里挑两样，而是说“平时 C 和 A 都能要，网络一断，这一段时间里只能保一个”。分区容忍描述的是环境——网络会丢消息、会超时——不是你可以勾掉的选项。

典型场景：库存扣减和支付要拒绝超卖，宁可写失败；购物车、商品详情、社交 feed 可以返回旧值，宁可稍后合并。同一个系统里这两类接口常常并存，所以 CAP 的取舍发生在接口粒度，而不是“我们公司选了 AP”这种粒度。

BASE 是同一枚硬币的另一面：Basically Available（基本可用，允许降级）、Soft state（软状态，状态可因后台同步而变）、Eventually consistent（最终一致）。它由 Brewer 等人在 1990 年代末的工程实践中概括，eBay 的 Dan Pritchett 在 2008 年把它写成文章。BASE 不是“不要一致性”，而是承认分区期间的一致性要拿可用性来换，并把补齐工作放到分区之后。

## 核心原理

### 一次分区如何把 C 和 A 逼成单选

设两个副本 A、B，网络断开。客户端先向 A 写 x=1，再向 B 读 x。若 B 必须可用，它只能返回旧值 0，违反线性一致；若 B 必须一致，它只能拒绝或一直等到通信恢复，违反可用。没有第三种解法：任何“既回得快又保证最新”的实现，都需要 A 与 B 先通信。

注意证明里的两个定义常被换掉。CAP 的 C 是原子一致性（线性一致），比 ACID 的 C 强：ACID 的 C 只要求事务不破坏业务约束（唯一键、外键），CAP 的 C 要求所有节点在实时序上看到同一条写。CAP 的 A 只要求“最终给出响应”，没有延迟上界——一个等三十秒才返回的请求，在 CAP 意义上仍算可用。这两处错位，是面试里最常见的失分点。

“选 CA”因此是个伪选项。分区不是你能关掉的开关；单机房也会因为交换机抖动、内核丢包、长时间 GC 出现事实上的分区。Brewer 在 2012 年的[回顾](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/)里说得很直接：分区的本质是“通信超出了时间上界”，你设的超时越短，系统越容易判定自己在分区。所以 CAP 从来不是三选二，而是“分区窗口内 C 与 A 二选一”。

### 超时把 CAP 和延迟绑在一起

既然分区由超时判定，CAP 就必然和延迟纠缠：把 RPC 超时从两秒调到两百毫秒，系统并不会变得更“分区容忍”，只会更频繁地进入分区模式。这就是 PACELC 的出发点：分区时在 A 与 C 之间选，没有分区时在 L（延迟）与 C 之间选。

Dynamo 风格的 quorum 把这件事变成了三个数字：N 副本、W 写成功所需副本数、R 读所需副本数。W+R>N 保证读集合与写集合必有交集，从而能读到最新写；但代价是读要等最慢的 R 个副本，写要等最慢的 W 个。把 W、R 都设成 1，延迟最低，却可能在分区两侧各写各的。

```python
# N=3，W=2，R=2：一次分区把 {A,B} 和 {C} 切开
store = {"A": [], "B": [], "C": []}

def put(v, side):
    for node in side:
        store[node].append(v)
    return len(side) >= 2            # 凑不够 W=2 就拒绝写

def get(side):
    seen = sorted(v for n in side for v in store[n])
    return seen[-1] if len(seen) >= 2 else None   # 凑不够 R=2 就拒绝读

print(put(1, ["A", "B"]))   # True：多数派写入成功
print(get(["C"]))           # None：少数派读不到，CP 只能拒绝服务
print(put(2, ["C"]))        # False：小分区永远写不进去
```

把 W、R 改成 1，两侧都能读写，可用性回来了，但 C 侧读不到刚写进 {A,B} 的那个 1；分叉只能留到分区恢复后合并。W+R>N 保证的是“能凑齐 quorum 时读得到最新值”，它并不保证分区两侧都凑得齐——这一点最容易被背成“配了 quorum 就强一致”。

### BASE 的“最终”要靠机制兑现

BASE 的三句话里，最容易被误读的是“最终一致”。它只说：如果不再有新的写入，副本之间的差异最终会消失。它没有承诺多快，也没有承诺怎么消。把差异消掉需要具体机制：

- Dynamo 用向量时钟记录因果，发现并发版本后交给业务合并（购物车取并集），再用 Merkle 树做反熵，把副本差异找出来（[Dynamo 论文](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)）。
- Cassandra 一类系统默认按时间戳做 last-write-wins，实现简单，但节点时钟偏移时后到的写会被旧时间戳覆盖，属于静默丢数据。
- CRDT 把操作限制成可交换或单调的，让合并天然收敛（计数器取最大值、集合取并集），代价是数据模型受限，删除要留墓碑。

还有一类“最终一致”根本不在存储层，而在业务层：写主库后立刻读从库读不到，需要粘性路由、回主库读，或者带上位点等到复制追上。这不是配置问题，是接口语义问题。

## 常见考点与误区

- **“CAP 三选二，我们选 CA”**：P 不是可选项，CA 只是“假设不会分区”的模型。真出现分区，系统仍要临时退回 C 或 A；单机系统根本不在 CAP 的讨论范围内。
- **“CAP 的 C 就是 ACID 的 C”**：一个是线性一致，一个是约束不被破坏。AP 系统照样可以有唯一键、外键这些 ACID 约束；而一个 ACID 数据库在分区时，主库之外的读也可能不满足线性一致。
- **“CAP 的 A 就是高可用”**：A 只要求非故障节点给出响应，允许很慢；99.99% 是可运营指标，两者不能互换。反过来，进程活着但每个请求都超时，在 CAP 意义上就是不可用。
- **“标称 CP 的系统，读一定最新”**：ZooKeeper 官方文档明确不保证跨客户端同时一致——A 把某个 znode 从 0 改成 1 后通知 B 去读，B 可能连到另一台服务器读到旧值，需要先 `sync()`；etcd 默认线性一致读，但显式选择串行读时会走本地副本。CP 是系统级标签，不是每个 API 的承诺。
- **“BASE 就是放弃一致性”**：放弃的是分区期间的强一致，不是正确性。没有冲突合并、对账和补偿的 AP 系统，得到的是“永远不一致”，而不是“最终一致”。
- **“Spanner 打破了 CAP”**：TrueTime 把时钟不确定性压到有界，代价是提交要等不确定窗口过去；分区时它仍是 CP，少数派不能写。它优化的是“判定与代价”，不是推翻定理。

## 实践建议

- **按操作定取舍，不按系统定**：下单、扣库存、扣余额走 CP，用事务、唯一约束和条件更新挡住超卖；商品详情、评论、推荐走 AP，允许旧值。把这条写进接口契约，别让默认配置替你做决定。
- **给“不可用”设计好降级**：写失败返回什么、要不要进本地待发队列、能不能切只读；库存要先明确“宁可少卖”还是“允许超卖后补偿”，这两种目标的实现完全不同。
- **让最终一致可验证**：幂等键加版本号做条件写，定义冲突合并规则，配一个对账任务，监控复制延迟与陈旧读窗口。别只口头承诺“最终会一致”。
- **用故障注入验收**：主动制造分区与延迟，验证三件事——分区期间哪些操作被拒、恢复后能否收敛、补偿会不会重复执行。架构图上画两个机房，不等于系统真的能扛分区。

*一句话总结：CAP 只约束分区期间那一次选择，真正决定系统好不好用的，是分区结束后能不能收敛、代价由谁承担。*
