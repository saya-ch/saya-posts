## 是什么

ThreadPoolExecutor 是 Java 里把「任务提交」和「线程执行」解耦的执行器：调用方只管把 Runnable 交出去，池子负责决定用哪条线程跑、先排队还是直接拒绝。它的构造函数有七个参数——corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler——面试常把它们当成七个可以各自调优的旋钮，实际上只有三个真正在改变行为：核心线程数、队列容量、最大线程数；keepAliveTime 与 unit 是回收策略，threadFactory 与 handler 是创建与兜底两个钩子。

一句话直觉：core 是常开窗口，workQueue 是蛇形等候区的容量，maximumPoolSize 是高峰期最多能开多少窗口，keepAlive 决定临时窗口空闲多久撤掉，handler 是栏杆也满了之后的处置办法。

典型场景是 Web 请求处理、批量文件与网络 IO、把串行流程拆成并行子任务。它们的共同点是任务到达速率和单任务耗时都不稳定，而线程是昂贵资源：既不能来一个建一个，也不能无限排队。

## 核心原理

先看一个容易被忽略的实现细节：线程池的运行状态和线程数并没有分成两个字段，而是被塞进同一个 `AtomicInteger` 型的 ctl 里。高 3 位存状态，低 29 位存 worker 数量，所以线程数上限是 2^29-1，而不是 `Integer.MAX_VALUE`。这不是炫技，而是为了让「判断状态」和「增减线程数」能用一次 CAS 完成，避免两个字段各自更新时出现状态与数量不一致的窗口。

```java
public class CtlDemo {
    static final int COUNT_BITS = Integer.SIZE - 3;              // 29
    static final int CAPACITY   = (1 << COUNT_BITS) - 1;         // 536870911
    static final int RUNNING    = -1 << COUNT_BITS;
    static final int SHUTDOWN   =  0 << COUNT_BITS;
    static int runStateOf(int c)   { return c & ~CAPACITY; }
    static int workerCountOf(int c){ return c & CAPACITY; }
    static int ctlOf(int rs, int wc){ return rs | wc; }

    public static void main(String[] args) {
        int c = ctlOf(RUNNING, 3);
        System.out.println(runStateOf(c) == RUNNING); // true
        System.out.println(workerCountOf(c));         // 3
        c = ctlOf(SHUTDOWN, CAPACITY);
        System.out.println(workerCountOf(c));         // 536870911
    }
}
```

状态的五个取值是一条单向路：RUNNING 接受新任务并处理队列；SHUTDOWN 不再接受新任务，但队列里的任务照跑；STOP 连队列也不处理，还要中断正在执行的线程；TIDYING 是清场完毕、`terminated()` 钩子执行前的瞬间；最后是 TERMINATED。`shutdown()` 走的是第二条路，`shutdownNow()` 走第三条路，这个差别决定了「停机时队列里那批任务还能不能跑完」。

再看参数如何落到线程上。每个工作线程被包成一个 Worker，Worker 继承 AbstractQueuedSynchronizer，用一把不可重入锁标记自己是否正在执行任务：state 为 0 表示空闲，为 1 表示锁已被持有。`shutdown()` 调用的 `interruptIdleWorkers()` 会逐个尝试 `tryLock()`，只有拿到锁的空闲线程才会被中断；正在跑任务的线程锁在别人手里，不会被误伤。`shutdownNow()` 则不问忙闲，直接中断所有线程。

keepAliveTime 的作用域也常被记错。取任务的 `getTask()` 里有一个布尔值 timed，等于「允许核心线程超时」或「当前 worker 数大于 corePoolSize」。也就是说，默认情况下 keepAlive 只作用于超出核心数的那部分临时线程；核心线程即使闲到长草也会用 `take()` 一直阻塞。只有调用 `allowCoreThreadTimeOut(true)`，核心线程才纳入超时回收，而且这个调用要求 keepAliveTime 大于 0，否则直接抛 IllegalArgumentException。反过来，核心线程也不是「启动即创建」：任务来了才 `addWorker`，想要预热得显式调用 `prestartCoreThread()` 或 `prestartAllCoreThreads()`。

三个阈值之间的耦合才是参数调优的真正难点。提交任务时，池子先看 worker 数是否小于 core，是就新建线程；否则尝试入队；只有入队失败（队列满）才去比较 worker 数与 max；两者相等才交给 handler。这条链路意味着：队列容量直接决定了 max 有没有机会生效，队列越大，max 越像摆设；core 设得过接近 max，扩容空间同样被吃掉。而 handler 并不是「任务一出错就触发」，它只在「队列满且线程到顶」这个双重条件下才被调用。

## 常见考点与误区

- **误区一：「线程池一创建，核心线程就都起来了」**：构造只保存参数，线程是提交任务时按需创建的。要预热必须显式调用 `prestartAllCoreThreads()`，而预热过的核心线程在开启核心超时后同样会被回收。
- **误区二：「keepAliveTime 管所有线程」**：默认只管 `workerCount > corePoolSize` 的线程。核心线程默认用 `take()` 永久阻塞，只有 `allowCoreThreadTimeOut(true)` 才改变这一行为，并且此时 keepAlive 必须大于 0。
- **误区三：「getActiveCount 就是正在跑任务的线程数」**：它要拿 mainLock 遍历整个 worker 集合，边遍历边统计 `isLocked()`，是一个近似快照；高并发下既有延迟也不精确，只能当监控趋势看。
- **误区四：「shutdownNow 一定能停掉正在执行的任务」**：它做的是 `interrupt()`，任务是否退出取决于自己是否响应中断。纯计算循环、忽略中断标志的阻塞调用照样会跑完；而且返回的 List 只包含「从未开始执行」的队列任务，正在跑的不在列表里。
- **误区五：「submit 提交的任务抛异常会被线程池的 handler 捕获」**：`submit` 会把异常封进 FutureTask 的 outcome，不调用 `get()` 就永远静默；只有 `execute` 提交时异常才会冒到线程的 UncaughtExceptionHandler。
- **误区六：「core 设成 CPU 核数就是标准答案」**：这只对 CPU 密集型近似成立。IO 密集型取决于等待时间占比，还要受下游连接池、内存与超时预算约束；把核数当万能公式，往往得到一支「都在等、没人算」的线程队伍。
- **考点七：「core=0 时第一个任务会怎样」**：任务先入队，随后 recheck 发现 worker 数为 0，再补一个线程去消费。它说明 core 并不是「至少有这么多个线程」的硬承诺，只是扩容的第一个阈值。

## 实践建议

- 先按任务类型分池，再谈参数。CPU 密集与 IO 密集混在一个池里，慢任务会把队列占满、把快任务一起拖死；隔离之后每类池子才能用各自的队列与拒绝策略。
- 用有界队列，并给拒绝策略一个明确语义。CallerRunsPolicy 把压力反弹给提交方，天然形成背压；但如果是 Web 请求线程，要确认它能承受这段额外耗时。其余场景建议自定义策略，记录任务类型、计数并告警，而不是静默丢弃。
- 并发度用 Little's Law 估：并发 ≈ 到达率 × 平均停留时间。比如每秒 200 个任务、单个平均耗时 50ms，理论并发约 10；CPU 密集再套 `核数 × 目标利用率 × (1 + 等待/计算)` 修正，最后用压测校准，别拿公式当结论。
- 监控至少覆盖五项：当前线程数、活跃线程数、队列长度与剩余容量、拒绝次数、已完成任务数。用 Micrometer 把 executor 的指标绑成 Gauge，再配合队列容量的使用率设告警，比在日志里打 `activeCount` 可靠得多。
- 优雅停机按三步走：`shutdown()` 停止接收新任务，`awaitTermination()` 等待时间要大于单任务 P99，超时再 `shutdownNow()`，并把返回的未执行任务落库或重投。停机顺序错了，丢的往往是队列里那批已经承诺给用户的任务。
- 线程复用的副作用要主动清理：ThreadLocal 与 MDC 在任务结束时用 finally 移除，否则下一条任务会读到上一条的残留；`InheritableThreadLocal` 也不会在线程池里自动传递，因为线程不是为这条任务新建的。

*一句话总结：线程池的参数是一套互相牵制的准入规则，调参之前先想清楚队列与生命周期。*
