## 是什么

最近公共祖先（Lowest Common Ancestor，LCA）是根树上的一个查询：给定两个节点 u、v，找出同时是二者祖先、且深度最大的那个节点。一句话直觉：把两个节点到根的路径各写成一列，从下往上比对，第一个重合的名字就是 LCA；这里的"最近"指的是离根最远、离两个节点最近，而不是数值上最近。按定义，节点也可以是自己的祖先，所以当 u 本身就是 v 的祖先时，答案是 u；而根永远是任意两点的公共祖先，这保证了查询一定有解。

典型场景很多：DOM 事件冒泡时要判断两个节点是否落在同一棵子树；文件系统求两个路径的公共目录；组织架构里找两名员工的最低共同上级；编译器的作用域树判断一个变量在哪个最近公共作用域内可见。面试里最常考的形式是"给一棵普通二叉树和两个节点，求它们的 LCA"，题目本身只有几行，考的是你能不能在结构、边界和复杂度上都讲清楚。

## 核心原理

先看最朴素的解法。如果每个节点存了父指针和深度，就把较深的那个往上抬，直到两者同深度；再一起往上走，第一次相遇就是答案。单次最坏 O(n)：一棵退化成链的树，两个叶子要爬将近 2n 步。倍增（binary lifting）要解决的就是"往上爬得太慢"这个问题。

它的想法和跳表、二进制拆分同源：任何一个深度差都能写成 2 的幂之和，于是不必记 1 级、2 级、3 级祖先，只记 1、2、4、8……级祖先。定义 `up[j][v]` 为 v 的第 2^j 级祖先，就有递推 `up[j][v] = up[j-1][up[j-1][v]]`：先跳 2^(j-1) 步，再跳 2^(j-1) 步，合起来正好 2^j 步。预处理一遍 DFS 或 BFS 填表，O(n log n) 时间与空间；之后每次查询 O(log n)。这套定义与查询流程在 [cp-algorithms 的倍增 LCA 页面](https://cp-algorithms.com/graph/lca_binary_lifting.html)有完整推导。

查询分两段。第一段把深度差 diff 按二进制拆开，用 up 表把 u 抬到与 v 同深度；如果此时 u 已经等于 v，说明两者原本就是祖先关系，直接返回。第二段两人同深度但不同节点，从最大的 j 往小试：如果 `up[j][u] != up[j][v]`，说明跳 2^j 步后还没到公共祖先，可以安全地一起跳；否则这一步会跨过 LCA，不能跳。循环结束时 u、v 停在 LCA 的两个不同儿子上，返回 `up[0][u]` 即父亲。注意第二段必须从大到小，且判断条件是"不相等才跳"——这两点是把 LCA 留在正上方、而不是跳过头或原地不动的关键。

```python
LOG = n.bit_length()
up = [parent[:]]                     # up[0][v] 是父亲，根的父亲设为自己
for j in range(1, LOG):              # up[j][v] 是 v 的第 2^j 级祖先
    prev = up[j - 1]
    up.append([prev[prev[v]] for v in range(n)])

def lca(u, v):
    if depth[u] < depth[v]:
        u, v = v, u
    diff = depth[u] - depth[v]
    for j in range(diff.bit_length()):   # 按二进制位消掉深度差
        if diff >> j & 1:
            u = up[j][u]
    if u == v:
        return u
    for j in range(LOG - 1, -1, -1):
        if up[j][u] != up[j][v]:          # 只跳到 LCA 的正下方
            u, v = up[j][u], up[j][v]
    return up[0][u]
```

`depth` 由一次 BFS 或 DFS 得到；若节点编号不保证父节点先于子节点出现，建表前要先按遍历序排好，否则 `up[j][v]` 会引用到还没算出的祖先。

另一条常见路线是递归后序：在普通二叉树里，若当前节点为空或等于 u、v 就返回；左右子树分别递归，若两边都非空，当前节点就是 LCA；否则返回非空的那一边。它不需要父指针和预处理，单次 O(n)，适合只问一两次的场景，但递归深度等于树高，链状树上要改成显式栈。

倍增还有一个小变体：预处理 DFS 的进入、离开时间 `tin`、`tout`，用 `tin[u] <= tin[v] && tout[v] <= tout[u]` 就能 O(1) 判断祖先关系；查询时先看谁是谁的祖先，否则从高位往低位把 u 抬到"最深的、仍然不是 v 祖先"的位置，再取它的父节点。这个写法少了一次深度对齐，但要求树结构静态，加叶子会让时间戳整体失效。

LCA 还是许多树上算法的地基。两点距离可以写成 `dist(u, v) = depth[u] + depth[v] - 2 * depth[lca]`；路径加、路径求和可以用树上差分，边差分在 u、v 处各加一、在 LCA 处减二，点差分再对 LCA 的父亲补一次减一，本质上都是把路径拆成几条到根的链；多个节点的 LCA 满足结合律，可以逐个合并。面试常从这里追问"求树上两点距离"，答不出来往往不是不会 LCA，而是没把它和深度联系起来。

如果查询量很大，还有两条路线：欧拉序加 RMQ，把 LCA 转成"两个节点首次出现位置之间深度最小的点"，稀疏表预处理 O(n log n)、查询 O(1)；Tarjan 离线，把查询挂到节点上，DFS 回溯时用并查集合并已完成的子树，整体 O((n+q)α(n))，但要求所有查询事先已知。它们和倍增的差别不是"谁更高级"，而是在预处理时间、查询时间、内存、是否在线这四项之间做交换，[OI Wiki 的 LCA 条目](https://oi-wiki.org/graph/lca/)把这几种写法并列得很清楚。

## 常见考点与误区

- **"比较节点值就能确定 LCA"**：这只在二叉搜索树上成立，靠的是 BST 的有序性，而不是某个"最小公共祖先"的规则；普通二叉树没有大小序，必须靠结构判断。面试给的是任意二叉树却拿值比较，是 [LeetCode 236](https://leetcode.cn/problems/lowest-common-ancestor-of-a-binary-tree/) 最经典的错误。
- **"最近"是指两个节点距离最近**：错。LCA 的定义是深度最大的公共祖先，也就是离根最远；它到两个节点的距离不一定相等，更不一定最小。
- **第二阶段从小到大跳，或者"相等才跳"**：从小往大跳会让后面的大步失去落点，容易停在半路；"相等才跳"则会直接越过 LCA。正确写法是从高位到低位、不相等才跳。
- **忘了先对齐深度**：不同深度的两个节点直接一起往上跳，相遇点可能比真正的 LCA 更靠上，答案就错了。
- **把根的父亲留成 0 号节点却不处理**：0 号若是真实节点，会造出一个环；应让根指向自己，或用深度为 -1 的哨兵，并在越界时停下。
- **以为递归版一定比倍增快**：单次查询递归是 O(n)，倍增是 O(log n)；q 次查询下前者是 O(nq)，只是常数小，不是复杂度更优。
- **把 Git 的 merge-base 当树上的 LCA**：提交历史是有向无环图，不是树；[git merge-base](https://git-scm.com/docs/git-merge-base) 的文档明确说，交叉合并时可能存在多个"最佳共同祖先"，不加 `--all` 时输出哪一个并未指定，不能拿树的唯一性直觉硬套。

## 实践建议

- 先数查询量再选结构：一次性的树问题用递归后序最省事；q 与 n 同阶且树静态，用倍增；要 O(1) 查询且内存宽裕，用欧拉序加 RMQ；查询可离线批处理，用 Tarjan。
- 建表用迭代 DFS 或 BFS，别用递归：生产里的链状树（文件目录、退化索引树）深度可能上万，递归会先把调用栈打爆。
- 把"是否同一棵树"作为前置校验：LCA 只在同一棵根树上定义，工程里两个节点来自不同租户、不同版本树时，应先判根或直接返回"无"，不要算出一个看似合理的节点。
- 需要频繁加叶子时，倍增表可以 O(log n) 增量维护，只补新节点那一列；欧拉序加 RMQ 则要重算时间戳；如果要任意 link/cut，才轮到 Link-Cut Tree 这类更重的结构。
- 对重复查询做缓存，键用规范化后的节点对；同时给向上跳加深度上限或访问计数，避免脏数据里的环把查询变成死循环。
- 上线前用随机树对拍：写一个沿父指针暴力爬的版本作为对照，随机生成链、星形、随机树各几百组查询，比对节点编号与深度；这比盯着转移方程更能抓出根指针和越界问题。

*一句话总结：LCA 的难点不在"找共同祖先"，而在用预处理把一步一步爬换成按二进制跳，并认清它只属于树、不属于大小序。*
