## 是什么

多租户隔离是让多个客户共用一套系统，同时保证任何一个客户都看不到、改不了、也拖不垮别人的数据与算力。一句话直觉：共享是为了省钱，隔离是为了在共享的前提下，把“出事”限制在一个格子里。

它要解决的不只是权限，而是三类边界：**权限边界**（谁能读到哪一行）、**资源边界**（一个人用爆了会不会挤死别人）、**故障边界**（出问题时能不能只切掉一个租户）。典型场景是 SaaS：一套应用、一个数据库，服务几百家企业；也可以是内部平台，多个团队共用一组 Kubernetes 集群。这三类边界经常被混为一谈，结果就是数据锁住了，但一个租户的慢查询仍能把所有人拖下水。

## 核心原理

先看隔离强度这张谱。最省的是**共享库共享表**，每张表加 `tenant_id`，靠查询条件过滤；往上一档是**共享库独立 schema**，表结构相同但物理分开；再往上是**独立数据库**，最后是**独立实例或集群**。每往右走一步，爆炸半径小一圈，成本、迁移复杂度、跨租户统计难度也各涨一截。要注意独立 schema 只把表分开了，连接数、内存和实例级故障仍然共享，别把它当成完整隔离。没有“最先进”的档位，只有和信任模型匹配的档位：内部团队可以软隔离，互不信任的外部客户、尤其是能上传并执行代码的租户，就得考虑硬隔离。

共享表方案真正的难点不是加列，而是**强制点放在哪**。应用层的 `WHERE tenant_id = ?` 是约定：只要有一个人写了原生 SQL、用了 ORM 的绕过接口、跑了离线脚本，约定就失效。所以要把约束尽量下沉到共享资源那一侧，让“忘记写条件”变成查不到数据，而不是查到别人的数据。

PostgreSQL 的[行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)（RLS）就是这种下沉：策略由数据库对每一行求值，普通查询、UPDATE、DELETE 都绕不过。但它有几个必须同时满足的前提，缺一个，策略要么形同虚设，要么把所有人都挡在外面。

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;  -- 表 owner 也受约束

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);

BEGIN;
SET LOCAL app.tenant_id = '6f1c2a9e-3b4d-4c5e-8f90-1a2b3c4d5e6f';
SELECT * FROM orders;
COMMIT;
```

第一，应用连接使用的角色不能是表 owner；是 owner 就得加 `FORCE`。第二，这个角色不能有 `BYPASSRLS`，更不能是超级用户——这两者**永远**绕过行安全。第三，租户上下文必须用 `SET LOCAL` 绑在事务上，而不是会话上：连接池会把同一条连接还给下一个请求，会话级变量一旦残留，下一个租户就继承了上一个租户的身份。用 `current_setting(..., true)` 让缺失的上下文返回 NULL，策略求值为 NULL 即不匹配，形成“没有上下文就一行都看不到”的默认拒绝。

同样的道理适用于每一层共享资源。Kubernetes 的 namespace 只是命名与授权的作用域，不是内核边界：[官方文档](https://kubernetes.io/docs/concepts/security/multi-tenancy/)明确说命名空间隔离还需要网络插件、配额、准入控制等一系列配置配合，而集群默认允许 Pod 之间自由通信，容器又共享同一个内核。所以 namespace 之外还要有默认拒绝的 NetworkPolicy、ResourceQuota、Pod Security 与沙箱运行时；对真正恶意的租户，独立集群或虚拟控制面才是边界。

再往外，还有一堆容易被漏掉的旁路。缓存键如果只写业务 ID，两个租户的同号订单就会互相命中；消息队列的分区键、搜索引擎的索引与别名、对象存储的前缀与签名 URL、向量库的 collection、日志里的查询条件，每一条都是独立的数据通路。主库锁得再死，旁路漏一条就等于没隔离。资源侧同理：一个租户的大查询占满连接池，或者一批任务打满 CPU，其他人不是“慢一点”，而是直接不可用——这就是噪声邻居。

所以隔离的本质可以压成一句话：在每一个共享资源上，找到一条能强制执行的边界，并让越界请求失败，而不是越界成功。

## 常见考点与误区

- **“每张表加 tenant_id 就够了”**：不够。加列只提供了过滤的依据，没有提供强制。ORM 的全局 scope、手写 SQL、JOIN 子查询、批量导入、后台补偿任务，任何一处绕过都会穿透。面试里如果只答“加字段加索引”，通常会被追问“怎么保证没人漏写”。
- **“开了 RLS 就安全了”**：最常见的翻车是应用连的就是表 owner，策略建了但一行都没过滤；其次是拿超级用户跑集成测试，永远测不出来。记住 `FORCE` 管得住 owner，管不住超级用户和 `BYPASSRLS`。
- **“连接池里 SET 一下租户就行”**：会话级设置会跟着连接走到下一个请求。事务池模式下更不可靠，必须 `SET LOCAL`，并且保证每个请求都在事务里。
- **“namespace 就是安全边界”**：它默认不是。没有 NetworkPolicy 时 Pod 之间全通；CRD、StorageClass、webhook 等集群级资源也不受 namespace 约束；容器共享内核，一旦逃逸就是整台节点。
- **“隔离只关数据”**：连接数、QPS、存储、队列积压、缓存命中率都是共享的。一个租户的慢查询可以把共享连接池占满，让所有租户一起 500。
- **“独立库一定更好”**：它把成本、连接数、schema 变更次数都乘以租户数，跨租户报表也更难做。共享表不是原罪，缺少强制点才是。

## 实践建议

- **先定信任模型，再选档位**。问三个问题：租户之间是否互相信任、是否有人能上传并执行代码、合规是否要求数据物理分开。答案决定你停在共享表还是走到独立实例；常见做法是分层，小客户共享、大客户独立，并预留 `tenant → shard` 的映射，别等迁不动了再改。
- **入口只认可信来源**。租户身份从令牌、域名或网关注入的签名头里取，绝不接受请求体里自报的 `tenant_id`；把它做成请求级不可变上下文，往下传参而不是读全局变量。
- **做跨租户测试，而不是只测功能**。用两个租户、两个真实角色，对每张表跑读、写、改、删，断言 A 看不到也改不了 B；把“每张业务表必须有 tenant_id 且启用策略”做成 CI 检查，比代码评审可靠。
- **给每个共享组件列一张清单**：数据库、缓存、队列、搜索、对象存储、向量库、日志、CDN。逐项写清租户维度加在哪里、由谁强制、越界时返回什么，新组件上线前过一遍这张表。
- **资源也要设边界**。每租户的连接数、并发、QPS、存储配额，加上语句超时与队列隔离；宁可让超额的那一个租户排队或失败，也不要让所有人一起慢。指标按租户打标，既用于告警也用于计费。
- **别让策略变成全表扫描**。RLS 的条件最终要落到执行计划里，租户列应进联合索引的最左列；上线前用真实数据跑一遍 `EXPLAIN`，确认走的是索引而不是每行求值后再过滤。
- **想清楚怎么退出**。租户注销时要能证明数据删干净：逐表删除、缓存失效、备份到期，敏感场景可以用按租户的加密密钥，销毁密钥即让残留密文不可读。

*一句话总结：多租户隔离的难点不在加一列，而在每个共享资源上都找到绕不过的强制点。*
