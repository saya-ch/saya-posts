## 是什么

LLM-as-Judge 的做法很直接：把问题、待评的回答，连同评分标准（有时还有参考答案）一起交给一个能力更强的模型，让它给出分数、通过或不通过，或者判断两个回答里哪个更好。

把它想成一台测量仪器，而不是一位更聪明的考官。考官可以讲得头头是道却给错分；仪器只看两件事：同样的输入重复测，读数稳不稳；读数变化对应的那个东西，是不是你真想测的东西。前者叫信度，后者叫效度。

它最常出现在四个地方：提示词改一版，拿几百条历史样本跑回归；RAG 系统每天抽检回答有没有被检索到的上下文支持；两个候选模型做 A/B；人工标注之前先做一轮预筛。共同点是量大、人工评不起、又必须每天给结论。

关键在于，裁判吐出来的是离散标签或序数分数，所以它首先是一个分类器。分类器就该按分类器的规矩验收：先看混淆矩阵，再看它说话像不像人。

## 核心原理

**第一步是确定拿什么当金标。** 裁判要和人类比，但人类自己也会分歧：同一批回答让两个人独立标注，八成一致很常见。如果直接拿其中一个人的标签当标准答案，你测到的只是"裁判像不像这位标注员"。稳妥的做法是双人标注、分歧交第三人仲裁，把仲裁后的结果冻结成标定集；同时记录人类之间的一致性，它是裁判一致率的天花板。

**第二步是别被一致率骗了。** 假设标定集一百条，九十条合格、十条不合格，裁判一律判合格：

```python
# 1 表示不合格；human 是仲裁后的人类标签，judge 是裁判判定
human = [1] * 10 + [0] * 90
judge = [0] * 100          # 裁判一路点头

tp = sum(h and j for h, j in zip(human, judge))
tn = sum((not h) and (not j) for h, j in zip(human, judge))
fn = sum(h and not j for h, j in zip(human, judge))
fp = sum((not h) and j for h, j in zip(human, judge))

acc = (tp + tn) / len(human)
tpr = tp / (tp + fn)       # 不合格里抓出多少
tnr = tn / (tn + fp)       # 合格里正确放行多少
po = acc
pe = 0.1 * 0.0 + 0.9 * 1.0 # 两边边际分布算出的随机一致率
kappa = (po - pe) / (1 - pe)
print(f"acc={acc:.0%} tpr={tpr:.0%} tnr={tnr:.0%} kappa={kappa:.2f}")
# acc=90% tpr=0% tnr=100% kappa=0.00
```

准确率九成，看起来可以发版；实际上它一条不合格都没抓到，kappa 是零。原因不复杂：合格样本占了九成，全判合格这条最偷懒的策略就能拿到九成准确率。所以验收裁判要同时报 TPR（不合格里抓出多少）、TNR（合格里放行多少），以及二者的平均，也就是 balanced accuracy。

**kappa 也不是万能药。** κ=(po-pe)/(1-pe) 扣掉了"随机也能碰对"的部分，pe 由两边的边际分布算出。合格率九成时，若裁判也判九成合格，随机一致率 pe 就有 0.82，po=0.90 代进去只剩 0.44。Feinstein 与 Cicchetti 把这种"高一致、低 kappa"称为[患病率悖论](https://doi.org/10.1016/0895-4356(90)90158-L)：边际越偏，kappa 越被压低；反过来在极端偏斜下，也可能出现 kappa 不低而实际一致率并不高。所以别指望一个数字定生死，混淆矩阵、TPR/TNR、kappa（或 PABAK）要摆在一起看。

**如果裁判是过滤器，还要算基数。** TPR 80%、TNR 95% 听起来不错，可若真正不合格的只占 2%，被它拦下的一百条里大约只有四分之一真有问题，其余都是误杀。裁判越敏感，误杀越多；阈值定在哪，取决于漏放一条和误杀一条各自要付多少成本，而不是取个 0.5 图省事。

**分数尺度是另一个坑。** 让模型打 1 到 10 分，分数会向 7、8 分挤，均值差 0.2 很可能落在重复测量的噪声里；评分标准改一句话，历史分数立刻不可比；裁判换个版本，整条分布平移。两种解法：把标准拆成能二元判定的原子条目，比如忠实度等于"被上下文支持的 claim 数除以 claim 总数"（[Ragas 的 faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 就是这么算的），既可解释也能定位；或者做成对比较，只问"哪个更好"，但必须交换 A/B 顺序各问一次来压位置偏差。

**最后是复现。** 温度设成 0 不等于确定：批处理形状、MoE 的路由、后端静默升级，都会让同一个输入给出不同判定。固定裁判的模型版本与提示词哈希，同一批样本重复跑三次看翻转率，比事后争论"模型不稳定"有用得多。

## 常见考点与误区

- **误区一："一致率九成就能上线"**：类别不平衡时，全判通过也能拿到九成。面试问"怎么验收一个裁判"，要答标定集、混淆矩阵、TPR/TNR，以及按业务代价选的阈值，而不是一个准确率。
- **误区二："和人类一致就说明裁判准"**：人类之间的一致率才是上限；标签本身有噪声，没仲裁的金标只能测出"像不像某个人"。此外，和标注员高度一致也可能是双方共享同一种偏好，不构成效度证据。
- **考点三："kappa 与准确率差在哪"**：kappa 扣掉了随机一致，适合比较不同任务、不同合格率下的判定；但边际分布极端时会被压低甚至失真，要配合 PABAK 与分指标解释。这是统计题，也是评测题。
- **误区四："1 到 10 分求平均就能比较模型"**：这是序数尺度，不是连续量；分数向中高段压缩，跨批次、跨裁判版本都不可比。要么用二元判据的比例，要么用成对比较加聚合模型（如 Bradley-Terry），并报样本量。
- **误区五："温度设 0 就能复现"**：批不变性、专家路由、模型别名静默升级都会破坏复现。真正要固定的是模型快照、提示词版本和解析逻辑。
- **考点六："pointwise、pairwise、reference-based 怎么选"**：有可靠参考答案就用 reference-based；只比两个模型就用 pairwise 加双向提问；要定位失败原因就用原子 rubric 分解。别把裁判当 oracle：[JudgeBench](https://arxiv.org/abs/2410.12784) 用一正一错的困难对测裁判，普通提示下强模型也只有五成上下，推理型裁判才拉到七八成。

## 实践建议

- 建一套一百到三百条的标定集，覆盖典型样本与边界样本，双人标注加仲裁后冻结；换裁判模型、改评分标准，都重跑一遍 TPR/TNR 与 kappa，别凭感觉发版。
- 评分标准原子化并给锚点：每条判据写清"满足"和"不满足"各长什么样；能用代码判的（JSON 合法性、字段齐全、引用是否存在）先用代码，模型只判语义部分，成本和方差都会降。
- 成对比较正反各问一次，两次一致才算赢，不一致记为平局；报告胜率时带上样本量与区间，避免把三场两胜说成显著领先。
- 分层抽样加缓存：全量跑规则，按比例抽模型复核；以提示词哈希、答案哈希、裁判版本为键缓存结果，既省钱又能复现历史结论。
- 把裁判接进持续集成：固定版本，回归集掉分就阻断发布；同时监控通过率与分数分布的突变，那往往比单条差评更早暴露问题。
- 不要让裁判分数成为训练奖励的唯一来源，模型会学会讨好判据而不是解决问题；关键决策保留人工抽检。

*一句话总结：裁判不是更聪明的考官，而是一台需要标定、需要看混淆矩阵的仪器。*
