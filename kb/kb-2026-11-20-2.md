## 是什么

InnoDB 的表不是"一堆行加若干指向行的索引"，而是**一棵以主键为键的 B+ 树，行本身就躺在叶子页里**。这棵树叫聚簇索引（clustered index），索引和数据是同一份结构，没有独立的堆表。除它之外的索引都叫二级索引（secondary index），叶子节点只存两样东西：索引列的值，以及这一行对应的主键值。

一个直觉：聚簇索引是按身份证号排的档案柜，档案就放在格子里；二级索引是按姓名排的卡片盒，卡片上只抄了一行身份证号，想看档案还得回档案柜按号取。这个"按号再取一次"的动作，就是回表。

典型场景很清楚：`WHERE id = ?` 走聚簇索引一趟到位；`WHERE user_id = ?` 走二级索引拿到主键，再回表取整行；`ORDER BY id` 常常天然有序，因为聚簇索引本来就按主键排；而 `SELECT *` 几乎永远不会被任何二级索引覆盖。

## 核心原理

**一张表只有一棵聚簇索引。** 有 PRIMARY KEY 就用它；没有主键，就用第一个所有列都声明为 NOT NULL 的 UNIQUE 索引；两者都没有，InnoDB 会生成隐藏的 GEN_CLUST_INDEX，用一个 6 字节、单调递增的 row ID 当键，行的物理顺序随之退化成插入顺序。所以"聚簇"描述的是"行数据与索引同页"这一存储事实，不是"名字必须叫 PRIMARY"。

**两种叶子页装的东西不一样。** 聚簇索引的叶子页是完整行，还带两个隐藏列：DB_TRX_ID（6 字节，最后修改它的事务号）和 DB_ROLL_PTR（7 字节，指向 undo log 里的旧版本）。二级索引的叶子页只有"索引列 + 主键值"，**没有这两个隐藏列**。这个细节在后面会直接引出一个高频陷阱。

**回表贵在哪。** 通过二级索引查一行，实际是两次 B+ 树定位：先在二级索引里找到主键，再拿主键去聚簇索引里取整行。第一趟通常很便宜——索引窄、单页装得多、缓存命中率高；第二趟是按主键的点查，如果主键是随机的，这些点查落在聚簇索引上就是随机 IO，范围扫描返回几千行，就是几千次散落在不同页的访问。优化器真正在算的账是：走二级索引加 N 次回表，和直接顺序全表扫，哪个更便宜。这正是"区分度低的列建了索引反而不走"的原因——回表次数太多，不如扫全表。

**覆盖索引省的是哪一段。** 如果查询需要的列全在二级索引里（主键是隐式包含的），就不必回表，EXPLAIN 的 Extra 会显示 `Using index`。

```sql
CREATE TABLE orders (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,
  status TINYINT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  KEY idx_user (user_id)
) ENGINE=InnoDB;

-- 回表：idx_user 只给 id，status/amount 还得回聚簇索引取
EXPLAIN SELECT status, amount FROM orders WHERE user_id = 42;

-- 覆盖：把 amount 并进二级索引，查询列全在索引里
ALTER TABLE orders ADD KEY idx_user_amount (user_id, amount);
EXPLAIN SELECT user_id, amount FROM orders WHERE user_id = 42;  -- Extra: Using index
```

**主键为什么会被复制很多份。** 每个二级索引的每条记录都带着主键值。表上有五个二级索引，主键加长 8 字节，等于整表多出五份 8 字节的额外体积，还要在每次写入时一起维护。这就是"主键要短"的真正来源，不是审美问题；用 utf8mb4 的长 VARCHAR 当主键，代价会摊到每一棵二级索引上。

**插入顺序决定页的命运。** 自增主键的插入永远落在最右叶子页，页填满再开新页，填充率高、几乎没有随机写。UUID 这类随机主键会把插入打散到整棵树，目标页大概率不在 buffer pool 里，于是触发页分裂：一个满页拆成两个半满页，父页要更新，碎片率上升，二级索引也跟着随机。更麻烦的是更新主键——行的聚簇键变了，物理位置就得搬，所有二级索引里存的旧主键值全部失效要重写，本质上等价于删掉旧行再插入新行。

**MVCC 的账挂在聚簇索引上。** 因为二级索引没有 DB_TRX_ID 和 DB_ROLL_PTR，它无法自己判断"这个索引项对应哪个版本、对当前事务可不可见"。所以一旦涉及旧版本可见性，仍然要回到聚簇索引去读版本链。覆盖索引省掉的是"取列"这一趟，不是"版本判断"这一趟，这两个概念经常被混为一谈。

**大范围回表怎么救。** MRR（Multi-Range Read）先把二级索引命中的主键收进缓冲，按主键排序，再按序回表，把随机 IO 变成接近顺序的 IO；缓冲大小由 `read_rnd_buffer_size` 控制，EXPLAIN 里会显示 `Using MRR`。写路径上还有 change buffer：非唯一二级索引的页不在 buffer pool 时，修改先记进 change buffer，等页被读上来再合并；聚簇索引不享受这个待遇，因为行本身必须就地更新，而且唯一索引要校验唯一性，也得先把页读上来。

## 常见考点与误区

- **"聚簇索引就是主键索引"**：多数时候成立，但反例恰好是考点——没主键时可能是某个合适的 UNIQUE 索引，也可能是不存在于表结构里的 GEN_CLUST_INDEX。聚簇描述的是存储方式，不是约束的名字。
- **"二级索引里存的是行地址"**：那是 MyISAM 存行号的做法。InnoDB 存的是主键值，所以页分裂导致行搬迁时二级索引不用改物理指针，但主键一改就要全量重写。答错这一条，后面关于主键选择的所有推论都会跟着错。
- **"建了索引就一定比全表扫快"**：低区分度列加上大结果集，回表次数可能远超一次顺序扫描。要看 EXPLAIN 的 rows、实际回表行数，以及 `Handler_read_*` 的变化，不能只看有没有用上索引。
- **"覆盖索引一定不回表"**：`SELECT *` 永远不覆盖；索引条件下推、需要回表校验、以及上面说的 MVCC 版本判断，都可能让"看起来覆盖"的查询仍然访问聚簇记录。
- **"主键随便选，唯一就行"**：随机主键带来页分裂、碎片和所有二级索引膨胀；拿业务字段当主键还会遇到"业务允许修改"的尴尬，一改就是全索引重写加行搬迁。
- **"一张表可以有多个聚簇索引"**：只能有一个，其余全是二级索引。想让表按另一列聚簇，只能换主键，或者退一步用覆盖索引把查询收口。

## 实践建议

- 主键选短的、单调的、不可变的值：BIGINT 自增，或时间有序的 UUIDv7、雪花 ID。别用 36 字符的随机 UUID，也别用可能被业务修改的编号。
- 高频查询用覆盖索引收口：把 SELECT 里那几列并进联合索引，让 Extra 出现 `Using index`；但要同时算索引体积和每次写入的维护成本，为了覆盖三个宽列而加的索引往往不划算。
- 数一数二级索引：每个索引都是一次写放大。用 performance_schema 或 `sys.schema_unused_indexes` 找长期零命中的索引，删除前先确认没有低频但关键的查询依赖它。
- 大范围扫描别一口气回表：分批按主键推进（keyset 分页），或让优化器用上 MRR；深分页的 `LIMIT offset` 本质就是取了几十万行再丢掉，代价全在回表上。
- 排查慢查询时把"回表行数"当独立指标看：EXPLAIN 的 rows 只是估算，真正疼的是回表引发的随机 IO 和它对 buffer pool 的污染。

*一句话总结：聚簇索引把整行放进了主键树，二级索引只抄了一张写着主键的卡片，回表、覆盖索引与主键选择的全部结论都从这张卡片推出来。*
