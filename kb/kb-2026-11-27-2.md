## 是什么

堆是一种满足「堆序」的完全二叉树：每个节点的值都不小于（大顶堆）或不大于（小顶堆）它的孩子。它只保证父子之间的偏序，兄弟之间、左右子树之间没有任何约定，所以堆不是排序结构，而是一个「随时能取出最值」的结构。可以把它想成医院的分诊台：不要求所有病人按顺序排好，只要求当前最紧急的那一个永远站在最前面。

因为是完全二叉树，堆可以直接塞进一个数组，不需要指针：下标 i 的父节点是 (i-1)//2，两个孩子是 2i+1 和 2i+2，树的层序就是数组顺序，中间没有空洞。典型场景是优先队列：任务调度、定时器、Dijkstra 与 Prim 取最小边、Top-K 统计、合并 K 个有序链表、双堆求中位数，以及堆排序本身。

## 核心原理

堆的所有操作都围绕一条路径做文章：从某个节点一路向上或向下，把不满足堆序的那一对父子交换过来。因为树高是 ⌊log₂n⌋，一次上浮或下沉最多走这么多层，单次代价 O(log n)。

插入是「上浮」：新元素先放到数组末尾，也就是完全二叉树的最后一个位置，然后不断和父节点比较，比父节点更优先就交换，直到根或者不再需要交换。删除堆顶是「下沉」：把最后一个元素搬到根上，堆大小减一，再让它和两个孩子中更优先的那个比较、交换，一路沉到底。这里必须先选出「更大的孩子」再和父节点比，如果随便挑一个孩子换，另一个孩子可能立刻违反堆序。

批量建堆不是做 n 次插入，而是从最后一个非叶节点 n//2-1 开始，倒着对每个节点做一次下沉。这一步的复杂度是 O(n)，不是 O(n log n)，原因在于代价按「高度」分摊：高度为 h 的节点最多有 n/2^(h+1) 个，每个最多下沉 h 层，总代价是 n 乘以 Σh/2^(h+1)，而这个级数收敛到 1。换成人话：绝大多数节点都在树的最底下，它们几乎不用动；真正昂贵的只有根附近那寥寥几个节点。反过来，如果从空堆开始逐个插入，每次都要上浮到接近根，最坏才是 O(n log n)。

堆排序把这两步接起来：先在原数组上建一个大顶堆，然后反复把堆顶（当前最大值）和堆的最后一个元素交换，堆的有效范围减一，再对新根做一次下沉。最大值就这样从后往前依次归位，n-1 轮之后整个数组有序。整个过程只用了常数个额外变量，空间 O(1)；每一轮下沉 O(log n)，总计 O(n log n)，而且最好、最坏、平均都是这个数，没有快排那种 O(n²) 的最坏情况。

那为什么工程里排序默认不用它？因为堆排序的访存模式太跳。下沉时从 i 走到 2i+1，下标跨度越来越大，每一步都踩在不同的缓存行上；快排的分区则是从头到尾顺序扫一遍，缓存命中率高得多。同样是 O(n log n)，实测快排通常快两到三倍。堆排序还多做了近一倍的交换，分支预测也更难做。它的真正价值是「兜底」：C++ 的 std::sort 用内省排序，递归深度超过 2log n 就切到堆排序，把最坏情况钉死在 O(n log n)。

```python
def sift_down(a, i, n):
    while True:
        big, l, r = i, 2 * i + 1, 2 * i + 2
        if l < n and a[l] > a[big]: big = l
        if r < n and a[r] > a[big]: big = r
        if big == i:
            return
        a[i], a[big] = a[big], a[i]
        i = big

def heapsort(a):
    n = len(a)
    for i in range(n // 2 - 1, -1, -1):   # 建堆，O(n)
        sift_down(a, i, n)
    for end in range(n - 1, 0, -1):       # 依次把堆顶换到末尾
        a[0], a[end] = a[end], a[0]
        sift_down(a, 0, end)              # 堆的有效长度在缩小
```

这段代码有两个容易写错的边界：建堆循环的起点是 n//2-1（最后一个有孩子的节点），不是 n-1；下沉时传入的 n 是「当前堆的有效长度」，排序阶段它是不断缩小的 end，而不是数组原长。写成全局长度，会把已经归位的最大值又卷回堆里。

## 常见考点与误区

- **建堆是 O(n log n)**：这是最高频的错答。n 次插入确实要 O(n log n)，但自底向上的建堆是 O(n)，推导就是上面那个收敛级数。面试追问「为什么」时，要能说出「代价按高度加权，底层节点占多数且几乎不动」，而不是只背结论。
- **堆排序是稳定的**：错。它要把堆顶和末尾元素远距离交换，相等元素的相对次序会被打乱。比如 [2a, 2b, 1]，建堆后把 2a 换到末尾，再下沉会把 2b 顶上来，最终 2b 排在 2a 前面。需要稳定就选归并或 Timsort，堆排序给不了。
- **求第 k 大要用大顶堆**：方向反了。流式数据求前 k 大，应该维护一个大小为 k 的**小顶堆**：堆里始终是「目前最大的 k 个」，堆顶是这 k 个里最小的那个，正好用来判断新元素要不要挤进来。如果建大顶堆再弹出 k 次，空间是 O(n)，流式场景直接不可用。
- **堆里查找任意元素是 O(log n)**：错。堆只约束父子，没有 BST 那种全局有序，找一个值只能线性扫，O(n)。能 O(1) 拿到的只有堆顶。Dijkstra 里的 decrease-key 之所以要额外的位置索引，就是为了绕开这个限制。
- **下标公式记混**：0 基数组是孩子 2i+1、2i+2，父 (i-1)//2；1 基数组才是 2i、2i+1、i//2。面试手写代码时错这一处，整个下沉就错了。
- **堆排序最坏会退化成 O(n²)**：不会，这是快排的问题。堆排序三种情况都是 O(n log n)，代价是常数大、不稳定。

## 实践建议

- 流式 Top-K 用大小为 k 的小顶堆，复杂度 O(n log k)；k 和 n 同量级时直接全量排序更划算，别为了「用堆」而用堆。k 很小且数据可随机访问时，quickselect 平均 O(n) 也值得考虑，但要接受最坏 O(n²)。
- 定时器、延迟队列用最小堆存 (到期时间, 序号)，序号用来打破相同到期时间的比较僵局；需要取消任务时，别在堆里线性找，用一张 id 到下标的哈希表，或者干脆标记删除、到期时再跳过（延迟删除）。
- 用 Python 的 heapq 时，批量建堆用 heapify（O(n)），不要循环 heappush；它只有小顶堆，取大顶堆就存负数；元素是元组时把不可比较的字段换成自增序号，避免 TypeError；heapq 不是线程安全的，多线程访问要自己加锁。
- 对延迟敏感的调度器可以试 4 叉堆：层高减半，下沉路径更短、缓存更友好，代价是每层要多比较几个孩子。整数键、范围不大的场景，基数堆能把部分操作做到接近 O(1)。
- 排序选型上，除非明确需要原地且最坏可控，否则优先快排或 Timsort；把堆排序留给「内存紧张 + 不能接受 O(n²)」的场合。

*一句话总结：堆用数组藏起一棵完全二叉树，用 O(log n) 的路径换 O(1) 的最值；建堆线性，排序却输在访存。*
