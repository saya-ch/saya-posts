## 是什么

分布式锁是让多个进程在同一份共享资源上互斥进入的协调原语。它通常不是一把永不松手的锁，而是一份带过期时间的租约：加锁时写入一个只有自己知道的值，到期自动释放，避免持锁进程崩溃后资源被永久占住。幂等则是另一条约束：同一个业务意图被提交一次还是十次，最终副作用都只发生一次，重复请求拿到的也是同一份结果。一句话直觉：**锁管“同一时刻有几个人”，幂等管“同一件事发生了几次”**。

典型场景是定时任务只允许一个副本执行、订单创建与支付回调、库存扣减、消息重投。它们往往同时需要两者：锁减少并发冲突，幂等兜住重试与重复投递。

## 核心原理

先看锁本身。单机 Redis 上，正确写法是一条命令同时完成“不存在才写入”和“设置过期”：`SET lock:order:42 <token> NX PX 30000`。token 必须随机，释放时不能直接 `DEL`，而要用 Lua 比较值再删除；否则前一个持有者超时醒来，会把后来者的锁删掉。ZooKeeper 用临时顺序节点，etcd 用租约加事务，思路相同：**先证明自己拿到了入场券，再进临界区**。

问题在于这张入场券会过期。持锁进程可能被 stop-the-world GC、缺页、SIGSTOP 或 CPU 饥饿暂停几秒甚至几分钟；消息也可能在网络上延迟很久才到达。等它醒来，租约早已失效，另一个进程已经拿锁并完成了修改，而它仍以为自己持有锁，继续把旧计算写回去。更麻烦的是，在“检查锁是否还有效”和“真正写入”之间，进程同样可能被暂停，所以临时检查一次过期时间救不了。**只要承认进程会暂停、网络会延迟，就没有哪个有限的 TTL 能保证临界区全程独占**。

这就是 fencing token 的用处：让锁服务在每次授锁时附带一个单调递增的编号，客户端把编号一并写给被保护的资源；资源只接受比已见过的编号更大的写，旧持有者醒来后被直接拒绝。ZooKeeper 的 zxid、etcd 的 revision 都能充当这个编号，而 Redlock 只返回随机值，没有单调性，也就无法生成 fencing token。编号必须由资源侧校验才有意义，光在客户端比较没有用。

再往下才是幂等。它不靠“这次别再执行了”的祈祷，而靠一个持久化的判定点：调用方生成幂等键，服务端把键、请求指纹、状态与结果写进同一张表，并给键建唯一索引。如果副作用就在同一个数据库里，把幂等记录、业务写入和结果放进同一个事务，唯一索引会让后到者插入失败，再读回首次结果即可。如果副作用是一次外部调用，事务包不住它，就只能先提交 `DOING` 标记，调用成功后回填 `DONE`；重复请求读到 `DOING` 返回处理中，崩溃留下的 `DOING` 记录则靠查询渠道或对账收敛。关键在“同事务”或“可对账”，否则在两步之间崩溃，重试仍会多做一次。

```sql
INSERT INTO idem (idem_key, request_hash, state, result)
VALUES ('8f3c...', 'sha256:...', 'DOING', NULL)
ON CONFLICT (idem_key) DO NOTHING
RETURNING id;
-- 无返回行：键已存在，按 state 回放结果或返回处理中
```

这张表回答的是“这件事是否已经发生过”，而不是“现在有没有人在做”。所以锁和幂等不是二选一：锁首先负责并发控制，能让大多数重复请求根本进不来；幂等负责重复执行的正确性，接住那些锁没拦住的漏网之鱼。当锁被用于正确性而不只是省资源时，必须再配 fencing token 或资源侧的条件写。把二者混为一谈，就会写出“加了锁所以不会重复”的代码。

## 常见考点与误区

- **误区一：“SETNX 成功后再 EXPIRE 就行”**：两条命令之间崩溃，锁就永久不过期；而且很多客户端把“拿到锁”和“设置过期”分成两次网络往返。要用 `SET NX PX` 一条命令，或把两步写进同一段 Lua。
- **误区二：“释放锁就是 DEL”**：租约过期后，key 可能已属于别人，直接删等于帮别人开门。释放必须比较 token，值相等才删；拿不到锁时也不该进 `finally` 乱释放。
- **误区三：“TTL 设长一点，或者加看门狗续租就安全”**：任何有限 TTL 都可能被更长的暂停击穿，看门狗自己也跑在被暂停的进程里；续租还必须用 CAS，否则会把别人的锁续上。续租只是缩小窗口，不能消除窗口。
- **误区四：“Redlock 在多数节点上加锁，所以是强一致”**：多数派投票不等于共识。它的安全性依赖“网络延迟、进程暂停、时钟漂移都远小于 TTL”这一组同步假设；时钟跳变或 GC 暂停就能让两个客户端同时认为自己持锁。它又没有 fencing token，因此既不够轻，也不够安全。
- **误区五：“幂等键放 Redis 去重就够了”**：缓存会淘汰、会主从切换丢写，TTL 也可能短于重试窗口；键一旦消失，重复请求照样能钻进来。幂等判定要落在有事务和唯一约束的持久存储里。
- **误区六：“参数一样就可以自动当幂等键”**：两次完全相同的请求可能代表两个合法意图，比如用户确实想开两台一样的机器；参数哈希会把它们误合并。键应由调用方按“调用方 + 操作 + 意图”生成，服务端只负责识别。
- **误区七：“用了 ZooKeeper 就没有租约问题”**：临时节点同样靠 session 超时判断存活，客户端暂停超过 session 超时，节点照样消失；旧客户端醒来后仍可能写。共识系统解决的是锁服务的可靠性，不解决持有者暂停。

## 实践建议

- **先分清锁的用途**：只防重复计算、缓存回源这类“多跑一次多花点钱”的场景，用单机 Redis 锁足够，接受偶尔双跑；涉及资金、库存、状态机的正确性锁，必须让资源侧参与，唯一索引、条件更新或 fencing token 至少上一样。
- **锁的模板固定下来**：`SET key token NX PX ttl` 加锁，随机 token 标识持有者，Lua CAS 释放，续租也走 CAS；TTL 取临界区 P99.9 时长再加安全余量，别超过上游超时预算；持锁期间不做无界等待和重试，并上报 lock_lost 指标。
- **幂等表按“键 + 指纹 + 状态 + 结果”设计**：键由调用方生成，唯一索引兜底，业务写与幂等记录同事务；`DOING` 返回 202 或 409，`DONE` 回放首次结果，参数不一致直接报错；保留期覆盖最大重试窗口，别拍脑袋设成五分钟。
- **下游写入带上栅栏**：数据库用 `UPDATE ... WHERE version < :token` 之类的条件写，对象存储和消息队列用它们支持的幂等键，外部支付用渠道自己的幂等参数；不要用“先查再写”代替原子条件写。
- **把故障注入当成验收项**：模拟 STW、`kill -STOP`、主从切换、网络分区、重复投递和超时重试，断言副作用只发生一次；再配一个按业务键聚合的对账任务，发现双写能补偿。
- **锁的粒度按聚合根**：不要一把大锁盖住整个流程；多把锁按固定顺序获取；锁内不做跨服务长调用。长任务改成状态机加短租约，比硬撑一把锁更稳。

*一句话总结：锁降低同时发生的概率，幂等保证重复发生也不出错；把正确性押在锁上，等于把命交给一次进程暂停。*
