## 是什么

LoRA（Low-Rank Adaptation，低秩适配）是一种参数高效微调方法：冻结预训练模型的全部权重，只在选定的线性层旁挂一对小矩阵 A、B，用它们的乘积 BA 去近似这次任务真正需要的权重改动。一句话直觉是：不重写整本手册，只在相关页边贴一张可随时撕下的便签。它最常出现在三类场景：把通用基座适配到法律、医疗、代码等垂直领域；做指令跟随与说话风格的对齐；以及一份基座同时服务多个客户——每个客户只加载几十 MB 的适配器，而不是各自复制一份完整模型。

与全参微调相比，LoRA 不改主干结构，也没有 Adapter 那种串在推理路径上的额外层；训练结束后可以把 BA 加回原权重，推理图与原始模型完全一致。名字里的 low-rank 指的是更新矩阵 BA 的秩不超过 r，而不是把基座本身做低秩分解，这一点常被望文生义。

## 核心原理

把某个线性层写成 h = W0 x。全参微调要学一个新的 W，LoRA 则假设这次改动是低秩的：

h = W0 x + (α/r)·B A x

其中 W0 是 d×k 的冻结权重，A 是 r×k，B 是 d×r，r 远小于 d 和 k。A 用高斯随机初始化，B 全零，于是训练第一步 BA=0，模型输出与基座逐位相同——这是一次“从原模型出发”的热启动，而不是随机扰动。有人担心 B 为零会让梯度消失，恰恰相反：B 的梯度正比于 A x 和上层回传的梯度，只要 A 不是零就有信号；真正学不动的是 A、B 同时为零的写法。

参数量从 dk 降到 r(d+k)。以 4096×4096 的投影层、r=8 为例，原层约 1678 万参数，旁路只有 6.5 万，约 1/256。整个模型的可训练比例通常落在 0.1% 到 1% 之间，这就是优化器状态能大幅缩水的原因。

为什么不直接学一个低秩的 ΔW，而要拆成两个矩阵？因为参数化成 BA 之后，梯度可以分别落到两个小矩阵上，不必每步做奇异值分解；A 提供 r 个基方向，B 负责把这些方向组合成 d 维输出，乘积天然把更新限制在 r 维子空间里。r 就是容量旋钮：它决定这条旁路能表达多少种方向，却不改变前向的宽度。

缩放因子 α/r 不是装饰。r 变大时 BA 的数值尺度会变，α/r 把不同秩的更新拉回可比的量级；换句话说，改 r 而不改 α，等价于悄悄改了学习率。秩稳定化的工作（rsLoRA）进一步把缩放改成 α/√r，避免大秩时更新被压得过小。

低秩假设为什么成立？微调相对预训练只是一次小扰动，任务所需的方向往往只占参数空间的一小部分。但“小”不等于“很窄”：有研究比较全参微调与 LoRA 学到的扰动，发现全参的扰动秩比常见的 LoRA 配置高 10 到 100 倍。这解释了为什么在代码、数学这类需要新能力的持续预训练上，LoRA 会明显落后于全参。

训练时前向仍然穿过整个 W0，反向也要穿过它，只是不为 W0 计算和保存参数梯度；中间激活一个都不能少。省下来的是梯度、优化器状态和 fp32 主权重，不是激活。推理时若只有一个适配器，直接合并成 W0 + (α/r)BA，延迟与基座相同；若要在一份基座上切换多个适配器，就保留未合并形态，多花两次小矩阵乘法，换取批量调度不同适配器的能力。

```python
import torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base, r=8, alpha=16):
        super().__init__()
        self.base, self.scale, self.merged = base, alpha / r, False
        base.requires_grad_(False)
        self.A = nn.Parameter(torch.randn(r, base.in_features) * 0.01)
        self.B = nn.Parameter(torch.zeros(base.out_features, r))

    def forward(self, x):
        y = self.base(x)
        return y if self.merged else y + self.scale * (x @ self.A.T @ self.B.T)

    @torch.no_grad()
    def merge(self):
        self.base.weight += self.scale * self.B @ self.A
        self.merged = True
```

## 常见考点与误区

- **“LoRA 能把大模型塞进小显卡”**：只对了一半。省的是参数相关开销，激活仍随批量、序列长度和层数增长。7B 模型做全参 Adam 大约要按 16 字节/参数准备（权重、梯度、fp32 主权重、两个动量），LoRA 的基座只按 2 字节/参数常驻，但长上下文照样能把卡撑爆。真要在单卡上跑大模型，还得叠加 4-bit 基座、梯度检查点和 FlashAttention。
- **“B 初始化为零，梯度就没了”**：错。B 的梯度来自 A x，非零；A、B 同时为零才会死。把两者的初始化对调（A 零、B 随机）在数学上等价。
- **“rank 越大效果越好”**：容量、显存、过拟合要一起算。风格与格式类任务 r=8 到 16 通常够用，重领域适配才考虑 32 到 64；继续加大不会自动变成全参微调，反而更难优化。
- **“LoRA 等于便宜版全参”**：在需要注入大量新知识的任务上不成立。LoRA 学得更少，但也忘得更少；它的权重里会出现与预训练主方向近乎正交的“侵入维度”，行为分布与全参模型不同，不能只拿下游准确率一项对齐。
- **“训练完随手 merge 进 4-bit 基座”**：量化权重不能直接加 fp16 增量。要么反量化到 bf16 再合并，要么保留旁路；而且合并会改写基座，想在同一份权重上挂多个租户适配器就不能合并。
- **“α 随便设”**：α/r 是有效缩放，直接决定更新幅度；换 r 时不同步调 α，学习率实际上已经变了。
- **“只能加在 attention 的 q、v 上”**：原始论文的消融确实以 q、v 为主，但工程上 q、k、v、o 全加通常更稳，难任务再加 MLP 的三层投影；每多一类模块，可训练参数就多一份，收益要用验证集换，不能凭感觉堆。

## 实践建议

- **目标模块从 attention 铺开**：先给 q、k、v、o 全部加旁路，再看验证集决定是否加到 MLP 的 gate、up、down。模块越多可训练参数越多，别只报一个 r 就说“参数量很小”。
- **r 与 α 一起调**：格式、语气、简单分类从 r=8 到 16、α=2r 起步；领域迁移用 r=32 到 64，并考虑 α/√r 的秩稳定缩放。学习率常比全参微调大，但最终要按 α/r 折算后做小网格搜索，不要照搬别人的数字。
- **显存先算激活，再算权重**：开 bf16、梯度检查点与 FlashAttention；单卡吃不下时上 QLoRA 的 NF4、双重量化和 paged optimizer，同时把序列长度当成一等公民——很多 OOM 是长样本而不是秩造成的。
- **服务形态决定是否合并**：单适配器合并换零延迟；多适配器保持未合并，用支持多 LoRA 的推理栈做批量调度。合并前后跑同一套固定评测，确认 fp16 舍入没有把分数拉偏。
- **评估要双向**：目标域看提升，通用集看遗忘。LoRA“忘得少”是相对优势，不是免检章。
- **把适配器当版本化物件**：只存几十 MB 的旁路很省，但必须同时记录基座版本、tokenizer、目标模块和 α/r；基座一换，旧适配器不能假装还能用，线上回滚也要连基座一起回滚。

*一句话总结：LoRA 用一条可合并的低秩旁路，把微调的账从全参挪到小矩阵；它省下的是优化器成本，不是模型容量的上限。*
