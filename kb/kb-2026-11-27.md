## 是什么

闭包陷阱（stale closure）指的是：回调函数在某一轮渲染中被创建，之后被定时器、事件监听、WebSocket 或 Promise 长期持有，等它真正执行时，读到的仍是创建它那一轮的 props 与 state。可以把一次渲染想成一次快照：界面已经换成了新照片，可外部系统手里还捏着旧照片。

它和普通 JavaScript 的闭包问题同源，只是 React 让它变得高频：组件一天要渲染成百上千次，而 state 看起来像一个可变的变量，让人误以为回调里的 `count` 会跟着变。判断有没有踩中，看的是回调寿命有没有超过创建它的那一轮渲染，而不是代码里有没有出现闭包。典型场景是倒计时、轮询、订阅回调、`addEventListener`、防抖节流包装，以及请求回来后基于旧值做判断。

## 核心原理

先看 JavaScript 这一层。闭包捕获的不是“值”，而是**绑定**——函数创建时所在的那个词法环境。每次调用函数都会新建一套环境记录，同一份源码在不同调用里产生的是不同的变量，只是名字相同。如果这个绑定从未被重新赋值（`const`、参数、`useState` 返回的那一格），看起来就像把值复制了一份，“快照”的错觉就是这么来的。一个经典对照是循环里的 `var` 与 `let`：`var` 只有一份绑定，被反复赋值，所以所有回调最后都读到同一个终值；`let` 每轮迭代新建绑定，回调才各读各的。

React 这一层只是把这个机制暴露得更彻底。函数组件每次渲染就是一次普通函数调用；state 并不存放在闭包里，而是存放在 fiber 的 hook 链表上。渲染时 `useState` 把当前值取出来，赋给这一轮新建的 `const` 绑定。组件返回的 JSX、注册的 Effect、传给子组件的回调，闭包的都是这一轮的环境。渲染结束，这一轮的环境就定型了：没有任何机制会回头改写它。

```js
let state = 0;
let installed;

function render() {
  const count = state;                 // 本轮新建的绑定
  const setup = () => console.log("读到", count);
  if (!installed) installed = setup;   // 空依赖：只保留首轮的引用
}

render();        // 第一轮，count = 0
state = 1;
render();        // 第二轮，count = 1，但 installed 没被替换
installed();     // 仍然打印 0
```

第三层才是关键：**谁持有这个函数，谁决定什么时候换掉它**。在 React 里，[Effect](https://react.dev/reference/react/useEffect) 是唯一被托管的替换点：依赖数组逐项用 `Object.is` 比较，变了就先执行上一轮的 cleanup，再执行这一轮的 setup。比较的基准是上一次提交时记下的数组，不是“上一次 Effect 执行的时刻”，所以中间被丢弃的渲染不会改变这个基准。空数组的含义是“没有响应式依赖”，于是 setup 只跑一次，`setInterval`、事件总线、连接对象拿到的就是首轮那个函数对象；后面几轮渲染产生的新函数，根本没有被交出去。旧函数加上旧环境，读出来自然是旧值。这也解释了[Effect 的同步周期](https://react.dev/learn/lifecycle-of-reactive-effects)为什么要按“开始、停止”而不是“挂载、卸载”来理解。

反过来看，为什么普通按钮的 `onClick` 很少出问题？因为 JSX 每次渲染都会产生新的处理函数，React 在提交时把新 props 记到对应的 fiber 上，事件委托下一次派发调用的就是新函数，旧的自然被丢弃。会滞留的，都是绕过这套替换、由你的代码手动交给外部系统的回调——这正是陷阱在 Effect、订阅和第三方 SDK 里高频出现的原因。

这还牵出两个常见的次生 bug。其一，cleanup 也是创建 Effect 那一轮的闭包，如果它靠读 state 来清理资源，清掉的可能并不是 setup 建立的那个。其二，被 `React.memo` 挡住的子组件不会重渲染，它内部的回调比父组件“更老”，同一棵树里因此并存着不同年代的闭包。

有人因此把变量提到组件外，改成模块级的 `let`。值确实变成最新的了，但更新不再触发渲染，多个组件实例之间还会互相污染——这只是把闭包问题换成了全局可变状态问题，并没有回答“谁在什么时机把哪个值交出去”。

## 常见考点与误区

- **“闭包捕获的是值”**：不准确。捕获的是绑定；对没有被重新赋值的 `const` 和参数来说效果等同于值，对 `let`、对象属性、模块变量来说则不是。面试里用 `var` 加 `setTimeout` 追问一轮，就能分辨是否真的理解。
- **“空依赖数组等于只执行一次，所以安全”**：`[]` 的语义是“这段逻辑不读任何响应式值”，不是“只跑一次”。只要 Effect 里读了 props 或 state，`[]` 就是把首轮的值焊死。依赖不能自选，这是规则而不是风格。
- **“依赖数组是控制何时运行的开关”**：它是声明“读了哪些响应式值”。比较用 `Object.is`，每次渲染新建的对象和函数永远不相等，于是“想让它少跑”反而变成“每次都重跑”。真正的开关是改变代码结构，不是删依赖。
- **“用 ref 存最新值就万事大吉”**：`useRef` 返回的对象跨渲染保持同一身份，`.current` 可写，回调确实能读到最新值；但渲染期间读写 ref 破坏纯度，渲染被中断重来时这些写入不会回滚，而且改 ref 不触发重渲染。它适合“记录”，不适合替代“响应”。
- **“setState 之后下一行就能读到新值”**：不会。`count` 是这一轮的 `const`，`setCount` 只是排队一次新渲染；连续三次 `setCount(count + 1)` 会合并成一次加一。
- **“旧值只出现在 setTimeout 里”**：任何寿命超过一轮渲染的回调都算，包括 `addEventListener`、`IntersectionObserver`、WebSocket 消息处理，以及被 memo 缓存住的子树。

## 实践建议

- 先分清这个值该不该让 Effect 重跑：该重跑就进依赖数组；不该重跑，就用 ref 或 [useEffectEvent](https://react.dev/reference/react/useEffectEvent) 把非响应式逻辑抽出来。后者只能从 Effect 内部调用，官方明确说它不是逃避依赖的工具。
- 基于旧值累加时，把“读最新值”换成“让 React 把最新值交给你”：写 `setCount(c => c + 1)`，而不是 `setCount(count + 1)`。
- 长期订阅把“注册”和“读值”拆开：注册只依赖真正需要重建连接的 key，回调内部通过 ref 或 Effect Event 读最新值；cleanup 与 setup 用同一份局部变量配对，不要在 cleanup 里重新读 state。
- 同一个函数不要既当交互回调又当订阅回调：前者每轮渲染都会换，后者只在依赖变化时换，混用会让其中一侧永远读到旧值。
- 打开 [exhaustive-deps](https://react.dev/reference/eslint-plugin-react-hooks/lints/exhaustive-deps)，把每一处 `eslint-disable` 当成待还的债；开发环境下 React 会额外跑一遍 setup 与 cleanup，cleanup 写得不对会立刻暴露。
- 排查时先确认“旧”的是值还是引用：在回调里打印一个自增的渲染序号或时间戳，就能看出它属于哪一轮；再用最小例子复现，比在业务代码里猜快得多。

*一句话总结：闭包从不撒谎，它忠实保留了你交给它的那一轮；陷阱在于新值交给了新函数，旧函数却一直留在原地。*
