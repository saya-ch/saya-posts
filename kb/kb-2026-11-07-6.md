## 是什么

区间合并（merge intervals）是给定一组区间，输出数量最少的互不相交区间，使它们的并集与输入完全相同。一句话直觉：把一叠画着横线的透明胶片摞起来，只留下有墨的部分，再把连成一片的墨迹各画成一条。输入怎么切分不重要，输出的点集才是答案。

这层"只保并集、不保切分"的性质，使它输出的是规范形式（canonical form）：同一堆区间无论以什么顺序、什么粒度给出，只要端点规则一致，合并结果就唯一。工程上凡是要把"零散的占用"变成"可比较的占用"，都会用到它——日历里把多个日程合成忙闲块、防火墙把上千条 IP 段聚成更少的连续范围、数据库把并发事务的行锁区间并成冲突范围、日志系统把密集的时间窗口压成连续段。

要注意它和区间调度不是一回事。合并求的是并集，输入全部保留；调度求的是最大不相交子集，要丢掉一部分。前者按左端点排序，后者按右端点排序，混用会直接算错。

## 核心原理

把每个区间想成图上的一个点，两个区间有公共点就连一条边。合并要做的，其实是找出这张相交图的每个连通分量，再取覆盖该分量的最小连续区间——左端取分量内最小起点，右端取最大终点。所谓"合并"，就是求连通分量的凸包。

这一步转换解释了很多现象。重叠关系本身不传递：闭区间 [1,2]、[2,3]、[3,4] 里，第一个和第二个在 2 相交，第二个和第三个在 3 相交，第一个和第三个却毫无交集。可它们的并集仍然是完整的一段 [1,4]，必须并成一条。所以正确性不取决于"相邻两个是否重叠"，而取决于"沿着链能不能走通"。只看输入里相邻的两项，结果会随输入顺序变化，这就是不排序直接扫必然出错的根本原因。

排序的作用，是把"连通"变成"连续"。按左端点升序之后，同一个连通分量的成员在序列里一定挨在一起，于是不需要真的建图，一趟扫描加一个游标就够了。

**为什么按左端点排序后，一趟扫描就够。** 设当前正在构建的分量右端为 R。处理到下一个区间 [s, e] 时：若 s ≤ R，它与当前分量有公共点（闭区间语义），扩展 R = max(R, e)，继续；若 s > R，则它和当前分量不相交。关键在后半句：由于序列按起点升序，后面所有区间的起点都 ≥ s > R，不可能再有一个区间回头碰到当前分量。于是当前分量可以安全封存，永远不会被后续区间延长。

这条"安全封存"的论证，就是"排序键必须选左端点"的全部理由。它不是为了遍历方便，而是为了让"未来不可能再相交"成为可判定的事实。

**右端点必须取 max，不能直接覆盖。** 这是实现里最高频的 bug。输入 [1,10]、[2,3]、[4,5]：第二个区间完全被第一个包住，如果合并时把 R 改成 3，第三个区间就会因为 4 > 3 被误判成新的一段，最终输出 [1,10] 和 [4,5] 两个仍然相交的区间。正确写法永远是 R = max(R, e)，让大区间不被小区间截短。

```python
def merge(intervals, touching=True):
    # 闭区间语义；touching=False 时，首尾仅相接不算连通
    intervals = sorted(intervals, key=lambda x: (x[0], x[1]))
    out = []
    for s, e in intervals:
        if out and (s <= out[-1][1] if touching else s < out[-1][1]):
            out[-1][1] = max(out[-1][1], e)
        else:
            out.append([s, e])
    return out

print(merge([[1, 3], [2, 6], [8, 10], [15, 18]]))
print(merge([[1, 2], [2, 3]], touching=False))
```

**端点开闭不是学术细节，它决定 `<=` 还是 `<`。** 闭区间 [1,2] 与 [2,3] 在点 2 相交，并集是 [1,3]，应当合并。半开区间 [1,2) 与 [2,3) 交集为空，但并集仍是 [1,3)，如果目标是"最少区间表示"，它们照样可以并；如果目标是"判断两段占用是否冲突"，它们必须算不冲突。同一个 `<=` 不可能同时满足这两种目标，所以函数要显式区分"合并相接"与"检测重叠"。

时间场景尤其容易在这里翻车。用 [start, end) 表示一天，end 取次日零点，相邻两天天然无缝；若用闭区间并把结束写成 23:59:59，那只是在秒级粒度上勉强闭合，遇到毫秒或更细的时间戳就会漏掉最后一秒内的事件。半开区间还有一个好处：长度可以直接用 end - start 算，不用再 +1。

**复杂度与适用边界。** 排序 O(n log n) 是主要成本，扫描 O(n)，输出另占 O(n)。如果输入已经按起点有序，比如往一个有序列表里插入一个新区间（[LeetCode 57](https://leetcode.cn/problems/insert-interval/)），就不必重排，一趟 O(n) 拼接即可。动态场景则换结构：用 TreeMap 或跳表按起点维护一组不相交区间，插入时用 floor/ceiling 查询找到左右邻居，只做局部合并，代价 O(log n)，这也是日历类服务的常见做法。

## 常见考点与误区

- **误区一："不排序，扫一遍也能合并。"** 只比较输入里相邻的两项，遇到 [5,6]、[1,10]、[2,3] 这种顺序就会把本属同一分量的区间拆开。重叠的传递闭包要求全局有序，排序不是优化，是正确性的一部分。
- **误区二："按右端点排序也能合并。"** 按右端点排序是区间调度的贪心，不是合并。反例 [1,2]、[3,4]、[0,100] 按右端点排完是 [1,2]、[3,4]、[0,100]，处理到 [0,100] 时前一段 [1,2] 已经封存，最后输出两个相交的区间。合并必须按左端点。
- **误区三："合并时把右端改成当前区间的右端就行。"** 一旦遇到被包含的区间，右端会缩水，后面的区间就被误判为新段。必须取 max，这是"大包小"用例的必现错误。
- **误区四："相接算不算重叠，背一个结论就行。"** 要看目标：求并集的规范形式，相接的半开区间也可以并；判冲突或排会议室，相接必须算不冲突。判冲突时，闭区间用 `<=`、半开区间用 `<`；求并集时则单独决定要不要把相接的两段并掉，两件事不要共用一个条件。
- **考点五："合并能顺便去重或还原原始区间吗？"** 不能。合并只保留并集，丢掉了切分边界、原始条数和来源标识；[1,10] 并掉 [2,3] 之后，再也拆不回去。需要审计或回滚时，原始记录必须另存，输出只作为索引。
- **考点六："求最大重叠数也用合并吗？"** 不必。那种问题用扫描线：每个区间在起点 +1、终点 -1，按坐标排序后累加取峰值。但同一坐标上要先处理 -1 再处理 +1（半开语义），否则首尾相接的两段会被算成同时占用，峰值虚高一。

## 实践建议

- 先写语义契约再写代码：端点开闭、相接是否合并、是否允许空区间，三句话写进 docstring，函数名体现差异（merge_touching / overlap）。测试固定覆盖空输入、单点、完全包含、首尾相接、逆序输入、重复区间六类，尤其别漏"大包小"。
- 排序键写成 `(start, end)`，不要依赖排序的稳定性来兜底；Python 的 `list.sort()` 是稳定排序，但业务正确性不该建立在输入顺序上。大列表优先原地 `sort()`，避免 `sorted()` 多复制一份。
- 更新右端一律 `max`；输出用新列表，不要直接复用输入的内层列表，否则调用方手里的数据会被悄悄改掉。合并完成后加一条断言：若相接已经合并，相邻两段必须严格满足 `out[i][1] < out[i+1][0]`；若允许相接保留，才是 `<=`。把不变量变成可执行的检查，比事后盯输出可靠。
- 输入有序或近似有序时别重排：插入单个区间用二分定位加三段拼接；高频动态合并用 TreeMap 维护不相交集合；数据量大到内存放不下时先分桶，各桶内合并后再处理跨桶边界的相接，别在分片处漏并。
- 时间区间统一存 UTC 毫秒整数，展示层再转时区；避免用浮点秒做端点比较，也避免把"当天结束"写成 23:59:59。跨时区、夏令时切换的日子，半开区间加时区库比手工加减更可靠。

*一句话总结：区间合并的关键不是把碰到的段粘起来，而是排序把连通分量排成连续，再用 max 守住每个分量的右边界。*
