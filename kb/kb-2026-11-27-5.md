## 是什么

读写分离（read-write splitting）是把数据库的写操作固定发往主库、读操作按策略分摊到一个或多个从库的部署方式。一句话直觉：主库是唯一记账的柜台，从库是不断誊抄的副本，改账只能去柜台，查账可以翻副本。它最常见的场景是读多写少的业务——商品详情、内容列表、订单查询，以及把报表和统计查询从在线库挪走。

需要先纠正一个预期：读写分离扩展的是**读吞吐**，不是写吞吐。写仍然只有主库一个入口，从库再多也不能分担一次 INSERT。它的价值在于用较便宜的只读副本接住大部分 SELECT，同时把分析型查询与在线交易隔离。真正要扩写，得走分库分表或换存储引擎。

## 核心原理

复制链路决定了延迟从哪来。以 MySQL 为例：主库把变更写进 binlog，每个从库有一条 dump 线程负责把 binlog 事件发给它；从库的 I/O 线程收下后写进 relay log，再由 SQL 线程（或 worker 线程）回放成实际数据。只有回放完成，从库上的 SELECT 才能看到这笔变更。所以"主库提交成功"与"从库可见"之间，隔着网络传输、relay log 落盘，以及最关键的**回放**三段。

类比：主库是总账房，binlog 是流水单。从库的 I/O 线程只是把流水单领回来放进信箱（relay log），SQL 线程才是照单记账的人。信箱里有单子，不代表账本已经更新——半同步复制的确认，确认的正是"单子收到了"，而不是"账记完了"。

MySQL 8.4 的[半同步复制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync-interface.html)默认 `AFTER_SYNC`：主库把事务写进 binlog 并刷盘、发给从库，等到从库确认收到后才提交存储引擎并向客户端返回。这比旧的 `AFTER_COMMIT` 更稳——后者先提交再等确认，在确认到达前其他客户端已经能看到这笔事务，一旦主库故障切到从库，这些客户端可能看到"数据倒退"。但即使是 `AFTER_SYNC`，确认也只到 relay log，SQL 线程回放仍需时间；从库负载高或遇到大事务时，这个窗口会被拉长。要更强的一致性，得靠 Group Replication、共享存储或数据库原生的强同步读，而不是把半同步当成"从库实时"。

路由发生在更上层。无论是驱动层（如 ShardingSphere-JDBC）、代理层还是云数据库的只读地址，都要解析 SQL 判断读写，并结合事务状态决定发往哪里。这里有个容易被忽略的默认值：ShardingSphere 的 [`transactionalReadQueryStrategy`](https://shardingsphere.apache.org/document/current/en/user-manual/shardingsphere-jdbc/java-api/rules/readwrite-splitting/) 默认是 `PRIMARY`，即事务内的读一律走主库；只有显式改成 `FIXED` 或 `DYNAMIC` 才会在事务内读从库，而官方文档明确提示这两种取值要求数据库支持强主从同步（如 openGauss）。很多人以为"配了读写分离，事务里自然读从库"，实际恰恰相反——这是中间件用一点读扩展性换事务内的一致性。

```yaml
rules:
  - !READWRITE_SPLITTING
    dataSources:
      readwrite_ds:
        writeDataSourceName: write_ds
        readDataSourceNames:
          - read_ds_0
          - read_ds_1
        transactionalReadQueryStrategy: PRIMARY
        loadBalancerName: round_robin
    loadBalancers:
      round_robin:
        type: ROUND_ROBIN
```

三种落地形态的取舍也不同。驱动层（ShardingSphere-JDBC）少一次网络跳转、性能最好，但把路由逻辑耦合进应用，升级要跟着发版；代理层（ShardingSphere-Proxy 等）对应用透明、多语言通吃，代价是多一跳网络，以及代理自身的容量与高可用问题；云数据库的只读地址最省事，但路由策略和强制主库的手段受厂商限制。选型时先看团队能否接受"改配置就要发版"，再看代理层能不能扛住连接数与峰值 QPS。

一致性上有两个绕不开的概念：读己之写（read-your-writes）要求用户提交后立刻能看到自己的修改；单调读（monotonic reads）要求同一个用户不会先看到新值、再看到旧值。异步复制下，前者会被"写主读从"打破，后者会被"两次读打到延迟不同的从库"打破。延迟越大、从库越多，这两种"时间倒流"越容易出现。

最后是容量账。加从库能线性增加读 QPS，但主库要为每个从库各发一份 binlog，网络与 dump 线程都是成本；从库越多，主库的发送放大越明显。级联复制（从库再挂从库）能把发送压力分散，代价是延迟多一跳。这也是为什么从库数量要按读流量和延迟预算定，而不是"越多越稳"。

## 常见考点与误区

- **误区一：读写分离等于读写一致。** 异步复制下，主库提交成功不代表从库已回放；写完立刻读从库读到旧值是正常现象，不是"丢数据"。面试里如果只答"主从同步"，通常会被追问同步的是 binlog 还是数据页。
- **误区二：半同步复制能保证从库读到最新值。** 不能。`AFTER_SYNC` 保证的是事务已到从库的 relay log，SQL 线程是否回放完是另一回事；`AFTER_COMMIT` 甚至连"其他客户端看不到未确认事务"都保证不了。
- **考点三：事务内的读走主库还是从库。** ShardingSphere 默认 `PRIMARY`，事务内读走主库；要事务内读从库得改策略，并且前提是强同步。答"读写分离后所有 SELECT 都走从库"是典型错误。
- **误区四：从库加得越多，读能力越强。** 主库 binlog 发送会放大，复制延迟受从库回放能力限制；从库上的大查询、DDL、无主键表的批量更新都会拖慢回放，进而把延迟传导给所有读请求。
- **考点五：怎么保证读己之写。** 常见做法是写后短窗口内强制走主库（会话粘滞）、用 Hint 强制路由主库（ShardingSphere 提供 [`HintManager.setWriteRouteOnly()`](https://shardingsphere.apache.org/document/5.3.2/en/user-manual/shardingsphere-jdbc/special-api/readwrite-splitting/hint/)），或按 GTID 等待从库追平（[`WAIT_FOR_EXECUTED_GTID_SET`](https://dev.mysql.com/doc/refman/8.4/en/gtid-functions.html)）。全局强一致代价太大，通常只对少数接口开启。
- **考点六：`Seconds_Behind_Source`（旧名 `Seconds_Behind_Master`）能准确反映延迟吗。** 不可靠。它衡量的只是回放线程当前处理事件与主库时间戳的差，主库长时间空闲时会显示 0，多线程回放时也不代表所有 worker 都已追平；更稳的做法是对比主从 GTID 差集，或看 `performance_schema.replication_applier_status_by_worker` 的进度。

## 实践建议

- **先量延迟，再定一致性策略。** 上线前压测出复制延迟的 p99，线上按 GTID 差集监控而不是只看 `Seconds_Behind_Source`；把"写后立读"的接口列出来，单独给它们开主库路由或短粘滞窗口，其余读继续走从库。
- **把强一致需求收窄。** 不要为了少数场景把整条链路切回主库；优先用"写后跳转到详情页时读主库"这类业务手段，其次才是 Hint 或 GTID 等待。等待必须带超时，超时后降级读主库，避免把从库延迟放大成接口超时。
- **管住事务边界。** 长事务会让事务内所有读都压在主库，还持有锁、拖慢复制；把只读查询移出事务，能显著降低主库压力，也让读写分离真正生效。
- **给从库分工。** 在线读、报表分析、备份各用独立从库或级联从库，避免一条大聚合 SQL 拖慢在线读的回放；对从库上的重查询做超时和限流。
- **把切换演练当常规项。** 主从切换后，代理或 SDK 要能探活并更新路由，连接池里的旧连接要能被剔除；只读账号权限、从库的只读设置、以及切换后的延迟回落都要在演练里验证。

*一句话总结：读写分离卖的是读吞吐，复制延迟就是它的价格，落地时要按接口把这笔账算清。*
