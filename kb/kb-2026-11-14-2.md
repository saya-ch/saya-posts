## 是什么

TCP 把应用层交下来的字节看成一条没有边界的流，每个字节都有序号。发送方不能把所有字节一次丢出去：它维护一个**发送窗口**，窗口内是"已发出等确认"和"还没发但允许发"的字节，窗口右边界之外的数据，必须等前面的确认回来才能推进。这个会随 ACK 向前滑动的区间，就是滑动窗口。

一个直觉：窗口是流水线的宽度。宽度为 1 就是停等协议，发一个包等一个 ACK，吞吐被 RTT 死死按住；把宽度放大，链路上同时飞的数据变多，吞吐才上得去。但宽度由两个数共同决定——接收方通告窗口 `rwnd` 表示"我的接收缓冲区还剩多少"，拥塞窗口 `cwnd` 表示"发送方估计这条路径还能承受多少"。真正能发的字节数是 `min(rwnd, cwnd)` 再减去已在途的数据。前者回答"对方接不接得住"，后者回答"中间的路撑不撑得住"。

典型场景随处可见：跨地域传大文件、CDN 回源、弱网下的视频、以及抓包里明明带宽没跑满、`win` 却小得反常的连接。不理解这两个上限，调优就只能靠猜。

## 核心原理

### 一条流水线：窗口在动什么

把序列号空间想成一条数轴，窗口是上面的一段。段的左边是已发送且已确认，中间是已发送未确认，右边是还能发但没发，再往右是禁区。收到累计确认后，左边界右移，右边界随之右移，窗口"滑"了过去。接收方在每个 ACK 里带上自己的剩余缓冲，发送方据此调整右边界；而且 TCP 规定窗口右边界不能往左缩，否则已经发出的数据会失去合法性。

有滑动就有丢包处理。重传超时（RTO）是最笨但兜底的一条路：等不到确认就重发最早的那个缺口，同时把窗口打回去。更常见的是快速重传——后面没有缺口的报文陆续到达，接收方只能反复确认缺口前那个字节，发送方连着收到三个重复 ACK，就判断缺口大概率真丢了，立刻重发而不必等定时器。SACK 选项把"我收到了哪些段"说得更细，让一次 RTT 内能补多个洞。

### 两个上限：rwnd 与 cwnd

先看 rwnd 为什么会成为瓶颈。要让一条链路跑满，在途数据至少要等于"带宽 × RTT"，这个量叫带宽时延积（BDP）。一条 100 Mbps、RTT 80 ms 的链路，BDP 约 1 MB；若接收方只通告 64 KB 窗口，吞吐上限就是 64 KB / 0.08 s ≈ 6.4 Mbps，剩下九成带宽闲着。16 位的窗口字段最大只能表示 65535 字节，所以长肥管道必须靠窗口缩放选项把字段左移，两端都要支持才生效。

再看 cwnd。接收方就算把窗口开到 4 MB，路径中间的路由器队列也未必接得住。发得太猛，队列溢出丢包，重传又加剧拥塞，1980 年代中期的拥塞崩溃就是这么来的。于是发送方必须自己维护一个 cwnd，把"网络大概能吃多少"这件事估出来，而且这个估计只能靠 ACK 和丢包间接推断，没有谁会给它发一个准确数字。

```python
MSS = 1460
def ceiling(cwnd_mss, rwnd, rtt):
    win = min(cwnd_mss * MSS, rwnd)   # 两个窗口取小
    return win, win / rtt             # 字节数、字节/秒

bw, rtt = 100e6 / 8, 0.080            # 100 Mbps 链路，80 ms 往返
print("BDP =", int(bw * rtt), "bytes")
for cwnd_mss, rwnd in [(64, 256 << 10), (1024, 256 << 10), (1024, 4 << 20)]:
    win, bps = ceiling(cwnd_mss, rwnd, rtt)
    print(f"cwnd={cwnd_mss} MSS rwnd={rwnd >> 10} KiB -> "
          f"{win / 1024:.0f} KiB, {bps / 1e6 * 8:.1f} Mbps")
```

三段输出恰好演示了三种受限状态：cwnd 只有 64 个 MSS 时窗口约 91 KB，链路只跑到 9 Mbps 左右；把 cwnd 提到 1024 个 MSS，瓶颈换成了 256 KB 的 rwnd，约 26 Mbps；再把 rwnd 放到 4 MB，窗口终于超过 BDP，100 Mbps 的链路被喂满；打印值只是窗口允许的上限，实际速率仍受链路带宽封顶。调优时先判断是谁在卡，比盲目加倍缓冲区有效得多。

### cwnd 怎么长、怎么退

慢启动这个名字很有迷惑性，它其实是指数增长：每收到一个 ACK，cwnd 就增加一点，效果是每个 RTT 翻一倍。初始窗口按 RFC 6928 的建议取 `min(10×MSS, max(2×MSS, 14600))`，MSS 为 1460 时正好 10 个 MSS，而不是很多人以为的 1 个。涨到阈值 `ssthresh` 后进入拥塞避免，改成每个 RTT 只加约 1 个 MSS，也就是 AIMD 里的"加性增"。

一丢包就"乘性减"：三个重复 ACK 触发快速重传，`ssthresh` 砍成在途量的一半，cwnd 设成 `ssthresh + 3×MSS` 进入快速恢复，每多一个重复 ACK 就临时把窗口撑大一点，直到缺口被补上再降回阈值；如果是超时重传，则说明情况更糟，cwnd 直接回到 1 个 MSS 重新慢启动。这套 Reno 家族的逻辑把"丢包"当成"拥塞"的同义词，简单有效，却是后面所有争议的源头。

于是有了两代改良。CUBIC（RFC 9438）仍是丢包驱动，但把窗口写成距上次减窗时间的三次函数，长 RTT 链路上恢复得更快，并保留一条 Reno 友好的估计曲线，Linux 长期把它当默认算法。BBR 走得更远：它分别估计瓶颈带宽和最小 RTT，用两者的乘积当作目标在途量，按估计速率做 pacing，丢包不再直接触发砍窗。代价是 BBR 在浅缓冲队列、与 CUBIC 流共存时的公平性一直有争议，所以它更像一个需要按场景验证的选项，而不是无条件的升级。

## 常见考点与误区

- **"窗口大小就是接收方通告的值"**：错。发送方实际受 `min(rwnd, cwnd)` 约束，抓包里的 `win` 还可能只是缩放前的 16 位原始值。面试问"窗口为 0 意味着什么"，答"接收缓冲满"只对了一半，还要提零窗口探测与窗口更新。
- **"慢启动很慢"**：它每个 RTT 翻倍，从 10 个 MSS 涨到几百个 MSS 只要几个 RTT。真正慢的是超时后的重启，那时 cwnd 才回到 1 个 MSS。把"初始窗口是 1"当常识答，是典型的旧教材记忆。
- **"丢包一定是拥塞"**：无线误码、链路抖动、甚至中间设备策略丢包都会触发。Reno 家族一律砍半，在高误码链路上会严重低估容量；BBR 换成带宽与 RTT 信号，但它在共享瓶颈上的侵略性也需要实测，不能反过来说"丢包与拥塞无关"。
- **"窗口越大越快"**：超过 BDP 的窗口只是把数据堆进瓶颈队列，换来排队时延和 bufferbloat，吞吐并不增加。上限是 `min(cwnd, rwnd) / RTT`，不是缓冲区大小。
- **"三个重复 ACK 是随便定的"**：一个重复 ACK 可能只是乱序，三个说明缺口之后至少有三个报文到达，缺口是真丢的概率已经很高。这是误判率与恢复速度的工程折中，SACK 能提高判断精度，但阈值本身仍保留。
- **"流量控制就是拥塞控制"**：前者是点对点的接收能力协商，靠 rwnd；后者是发送方对全局路径的自我约束，靠 cwnd。把两者混为一谈，就会在"对方还能收"和"网络还能撑"之间做出错误判断。

## 实践建议

- 先算 BDP 再动参数。用 `ss -ti` 看连接的 cwnd、rwnd、rtt、retrans，估算 `带宽 × RTT`；socket 缓冲区与内核 `tcp_rmem`/`tcp_wmem` 至少要覆盖它，并确认窗口缩放两端都生效。只把缓冲区翻倍，往往只是把瓶颈从 rwnd 换到 cwnd。
- 长肥管道或高误码链路，把拥塞算法当成可 A/B 的选项。CUBIC 是稳妥默认，BBR 在有大缓冲、丢包以拥塞为主的环境常有明显收益；但要在真实拓扑上测共存公平性与队列时延，别在核心链路上一次性全量切换。
- 交互式小请求优先处理延迟而不是吞吐。Nagle 与延迟 ACK 叠加可能带来几十毫秒的额外等待，这类连接可以设 `TCP_NODELAY` 并合并写；但大块顺序传输不要盲目关 Nagle 后连发小包，那是在给网络制造更多首部开销。
- 应用层重试要带退避和抖动。拥塞期间固定间隔重试会形成同步雪崩，把一次丢包放大成持续过载；给重试设预算、熔断和随机抖动，比调大任何窗口都更能救火。
- 自研可靠传输时别只抄"超时重传"。pacing、拥塞控制、按流避免队头阻塞是一整套，QUIC 把这三件事放到用户态做，正是为了能独立演进；只补重传而不控制发送速率，等于把拥塞崩溃的老路重走一遍。

*一句话总结：滑动窗口决定一次能发多少，拥塞控制决定敢发多少，真正跑多快取两者与 RTT 的共同下限。*
