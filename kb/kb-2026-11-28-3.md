## 是什么

协程（coroutine）是一段可以中途挂起、之后从挂起点继续执行的函数。它不像普通函数那样一进去就必须跑到 `return`：执行到某个等待点时，它把当前进度存好、把控制权交还给调度者，等条件满足再被恢复。一句话直觉：协程像书里的书签，读到一半可以合上书，下次从书签那页接着读，而不是从头再读。

它真正有用的场景是“大量任务同时等待”：一个网络服务同时挂着十万条连接，每条连接大部分时间都在等数据；如果每个连接占一条内核线程，光是栈和调度就先把内存吃光。协程把“等待”从线程里剥出来，用少量线程轮转推进大量任务。Go 的 goroutine、Python 的 async/await、Kotlin 的 suspend 函数、Lua 的 coroutine 都属于这个家族，但实现方式差别很大。

需要先厘清一点：协程是语言或运行时的概念，不是操作系统的概念。内核只看见线程，协程的创建、挂起、恢复和排队，全部发生在用户态。

## 核心原理

**一次切换，搬走的是“执行到哪”。** CPU 里跟执行位置有关的状态很少：程序计数器、栈指针，以及一组被调用者保存寄存器。把这些写进协程自己的控制块，再从另一个控制块里恢复，就完成了切换。整个过程没有系统调用、没有特权级转换，也不经过内核调度器，因此比线程切换便宜一个数量级。

省下来的钱不是白省的：内核不知道协程的存在，就不会替它做抢占、负载均衡和阻塞处理，这三件事全部落到运行时头上。协程轻不轻，取决于运行时怎么解决它们。

**有栈协程：每个协程一张自己的栈。** 挂起时切栈指针即可，所以它能在任意调用深度挂起——A 调 B、B 调 C，在 C 里等待也没问题。代价是每个协程都要预留栈空间。Go 的做法是先用一张很小的栈（2KB 量级），不够时再扩：运行时把整张栈复制到更大的内存块，再把指向栈内的指针全部改掉。这正是 Go 需要精确栈映射的原因——GC 和栈复制都必须知道每个栈槽里放的是指针还是普通值。Go 1.4 从分段栈改成连续栈复制，就是为了避开跨段调用造成的热分裂问题（[Go 1.4 release notes](https://go.dev/doc/go1.4#runtime)）。

**无栈协程：把函数改写成状态机。** 编译器在每个 `await`/`suspend` 点把函数切成若干段，跨挂起点还要用的局部变量被搬进一个堆上的协程帧（Python 的 coroutine 对象、C# 的状态机、C++20 的 coroutine frame）。挂起就是返回到调用者，恢复就是带着保存的状态再进去。它不需要为每个协程准备栈，但挂起点被限制在 await 处，帧的大小在编译期就定了：一个跨 await 持有的大缓冲区会把整个帧撑大。调用链上的函数也必须逐层声明 async，这就是常说的“函数着色”问题。

**调度器：把 N 个协程映射到 M 条线程。** Go 用 GMP 模型：G 是协程，M 是内核线程，P 是执行 Go 代码所需的上下文，内含本地就绪队列。一个 G 必须在某个 P 上才能跑，P 的数量由 GOMAXPROCS 决定，默认等于 CPU 核数。P 的本地队列空了，就去别的 P 那里偷一半，这是 work-stealing；本地队列满了，就溢到全局队列。

阻塞是这套模型最需要小心的地方。发起网络读写时，goroutine 被挂起并注册到 netpoller（Linux 上是 epoll），M 不被占住，可以继续跑别的 G；如果是阻塞式系统调用，运行时会把手里的 P 交出去，让别的 M 带着这个 P 继续跑，系统调用返回后再抢一个 P。所以 GOMAXPROCS 限制的是同时执行 Go 代码的 P 数，不是线程总数，阻塞调用多的时候 M 可以远多于 P（[runtime/proc.go](https://go.dev/src/runtime/proc.go)）。

**协作式调度需要抢占兜底。** 纯协作调度只在挂起点切换，一个不 await 的死循环就能占住线程。Go 早期靠函数入口的栈检查制造协作点，Go 1.14 起加入基于信号的异步抢占，长时间运行的循环也能被打断（[Go 1.14 release notes](https://go.dev/doc/go1.14#runtime)）。Python 的事件循环没有这层机制：一个协程里跑了 CPU 密集循环，其它协程只能等它跑完。asyncio 本身是单线程事件循环，靠 selector 等待 I/O，再把就绪回调放回队列（[asyncio 事件循环文档](https://docs.python.org/3/library/asyncio-eventloop.html)）。

下面这段代码把两种等待放进同一个事件循环：

```python
import asyncio, time

async def blocker():
    time.sleep(0.5)          # 同步阻塞，事件循环停摆
    print("blocker done")

async def ticker():
    for i in range(4):
        print("tick", i, round(time.perf_counter() - t0, 2))
        await asyncio.sleep(0.1)

async def main():
    asyncio.create_task(blocker())
    await ticker()

t0 = time.perf_counter()
asyncio.run(main())
```

只有第一个 tick 落在 0 秒，第二个 tick 会被推到 0.5 秒，之后才恢复 0.1 秒的节奏。原因不是 `asyncio.sleep` 不准，而是 `time.sleep` 阻塞了唯一那条线程，事件循环根本没有机会回到 selector 上取下一个到期任务。

## 常见考点与误区

- **“协程是轻量级线程，由操作系统调度”**：错。内核只调度 M 条线程，协程的排队和切换都在用户态完成；也正因如此，内核不会替协程做抢占和公平性保证。
- **“协程一定不会阻塞”**：错。阻塞式系统调用、同步锁、CPU 密集循环都会占住底层线程。Go 能靠 netpoller 和 P 交接绕过系统调用阻塞，但纯计算仍要靠抢占点；Python 的单事件循环则会被直接按住。
- **“无栈协程没有栈开销”**：不准确。它省掉的是独立栈，协程帧仍然在堆上，大小约等于跨挂起点存活变量的总和；一个跨 await 持有的大数组会让每任务的内存成倍上涨。
- **“协程越多，吞吐越高”**：错。协程本身要占内存，调度和 GC 都要扫描它们，下游连接池、数据库和文件描述符也有上限。无界 `spawn` 的终点通常是内存告警和尾延迟飙升，而不是更高 QPS。
- **“GOMAXPROCS 是线程数，也是协程数”**：都不是。它是 P 的数量，只限制同时执行 Go 代码的并行度；`GOMAXPROCS=1` 时仍然可以有几十万 goroutine，只是它们轮着跑。
- **“用了协程就自动多核并行”**：并发不等于并行。单线程事件循环再忙也只用一个核；要并行，必须有多个线程或多个 P，而且 CPU 密集任务不会因为套了 async 就变快。

## 实践建议

- **给并发设上限，而不是给协程数加油。** 用信号量、`errgroup.SetLimit` 或 TaskGroup 按下游容量限流，让队列长度成为背压信号；无界并发只是把过载从入口推迟到内存和连接池。
- **把阻塞隔离出去。** Python 里用 `asyncio.to_thread` 或线程池包住同步驱动，Go 里把长计算放进固定 worker 池；异步链路中混入同步调用，等于在调度器上埋雷。
- **让生命周期可取消。** Go 用 `context` 贯穿调用链，Python 用 [`TaskGroup`](https://docs.python.org/3/library/asyncio-task.html#asyncio.TaskGroup) 或显式 cancel，避免任务挂起后永远没人回收；goroutine 泄漏和未取消的 task 都会在压测时伪装成“内存泄漏”。
- **按证据调参。** Go 用 `go tool trace` 看调度延迟和 P 的利用率，Python 开 asyncio debug 看慢回调；容器里按 CPU quota 校准 GOMAXPROCS，别直接信宿主机核数。观测指标至少包括协程数、栈内存、就绪队列长度和 P99 延迟。
- **选型看挂起位置。** 需要在任意调用深度挂起、且能接受每任务一张栈，选有栈协程；任务数量极大、挂起点集中在 I/O 边界，选无栈协程更省内存。两者都不负责替你消灭阻塞，边界要靠代码约束。

*一句话总结：协程的轻来自用户态调度，它的边界也来自用户态调度——谁在跑、在哪挂起、挂起时占多少内存，才是选型时要算的三笔账。*
